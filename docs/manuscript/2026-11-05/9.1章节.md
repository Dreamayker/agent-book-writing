# 9.1 评审的困境与证据闭环

## 9.1.1 代码更简洁，为什么仍然有错

“复用已有方法，减少重复代码，建议合并。”这条评审意见语气明确，也符合常见的重构偏好。但面对退款变更，它没有回答最关键的问题：被复用的方法读取的是下单时的价格，还是现在的价格？

设想一次普通的网上购物：周一购买商品，周三促销规则调整，周五申请退货。你期待商家核对的是周一的付款记录。周三的优惠可以影响新的购买，是否影响旧订单，则需要另一条明确的业务规则。这种生活经验帮助我们理解代码中的两个动作：购买前的“试算”和购买后的“核对历史”。它们可能返回同样的金额类型，承担的含义却不同。

代码评审经常遇到这种情况：类型系统认可的替换，并不一定得到业务规则认可。一个 `long` 可以表示当前报价、原始实付、累计退款或剩余额度。编译器知道它是整数，评审者还要知道它属于哪个时间、哪笔交易、哪位用户。AI 如果只读到方法调用，很容易把这些含义压成“计算金额”。给它更多语法说明无法补回缺失的业务关系。

因此，我们先不急于设计提示词。先用一句普通话说清改动的风险：“旧订单的退款，可能被新规则重新定价。”这句话暂时只是待验证的判断，但已经给出了下一步：找出旧依据的保存位置、新规则的读取位置，以及两者可能不一致的输入。

本章将这种“操作发生在不同时间，仍须使用正确依据”的关系作为主线。先从一笔能够手算的订单开始，后面再看这份依据怎样进入源码、评审材料与测试。

本章使用整数分表示金额。A、B、C 的活动价分别是 12000、20000、8000 分，合计 40000 分；满减券抵扣 5000 分，新人券抵扣 2000 分，订单实付 33000 分。各单位最终实付为 9900、16500、6600 分。9.7 将完整推导这些数值。

## 9.1.2 把业务期待改写成不变量

不变量是在允许的操作和输入范围内应持续成立的关系。它必须有可反驳的条件；“代码质量良好”没有明确反例，“每个购买单位最多退款一次”则可以通过两个请求挑战。

### 从一句要求到一个可以检查的关系

“退款要正确”对业务沟通有意义，对程序检查还太宽。把它展开，可以得到三个层次。对象层说明退什么：本章退的是可单独标识的购买单位。依据层说明按什么退：按下单时已经分配到该单位的实付。状态层说明何时还能退：该单位此前没有成功退过。三个层次分别决定数据结构、金额来源和状态约束。

以 C 为例，6600 分是这一组输入下的结果。“无论什么订单都退 6600 分”显然不成立；“退款等于原快照中所选单位的实付之和”才是可以迁移的关系。用具体数字让读者看见问题，用一般关系指导实现，二者需要来回对应。

一个实用的写法是：**在什么前提下，执行什么动作，哪些关系必须成立。** 例如：在下单快照完整、用户有操作权、所选单位未退的前提下，退款成功后，返回金额与退款记录应相同，且等于这些单位的历史实付。若前提不成立，就应进入相应的拒绝或人工核对流程。这个写法也提醒我们，正确性包含“该成功时成功”和“该拒绝时拒绝”。

**表 9-1 订单不变量与可观察证据**

| 不变量 | 可观察证据 | 容易遗漏的情况 |
| --- | --- | --- |
| 活动价合计 = 实际优惠 + 实付 | 计价结果、各阶段金额 | 抵扣封顶后仍按券面值记账 |
| 每张券分摊总和 = 该券实际抵扣 | 单位分摊与整单优惠 | 向下取整后丢失尾差 |
| 退款使用原始单位实付 | 快照、退款记录、计价调用次数 | 规则不变时错误重算也能通过 |
| 每单位最多退一次 | 单位状态、退款笔数 | 整单上限没超，单位已经多退 |
| 同键同请求返回原结果 | 响应、指纹、持久化记录 | 没有二次效果，却错误拒绝重试 |
| 只有所有者能操作订单 | 跨用户 HTTP 请求 | 资源 ID 被误当作授权凭据 |
| 拆单保留原单位分摊 | 子单金额、单位身份、根账本 | 子单金额正确但父单仍能再退 |

这些关系来自业务契约 `order-rules-v1`，不是模型自行决定的偏好。规则存在歧义时，应回到需求负责人确认；评审者不能通过给 confidence 打高分来消除歧义。

## 9.1.3 工具、模型、策略和人工各自判断什么

可以把一次评审理解成四个连续的问题。第一，程序做了什么？测试和日志给出观察。第二，这个行为为什么违背规则？模型和评审者把观察连接到源码。第三，这种风险按团队约定如何处理？策略规定报告动作。第四，规则适用于哪些历史订单、修复能否发布？这些问题需要业务和技术责任人确认。

假如日志只显示 6400，缺少期望值，我们还不知道它是否有错。假如模型知道应退 6600，却没有任何可触发的输入，开发者也很难验证。假如技术上已经确定少退，但业务规则要求历史订单人工处理，自动生成一个补丁仍然不能完成决策。每一层都提供后一层需要的材料，同时保留自己的边界。

以本章为例，工具报告 6400 与 6600 的差额，模型连接实时 quote 与业务规则，策略要求核心退款变更交人工，责任人再核对历史依据及修复范围。某一层得到正确结果，仍需由其他层完成各自判断。后面遇到字段和接口时，可以沿这四个问题理解它的用途。

本章称一条结构化评审意见为 Finding。它指出位置、问题、证据与修复方向。Oracle 是评分时使用的参照答案，记录已标注的根因；它不应提前进入待评审模型的输入。manifest 是证据清单，记录案例、版本、运行标识和文件哈希。fixture 是为了重复验证程序行为而预设的数据。

## 9.1.4 为什么正常退款测试容易漏检

如果下单与退款之间规则未变，重新计价仍可能得到 6600 分。ORD-09 特意改变时间条件：按满减 5000 分下单，再把实时满减改为 6000 分，随后退 C。正确实现读取原快照；错误实现按新规则计算为 6400 分。

测试同时检查返回值、数据库退款金额与退款期间的实时计价调用。只修 HTTP 返回值可能让客户看到正确数字，账本仍然错误；只断言“不超过原实付”则抓不到少退。有效测试需要与被怀疑的错误机制相对照。

重算也可能造成多退。例如另一种算法用原订单实付减去剩余商品的新实付，可能产生不同金额。因而事故描述必须绑定具体错误变体；不能把所有“重算”都解释成相同的 200 分差额。

### 从反例理解测试的作用

普通测试选择一种系统可以正常工作的情境；有针对性的反例则创造一种情境，让两个候选实现表现不同。这里的两个候选实现是“读取历史快照”和“按当前规则重算”。规则不变时，两者可能给出同一个答案，测试无法区分；规则变化后，结果分叉，测试才具有辨别力。

这种方法可以迁移。怀疑授权缺失，就用另一位已登录用户访问同一对象；怀疑重试协议，就让请求键保持不变再发送相同请求；怀疑单位重复退款，就换一个请求键，再退同一个单位。每次只改变与假设有关的条件，结果也更容易解释。

读到一条“建议补充测试”的意见时，可以继续追问：这个测试准备区分哪两种行为？如果回答仍是“提高覆盖率”，说明意见还没有展开到可执行程度。

## 9.1.5 从评审意见到可复核的证据链路

```text
业务契约 → 冻结版本与 Diff → 执行工具
→ 绑定原始证据 → 形成 Finding → 校验与仲裁
→ 人工复核 → 修复 → 同条件验证与相关回归
```

每个箭头都可能出错。Diff 可能对应旧提交，日志可能来自另一案例，Finding 可能引用不存在的文件，去重可能合并两个独立问题。证据闭环要求逐段检查这些关系，而非只保存最后一段自然语言总结。

本项目顺序执行角色，仲裁为确定性 Python 函数；不会因为报告给出 approve 就直接合并 GitHub PR。这样读者可以先观察最小流程，再判断哪些复杂能力值得增加。

### 一条值得处理的评论如何组织

可以先写现象和条件，再写原因与动作：“规则变化后退款少 200 分；退款路径调用了读取当前券规则的 quote；请恢复历史分摊来源，并在改变规则后验证退款。”即使暂时不用结构化字段，读者也能知道为什么需要关注、到哪里检查、怎样确认已经解决。

评论的长度应服务于判断。贴出整段测试日志，会把关键差额埋掉；只有“存在资金风险”，又无法支持行动。正文保留关键输入、出错位置和最小证据，完整材料通过路径追溯。随着流程自动化，这个写法会自然转化成 9.4 中的 Finding，而不需要先背诵一套字段。

### 同一条意见，怎样逐步变得有用

我们把一条评论改写三次，观察新增信息究竟解决了什么问题。第一版是“退款逻辑存在风险，建议检查”。开发者无法知道检查范围，也无法判断优先级。它表达了担忧，还没有交付一个可以验证的问题。

第二版是“退款不应调用实时 quote，应改用 snapshot”。这次有了位置和方向，但仍缺少成立条件。如果这笔订单的规则始终不变，两种调用都可能返回相同金额；如果业务契约本来要求重新定价，这项建议甚至可能违背需求。仅凭方法名和个人经验，尚不足以要求别人修改。

第三版把条件补齐：“业务契约要求按下单分摊退款。此调用读取当前券配置；若下单后满减由 5000 调为 6000 分，C 的重新计价会从 6600 变为 6400 分。应保留历史来源，并用规则变化后的部分退款验证。”在尚未运行时，这是一条有具体反例的源码判断；取得本章的失败日志后，才能再加上“目标用例已观察到该差额”。

三次改写增加的主要价值，是减少接手者需要猜测的内容：规则由谁规定，什么条件会触发，哪条数据路径改变了结果，怎样判断修复成功。它也给反对意见留出入口。开发者可以证明 quote 实际读取的是冻结数据，可以指出契约已正式改变，或者运行反例发现推断不成立。能够接受这类核对，评论才真正进入了协作。

反过来，如果资料中根本没有退款口径，合适的交付可以是一个明确的问题：“历史订单是否允许按新券规则重算？此选择会改变部分退款金额，需先确认规则。”这时补一个看似笃定的错误结论，会使团队绕过真正需要决定的事情。

## 9.1.6 练习：改写一条无效意见

将“复用 quote 更简洁，建议通过”改写为一条值得审阅者采取行动的意见。要求写出被破坏的关系、触发输入、实际与预期，以及下一步需要查看的证据。

参考要点：应指出退款必须依赖原始分摊，规则变更后退 C 应为 6600 分；若暂时没有运行结果，就明确标为待验证假设并提出用例，不虚构已经观察到的金额。完整的字段表达见 9.4，金额与执行结果见 9.7。

本节先把一条局部修改转化为有规则、有条件、有观察的评审问题。下一节据此设计检查流程：先选择投入深度，再补充必要上下文，并检查任务是否真正完成。
