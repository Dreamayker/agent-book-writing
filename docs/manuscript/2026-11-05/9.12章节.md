# 9.12 端到端演练：让一个订单变更走完证据闭环

前面每节只放大流程中的一个部分，本节把这些部分重新连起来。你将以评审者身份接收一个变更，先形成自己的判断，再核对执行证据和报告，最后交出一份说明依据与待办的复核材料。离线回放用于理解流程，真实模型调用仍是需要另外配置和记录的实验。

阅读时可以分三遍进行。第一遍只沿正文理解“现在知道什么、下一步为什么需要它”；第二遍在独立克隆中运行，记录实际版本和结果；第三遍更换一个条件，检查自己能否迁移方法。命令执行完以后，能够解释产物之间的关系，才表示这次练习真正连通了前面的概念。

## 9.12.1 准备独立练习目录

本节采用连续步骤：第一条克隆命令从你选定的父目录执行，成功后进入练习仓库；后续代码块均从仓库根目录开始。需要切换到子工程的代码块使用子 shell，执行后返回仓库根目录；其余检查命令不会改变目录。需要 Git、JDK 17、Docker、Python 3.12 和 uv；网络需能取得依赖及 MySQL 镜像。

建议单独克隆练习目录。以下 shell 中 clone 成功后才进入目录；若目标目录已存在，另选新目录，不覆盖已有工作。

```bash
git clone https://github.com/Dreamayker/agent-book-writing.git agent-book-exercise && cd agent-book-exercise
```

随后记录版本并确认环境：

```bash
git rev-parse HEAD
java -version
docker info
uv --version
```

主线可能增加测试和补丁依赖。冻结教学基线是 `order-baseline-v1`，各案例清单保存自己依赖的完整提交。为了运行当前配套脚本，先保留克隆后的主线；运行器会自行创建基线 worktree，不需要把整个目录切到旧标签。

### 开始前，给自己留一页实验记录

记录不必复杂，先写练习目录、当前提交、准备检查的问题，以及你打算先读哪些材料。随后记录实际命令和结果的位置。第一次失败时，保留错误信息，不要立刻改业务代码。你需要先知道是环境未准备好，还是已经走到了目标行为。

独立克隆有两个作用：让练习生成的分支和日志有明确归属，也让作者保留的冻结材料继续可以对照。它仍不是安全沙箱，处理不可信构建时要回到 9.11 的执行边界。这里运行的是书中构造并说明的教学变更。

## 9.12.2 先验证主线正确版本可以工作

```bash
(
  cd order-review-lab
  ./mvnw -B -ntp clean verify
  python3 scripts/check_coverage.py
)
```

主线正确版本预期 Maven BUILD SUCCESS，8 项核心与 11 项集成测试通过，核心覆盖率不少于 90%，聚合不少于 80%。具体比例和版本以本次日志为准；冻结案例仍使用 18 项测试的旧基线，用于回放历史证据，不替代主线验收。

```bash
(
  cd review-harness
  uv sync --extra dev --locked
  uv run pytest
  uv run ruff check .
  uv run mypy review_system evaluation
)
```

本版预期 46 项 Python 测试通过，Ruff 和 mypy 无错误。这组检查包含共享评审能力，不是另一套订单计价实现。任何一步失败，先定位环境或代码问题，不直接开始把差异归为教学缺陷。

### 为什么先跑正确版本

如果正确基线也无法完成构建，就无法解释后来错误版本的非零退出。先建立一次正常运行，可以确认依赖、数据库和测试选择这条路径基本可用，同时获得对照输出。随后重放缺陷时，才有机会把新增失败与目标变更联系起来。

遇到失败，可以先沿 9.6 的阶段线定位：准备、构建、测试、业务断言。比如 Docker 无法启动，应先处理数据库环境；目标用例得到 6400，才开始讨论退款原因。把环境排查与业务分析分开记录，会让后续复核省去大量猜测。

## 9.12.3 独立整理自己的意见，再核对参考材料

本章已经讲解过 ORD-09，因此这里检查的是能否自行组织规则、因果与证据，不计作独立发现成绩。若要盲评，应按 9.9.4 改用未讲解的保留样本。

先读以下材料：业务契约、ORD-09 requirement.md、buggy.patch，以及 `tool-evidence/raw/buggy-source.txt`。只做源码发现练习时暂不读错误日志；证据解释练习再加入 buggy.txt。这一阶段先不打开 Oracle、fixed.patch 和录制 Finding，把它们留作后续核对；这不会消除前文已经介绍答案的影响。

在笔记中提交四项内容：规则依据；调用位置；触发条件及预计后果；下一步要取的证据。然后计算 A/B/C 的实付，核对自己是否把当前配置与历史快照混淆。

完成标志不是猜到“快照”两个字，而是能说明 quote 为什么会跨越时间边界。若把问题归为 double 精度或只要求退款不超过整单实付，返回 9.7 重新核对金额推导。

### 先写一段人能读懂的评审意见

此时可以暂时不写 JSON。用一小段话解释：退款本应读取哪一份历史依据，当前调用换成了什么，什么条件会让两者不同，以及你准备怎样验证。能够写清这段话以后，再把位置、证据和修复方向放进 Finding 字段。

如果暂时无法确定结果，写出竞争解释也有价值。例如怀疑实时规则与原快照不一致，同时需要排除分摊或单位选择错误。接下来的证据应帮助缩小解释，而不只是寻找一句支持原先猜测的日志。这样做也能减少看过答案后回头编排“早已知道”的错觉。

## 9.12.4 读取冻结证据，或重新生成一次运行

先读取 buggy.txt 与 observed.yaml 中的错误运行记录，核对 expected 6600、actual 6400，并形成自己的证据解释。需要观察修复验收时，再读取 fixed.txt，核对 expected=6600 actual=6600 与 livePricingReadsDuringRefund=0。fixed.txt 仅用于验收，不加入后续角色的待审上下文；依次阅读这些文件不会改写案例资产。

需要重新执行时，在这个独立练习克隆中运行：

```bash
(
  cd order-review-lab
  python3 scripts/replay_cases.py verify --case ORD-09
)
```

verify 会创建临时 worktree、应用补丁、建立新的本地 case/fix 分支提交，执行错误与修复测试，并更新该案例的日志、manifest、observed、录制夹具及案例清单版本。它不是只读检查，也不会自动把新证据推送远端。不要在保存作者改稿的工作区直接运行后，把这些变化误作正文修改。

```bash
git status --short
git diff --stat
```

新日志时间、SHA 与 run_id 不必等于纸面摘录，但各文件必须彼此一致。错误运行必须失败在目标业务断言，修复运行必须通过相同测试；网络、Docker 或编译失败不满足本步骤验收。运行器会清理临时 worktree，生成的证据则留在练习目录供核查。

### 重新执行后怎样读变化

这一步可能产生新的提交、运行标识和时间戳。先检查材料之间是否属于同一次执行，再比较行为：错误是否仍落在预期断言，修复是否在相同条件下通过。新旧原始文件逐字不同，未必说明实验不一致；没有变化也未必说明真的重新运行。需要回到 observed 和执行日志核对。

读者还应注意，错误测试在第一条断言失败后就会停止，测试文件后续写着哪些检查，与本次实际执行到哪里并不相同。记录结果时只描述真正观察到的部分，修复通过后再说明完整断言共同支持了什么。

## 9.12.5 经过三种评审模式

下面是只读取现有或本次新生成资产的录制回放：

```bash
(
  cd review-harness
  for mode in single multi multi_arbitrated; do
    uv run python -m evaluation.projects ../order-review-lab/evaluation/cases.yaml --mode "$mode"
  done
)
```

预期报告包含 `kind=recorded-control-fixture`。ORD-09 在三种模式都为 escalate；single 为零 Finding，multi 为两条预设重复意见，multi_arbitrated 为一条。ORD-01 无缺陷文档为 approve。回放会处理清单中的十二案例，不仅 ORD-09。

写下模式改变了什么、没有改变什么：检查角色和去重发生变化，核心路径人工门禁保持。不要把夹具结果写成模型实测 Recall；这里没有远端模型调用，也不会产生真实模型计费。

9.4 的上下文与拒绝示例、9.5 的去重示例可作为补充练习。每段 Python 明确在 `review-harness` 环境执行，若要连续运行，应保留前段定义的 context、case 等变量。

### 看懂回放结果，再思考模型实验

三种模式使用作者预设的角色输出，类似给流程喂入一组已知输入，检查它是否按设计分组、校验和裁决。single 的空列表与多角色的重复意见，都是为了让流程差异可见。你可以改变临时副本中的字段，预测哪一道校验会拒绝，然后再运行确认。

若下一步接入实时模型，变化发生在意见产生环节。材料选择、引用检查、去重与风险门禁仍应保留。需要另存真实输入输出、失败和用量，才能讨论模型表现；不能直接沿用夹具的 TP、FP、FN。先把流程回放与能力实验分清，后面的比较才有解释基础。

## 9.12.6 形成复核记录，再检查状态副线

报告完成后再打开 Oracle，核对根因与位置。使用 9.8 的空白复核模板写明已检查的证据和未解决的问题，保持 pending-human-review，直到实际审阅者作出决定。填写练习答案不等于完成真实业务批准。

下一步阅读 `splitKeepsOriginalSharesAndSharedRefundLedger`，说明子单退 C 后父单为何应拒绝再退。再在练习克隆中重放 ORD-04，区分锁、已退检查和条件更新的职责；重放 ORD-05，解释为什么没有二次退款仍可违反幂等协议。

## 9.12.7 常见故障如何处理

**表 9-18 环境失败与证据失败的定位**

| 症状 | 优先检查 | 不能得出的结论 |
| --- | --- | --- |
| Java 不存在或版本错误 | JDK 17 与 JAVA_HOME | 订单算法有缺陷 |
| Testcontainers 无法启动 | Docker、DOCKER_HOST、镜像网络 | 并发门禁被绕过 |
| Maven 下载失败 | 仓库访问和依赖缓存 | 错误补丁已被测试击穿 |
| hash mismatch / revision mismatch | 是否混用了重跑前后资产 | 模型业务解释错误 |
| 引用 fixed.txt 被拒 | 是否把验收证据当作待审输入 | 应该放宽门禁以通过流程 |
| 报告显示 recorded-control-fixture | 正常的离线回放标记 | 已完成真实模型比较 |

核心验收是每项结论都能回到对应输入和执行结果。真实模型调用另行配置模型、端点和预算，先试跑再扩展；其费用与能力只有保存完整记录后才能发表。读者到这里已经能完成一条包含意见、证据与待人工复核材料的教学流程；具名批准仍由实际审阅者完成。

## 9.12.8 本章回顾：把方法带回自己的项目

离开订单案例，可以先选一条与历史有关的业务承诺：库存是否只能扣一次，订阅升级是否影响旧账单，审批重试是否返回同一结果。写清对象、依据、状态和允许操作，再找一段可能改变这些关系的变更。无需一开始复制十二案例和四个角色。

接下来建立最小路径：给一位评审角色明确材料和交付，构造一个能区分候选行为的输入，保存执行与引用，再决定是否需要另一个专业视角。若现有规则无法回答问题，先确认规则；若材料不足，先补材料；若检查完整但判断失败，再研究模型与角色配置。

回顾本章，系统从一条退款改动开始，逐步长出了上下文、结构化意见、角色分工、证据管理、治理和评测。每个部件都对应实践中遇到的一个困难。能够说明这些困难和选择，比记住角色名称或复制一份配置更有助于设计下一套系统。下一章沿同一事故继续研究诊断与修复，考察提出修复以后怎样证明它真正恢复了约束。
