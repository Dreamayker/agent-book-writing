# 第 9 章出版视角审阅与修改建议

审阅日期：2026-11-06。审阅基线：`6db0189`。范围为[章首导语及 9.1～9.12](manuscript/2026-11-05/README.md)，并参照案例说明、业务契约、案例材料和评审实现。未取得全书其他章节全文、出版社版式和约定字数；以下为本章的内容与教学审阅，不代替外部文献核验或排版终审。以下保留改写前审阅结论及统计口径；作者随后授权的第一版改写结果见 [改写说明](publication-rewrite-2026-11-06.md)，此处各项问题描述针对基线稿。

## 一、总体判断：素材充分，教学展开不均衡，需要一次内容编辑

本章已有可出版的选题价值和工程素材基础：金额与历史状态问题有明确的业务后果；十二个案例覆盖计算、授权、请求状态、依赖和提示注入；失败与修复有实际执行记录；单 Agent、多角色和人工治理围绕同一业务系统展开。这些内容值得保留。

当前稿件可以承担工程伴读材料，但尚不足以直接作为成熟的实战章节交付出版社。主要问题是核心教学过程被压缩，外部资料占据较大篇幅，读者容易理解原则，却难以照着构建评审流程。增加案例数量的收益有限，应先把已经存在的案例写透。

还有一个标题承诺需要兑现：《AI 代码评审与多 Agent 协同》应让读者看到模型收到什么、怎样形成意见、角色意见如何互补或冲突、流程如何作出决定。当前更多展示业务测试和录制夹具，对真实模型调用的完整展示仍不足。不能把录制输出包装成模型实验，但可以先用明确标注的教学输出展示协议，再补真实调用与失败记录。

## 四、最有价值的五组新增内容

### 1. 把 ORD-09 写成真正的评审过程

现有“一行正确代码、一行错误代码”值得保留，但它只能说明答案。正文应进一步呈现：变更作者为什么想复用 quote；只读 Diff 的评审者为什么可能认同；补充哪些规则和调用上下文后才能识别时间边界；怎样用失败测试排除浮点、分摊或返回值错误等替代假设。

建议用七个连续片段展开：变更动机 → 局部 Diff → 必要上下文 → 6600/6400 原始断言摘录 → Finding → 人工需判断的部分 → 同一条件下修复验收。金额推导和完整 Diff 在 9.7 详细呈现，其他节只提取本节需要的一步。

9.7 展示“评审者如何形成判断”；第 10 章再详细解释“修复 Agent 如何生成假设、构造反例和做最小修复”，避免两章重复讲同一事故的全部过程。

### 2. 展示多角色“为什么有用”和“何时没用”

ORD-09 当前 correctness 与 test 的录制 Finding 在 claim 和证据上基本相同，security/impact 输出为空。这能测试去重，却不足以展示专业化协同的教学价值。

可以增加明确标为教学构造的不同角色分析样例：correctness 解释时间不变量，test 评估测试是否击穿缺陷，impact 检查快照和拆单的传播路径。尚未验证的新缺陷只写成假设或待查项，不能为了凑角色把同一问题拆成多个缺陷。再加入一组两个角色同意但证据不足的反例，说明人数与正确性无必然关系。

顺序调度、无并行与无模型仲裁均可保留，这些是合理的教学简化。需要补的是设计推导与中间产物，不必为追求章节丰富而立即实现队列、分布式调度或自动合并。

### 3. 利用本项目真实发生的工具分歧

[依赖审阅记录](dependency-advisories.md) 比增加一个新厂商案例更有价值：扫描器识别了包却返回空结果，直接 API 返回公告；随后补充已知漏洞控制样本、升级依赖，并对未使用的 Spring 视图功能绑定版本、源码哈希和复查期限。

这是“工具执行成功为何不等于结论可靠”的具体教学材料，可在 9.6 讲交叉验证，在 9.7.7 讲公告适用性，在 9.8 讲有期限的判断。正文保留一次完整讲述，其余交叉引用。报告中的适用性判断仍需按既有复查机制更新，不能写成永久豁免。

### 4. 让成本节能够算、能够选

没有真实账单也能先写有价值的算例，但必须明确“假设单价、非报价、非实测”。给相同变更在单角色、四角色及一次重试下的输入/输出 Token，逐项计算，加入人工处理一次误报的时间成本，让读者比较不同方案。

真实模型实验完成后，再用保存的 usage 和价格日期替换示范数据。正文解释计算方法，易变的供应商价目表放到可维护配套资料中。预算上限、自动降级等尚未实现的控制标为设计方案，不能写成当前运行器已有能力。

### 5. 增加失败样例、练习答案与离线阅读支持

每个主要机制至少给一个失败路径：JSON 合法但引用错版本、两个根因被误合并、同键重试被错误拒绝、凭据未进入子进程但宿主仍未隔离。读者由此理解机制的必要性和边界。

练习分为判断、修改、迁移三类；为核心练习提供期望产物、评分要点及常见错误，答案放节末或配套资料。正文展示关键数据和日志摘录，完整日志仍在仓库。印刷版读者不应必须打开多个 JSON 文件才能理解一次金额推导。

## 五、统一读者体验和出版语言

1. **补学习入口。** 导语说明需要会读 Java/Python、理解事务和基本 HTTP；给概念阅读、实操阅读两条路径。9.3 解释业务工程与评审控制面为何分离，降低环境切换负担。
2. **建立术语表。** 首次出现时解释 Finding、Oracle、manifest、provenance、fixture、根因与风险等级。业务金额统一用整数分，必要时附元；区分订单商品行和购买单位，避免部分数量退款的语义跳跃。
3. **统一标注实测类型。** 在开篇说明“业务执行／录制教学输出／真实模型调用／外部声明”的差异，表格和示例用短标签继续区分。把多处相同的长边界声明合并到固定说明和文献表中，具体尚未验证事项仍就近标明。
4. **修整综述语言。** 减少反复的“三条判断”“与本章同构”“世界的共识”等收束句；“结构化是治本”应改为结构约束解决哪些格式问题、哪些语义问题仍未解决，防止超过证据范围。
5. **把资料生产过程移出正文。** “Gemini 报告给出”“两次读取失败”“未采信百科的某比例”等过程说明可留在作者研究记录；正式正文保留有出处的结论与必要局限。读者需要知道结论可信到什么程度，无需继承检索过程。
6. **统一图表与代码体例。** 章内图表连续编号，有图题/表题、正文指向和必要来源；解决孤立“表 9-15”。重点增加本地架构、角色交接、退款状态/时序、端到端证据四类图。JSON、伪代码、真实源码、日志和教学输出分别标注，示例用中文解释每个关键字段。
7. **版本信息分层。** 纸面正文固定教学版本和方法，仓库维护受支持主线及依赖补丁，实验报告绑定实际 SHA。明确标签基线与主线不同，避免读者看到不同测试数量、依赖版本时以为跑错了。

## 六、建议改稿顺序与交稿条件
