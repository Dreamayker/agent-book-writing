# 电商订单案例工程与第 9 章迁移规划

日期：2026-11-05。状态：已按作者指示实施业务工程、12 个案例和第 9 章正文迁移；本文件保留设计依据与原验收要求，实际结果见 [迁移状态](migration-status.md)。真实模型实验、外部引用复核与出版审校仍待完成。

依据：[IMA 案例说明](manuscript/2026-11-05/案例说明.md)、[最新十二节书稿](manuscript/2026-11-05/README.md)、现有 `review-harness` 实现。代码核对基线为 `4f26d9c`；架构变更记录见 [ADR-004](decision-records/ADR-004-order-case-migration.md)。

## 1. 建议与交付目标

建议在同一仓库新增 **`order-review-lab`，实现 Java 订单计价、优惠分摊、快照和退款的真实可运行教学工程**；现有 Python 评审控制面先以接口适配的方式复用。工程形成证据后，再将第 9 章的主线从钱包转账迁移到“优惠券叠加与退款计价”，保留十二节的知识推进顺序。

这次迁移涉及业务规则、事务、测试、工具链和章节证据的重建。现有钱包的 `Decimal`、进程内 `RLock` 和内存幂等表，不能通过改名变成 Java/MySQL 的订单计价与退款实现。

交付目标是让读者独立完成以下链路：

```text
优惠券叠加需求
  → 规则澄清与 ADR
  → 读取遗留计价和退款代码
  → 实现叠加、分摊与快照
  → 用真实测试和数据库观察错误变更
  → 单 Agent / 多 Agent / 规则仲裁评审
  → 人工裁决
  → 最小修复与回归
  → 留下可复现案例和章节素材
```

工程是依据虚构公司“星河优选”构建的教学实现。案例说明提供业务设定，当前仓库没有该公司的遗留 Java 源码或生产事故日志；新建的遗留版本、事故数据和缺陷补丁都应明确标为教学构造。

## 3. 新工程的范围与目录

### 3.1 第一版范围

首版采用 Java 17、兼容 Java 17 的 Spring Boot 稳定版本、Maven Wrapper、MyBatis、MySQL、JUnit 5、Testcontainers、JaCoCo。确切依赖版本在实施时锁定，记录于构建文件和实验环境清单。

业务包括：订单试算与提交、三类优惠券的资格校验和叠加、按商品行及购买单位分摊、计价快照、部分退款、退款幂等和累计额度约束、按已有分摊结果拆单。其他服务通过明确的接口和固定数据适配器提供：促销、会员、券资格、支付确认、退款回执均有契约与调用日志。

Redis 先作为可选缓存，SQL 数据是订单、快照、退款和幂等记录的事实来源。第一版用一个应用内的模块边界表达退款与拆单流程，避免先搭建多个需要独立运维的服务；库存扣减、真实支付和跨服务分布式事务不进入首版。

### 4.1 十条规则逐条落地

### 4.2 第一个阶段需要冻结的口径

案例说明没有明确以下细节。下面给出建议默认值，实施阶段先写成 ADR 与验收表，再据此生成代码；不得把建议写成已由业务确认的规则。

| 未定问题 | 建议默认值 | 影响 |
| --- | --- | --- |
| 同类券可否多张 | 首版每类最多一张；接口显式拒绝超出范围 | 控制组合空间，保证择优逻辑可验证 |
| 人工选券与自动选券 | 首版在用户提交的候选券内择优，返回选中/排除原因；全券包搜索后续扩展 | 避免后台悄悄使用未选券 |
| 折扣券表示 | 折扣用整数基点表示；单步舍入方法与时点固定 | 避免引入浮点或多个舍入口径 |
| 互斥方案相同金额 | 使用固定业务优先级，再按券 ID 排序 | 相同输入可回放，不能依赖数据库返回顺序 |
| 新人券自己的门槛基数 | 依据其生效阶段的剩余实付，另列新人身份条件 | 防止与满减券门槛混用 |
| 部分数量退款 | 下单时冻结到购买单位的分摊，绑定原行和单位序号 | 明确一行多件时每次退哪一部分 |
| 运费、积分、税费、券返还 | 首版用例不包含；API 不接受未定义金额项 | 避免退款总额混入未建模项目 |
| 缺少快照的历史订单 | 标记并进入人工核对，不以现行优惠规则自动补算 | 保护历史兼容性与用户权益 |

对互斥组合的具体计算：活动价和品类券阶段固定后，分别计算“满减券路径”和“新人券路径”，选择最终实付更低的合法方案；可叠加时再按既定顺序执行两个阶段。无资格、超期或不属于用户的券不能进入候选集合。

### 4.3 金额、分摊与快照

定义 `activityTotal` 为本章参与优惠的商品活动价合计，`D` 为三个券阶段的实际抵扣总额，`payable` 为最终应付。基础断言为：

```text
activityTotal = D + payable
每张券：sum(allocatedDiscount) = actualCouponDiscount
每个购买单位：grossCents = sum(discountShares) + payableCents
sum(unitPayableCents) = orderPayableCents
累计成功退款 <= 原始可退实付
每个购买单位最多成功退一次
```

原价与活动价差额另记活动优惠，不能在上述公式中重复抵扣。

分摊建议采用最大余数法：按当前阶段的合格剩余金额计算比例，先向下取整，剩余分依余数从大到小补齐；并列时按 `itemId + unitIndex` 稳定排序。每个阶段只在有资格且仍有余额的单位内分摊，实际抵扣先封顶，零基数直接返回零分摊。乘法中间值使用精确大整数或显式溢出保护。

`PricingSnapshot` 至少保存：版本、订单与用户、原始行/单位标识、活动价、券与规则版本、各阶段计算基数、实际抵扣、单位分摊、实付、时间及内容哈希。退款和拆单读取该不可变记录，不能再查询实时促销条件来计算金额。

### 4.4 订单、幂等和退款的事务边界

建议持久化 `orders`、`order_items`、`pricing_snapshots`、`discount_allocations`、`refund_requests`、`idempotency_records`、券使用记录。快照更新采用新版本而非覆盖历史值；退款引用明确的已提交版本。

退款用例按以下顺序执行：认证和对象授权→进入数据库事务→按用户、操作、幂等键查重并校验请求指纹→锁定订单退款状态→按快照核对可退单位与累计额度→保存退款记录及单位状态→保存幂等结果→提交。并发同键请求还需唯一约束与冲突后的结果读取，不能只有“先查再插”。

订单提交应在同一事务中落订单、券使用状态和计价快照；模拟支付回执仅决定状态，不实际转账。外部支付/退款出站调用不放入长数据库事务，首版使用固定适配器；如扩展真实异步调用，再单独设计 outbox 和状态机。

券使用状态通过行锁或带状态条件的原子更新控制，验证同一张券不能被两个并发订单重复消费。拆单后的退款仍以原订单购买单位作为额度账本的唯一身份，父单和子单共享该账本与锁定范围，防止分别退款造成重复退付。

数据库测试必须运行在 MySQL 的两个独立连接/事务上。通过测试同步钩子固定竞争窗口，验证不同幂等键并发也不会超退；不能把 Python 锁测试或 H2 测试结果写成 MySQL 事务证明。

## 5. 先把退款事故写成精确的可执行样例

### 5.1 正确结果

在支持满减券与新人券叠加的正确基线上，固定活动价和券配置如下：

| 商品 | 活动价（分） | 满减 5000 分分摊 | 新人 2000 分分摊 | 最终实付（分） |
| --- | ---: | ---: | ---: | ---: |
| A | 12000 | 1500 | 600 | 9900 |
| B | 20000 | 2500 | 1000 | 16500 |
| C | 8000 | 1000 | 400 | 6600 |
| 合计 | 40000 | 5000 | 2000 | 33000 |

本例新人券允许与满减券叠加，所有商品可参与这两个整单券阶段。按阶段剩余金额比例分摊可得到上表，退 C 的正确金额为 **6600 分**。原订单快照和分摊记录是 Oracle 的依据。

### 5.2 建议构造的主缺陷 ORD-09

教学错误实现：`RefundAmountCalculator` 重新调用当前计价规则，而没有读取下单快照。下单后将满减金额从 5000 分调整到 6000 分，保持原订单不变；错误重算会把 C 的优惠视为 1200 + 400 = 1600 分，从而只退 **6400 分**，少退 **200 分**。

测试步骤固定为：创建订单并保存上表→修改当前券规则→请求退 C→断言返回金额与持久化退款都是 6600 分，同时断言退款计算没有调用实时促销接口。错误分支应以实际 6400、预期 6600 稳定失败；修复为读取原始快照后，同一用例通过。

该教学设计已由 ORD-09 实际重放：错误版本退款 6400 分，修复版本退款 6600 分且零次实时计价调用。版本、命令与原始输出见 `order-review-lab/book-assets/ORD-09/`。规则变更、快照读取和接口调用计数仍是后续变体的必要证据。

### 5.3 为什么要先固定错误算法

案例说明列出了“按剩余商品重算”等多个疑似根因，尚未给出唯一算法。若用“原支付 33000 − 剩余 A/B 重算后 25000”计算退款，会得到 8000 分，反而多退；仅凭退款时重算不能推出必然少退。

因此 ORD-09 首先采用上面的实时规则变更反例；“剩余商品重算”“缺少分摊字段”“拆单丢快照”“舍入残差”分别做独立变体，每个变体都写明输入、错误公式、期望值和实际值。任何变体都不得共享一个含糊的事故结论。

### 5.4 跨第 9、10 章的叙事分工

第 9 章展示：评审一项优惠叠加或退款相关变更，发现快照契约风险、取证、仲裁和人工升级。第 10 章按案例说明，以冻结的历史事故版本展开定位、多个根因假设、失败用例、最小修复和回归。

两章共享同一业务模型、数据和 Case ID，但使用明确的版本快照。不能一边写第 9 章已通过完整门禁并验证修复，一边又声称相同发布版本在第 10 章首次发现同一已修复问题。第 9 章可提供修复验证附件，第 10 章负责完整修复工作流的教学展开。

## 6. 教学案例与现有钱包案例的迁移

### 6.1 新案例目录

### 6.2 每个案例的交付包

```text
book-assets/ORD-09-refund-snapshot/
├── requirement.md                 # 业务规则与验收条件
├── case.yaml                      # Case ID、项目、基线 SHA、变更 SHA、工具命令
├── oracle.yaml                    # 根因、位置容差、证据与允许修复；只用于评分
├── buggy.patch / fixed.patch

├── tool-evidence/raw/              # Maven/JUnit/SQL/扫描原始输出
├── tool-evidence/observed.yaml     # 命令、退出码、环境与摘要
```

使用独立 worktree 执行补丁和回归，记录基线/变更/修复 SHA，避免在主工作区反复切分支。每个错误补丁先在指定基线上验证可应用，再采集失败证据；修复后重放同一用例并运行相关回归，不能用一份手填 YAML 代替执行。

## 7. 评审控制面如何接入 Java 工程

### 7.1 第一批必要改造

| 当前文件 | 计划改造 | 验收标准 |
| --- | --- | --- |

| 新增工具执行层 | 执行 Maven、静态扫描、依赖分析并解析报告 | 保留退出码、命令、工具版本、报告路径和 SHA-256 |

证据门禁不仅校验 `ref` 非空，还要确认引用存在、属于本次运行、绑定同一代码版本且内容哈希一致。错误编译、业务断言失败、执行超时、缺少 Docker 和工具无法运行应分别记录，不能都计作“发现缺陷”。

### 7.2 权限与仲裁

第 9 章保留 `correctness / test / security / impact` 四角色及规则仲裁，按业务证据分工，不因案例说明提到更多全书 Agent 就把它们全加进一次评审。需求澄清、方案设计和编码 Agent 属于上游/修复工作流，其产物进入评审上下文，其权限与评审者隔离。

第一批保留当前可验证的顺序执行。并行度、超时和重试作为下一步调度能力；明确规则仲裁已经实现、模型仲裁尚待开发的差别。高风险结果在三种 Agent 模式下都必须人工升级，不能因专业 Agent 数量少而跳过门禁。

### 7.3 测试、扫描与 CI

建议拆成四类验证任务：

1. Java 编译与单元测试：计价、资格、互斥、最大余数分摊；JaCoCo 首版整体门槛建议 80%，核心计算模块 90%，以新工程实测后确定基线。
2. MySQL 集成与 API 测试：快照提交、重复请求、授权、并发退款、拆单、事务回滚和旧订单兼容。没有容器环境时标记基础设施未满足，不能以跳过测试获得“全通过”。
3. 静态与依赖检查：Java Semgrep、构建时静态检查、依赖树/SBOM 与 OSV；已有 Python 检查单独保留。SARIF 上传不受支持时保留报告 artifact，扫描失败仍影响门禁。
4. 案例重放：正确基线通过，错误分支出现指定业务失败，修复分支通过；同时回放评审策略与证据解析，录制输出只用于控制面验收。

公开 PR 中的任意测试脚本不接触模型密钥；需要真实模型的批量评测由受控执行任务读取已经冻结的输入与可信工具证据。GitHub Actions 的工作目录和扫描范围应覆盖两个工程，避免继续只扫描钱包目录。

## 11. 真实评测与出版证据

### 11.1 对照实验

先实现并明确四种比较条件：确定性工具、单通用 Agent、多角色不合并、多角色加规则仲裁。当前工程只实现后三种评审模式，确定性工具需要新增独立汇总路径；模型仲裁作为额外实验项，不能把现有规则函数改个名称就计为模型 B 仲裁。

双模型先用模型 A、B 分别运行同一组角色配置，比较稳定性；有实际模型仲裁器后，再增加 A 评审/B 仲裁的交叉实验。每个案例每种配置重复 3～5 次，完整记录运行数：例如 12 案例 × 3 种 Agent 配置 × 2 个模型 × 3 次 = 216 次案例运行，模型调用次数还需乘实际角色数及重试数。先用 ORD-01/09 做小规模试跑，再依据真实台账估算预算。

### 11.2 避免把答案喂给评审

Oracle、人工标准答案和 `fixed.patch` 只供评分与修复验收，评审输入只包含真实可见的需求、待审 Diff、受控上下文与明确允许的工具证据。

分别记录两种实验轨道：源码评审轨道不直接提供本次缺陷的专用失败测试结果，用于观察模型定位；证据解释轨道提供相同的可信工具输出，用于比较解释、去重和裁决。两轨结果分表，不能把读到失败答案后的命中率写成模型独立发现能力。

训练/调试使用的案例与保留变体分开。变体可改变金额、商品组合、规则生效时间、并发请求键和注入载体；同一根因变体不当作完全独立业务泛化样本。

### 11.3 必须记录的指标

逐案例根因 Precision/Recall、定位准确性、证据可解析率、严重性一致性、重复率、零缺陷误报率、PR 错误阻断率、人工升级率、修复回归结果、输入/缓存/输出 Token、延迟与实际计费。零预测或零缺陷时的指标记为 N/A 或明确约定，不能把“没有报错”直接记为 100% Precision。

ROI 另记录工程与人工复核用时、返工、遗漏和误报处理；案例说明中的转化率或客单价是业务目标，不能由代码实验推导为已提升的收益。
