# ADR-004：以电商订单案例承载新版书稿主线

- 状态：已采用。Java 订单基线、评审适配、12 个 ORD 案例和第 9 章正文迁移已实施；实时评测与出版验收另行跟踪。
- 日期：2026-11-05。
- 关联：[迁移规划](../order-case-migration-plan.md)、[IMA 案例说明](../manuscript/2026-11-05/案例说明.md)。

## 背景

ADR-001 为单章教学选择了数字钱包。最新案例说明希望以遗留电商系统中的优惠券叠加与退款计价 Bug 贯穿全书，技术栈为 Java/Spring Boot/MyBatis/MySQL。钱包工程的内存模型不包含计价阶段、分摊、快照与退款，不能承担这些业务契约。

## 决策

在同一仓库新增 `order-review-lab`：以模块化 Java 应用实现订单、优惠、分摊、快照、退款与拆单，使用真实 MySQL 集成测试；其他服务先通过固定适配器提供。Python 评审能力单独整理为 `review-harness`，通过项目和案例接口复用。

先形成正确业务基线和退款反例，再按阶段改写第 9 章十二节。订单使用独立 ORD 编号。以退款快照 ORD-09 为主线、并发退款 ORD-04 为副线，与第 10 章共用冻结事故素材并明确版本。

## 考虑的替代方案

| 方案 | 优点 | 代价与判断 |
| --- | --- | --- |
| 仅将钱包名词换成订单 | 工作量小 | 无法产生规则、分摊和快照证据，不能满足案例说明 |
| 在 Python 钱包应用中扩展完整订单域 | 能沿用运行环境 | 与 Java 遗留场景及 MySQL 事务教学存在偏差，适合作为原型而非本次目标 |
| 新建 Java 业务工程，复用评审能力 | 同时满足案例连续性和可复现性 | 引入双语言环境，需要契约与分阶段迁移；建议采用 |
| 一次性创建全部外部微服务并重写评审平台 | 接近完整企业架构 | 范围和运维成本过大，推迟第一个可验证用例 |

## 约束与后果

业务的十条规则需要先变成验收条件；未明确的舍入、选券、部分数量退款和历史快照规则要单独冻结。重建的遗留现场和事故必须标为教学构造。高风险人工终审、证据门禁、录制与真实模型结果分离继续沿用。

实现采用完整叠加基线 `7a61a4f`，18 项 Java 测试及 MySQL 回归通过，12 个案例均保存错误/修复执行证据；正文同步更新 Markdown 和富文本。`legacy/order-v0` 冻结 ORD-09 事故版本，没有另建单券旧应用。当前边界与剩余项见 [迁移状态](../migration-status.md)。
