# 第 9 章 AI 代码评审与多 Agent 协同

一笔订单的实付为 33000 分。用户退掉商品 C，系统应该退 6600 分；如果退款时读取已经更新的优惠规则，却会算成 6400 分。这两百分钱的差额不是模型观点，而是一条可以通过订单快照、数据库记录和失败测试共同核验的业务事实。

本章以“星河优选”的优惠券叠加与退款计价为贯穿案例。Java 17 工程 `order-review-lab` 实现业务；现有 Python `wallet-review-lab/review_system` 提供评审角色适配、Finding 校验、风险路由、去重与规则仲裁。公司、遗留版本和故障补丁均为教学构造，工程不连接真实资金。

阅读时带着三个问题：这个变更破坏了哪条业务不变量？工具给出了什么可以重放的证据？谁有权依据证据做最终决定？单 Agent 和多 Agent 的区别，只有落实到这三个问题才值得讨论。

9.1～9.2 建立判断框架与工业对照；9.3～9.6 建立环境、契约、角色和证据流程；9.7 展开 ORD-01～ORD-12；9.8～9.11 处理治理、评测、成本与安全；9.12 完成 ORD-09 的端到端演练。ORD 编号是订单案例 ID，不是 GitHub PR 编号；钱包 PR 编号保留历史含义。

业务测试是真实执行结果，录制 Agent 输出是人工构造的控制夹具。后者只能验证评审流程，不能证明模型发现缺陷的能力。正文中的实测与待验证项分开记录：模型重复评测、成本和跨模型效果仍须独立实验。
