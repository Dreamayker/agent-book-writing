## 1. 章首导语（不编号，置于"9.1"标题之前）

> 排版说明：以下为导语全文，正文中不加节号；两张表为无编号示意表，正式书稿可作引言表格处理。

本章把"AI 代码评审"从一个模型输出质量的问题，重构成一个工程系统的问题：怎样把模型放进一条可验证、可回放、可审计、可问责的证据流水线，让每一次评审结论都能追溯到缺陷证据、不变量与人工裁决。围绕这个目标，本章回答三个问题：

- **评审为什么需要证据而不是意见？** 模型说"这段代码有并发问题"，和它能拿出"在哪条执行轨迹上、违反哪条不变量、用什么测试复现"，是两回事。前者是意见，后者才是可以被复核、被回放、被问责的证据。

- **多个 AI Agent 如何分工、如何仲裁？** 单一模型在单个任务上能力不足，专业化分工能提升覆盖率，但分工必然带来意见冲突。本章给出最小角色集、仲裁协议与人工治理的边界。

- **怎么证明这套系统可信？** 通过统一 Finding Schema、证据包、录制回放与双层 Oracle 评测，把"模型说得对不对"变成可测量的指标，而不是印象。

全章围绕一个可复现的实验场展开：**wallet-review-lab**，一个刻意保留缺陷的数字钱包仓库。它的四条业务不变量——金额守恒、余额非负、幂等键单次生效、对象所有权——构成评审、仲裁与评测的共同语言，本章每个案例都围绕其中一条或多条展开。

**案例体系与编号约定。** 本章用一套编号体系贯穿案例、Finding 与 Oracle，全书一致：

## 2. 9.1.6 修订（替换原"本章阅读地图"内容，标题保留）

承接 9.1.5"三个流行答案为什么不够"的论证，本章的路线可以概括为一条从困境到系统的链路：

- **9.2** 先看工业界三个系统（RADAR、CodeRabbit、CodeAgent）如何应对同样的困境，取其架构经验而非营销数字；

- **9.3** 建立实验场 wallet-review-lab：数字钱包、四项不变量、Oracle 与可回放基线，让后续每一节都有可执行的载体；

- **9.4–9.6** 从单 Agent 评审契约，到专业化多 Agent 分工，再到证据流水线（统一 Schema、证据包、风险路由、录制回放）——这是本章的机制内核；

- **9.7** 用六个案例深度实战，把机制放到真实缺陷上检验；**9.8–9.10** 解决治理、评测与成本问题；**9.11** 补上安全防御维度；**9.12** 以一次端到端演练收束全章。

全局导航——案例体系表、PR-06 编号约定、三档阅读路径——已在章首导语给出，本节不再重复；四角色命名以 9.5 为准，Finding 字段定义以 9.6 为准。读完全章后，建议回到导语对照案例表检查一遍：每个案例你都能说出它违反哪条不变量、最终由谁仲裁、如何被回放验证。
