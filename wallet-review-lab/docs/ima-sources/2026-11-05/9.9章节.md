# 9.9 评测与行业基准：让修对了可被判定

## 9.9.1 两种正确性需要不同参照

业务测试判定给定输入下订单行为是否满足规则；根因 Oracle 判定评审意见是否识别了正确问题。ORD-09 退款 6400 分构成业务失败，但模型若把它解释成“使用 double 导致精度损失”，根因仍不正确。业务失败不能自动记为 Agent 命中。

订单 Oracle 每条记录包含 root_cause_id、文件、允许行区间、严重性与可接受修复。评分器在每个案例内匹配根因和位置，要求有证据且严重性一致，再汇总 TP/FP/FN。不同案例即使使用相同 Finding 类型 ID，也不会在全局集合中坍缩成一个样本。

## 9.9.2 清单驱动与逐案例结果

```bash
cd wallet-review-lab
uv run python -m evaluation.projects ../order-review-lab/evaluation/cases.yaml --mode multi_arbitrated
```

清单指定项目根、策略、案例目录、变更路径、标签和代码版本。同一 ReviewPipeline 读取订单配置，不再依赖钱包专属硬编码。旧钱包套件仍保留历史接口，不能把旧评分结果与新评分口径直接拼接。

报告明确标识 recorded-control-fixture，逐项列出 case_id、verdict、Finding 数和 TP/FP/FN。ORD-01 的 Oracle 为空；它用于观察误报和错误阻断。其余 11 个案例有预设根因。夹具按设计命中，只能证明加载、证据校验、路由、去重和评分链路一致。

## 9.9.3 指标与匹配边界

Precision 衡量报告的问题中有多少被参照答案接受；Recall 衡量参照问题中找到了多少。零预测的 Precision 应记为 N/A 或事先约定，不能默认为百分之百。零缺陷样本还应单独报告误报率与错误阻断率；高风险人工升级不是错误阻断。

当前实现验证根因、文件、行区间、严重性及证据非空；证据文件另由门禁绑定本次代码和哈希。它尚不自动判定修复建议语义、跨文件任意等价根因或测试质量。模型提出 Oracle 之外的新问题时，需要人工补充标注，不能简单断言模型错了。

## 9.9.4 避免泄漏答案

评审完成后才读取 oracle.yaml 评分。评审上下文不含 fixed.patch、人工标准答案或保留测试答案。录制夹具本来就是预设输出，不能拿它做“盲评成功”的宣传。

真实实验分两轨：源码评审轨道只提供规则和待审源码；证据解释轨道提供相同的可信工具输出，观察解释与治理。看过“expected 6600 actual 6400”的模型，任务是解释证据，不能据此宣称独立发现退款缺陷。

调试案例与保留变体分开。可改变商品组合、金额、规则更新时间、请求键、数量和注入载体。同一根因的金额变体不能当作完全独立的业务泛化样本。

## 9.9.5 真实模型实验协议

比较确定性工具、单 Agent、多角色和多角色加规则仲裁。两个模型分别运行相同角色配置，每案例重复 3～5 次，保留失败和拒答。12 案例×3 种 Agent 配置×2 个模型×3 次为 216 次案例运行，实际调用数还需乘角色数和重试。

先以 ORD-01/09 做小规模试跑，再据真实延迟与用量估算预算。模型仲裁尚未实现，不能把规则函数记作模型 B。模型名称、兼容端点、输出格式和预算需明确配置；没有真实实验时，只发布工程与控制夹具验证结果。

以下行业基准对照保留既有来源边界，所述规模和指标属于外部资料，不是订单工程的测量结果。

## 9.9.6 与行业基准的对照

下表把本章评测层与外部的基准和方法学对照（外部资料访问日期 2026-10-20）：

| **本章机制** | **外部基准/方法** | **对照要点** | **来源** |
| --- | --- | --- | --- |
| 注入缺陷 + 测试 Oracle | Defects4J（Java 程序修复基准） | 提供带触发测试与 ground-truth 补丁的真实缺陷：早期 1.0.x 收录约 395 个可复现缺陷、来自 6 个真实 Java 项目；1.2 版为 357 个缺陷、5 个大型程序（22,000 LOC 以上），并给出按控制流/数据流分类的 488 个缺陷；数据库后续扩展至 15 个项目、597 个缺陷，另有讲义转述为 17 个系统、854 个缺陷 | web_486, web_487, web_489, web_490, web_491, web_500 |
| 版本化基准 = 分数不可跨版本比较 | 同上（Defects4J 版本演进） | 同一基准的不同版本（1.0.x/1.2/扩展版）缺陷数与项目数均不同，分数因此不可直接横向比较——印证本节"报告必须绑定基准版本"的纪律 | web_487, web_489, web_490, web_491 |
| 根因 Oracle 与去重 | SWE-bench 家族（issue→补丁→测试判定） | 原始 SWE-bench 含 2,294 个任务、来自 12 个 Python 项目；通过 patch 应用后跑测试判定 resolved；位于 Docker 沙箱中执行，属执行型（execution-based）评测 | web_503, web_504, web_511 |
| 人工验证子集 | SWE-bench Verified | 500 个经人工核查的实例，来自热门 Python 仓库，每例含真实 bug report 与判定补丁的单元测试（FAIL_TO_PASS/PASS_TO_PASS）；OpenAI o3-mini 系统卡记录为 N=477，并说明该子集修正了"正确解被错误评分、问题陈述欠明确、单元测试过度特定"三类缺陷 | web_458, web_465, web_470 |
| 通过率 ≠ 正确率 | SWE-bench 审计 | 测试是程序化 Oracle 而非唯一正确性证明：隐藏测试可拒绝正确的替代实现，覆盖薄弱可放过不完整补丁，环境配置会改变结果；有审计指出部分通过补丁行为与开发者修复不同甚至明显错误，建议抽样人工核对并报告调整后比率与区间 | web_509, web_510 |
| 门禁与抗 game | 在线/离线互检、迭代加难度 | 开源的 Code Review Bench 让在线与离线基准互相检查以防刷分，并公开数据、golden 评论、判官提示词与流水线；基准持续加难（如 SWE-bench-Pro 公开集 731 例、Terminal-Bench-2 n=89，pass@1/pass@2 报告，补丁在独立 evaluator 容器中重放） | web_472, web_512 |
| 评审质量的判定 | 代码评审基准 | 面向 AI 代码评审的基准正在成形：Turing 的 Code Review Bench 从 6,296 个任务中取 1,200 个，报告成功率与 Bug Catching Rate；GitHub ReviewBench 基于 219 个真实 PR、187 个开源仓库、19 种语言；综述指出该领域数据集分散、设计差异大，对"究竟评估了哪些评审能力"洞察有限 | web_473, web_475, web_480, web_485 |

**三条判断。** 第一，**基准的演进史就是"判定器不够用"的证据史**：Defects4J 从 6 个项目 395 个缺陷扩到 15 个项目 597 个缺陷，SWE-bench 从原始全集细分出 500 例人工验证子集以适应三类评分缺陷，说明"有测试"远不等于"判得准"；本章因此坚持双层 Oracle（测试 + 根因）。第二，**分数是口径的函数**：同一基准不同版本不可比、通过率与正确率有实测差距、评审基准之间设计差异巨大，这三条合起来指向同一结论——本章要求"评测报告绑定基准版本与评分器哈希"，不是形式主义。第三，**AI 代码评审的评测仍在形成期**：与缺陷修复相比，评审质量更依赖"评论是否值得人类采取行动"这类主观判据，因此该领域的基准要么正在从零建立，要么仍在争论指标本身是否有效——本章的 `evaluation/` 因此把自己定位为**可复现的内部判准**，而非对外可比的能力排名。

**事实边界声明**：本节外部资料访问日期为 2026-10-20。Defects4J 各版本缺陷数与项目数在不同来源与不同版本中口径不一（395/357/488/597/854 等），正文按来源分别标注、不合并为单一数字，此差异本身即正文论点的一部分。SWE-bench Verified 相关数字以 OpenAI 系统卡与论文/综述为据，其中"OpenAI 因测试缺陷停用该基准、约 60% 样本存在测试缺陷"的说法来自百科词条转述，**未获一手来源确认，正文不采信该具体比例**。Turing Code Review Bench 的成功率与 Bug Catching Rate 数值、GitHub ReviewBench 的规模均为机构公开发布口径，未独立复现。本节所有外部数字仅用于机制对照，不用于推导 wallet-review-lab 的实验结论。
