# 9.9 评测与行业基准：让"修对了"可被判定

前八节把流水线建到了"能产出裁决记录"的程度，但整条链上始终悬着一个未被回答的问题：**怎么知道 Agent 真的找对了、修对了？** 评审系统的产出是"评论与补丁"，而评论天然是意见、补丁天然是候选。评测层（evaluation）就是给这条流水线装上判定器的部分。本节先建立三个问题的框架——**Oracle（判准）、指标（怎么算）、样本（在什么上算）**，再把它与工业界成熟的基准对照。

## 9.9.1 评测层的三个问题

评测看似简单：拿一堆已知缺陷，看 Agent 抓到几个。但 9.9.6 的对照会显示，工业界在每一个环节上都踩过坑，所以先把问题拆清楚：

1. **Oracle：什么算"正确答案"？** 如果没有一份可判定的标准答案，"命中"就无从谈起。本章的 Finding Schema 中保留的 `root_cause`、`invariant_violated`、`acceptable_fix`、`severity`、`evidence` 五个字段，本质上就是一份逐案例的 Oracle。

2. **指标：多个 Agent、多次运行报出的重复评论怎么计数？** 同一个根因被四个角色各报一次，是四个真阳性还是一个？这是**根因去重（root-cause deduplication）**要解决的问题，也是 9.6.8 中 SARIF `partialFingerprints` 对照过的工业问题。

3. **样本：在什么缺陷集上算，且数字可不可比？** 缺陷集的选择、版本、生成方式，直接决定分数能不能横向比较。Defects4J 的版本演进（下节）正是一个反面教材。

评测层必须前置声明这三者的取值，否则"Precision 0.8"是无意义数字。这也解释了为什么评测配置要和裁决记录一样入证据包：**报告只有在口径被固定时才是证据。**

## 9.9.2 Oracle：从测试判定到根因判定

工业界最常用的 Oracle 是**程序化 Oracle（programmatic oracle）**：给定一组测试，补丁让目标测试通过且不破坏其它测试，则记为该任务"解决"（resolved）。SWE-bench 及其后续基准都建立在这一机制上：每个实例是真实 GitHub issue 加上一组单元测试，测试决定提交的补丁是否解决了底层问题。

但程序化 Oracle 有明确边界，本节必须写清楚，因为它是本章反复保留的纪律的技术根据：

- **它是必要而非充分的判据**。有分析指出，测试是"程序化 oracle，而非补丁唯一正确的证明"：一个正确的替代实现可能因为隐藏测试强制了未声明的细节而被判失败，而一个不完整的补丁可能因为覆盖薄弱而侥幸通过；环境配置也会改变结果。

- **通过率不等于正确率**。已发表的 SWE-bench 审计显示这一差距是真实的：部分通过的补丁行为与开发者的修复不同，有些则明显错误；有工程建议因此提出：在让通过率驱动选型决策之前，应当抽样、让专家逐条核对，并报告**调整后的比率与置信区间**。

这直接解释了本章为什么要在测试之上再加一层**根因 Oracle**。与"测试是否通过"相比，根因 Oracle 回答的是更接近需求层的三个问题：这个 Finding 指认的 `root_cause` 是否就是注入缺陷的根因？它命中的 `invariant_violated` 是否正确？它给出的 `acceptable_fix` 是否落在一组可接受修复之内（例如 PR-04 的 `restore_atomic_boundary`）？测试 Oracle 判"结果"，根因 Oracle 判"理由"——两者都算命中，才算真正判定。

需要标注的边界：根因 Oracle 由人工编写（教学环境中由缺陷注入脚本与人工标注共同给出），因此它的质量受标注者能力限制；本章不宣称根因 Oracle 比程序化 Oracle 更客观，只宣称**它管的是程序化 Oracle 管不到的那一半**（对照 9.6.8 中 SARIF 只解决格式、不解决审计的结论）。

## 9.9.3 指标：Precision、Recall 与零缺陷门禁

指标层要解决三件事：抓到的准不准、该抓的有没有漏、重复怎么算。

**第一，计数单位是根因，不是评论条数。** 若不做去重，一个"话多"的 Agent 可以用四条重复评论把 Recall 刷到 4/4，而一个精准的 Agent 只报一条却是 1/4——指标会奖励啰嗦而不是正确。根因去重的做法：为每个 Finding 计算稳定的去重键（根因类别 + 关键文件/符号 + 不变量名），同键只计一次，与 9.6.1 的去重纪律、9.6.8 的 SARIF `partialFingerprints` 同构。评测报告中应同时给出"去重前/去重后"的计数，让读者看到水分来自哪里。

**第二，Precision 与 Recall 都要报，且要报根因级。** `Precision = 去重后命中的真根因数 / 去重后报出的根因数`；`Recall = 命中的真根因数 / Oracle 中的真根因总数`。只报其中一个都会被轻易 game：只报 Recall 可以靠穷举刷分，只报 Precision 可以靠只报一条最明显的缺陷刷分。本章把二者与 `severity` 分档交叉报告——高危根因的漏报（Recall 损失）与低危误报（Precision 损失）的代价并不相同。

**第三，零缺陷（zero-defect）门禁。** 这是本章最严格的一档，对应 PR-01 的"零缺陷"要求：在一组**关键缺陷**上，门禁要求漏报数为零，任一高危根因被漏报即整体 fail。零缺陷门禁的合理性来自后果而非统计——它不追求平均分，而追求"这一类错误绝不允许发生"；因此它只适用于被明确列举的关键根因（如四项不变量对应的根因），不能作为 전체指标使用。实现上，`evaluation/` 中的门禁脚本读取 Oracle 与去重后的 Finding 集，输出 `verdict` 与逐条漏报清单——门禁失败同样产出 Finding，而不是静默重跑。

## 9.9.4 评测架构：gold 集、回放与防 game

评测层的工程结构（教学环境目录 `evaluation/`）：

- **gold 集**：与注入缺陷一一对应的 Oracle 记录，字段与 Finding Schema 对齐，但额外标记 `injected_at`（注入位置）与 `acceptable_fix` 集合。gold 集与测试代码分离存放，避免"改测试即改判准"。

- **回放模式与真实模式分离**。录制回放（`recorded-agents.json`）只验证编排、Schema、去重与评分逻辑本身是否正确；它**不测量真实模型能力**——这条边界在 9.1 已确立，本节再次保留：回放得到的高 Recall 只说明评分器工作正常，不说明模型会找 bug。

- **确定性评分**。评分器必须是纯函数：同 gold 集、同 Finding 集必得同分数；任何 LLM-as-judge 参与的部分（如评审评论质量）都必须标记为独立维度，不与根因命中率混合计分——因为 LLM 判官本身引入方差，混算会让分数不可复现。

- **防 game**。工业界的经验是：静态评测会被针对性优化而失效，因此成熟做法是让**在线与离线评测互相校验**，并把数据集、golden 评论、判官提示词与流水线全部开源，接受外部复现；另一个方向是让新增基准不断加难度（后续 9.9.6 会看到 SWE-bench-Pro、Terminal-Bench-2 等演进）。本章的对应做法是：把评测集与评分器一同冻结进证据包，并在每次评测报告中声明所用基准版本——不同版本的分数不可直接比较（下一节会用 Defects4J 证明这一点）。

## 9.9.5 演示：PR-04 的评测与零缺陷门禁

沿用统一教学结构，把评测落到 PR-04（并发双花，CONCURRENCY-001，`app/repository.py`）：

**需求与不变量**：转移操作须满足四项不变量；PR-04 的注入缺陷破坏"金额守恒"与"余额非负"。

**Oracle**：`root_cause = check_then_act_race`，`invariant_violated = conservation`，`severity = high`，`acceptable_fix = restore_atomic_boundary`（与 9.4、9.8 一致）。

**可复现测试**：`tests/test_transfer_invariants.py` 固定并发交错；`make replay-pr04` 回放同一录制数据。

**Finding**：correctness 报出竞态 Finding，security 报出守恒违反 Finding——两个 Finding 在去重后归入同一根因（同键：根因类别 + `app/repository.py` + 不变量名）。

**评测**：以下为教学简化示例（未声称可直接运行）：

```python
# evaluation/metrics.py（教学简化示例）
def dedup_key(f):                      # 稳定去重键，与 9.6.1 去重纪律一致
    return (f.root_cause, f.file, f.invariant_violated)

def score(gold, findings, gate_only_high=True):
    seen, hits = set(), set()
    for f in findings:
        k = dedup_key(f)
        if k in seen:                  # 同根因只计一次
            continue
        seen.add(k)
        if k in {g.key for g in gold}: # 命中 Oracle 中的真根因
            hits.add(k)
    tp = len(hits)
    reported = len(seen)
    recall = tp / len(gold)
    precision = tp / reported if reported else 1.0
    missed_high = [g.key for g in gold
                   if g.severity == "high" and g.key not in hits]
    gate = "FAIL" if (gate_only_high and missed_high) else "PASS"
    return {"precision": round(precision, 3),
            "recall": round(recall, 3),
            "zero_defect_gate": gate,
            "missed_high": missed_high}
```

**门禁与回归**：评审流水线的 CI 中，`uv run pytest` 保证测试 Oracle；`evaluation/` 的门禁在关键根因漏报时 fail 并列出漏报清单；`uv run mypy app review_system evaluation` 保证评测代码自身类型正确。**生产待验证**：本节的评测全部在注入缺陷与录制数据上完成，绝对数值不具外推性——它验证的是"评测机制能正确区分命中与漏报"，不是"模型在真实仓库上的能力"。后者只能在 9.9.6 那类外部基准上、并附带其自身的可比性警告来讨论。

## 9.9.6 与行业基准的对照

下表把本章评测层与外部的基准和方法学对照（外部资料访问日期 2026-10-20）：

| --- | --- | --- | --- |

**三条判断。** 第一，**基准的演进史就是"判定器不够用"的证据史**：Defects4J 从 6 个项目 395 个缺陷扩到 15 个项目 597 个缺陷，SWE-bench 从原始全集细分出 500 例人工验证子集以适应三类评分缺陷，说明"有测试"远不等于"判得准"；本章因此坚持双层 Oracle（测试 + 根因）。第二，**分数是口径的函数**：同一基准不同版本不可比、通过率与正确率有实测差距、评审基准之间设计差异巨大，这三条合起来指向同一结论——本章要求"评测报告绑定基准版本与评分器哈希"，不是形式主义。第三，**AI 代码评审的评测仍在形成期**：与缺陷修复相比，评审质量更依赖"评论是否值得人类采取行动"这类主观判据，因此该领域的基准要么正在从零建立，要么仍在争论指标本身是否有效——本章的 `evaluation/` 因此把自己定位为**可复现的内部判准**，而非对外可比的能力排名。

**事实边界声明**：本节外部资料访问日期为 2026-10-20。Defects4J 各版本缺陷数与项目数在不同来源与不同版本中口径不一（395/357/488/597/854 等），正文按来源分别标注、不合并为单一数字，此差异本身即正文论点的一部分。SWE-bench Verified 相关数字以 OpenAI 系统卡与论文/综述为据，其中"OpenAI 因测试缺陷停用该基准、约 60% 样本存在测试缺陷"的说法来自百科词条转述，**未获一手来源确认，正文不采信该具体比例**。Turing Code Review Bench 的成功率与 Bug Catching Rate 数值、GitHub ReviewBench 的规模均为机构公开发布口径，未独立复现。本节所有外部数字仅用于机制对照，不用于推导 wallet-review-lab 的实验结论。

## 9.9.7 练习与小结

**小结**：评测层回答"修对了没有"，由三件东西定义——Oracle（判准）、指标（计数口径）、样本（基准版本）。本章采用双层 Oracle（程序化测试判结果、根因记录判理由）、根因级去重后的 Precision/Recall，以及只覆盖关键根因的零缺陷门禁；并保留两条边界：回放不测模型能力，基准分数必须绑定版本与评分器。落到一句：**能复现的分数才是证据，能去重的命中才是召回。**

**练习**：① 给 `evaluation/` 增加一条去重规则：若两个 Finding 的根因类别不同但指向同一 `acceptable_fix`，是否合并？给出你的判据并说明对 Precision 的影响；② 为 PR-08（提示注入，AGENTSEC-001）设计 Oracle——这类缺陷的 `acceptable_fix` 如何定义？程序化测试能否判定？③ 用本节表 9-12 的判据检查：如果你要把本章指标与 SWE-bench Verified 分数并列展示，必须先声明哪些口径差异？
