# 9.9 评测与行业基准：让发现问题可被判定

假设系统生成了十条评论，开发者采纳了两条。它表现好不好？还不知道另外八条是否重复、错误或只是未被采纳，也不知道重要问题有没有漏掉。评价评审系统，需要先确定正在数什么，以及这个数字准备支持哪一种选择。

本节从一条问题是否被正确识别讲起，再介绍计数、样本和实验。阅读时可以暂时放下“哪个模型第一”的想法，先问：如果明天换一套配置，我需要看到哪些证据，才愿意让它进入团队工作流？

## 9.9.1 业务正确与评审正确分别判断

ORD-09 实际退了 6400 分，这是业务执行的失败；模型说“因为 double 精度损失”，则是错误的根因解释。不能因为它提到退款错误，就自动计作发现了预设问题。

业务测试检查输入到行为，根因 Oracle 检查意见是否命中参照问题。订单 Oracle 包含根因 ID、文件、允许行区间、严重性与可接受修复方向。评分器在每案内匹配，再汇总统计，不把不同案例的相同类型压成一个样本。

Oracle 也会遗漏。模型提出一个新问题时，应先验证、补充标注或保留争议，不能仅因未出现在预设答案中便认定为误报。当前自动评分器不会完成这一步人工分诊。

### 先确定评价对象

评审可以沿三个层次评价。意见层检查问题是否真实、位置是否可行动、证据是否支持解释；流程层检查哪些任务完成、失败有没有被隐藏、裁决是否符合策略；使用层检查开发者花多少时间确认和处理。这些层次有关联，但不能用其中一个数字替代全部。

例如路径策略把退款变更交给人工，说明流程门禁起效；它没有说明模型发现了快照错误。模型命中根因，说明意见层取得一个有效结果；若同根因反复发十条评论，使用层仍可能变差。评测应保存这些差异，而不是在最后压成一个没有含义的总分。

还需要决定计数单位。本章以案例中的独立根因作缺陷单位，用角色输出作重复负担的观察单位，用一次运行作失败与成本单位。相同记录可以服务不同问题，但分母需要对应，不能为了更好看的数值临时切换。

## 9.9.2 用一个小例子手算指标

教学假设：三个案例共标注四个独立根因，模型报告三个。其中两条命中根因，另一条确认是误报；还有两个标注根因没有被发现。于是 TP=2、FP=1、FN=2。

```text
Precision = TP / (TP + FP) = 2 / 3 ≈ 66.7%
Recall    = TP / (TP + FN) = 2 / 4 = 50.0%
```

这不是本项目模型实测。它演示为什么“报告了三条”没有明确价值含义，以及去重为何必须先于缺陷计数。同一根因被两个角色重复报告，应合并为一次命中，同时另报重复负担。

如果没有预测，Precision 分母为零，应记录 N/A；若有标注缺陷但没有预测，Recall 为零。零缺陷案例没有可计算的缺陷召回，应报告无缺陷样本中的误报和错误阻断。高风险被策略升级人工，并不意味着算法错误报告了业务缺陷。

当前只有 ORD-01 一个零缺陷样本，其结果只能用于流程检查，无法稳定估计一般误报率。要研究误报，应加入无缺陷重构、合法边界修订和普通注释等更丰富的保留样本。

### 查准与查全各自带来什么代价

Precision 常译为查准率，回答“已经报告的问题中，有多少经确认成立”；Recall 常译为查全率，回答“应该发现的标注问题中，发现了多少”。增加模糊告警，可能多覆盖一些真问题，也可能让人花更多时间排除误报。减少评论则可能让报告更干净，同时漏掉重要风险。

这两项指标不能独自决定策略。对于历史资金变更，团队可能更愿意保留待查风险，但仍要把假设与已确认缺陷分开；对于日常低风险文档，频繁错误阻断可能使工具难以使用。需要先说明任务要求，再比较相同要求下的不同配置。

重复项也要单独处理。若 correctness 与 test 同时找到 ORD-09，正确结果是一个根因被发现、两份角色输出、一个合并后的报告项。把两条评论计作两个 TP，会让多角色在没有多发现问题的情况下获得分数优势。

## 9.9.3 当前评分器实际检查哪些字段

评分器 match_roots 要求根因 ID、文件、允许起始行范围、严重性及证据非空相符。证据引用另由门禁校验。它不自动判断建议修复是否等价、自然语言因果是否完整、任意跨文件根因是否相同。

**表 9-13 自动匹配与人工分诊的边界**

| 意见情形 | 当前自动评分 | 还需检查什么 |
| --- | --- | --- |
| 根因、位置、严重性及证据都相符 | 可记 TP | 语义解释与修复建议质量 |
| 原因相同但模型自造了另一个根因 ID | 可能记 FP 并留下 FN | 人工等价映射与标注一致性 |
| 行号来自正确主线，而非错误提交 | 位置不匹配 | 固定待审版本，重新定位 |
| 找到 Oracle 外的新问题 | 无法自动接受 | 复现、分诊并修订标注 |
| 引用其他运行或修复日志 | 证据门禁拒绝 | 重新取证，不能计能力命中 |

录制夹具的根因 ID 由作者预先对齐，所以能验证评分逻辑；真实模型不会天然知道这套内部 ID。正式评测要说明规范化规则，盲评时不可把根因答案给模型只为方便精确匹配。

### 答案怎样保持可讨论

Oracle 可以理解为评测作者事先记录的一份参照：这个案例植入了什么问题，允许在哪里定位，哪些修复方向可接受。它使自动比较成为可能，也引入标注质量的问题。若只按内部 ID 精确匹配，一个解释正确但使用另一名称的模型，可能被程序判错。

因此真实评测需要保存“自动匹配结果”和“人工复核结果”之间的差异。复核者确认新的等价表达后，应更新一致的映射规则，并对比较组统一应用，避免只替某个配置放宽标准。发现新缺陷时，也应先复现再补标注，而不是为了维持原表格便把它归为误报。

这项工作看起来没有调用模型醒目，却直接决定分数代表什么。没有明确的根因边界，模型可能通过重复报告获益；没有一致的复核规则，人工也可能在知道配置名称后不自觉地改变要求。

## 9.9.4 两条实验轨道，避免看过答案再宣称发现

源码发现轨道提供业务规则、待审 Diff 和选定源码，让模型自行提出问题。证据解释轨道额外提供相同工具结果，检查能否准确说明和治理已观察到的失败。看过 expected 6600、actual 6400 后输出少退，不等于独立发现。

固定错误补丁与工具输入可以让各配置公平比较，但也限制泛化结论。开发集可用于调整提示与规范化规则；保留集应改变商品组合、数量、更新时间或载荷表达，测试规则是否能迁移。同根因的十个金额变体不能当作十种独立缺陷类别。

Oracle、fixed.patch 和人工标准答案只在报告生成后读取。已有目录同时保存它们，控制器必须显式选择材料；“模型只读目录”并不等于“没有泄漏答案”。

### 为什么要把“发现”与“解释”分开

给读者一个错误 Diff，让他自行寻找风险，与先告诉他“这里少退 200 分”再请他解释原因，考查的是两种能力。前者需要提出问题，后者已经得到失败线索。两种任务都重要，但结果应按各自输入解释。

这一区分也帮助设计公平比较。所有配置获得同一份失败日志时，可以研究它们是否正确连接规则与调用；只给规则和源码时，才观察是否独立提出时间边界问题。如果一组看过修复日志，另一组没有，比较出来的差异会混入答案信息量。

同样，提示词反复在十二案例上调整后，再用同样十二案报告表现，主要说明对开发材料的适应。可以保留一些修改条件但不提前调试的样本，观察方法是否迁移。例如改变数量和规则更新时间，或者给出一个仍然使用历史快照的合法重构。新的数字保持同一规则，却能挑战记住固定答案的做法。

## 9.9.5 怎样报告已有录制结果

从仓库根目录执行：

```bash
(
  cd wallet-review-lab
  uv run python -m evaluation.projects ../order-review-lab/evaluation/cases.yaml --mode multi_arbitrated
)
```

执行记录：报告标识 `kind=recorded-control-fixture`，十二案例中 ORD-01 无 Finding，其余各有一个去重根因，合计 TP=11、FP=0、FN=0。它说明加载、路由、校验、去重与评分在预设数据上保持一致。

single 的 general-review 预设为空，多角色输出则预设标注根因。这种差异由夹具设计产生；不得画成“单模型落后、多 Agent 完美召回”的能力图。即使真实模型获得相同计数，也需说明样本来源、规模和不确定性。

## 9.9.6 真实实验怎样逐步开展

先选择 ORD-01 与 ORD-09 试跑，固定模型、角色指令、输入哈希和输出格式，记录每次失败、拒答、用量与延迟。确认协议可执行后，再扩充样本和重复次数。拒答率和非法输出率应独立报告；不能从分母中静默删除困难运行。

规划中的两个模型、三配置、十二案例、三次重复，共 216 次案例运行，实际调用数还受角色和重试影响。这是可选研究规模，不是出版统一门槛。若只做小规模演示，应把主张限制在演示范围，不发布普遍优劣结论。

可比较的维度包括独立根因召回、无缺陷误报、重复评论、证据无效率、人工确认时间和费用。比较时报告分母及原始计数，小样本不只给一个精确到小数点后的百分比。重复运行只能衡量该样本上的稳定性，不能代替业务场景多样性。

### 一次小实验怎样写得有信息量

可以先固定一个模型配置，给 ORD-01 与 ORD-09 做小规模试跑。每次保存输入、输出、是否完成、是否正确、用量与时间。若接口连续出错，先解决可执行性；若输出格式正常却原因错误，再调整材料和任务。试跑的目的，是建立能够解释失败的实验流程。

随后比较单角色与多角色时，要尽量保持规则、待审版本、证据和判定方式一致。角色不同本来就可能改变总调用量，这项成本应如实记录。重试也进入原始记录：一次成功是否经历过两次失败，关系到可靠性和费用，不能只保留最后的漂亮结果。

在样本较少时，直接写“12 次中完成 10 次，其中 8 次根因正确”常比分别给出多个精确百分比更易理解。这里的数字只是报告写法示意，不是本项目实测。读者应该能从原始计数重新算出指标，并看清未完成任务去了哪里。

## 9.9.7 与公开基准的联系

SWE-bench 以真实仓库任务和执行测试评估修复，Verified 提供人工筛选子集。[R9] 它提醒我们重视环境、任务定义和判定器；本章评审任务却不等同于生成可通过测试的补丁。评论是否正确、定位是否有效和人是否愿意采取行动，都需要额外判断。

不宜把不同版本、不同子集、不同工具权限的分数直接排在一起。正文引用基准时固定版本与任务类型，将规模和榜单留给可更新的来源，而不是并列多个无法消解的数字。

练习：设计一个无缺陷样本和一个同根因保留变体，写出自动评分可能误判之处。参考要点是保留真实因果、定义允许位置及人工等价映射，并区分能力失败、证据无效与基础设施失败。
