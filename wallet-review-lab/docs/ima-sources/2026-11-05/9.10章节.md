# 9.10 成本与路由：让证据流水线付得起钱

前九节回答的是"判得准不准、证据全不全"，本节回答最后一个工程问题：**这套流水线付不付得起**。在证据闭环的框架里，成本不是挂在流水线外面的商业问题，而是流水线自身的一个可观测维度——每一次模型调用都是一次决策，都应当记账、可回放、可审计。本节先说明 Agent 成本的形状为什么不同于"多调用几次聊天"，再给出记账、路由、降级三层手段，最后与工业界的路由与成本治理实践对照。贯穿全节的纪律是：**不写脱离模型版本与价格日期的美元数字**——本节出现的每个单价都绑定版本与采集日期，发布前须重新核对。

## 9.10.1 成本的形状：Agent 不是"调用次数多一点"的聊天

先把最反直觉的事实摆出来：一个 Agent 任务的成本，不是"单个聊天成本 × 调用次数"，而是被循环结构放大的另一笔账。单次聊天是一次提示、一次补全；Agent 循环则要读上下文、调模型、调工具、再读工具结果、再调模型，反复直到终止条件满足，而每一轮都会**重新发送累积的历史**。所以 Agent 的成本不是有用工作的总和，而是"有用工作 × 轮数 + 轮间反复重读的开销"。

两个已公开的测量把这个放大系数定量化。Anthropic 工程团队在自研多 Agent 系统上报告：单个 Agent 的 token 消耗约为普通聊天的 **4 倍**，多 Agent 系统约为 **15 倍**，且 token 用量单独解释了约 **80%** 的 Agent 设计间性能方差（经二手转述，原始出处为 Anthropic Engineering 2025 的 multi-agent research system 博文）。独立研究（arXiv 2604.22750，转述）则指出同一任务上的 Agent 运行 token 消耗可相差至 **30 倍**，一次完整 Agent 运行的消耗量级为普通代码对话的 **1000 倍**，而模型对自己成本的预测与实际成本相关性仅 **0.39 或更低**——模型无法预言自己会花多少钱。另一篇 ICLR 2026 论文（"How Do Coding Agents Spend Your Money?"，转述）同样报告运行间方差可达 10 倍、任务描述与真实消耗的相关性低于 0.15（不同转述对研究归属与具体数字存在出入，本节按转述标注）。

对本章评审系统，这个形状意味着两件事。第一，**输入 token 是账单的主体**：五个角色各自携带角色提示词与共享上下文，每轮工具循环都重发一遍，缓存前的原始用量远大于"有用输出"。第二，**运行间方差极大**：同一次评审可能因为多一轮重试而多花数倍 token。结论不是"别用 Agent"，而是：**先测量，再优化**——在拿到按调用记账的观测数据之前，任何成本决策都是猜。

## 9.10.2 三要素：输入、输出、缓存

任何提供商的账单都由三个计价项构成，其行为完全不同。

**输入（input）token 是 Agent 成本的主体**，因为循环重发上下文。**输出（output）token 单价通常为输入的 3～6 倍**，但因为输出量远小于输入，多数 Agent 负载下输出不是账单大头。**缓存（prompt caching，提示缓存）**是厂商对"重复输入前缀"的折扣机制：请求若与前序请求共享相同的前缀（系统提示、工具定义、参考文档），命中的部分按标准输入价的 0.1 倍甚至更低计费；机制上提供商按前导 token 的哈希做**精确前缀匹配**，缓存命中要求前缀逐字一致，因此"静态内容放前面"是唯一可依赖的工程规则。

缓存有三个必须理解的代价结构。其一，**写入有成本**：Anthropic 对 5 分钟 TTL 的缓存写入按标准输入的 1.25 倍计费、1 小时 TTL 按 2 倍计费，官方文档说明 5 分钟缓存一次命中即可回本、1 小时缓存需两次命中。其二，**命中率决定收益**：批量场景下请求并发乱序，缓存命中是"尽力而为"，命中率低时写入成本会吃掉折扣收益。其三，**折扣系数因模型而异**：Anthropic 多数模型命中按 0.1 倍、Opus 5.5/Sonnet 5.5 按 0.05 倍、Fable 5.1 按 0.025 倍；OpenAI 的 GPT-6.1 Sol 命中按 0.05 倍；Google Gemini 4 Argon 为 0.05 倍。对评审系统，角色提示词、仓库上下文、PR diff 都是天然的可缓存前缀——把静态部分稳定地放在提示词头部，是成本杠杆最大的一笔。

还有两个改变账单的"隐藏乘法器"。**长上下文阈值**：OpenAI 多个模型在输入超过 272,000 token 时对整个请求按更高费率计费（如 GPT-6.1 Sol 从 $2/$10 升到 $4/$15），Google Gemini 3.1 Pro Preview 在 200,000 prompt token 之上翻倍，Anthropic Claude Haiku 5.5 在超过 100,000 token 时**整个请求**按 5 倍费率计费且阈值计入缓存读写；这意味着"只多了一点"也可能让整笔请求涨价。**批量（batch）折扣**：三大家厂商对异步批处理都给约 50% 折扣，但有限制——OpenAI 完成窗口 24 小时、单批最多 50,000 个请求与 200 MB 输入文件，Anthropic 批次 24 小时未完成即过期、结果保留 29 天。批量适合评测、回填、批量分类，**不适合交互式代码评审**——人还在等结论。

## 9.10.3 记账：把成本接进证据链

成本优化的前提是记账，而记账在本章不是财务需求而是**证据需求**：路由选择了哪个模型、消耗了多少 token、花了多少钱——这些都是流水线的决策事实，应当与 Finding 一起可回放、可审计。记账的三条纪律：

1. **按调用记录**。每条模型调用记 `model`（含版本）、`input_tokens`、`cached_tokens`、`output_tokens`、估算成本与 `priced_at`（价格生效日期）。价格来自**版本化的单价文件**，与代码一同入证据包；价格变动只改文件不改代码，账目按 `priced_at` 回算。

2. **成本进裁决记录**。9.8 的仲裁记录与 9.6 的证据包追加 `cost` 字段：一次评审"花了多少钱、得出什么结论"是一条完整证据，成本异常本身也是可疑信号（例如某角色突然多花 5 倍 token，可能意味着循环失控）。

3. **按单位经济汇报**。原始账单会被流量波动淹没，真正可比的指标是 `cost per PR`、`cost per accepted finding`（每个被采纳 Finding 的成本）与 `cost per zero-defect pass`（每次通过零缺陷门禁的成本）。若 `cost per accepted finding` 上升，可能是 Precision 恶化（垃圾 Finding 变多），也可能是路由失控——这两种原因需要的处置完全不同。

教学简化示例（未声称可直接运行，仅演示记账形态）：

```python
# review_system/cost_ledger.py（教学简化示例）
# 单价必须绑定模型版本与生效日期；以下价格采集于 2026-10-19
PRICES = {
    ("anthropic", "claude-sonnet-5.5", "2026-10"): {"input": 2.00, "cached": 0.10, "output": 10.00},
    ("anthropic", "claude-haiku-5.5", "2026-10"): {"input": 0.10, "cached": 0.01, "output": 0.50},
}

def record_call(model_key, input_tokens, cached_tokens, output_tokens, priced_at):
    p = PRICES[model_key]
    cost = ((input_tokens - cached_tokens) / 1e6 * p["input"]
            + cached_tokens / 1e6 * p["cached"]
            + output_tokens / 1e6 * p["output"])
    return {"model": model_key, "input_tokens": input_tokens,
            "cached_tokens": cached_tokens, "output_tokens": output_tokens,
            "cost_usd": round(cost, 6), "priced_at": priced_at}
```

记账本身不省一分钱，但它让 9.10.4 与 9.10.5 的优化有据可依——这正是"可回放"在成本维度上的含义。

## 9.10.4 路由：让贵模型只干贵活

记账回答"钱花在哪"，路由回答"钱该不该花在这"。工业界有两类机制，决策时机相反：**路由器（router）在调用前决策**——看一眼请求就预测难度并直接派发给合适的模型，只调用一次，代价是误判时悄无声息地拿到差答案；**级联（cascade）在调用后决策**——先让便宜模型试，用评分器检查答案质量，不够好才升级到强模型，代价是难任务要付两次钱与额外延迟。

公开数字提供了量级感（均以论文自评基准为口径，属"上限"而非承诺）：LMSYS 的开源框架 RouteLLM 报告在 MT-Bench 上成本降幅超 85%、MMLU 上 45%、GSM8K 上 35%，同时保留 GPT-4 质量的 95%；FrugalGPT 报告级联可在大幅降本的同时匹配最佳单模型，降幅"最高 98%"、因任务而异约 50%～98%。两个数字合起来读，结论是：**流量越"偏科"（简单请求占多数），路由越赚钱**；任务越难且越均匀，省得越少。反例同样存在：OpenAI 曾在 GPT-5 上内置实时路由，因体验回退而向免费与 Pro 用户回滚（媒体报道转述）——路由不可见、不可控，就是降级。

评审系统的路由应分三层设计：

1. **规则优先**。不需要模型的判断先用确定性工具做掉：lint、格式、类型检查（`uv run ruff check .`、`uv run mypy ...`）不进 LLM，直接产出 Finding 或排除项。这一层的"省"是 100%，且零幻觉风险。

2. **角色路由**。9.5 的最小角色集中，各角色的难度天然分层：impact 评估、triage 扫描用便宜模型（如 Haiku 5.5 档）；correctness 深查、根因判定与 9.8 的仲裁用强模型（如 Sonnet 5.5 档）。角色路由的粒度是**调用**而非 PR：同一 PR 内，扫描调用走便宜档、深查调用走贵档。

3. **难度路由**。对超大型 diff、涉及资金不变量的高影响文件，强制升级到强模型；这一层对应 9.5 的权限矩阵思想——路由权限同样"只追加、不收缩"，高危路径不允许便宜模型兜底。

关键工程纪律：**路由决策本身必须进审计**。每条调用记录 `route_reason`（为什么选这个模型）与 `model_choice`，随成本台账入证据包。这样"降级到便宜模型导致漏报"就能被事后追责定位——路由是证据闭环的一部分，不是不可见的外部优化。这也与 9.8 的人工裁决哲学一致：系统做出的每个自动决策都要留痕。

## 9.10.5 预算、降级与反模式

路由之后还有最后一道防线：**预算与熔断**。Agent 成本方差大（9.10.1），所以"无限重试"是最贵的默认值。工业实践给出的护栏清单：

- **重试上限与循环检测**。信号：每请求平均 token 显著高于设计值、成本增速快于用户量。处置：限制重试次数、检测自我循环并中断。评审系统的对应物是编排器的重试上限与超时（9.6.4 已有），现在给它加一个**每 PR 的 token 硬上限**——超出即降级为"仅产出确定性检查结果 + 人工复核"。

- **长上下文阈值监测**。跨过 200K/272K 阈值会让**整个请求**费率翻倍，账单上"每 token 单价高于预期"就是这个信号；处置是阈值检测、换分块策略或换模型。

- **僵尸功能与废弃实验**。用量已跌但仍在跑的功能、遗留的 API key 与资源，都在持续烧钱。

- **负单位经济**。单次交互亏钱、随用量放大；处置是功能定价、门禁或重新设计。

降级路径也分层：交互式评审优先**模型降级**（强模型→中档→入门档，保留规则层），非交互负载（批量回放、评测回填）走 **batch 折扣**；**语义缓存**（对相似问题直接复用旧答案）谨慎使用——它可能把"看起来相似"的问题答成过期答案，必须用评测持续看守。降级决策同样记录 `route_reason`，且降级永远不得触碰高危路径（9.10.4 第三层）。

**三条判断**。第一，**路由与级联的价值取决于流量分布与判据质量**：流量不偏科、或判不出好坏，路由省不到钱、级联只加延迟；评审系统先把规则层做满，再上模型路由，顺序不可颠倒。第二，**成本治理的有效单位是"功能级账目 + 单位经济"**，不是账号总账单：总账单无法定位到"某角色的循环失控"，`cost per accepted finding` 才能。第三，**价格是时间的函数**：表 9-13 中 GPT-5.6 Sol 促销价"至少持续到 2026-11-21"、Gemini 4 Argon 2026-12-01 涨价、Gemini 3.8 Flash 2027-01-01 涨价——任何跨期预算都必须按涨价后的价格建模，这正是本章"单价绑定版本与日期"纪律的工业界根据。

## 9.10.8 练习与小结

**小结**：成本是流水线的可观测维度而非外部约束。Agent 成本被循环结构放大且方差极大，必须先记账再优化；优化手段按顺序是——缓存（静态前缀置前、追踪命中率）、路由（规则优先、角色路由、难度路由，决策留痕）、预算与降级（重试上限、阈值监测、模型降级、批量卸载）。所有数字绑定模型版本与价格日期。落到一句：**贵模型只干贵活，便宜模型干大多数活，而每一笔账都要能回放。**

**练习**：① 给 PR-05（幂等重试，IDEMPOTENCY-001）设计成本台账：重试机制在什么条件下会让 token 成本翻倍？记账字段需要增加什么才能定位"重试风暴"？② 用表 9-13 的定价重算 9.10.6 的示例：若 correctness 深查的缓存命中率从 83% 掉到 50%，单次调用成本变多少？这个差异说明缓存命中率为什么必须纳入评测报告？③ 对照 9.6 的证据包：成本台账与 Finding 的不可变性要求有何冲突？你如何在"冻结证据"与"成本随价格日期回算"之间取舍？
