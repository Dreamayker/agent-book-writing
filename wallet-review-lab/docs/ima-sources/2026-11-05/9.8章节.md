# 9.8 仲裁与人工治理：把意见变成裁决

收集到意见以后，评审还没有结束。开发者需要知道现在能继续什么、还缺什么、由谁补齐。如果报告只列出一组 confidence，使用者还得自己猜测处理顺序；如果系统直接把所有问题转换为拒绝，又会把建议、缺陷和规则争议混在一起。

本节把判断落到下一步行动。可以先把裁决理解成一张带理由的处理单：当前掌握什么，哪些条件尚未满足，下一步交给谁。它既需要程序规则保证一致，也需要人在合适的位置作出业务决定。

## 9.8.1 先确认材料，再讨论意见

一条有说服力的解释，可能引用了错误版本；两条一致意见，也可能来自同一个夹具。仲裁开始前，先校验结构与证据关系。当前 ReviewPipeline 的次序是路由、角色执行、引用校验、可选去重、规则仲裁，不会用一轮投票替代证据检查。

可复核的结论还需区分“已经观察到的失败”和“仍待验证的风险”。前者应带输入与输出，后者应说明缺少什么。未验证假设可以要求补查，不应被写成已经确认的资金事故。

### 问题判断与处理决定怎样衔接

“存在少退”描述代码行为，“需要修改”描述处理要求，“必须人工核对”描述决策责任。它们可以同时成立。ORD-09 已有阻断 Finding，但仍进入人工，因为修复涉及历史依据及回归范围。报告不应因为只显示一个顶层动作，就丢掉其他层次的信息。

反过来，高风险路径进入人工，也不说明模型已经发现缺陷。即使一个角色返回空列表，团队仍可要求退款变更由责任人确认。这样设计的好处是把稳定的治理要求与不稳定的分析结果分开观察；代价是人工工作量不会因“没有 Finding”自动归零。

因此，一份报告至少要让使用者看见两件事：哪些意见需要处理，流程为什么停在当前状态。没有补证据清单的 escalate，很容易只增加等待；没有人工条件的 approve，也容易被误读为对整个系统作了保证。

## 9.8.2 重复、冲突与不同问题

以下为教学记录，用于说明处理方法：

**表 9-11 三类意见关系与处理方式**

| 输入意见 | 关系 | 处理 |
| --- | --- | --- |
| 两角色都指向同一实时 quote、同一错误运行 | 重复根因 | 合并来源与证据，不增加缺陷计数 |
| 一方主张复用，另一方以规则变化证明少退 | 设计偏好与业务失败冲突 | 保留理由，失败不能被维护偏好抵消 |
| 一条所有权缺失，一条快照绕过 | 独立根因 | 分别保留，分别验证 |
| 两角色都称少退，却引用修复日志 | 共同证据错误 | 先退回证据门禁，不计为共识 |

当前去重函数处理第一类，不理解第二类的自然语言争论。它选择主体意见并合并引用，不能保证保存全部相反理由。需要完整争议记录时，调用方应保留原始角色输出，再交人工复核；本章没有实现模型裁判或辩论协议。

## 9.8.3 当前规则怎样决定报告动作

规则函数的核心优先级可简化为：

```python
if high_risk or any(f.needs_human for f in findings):
    return "escalate"
if any(f.blocking for f in findings):
    return "request_changes"
if findings:
    return "comment"
return "approve"
```

高风险优先进入人工，意味着 ORD-09 即使有阻断意见，报告动作也为 escalate，而不是 request_changes。报告仍保留 blocking=true 的 Finding，不能把升级误解成缺陷被忽略。

**表 9-12 裁决值与执行权限**

| 报告值 | 含义 | 不自动发生的动作 |
| --- | --- | --- |
| escalate | 高风险或需人工判断 | 不代表人工已批准 |
| request_changes | 普通风险中存在阻断意见 | 不直接写修复代码 |
| comment | 有非阻断意见 | 不表示风险已消除 |
| approve | 未触发当前阻断及升级条件 | 不直接合并 GitHub PR |

工具授权、发布审批和 PR 报告是不同协议。即使另有允许执行工具的权限，也不能推断获得业务放行权。

### 先后顺序为什么会改变结果

假设先判断 blocking，就会把 ORD-09 归为 request_changes；先判断高风险，则归为 escalate。代码可能只差两行顺序，含义却不同。当前策略选择先保留人工责任，再在报告里列出必须修复的问题。阅读裁决代码时，要像阅读计价顺序一样，确认规则先后反映了哪一种治理选择。

approve 也应完整阅读为“在当前材料、规则和检查范围内，没有触发已定义的阻断或升级条件”。它不是对未知缺陷的证明。若检查没有完成，调用应失败或进入另行设计的未完成状态，不能借空 Finding 得到这个结果。

接入实际开发流程时，还要说明谁读取报告、哪个条件阻止合并、谁能覆盖并记录理由。本项目提供报告协议，落地仓库治理需要继续绑定真实权限和分支规则。这样才能让一个输出字符串产生可预期的组织行为。

## 9.8.4 人工复核应看到什么

ORD-09 的审阅包应先显示 200 分差额、受影响条件、错误调用和修复后的证据，再显示模型解释。这样审阅者可以先做判断，降低被流畅结论带着走的风险。

下面是一份空白复核模板；它是教学表单，不是已经发生的批准，也不等同于现有 human-verdict.yaml 的完整机器协议。

```yaml
case_id: ORD-09
reviewed_revision: 待填写
status: pending-human-review
reviewer: 待真实审阅者填写
decision: 待填写
rule_basis: order-rules-v1
checked_evidence: []
unresolved_questions: []
rationale: 待填写
follow_up_owner: 待填写
```

审阅者至少回答：历史分摊是否为业务认可依据；缺快照订单如何处理；规则、商品和数量变化是否有回归；修复是否影响拆单及幂等；仍有哪些风险未覆盖。没有历史依据的订单返回 MANUAL_REVIEW，不让模型猜一个金额。

### 让人工复核成为一次有内容的工作

人工不是程序无法回答时填入的万能角色。业务审阅者确认历史退款规则是否有效、缺失记录如何处置；技术审阅者确认调用、状态和回归是否恢复约束。团队可能由同一人承担两项任务，但复核记录仍应说明判断依据，便于后来接手的人理解。

以 ORD-09 为例，读到“恢复快照即可”还应继续检查：历史快照是否都能解码，子单是否读取同一根记录，部分数量如何选择，重试是否重放原结果。这些问题会把一句修复方向展开成可核对的范围。若某项没有验证，就明确留下待办与负责人。

材料呈现也会影响复核质量。先展示金额、条件和原始观察，再展示模型解释，可以让人先形成自己的判断。一次点击确认很快，但如果确认者必须重新搜索所有证据，系统只是把工作转移到了按钮后面。好的复核包应降低查找负担，同时保留检查原文的入口。

## 9.8.5 有期限的判断与责任归属

依赖适用性尤其需要期限。9.6.5 的 Spring 记录只针对当前版本及生产源码，原因是特定视图功能未使用；未来增加视图后，旧理由不再成立。绑定版本、源码哈希和复查日期，才能让“暂不受影响”成为可撤销的判断。

人工流程也需要触发条件。路径所有者变化、规则修订、最后一次推送改变代码，都可能使旧批准失效。CODEOWNERS 与分支保护可协助落实路径责任，[R1] 但仍应验证实际仓库配置，不能只创建一个文件便宣称治理完成。

本项目的 human-verdict.yaml 仍为 pending-human-review。机器测试通过可以形成待复核建议，真实批准由实际审阅者完成。无法投入复核资源时，应缩小范围或推迟高风险发布，不能让更多模型意见代替责任。

### 为什么旧批准可能需要重新核对

一项批准依赖当时审阅的对象。最后一次推送改了退款调用，之前针对旧提交的判断就不能自动覆盖；新增视图功能，则可能改变依赖公告的适用条件。记录版本和触发条件，是让判断能够被后来的变化重新检查。

复查也需要明确对象。如果只是评审文档的错别字变化，通常无需重新执行所有业务实验；如果规则、执行源码或证据绑定变化，就应沿相关关系重新确认。这个范围需要团队规定，不能让模型自行决定哪些修改足够“小”而跳过责任条件。

治理的目标是让决定有连续性：今天的审阅者知道依据是什么，明天的维护者知道什么时候该重看。代码和规则会继续变化，保存一次通过结果只是起点。

## 9.8.6 练习：为证据不足选择动作

给出两种情况：退款规则本身尚未确认；规则明确但 Docker 不可用。分别说明下一步交给谁、补什么材料，以及为何不能批准。

参考要点：前者需要业务澄清，重跑测试无法解决口径；后者需要恢复执行环境，不能把基础设施失败写成业务缺陷。两者都应保留未完成或升级状态，并记录责任与下一步，而非只输出一句“需要人工”。
