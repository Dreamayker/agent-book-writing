# 9.8 仲裁与人工治理：把意见变成裁决

## 9.8.1 仲裁先检查证据，再处理意见

ORD-09 中，一个角色可能认为“重用 quote 减少了重复代码”，另一个角色指出规则变更后少退 200 分。前者是设计偏好，后者有输入、失败输出和数据库行为；不能通过多数票平均掉确定性失败。

当前仲裁由 Python 规则执行，不是模型 B。它在 Finding 校验与可选去重之后，按风险和阻断条件返回 PR 评审动作。confidence 用来辅助排序，不替代证据充分性，也不授予执行权限。

## 9.8.2 根因去重与冲突保留

订单 Finding 使用 root_cause_id 描述同一案例的根因，symbol 和 invariant 进一步界定范围。具有相同显式根因的跨文件报告可合并来源与证据；不同根因保持独立。旧钱包夹具没有根因字段时，以规则 ID、文件和起始行作为兼容键。

重复根因与意见冲突不同。对少退金额、券资格或旧订单兼容的争议，应保留各自规则版本和计算过程。不能在合并时丢弃不利证据，再输出一个看似一致的结果。

## 9.8.3 PR 裁决动作

| 动作 | 当前含义 |
| --- | --- |
| escalate | 高风险或 needs_human，要求人工处理 |
| request_changes | 普通风险中存在有证据的阻断意见 |
| comment | 有非阻断意见 |
| approve | 当前策略下没有阻断或升级条件 |

三种 Agent 模式都遵守这套优先级。approve 是报告结果，不会自动合并 GitHub PR。工具调用的允许、拒绝和一次性授权属于另一类权限决策；本项目未实现自动财务审批，不应把两类动作混用。

## 9.8.4 人工应裁决什么

退款金额、历史缺快照、授权边界和规则变更需要业务与技术共同负责。对于无快照旧订单，系统返回 MANUAL_REVIEW；没有历史依据时，不能让模型猜测一个金额。对于 ORD-09，人工应检查规则口径、原始分摊、失败与修复版本，以及其他商品和数量的回归范围。

案例 human-verdict.yaml 使用 pending-human-review，没有伪造批准人、签名或“已获财务批准”。完成机器验收可以建议复核，但不能把作者尚未执行的批准写成已发生事件。

## 9.8.5 防止人工成为橡皮图章

复核界面或文档应先呈现业务差额、受影响订单范围、失败用例和未验证项，再提供模型解释。单纯展示一段流畅的结论会提高自动化偏误。需记录审阅者、版本、决定、理由、证据和后续责任；具体个人信息只在真实审查时填写。

对于高风险变更，增加模型数量不能取消人工责任。若复核时间预算不足，应缩小变更范围或延后发布，而不是把“模型都同意”当作放行依据。

## 9.8.6 练习

分别为 ORD-09 的快照修复、ORD-04 的单位状态修复、无快照旧订单写出人工检查项。指出哪些结论可由测试支持，哪些仍需业务负责人确认，并说明条件不足时如何保持升级状态。

**三条判断。** 第一，工业界与学术界对"机器裁决"的共识是：**聚合协议必须可配置、可记录、可怀疑**——多数票不是终点，稳定性检测、加权与反共识审计都在同一个方向上前进；本章的确定性选择是教学约束，不是工业结论。第二，"人在回路"在立法与工程两个方向上都已被降级为"需要被设计的控制"：EU AI 法案把自动化偏差写进第 14 条，工程实践则要求度量审批人本身——这印证了本章的立场：**人工治理的成败不在"有没有人"，而在"人有没有在看、看没看到证据"**。第三，所有权机制（CODEOWNERS）证明"具名+路径"是问责链的成熟工业形态，本章的 `named approver` 与路径路由与之同构；区别在于本章把同一机制延伸到 AI Agent 产出的裁决记录，并让记录参与证据包哈希链。
