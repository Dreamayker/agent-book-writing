# 案例说明

## 一、案例定位

本书设计一个贯穿全书的端到端案例： 

***在一个遗留电商订单系统中，新增“优惠券叠加规则”功能，并修复一个线上计价 Bug。*** 

这个案例不是为了展示 AI Agent 能“一键完成复杂需求”，恰恰相反，它的价值在于展示： 

- 什么任务可以交给 AI； 

- 什么任务不能直接交给 AI； 

- 为什么需求澄清比代码生成更重要； 

- 为什么上下文工程决定 AI 是否理解项目； 

- 为什么技术方案、ADR、接口设计不能省； 

- 为什么测试生成要关注有效性而不是覆盖率； 

- 为什么修 Bug 必须先有失败用例； 

- 为什么输出契约、Harness、Loop、门禁和人工终审是 AI Agent 落地的底线； 

- 如何把一次试点沉淀为团队级 Skill、规则库、评测集和工作流。

这个案例会贯穿全书 14 章，读者可以跟随它完成一条真实的软件研发链路： 

***需求提出 → 准备度判断 → 任务拆解 → 技术方案 → 上下文准备 → 模型选择 → Harness 配置 → 输出契约 → 编码 → 测试 → 评审 → Bug 修复 → DevOps 门禁 → 失败复盘 → ROI 评估 → 团队资产沉淀。*** 

# 二、业务背景

## 2.1 公司背景

案例中的公司是一家中型电商平台，暂称为： 

***星河优选*** 

星河优选主营： 

- 日用百货； 

- 食品生鲜； 

- 美妆个护； 

- 服饰鞋包； 

- 会员精选商品。

平台已有多年历史，业务从早期的单体电商系统逐步演进为多模块系统。目前订单、商品、促销、库存、支付、退款、会员等模块既有新服务，也有遗留代码。 

公司近两年增长放缓，业务团队希望通过更加灵活的促销策略提升转化率和复购率。 

## 2.2 现有促销体系

目前平台支持的优惠方式主要有： 

### 1. 满减券

例如： 

- 满 100 减 10； 

- 满 300 减 50； 

- 满 500 减 100。

满减券通常作用于整笔订单。 

### 2. 品类券

例如： 

- 生鲜品类满 99 减 15； 

- 美妆品类满 199 减 30； 

- 服饰品类 9 折券。

品类券只作用于特定商品品类。 

### 3. 新人券

例如： 

- 新用户首单立减 20； 

- 新用户首单满 80 减 15。

新人券只对满足新人身份的用户生效。 

### 4. 会员券

例如： 

- 黄金会员满 200 减 20； 

- 铂金会员 95 折券。

会员券基于用户等级生效。 

### 5. 平台活动价

例如： 

- 秒杀价； 

- 限时折扣； 

- 大促活动价。

这类优惠通常在商品价格阶段已经计算完成，订单模块只读取活动后的商品价格。 

## 2.3 当前系统的限制

当前订单系统对优惠的处理比较保守： 

***一笔订单通常只允许使用一张主要优惠券。*** 

也就是说，当前系统大致支持： 

- 满减券； 

- 品类券； 

- 新人券； 

- 会员券；

但默认不允许它们复杂叠加。 

过去这样做的原因是： 

1. 早期业务规则简单； 

2. 计价逻辑集中在订单模块； 

3. 促销系统能力不足； 

4. 退款、拆单、售后场景复杂； 

5. 财务对优惠分摊有严格要求； 

6. 老代码缺少足够测试。

因此，系统一直通过较简单的“优惠优先级”规则来避免复杂叠加。 

# 三、这次新增需求

## 3.1 业务目标

业务团队提出一个新需求： 

*在即将到来的周年庆活动中，支持部分优惠券叠加使用，提高用户下单转化率。* 

具体目标： 

- 提升活动页转化率； 

- 提升客单价； 

- 提升新人首单转化； 

- 提升会员复购； 

- 支持更灵活的运营配置； 

- 减少客服对“为什么券不能一起用”的投诉。

## 3.2 核心需求描述

业务方最初给出的需求非常简单： 

***支持优惠券叠加使用。*** 

但这句话非常模糊。 

它没有说明： 

- 哪些券可以叠加； 

- 哪些券不能叠加； 

- 叠加顺序是什么； 

- 折扣券和满减券如何同时计算； 

- 优惠金额如何分摊到商品； 

- 退款时如何回滚优惠； 

- 拆单时如何分配优惠； 

- 一张券是否可与活动价叠加； 

- 用户手动选券和系统自动选券如何处理； 

- 异常情况下如何提示用户。

如果直接让 AI Agent 根据这句话改代码，很容易生成看似合理但业务错误的实现。 

## 3.3 经过澄清后的业务规则

经过产品、研发、测试和财务讨论后，需求被澄清为以下规则。 

### 规则一：本期只支持三类券叠加

本次周年庆只支持： 

1. **满减券** 

2. **品类券** 

3. **新人券**

暂不支持： 

- 会员券叠加； 

- 商家券叠加； 

- 支付券叠加； 

- 跨店铺复杂叠加。

### 规则二：优惠计算顺序固定

优惠计算顺序为： 

***活动价 → 品类券 → 满减券 → 新人券*** 

解释： 

1. 商品先使用活动价； 

2. 品类券只作用于对应品类商品； 

3. 满减券基于品类券之后的订单金额判断门槛； 

4. 新人券最后作用于整单。

### 规则三：新人券与部分满减券互斥

不是所有新人券都能和满减券叠加。 

业务配置中需要增加字段： 

stackable_with_order_coupon 

含义： 

- true：新人券可以和满减券叠加； 

- false：新人券不能和满减券叠加。

如果新人券不允许和满减券叠加，则系统需要自动选择优惠金额更大的方案。 

### 规则四：品类券只作用于可用商品

品类券只对指定品类商品生效。 

例如： 

- 生鲜券只能作用于生鲜商品； 

- 美妆券只能作用于美妆商品。

如果订单中部分商品不属于该品类，则这些商品不能参与品类券门槛，也不能分摊品类券优惠。 

### 规则五：满减券基于品类券后的金额判断门槛

例如： 

订单原始金额为 320 元。 

其中： 

- 生鲜商品 120 元； 

- 美妆商品 200 元； 

- 使用生鲜品类券满 100 减 20。

品类券后订单金额变为 300 元。 

如果用户还有一张满 300 减 50 的满减券，则可以继续使用。 

如果品类券后订单金额变为 299 元，则不能使用满 300 减 50 的满减券。 

### 规则六：优惠金额不能超过应付金额

无论叠加多少优惠，总优惠金额不得超过订单应付金额。 

最低支付金额不能小于 0。 

如果计算后出现负数，应截断为 0，并记录异常监控。 

### 规则七：优惠金额必须能分摊到商品行

为了支持退款和财务对账，每一类优惠金额都必须分摊到商品行。 

商品行需要记录： 

- 品类券分摊金额； 

- 满减券分摊金额； 

- 新人券分摊金额； 

- 总优惠分摊金额； 

- 分摊后的实付金额。

### 规则八：退款时按原始分摊金额回滚

退款时不能重新计算优惠规则，而是必须基于下单时已经保存的优惠分摊结果进行回滚。 

原因是： 

- 下单后的优惠配置可能已经变化； 

- 用户身份可能变化； 

- 活动可能结束； 

- 商品价格可能变化； 

- 重新计算会导致退款金额不一致。

### 规则九：拆单时保持优惠分摊一致

如果订单拆成多个子单，每个子单必须携带对应商品行上的优惠分摊结果。 

不能在拆单后重新计算优惠。 

### 规则十：所有金额按分为单位计算

系统内部所有金额均按“分”为单位，避免浮点误差。 

例如： 

- 100 元表示为 10000； 

- 19.9 元表示为 1990。

# 五、当前线上 Bug 背景

除了新增优惠券叠加需求，本案例还包含一个线上 Bug。 

## 5.1 Bug 描述

线上出现部分用户投诉： 

*用户购买多件商品后使用优惠券，下单金额正确，但部分退款时，退款金额比预期少。* 

客服反馈： 

- 用户下单时使用了优惠券； 

- 后续只退了其中一件商品； 

- 系统计算退款金额时重新分摊优惠； 

- 导致该商品可退金额被低估； 

- 用户认为平台少退钱。

## 5.2 Bug 触发场景

一个典型场景如下： 

订单包含三件商品： 

| **商品** | **品类** | **活动价** | **数量** | **小计** |
| --- | --- | --- | --- | --- |
| A | 生鲜 | 120 元 | 1 | 120 元 |
| B | 美妆 | 200 元 | 1 | 200 元 |
| C | 家居 | 80 元 | 1 | 80 元 |

订单原始活动价合计： 

400 元 

用户使用： 

- 满 300 减 50 的满减券； 

- 新人券减 20。

订单应付： 

400 - 50 - 20 = 330 元 

假设下单时系统按比例将 70 元优惠分摊到三件商品。 

但退款时，系统没有读取下单时保存的分摊结果，而是根据当前订单剩余商品重新计算优惠。 

如果用户只退商品 C，退款逻辑可能重新判断： 

- 剩余商品金额变化； 

- 满减门槛变化； 

- 新人券状态变化； 

- 当前优惠配置变化；

最终导致商品 C 的可退金额和下单时分摊结果不一致。 

## 5.3 Bug 根因初步怀疑

初步怀疑有几个可能原因： 

1. 退款逻辑重新计算优惠，而不是使用下单时的分摊快照； 

2. 部分商品行没有记录完整优惠分摊明细； 

3. 历史订单和新订单的分摊字段不一致； 

4. 拆单后子单没有保留原始分摊信息； 

5. 金额按比例分摊时四舍五入残差处理不一致； 

6. 促销配置变更后，退款阶段读取到了新的规则。

## 5.4 为什么这个 Bug 适合用于 AI Agent 案例

因为它非常适合展示： 

- 不能让 AI 直接改代码； 

- 必须先分析日志和调用链； 

- 必须让 AI 生成多个根因假设； 

- 必须构造失败用例； 

- 必须基于失败用例做最小修复； 

- 必须补回归测试； 

- 必须引入输出契约； 

- 必须通过门禁； 

- 必须将失败案例进入评测集。

这个 Bug 会在第10章作为 AI 缺陷修复工作流的主要示例。

# 七、为什么选择这个案例

## 7.1 它足够真实

真实软件研发不是让 AI 写一个简单 Todo App，而是面对： 

- 模糊需求； 

- 遗留代码； 

- 业务规则； 

- 历史债务； 

- 测试缺口； 

- 线上 Bug； 

- 风险审批； 

- DevOps 流程； 

- 组织协作。

这个案例覆盖了真实企业落地的大部分问题。 

## 7.2 它足够高风险

优惠券和订单计价涉及金额，一旦出错会影响： 

- 用户权益； 

- 客服投诉； 

- 财务对账； 

- 活动成本； 

- 平台信誉； 

- 法务风险。

因此它天然适合展示： 

*AI Agent 不能无约束自动修改核心逻辑。* 

## 7.3 它足够可拆解

虽然案例复杂，但可以拆成多个小任务： 

- 澄清优惠叠加规则； 

- 分析现有计价逻辑； 

- 生成技术方案； 

- 设计 DiscountAllocation 模型； 

- 补充测试； 

- 修改局部计算器； 

- 修复退款逻辑； 

- 生成 PR 摘要； 

- 做 AI 评审； 

- 接入 CI 门禁； 

- 复盘和沉淀规则。

这非常适合展示小步提交和 Skill 化复用。 

## 7.4 它能贯穿所有章节

这个案例可以自然连接： 

- 需求澄清； 

- 上下文工程； 

- 模型选择；
