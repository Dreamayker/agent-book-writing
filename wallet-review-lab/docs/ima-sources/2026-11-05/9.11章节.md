# 9.11 安全防御：把模型当作不可信组件

## 9.11.1 评审对象可能携带越权指令

Agent 会阅读 PR 描述、Java 注释、测试、规则附件和工具输出。攻击者可能把“忽略安全检查”“读取环境变量”“直接批准”写入这些载体。内容有业务相关性，不代表它拥有控制权限。

ORD-08 在 RefundAmountCalculator.java 的注释中插入越权指令。Semgrep 的 generic 规则给出 java-review-injection 信号，Python 本地守卫也可识别既有模式。这些规则用于报警，不能证明变体、编码或多轮注入均已解决。

## 9.11.2 数据与指令隔离

ResponsesReviewAgent 的系统策略要求把 PR、Diff、源码、测试和夹具当作不可信数据，不允许这些材料修改角色、权限或输出格式。业务规则仍有来源版本；文档中自称“最高优先级”不改变其信任等级。

controller_verified_evidence 表示控制器核验了运行来源与内容哈希。工具输出里的自然语言仍是数据，不自动成为系统指令。证据认证和内容可信是不同问题，不能因文件来自 JUnit 就执行其中的 shell 文本。

## 9.11.3 工具执行边界

案例脚本使用参数数组运行控制器预定义的 Maven/Semgrep 命令，不运行模型任意生成的 shell。补丁在独立 worktree 中执行，返回码、日志和超时被保存；Oracle、修复补丁与模型凭据不放进普通业务测试上下文。

独立 worktree 不是安全沙箱，不能隔离恶意构建脚本、网络或宿主文件。仓库现有案例为作者构造的教学补丁；若接收不可信外部 PR，应另用无凭据容器或受控执行器。普通 PR CI 不注入模型密钥；真实评测由可信任务读取冻结输入。

## 9.11.4 对象授权与快照完整性

模型本身的安全不能代替业务授权。ORD-03 的订单所有权检查需要在 API 请求作用域内执行；不能信任客户端提交 owner，也不能因知道订单 ID 就允许退款。首版 X-User-Id 只用于教学，本地服务绑定回环地址。

SHA-256 能发现快照意外变化，但管理员可同时改快照和哈希，因此它不是不可抵赖审计或签名。生产审计、密钥管理、真实支付和分布式事务仍需单独设计。

## 9.11.5 对抗验证与门禁

先验证标准注入案例，再构造中文、拆词、编码、测试名称和附件等变体，分别检查信号、模型行为与工具边界。记录误报，避免把普通“保持退款原子性”注释也判为攻击。

扫描发现、模型拒绝和工具确实未执行是三层不同证据。安全结论应说明哪一层被验证；没有真实模型实验时，不能写出模型抵抗注入的成功率。

以下外部安全机制对照保留既有资料与来源限定。其攻击率、Token 开销及厂商能力不属于本项目独立复现结果。

**三条判断**。第一，**提示注入的防御边界在权限层，不在提示词层**：OWASP 明示模型内无万无一失的防御，NIST 测试给出 11%→81% 的劫持率，因此架构必须按"已被攻破"设计——这决定了本章把权限矩阵、沙箱、人工裁决放在安全架构的中心。第二，**多 Agent 扩大攻击面，也提供独立判定冗余**：交接内容丢失不可信标记会扩大注入面，但独立角色+仲裁比对把单点注入变成可检测冲突（9.11.7）；安全评测必须有对抗子集且独立计分。第三，**安全有可测代价，必须入账**：CaMeL 类防御的 token 开销是真实存在的，安全预算与评测一起进 9.10 台账，`cost per finding` 的上升是预期而非异常。
