# 9.4 单 Agent 评审：从任务分类到任务契约

9.3 建立了实验场：不变量给出裁决标准，Oracle 给出正确答案，基线给出可回放起点。本节把第一个 Agent 放进去。单 Agent 是本章的原子单位——一个受限组件，有明确的任务、明确的输入、明确的证据义务。要理解 9.5 的多 Agent 协同，必须先理解单个 Agent 的边界：它被允许看什么、被允许做什么、必须留下什么、绝对不能做什么。

## 9.4.1 四类任务：规范、缺陷、安全、影响

"代码评审"不是一种同质的工作。按**证据形态与决策风险**，可以划分为四类任务，每类的确定性工具、模型职责与证据义务都不同：

**表 9-4 四类评审任务的分工**

| **任务** | **确定性工具** | **模型的职责** | **必须产出的证据** | **代表案例** |
| --- | --- | --- | --- | --- |
| 规范 | Ruff、格式化器、依赖检查 | 把输出映射回文件与行号，解释为什么需要修改 | 命中的规则、位置 | PR-01 |
| 缺陷 | 不变量测试、屏障并发测试 | 沿状态读取→校验→写入→异常路径推理 | 位置＋失败模式＋可复现测试 | PR-04 |
| 安全 | 授权回归测试、Semgrep 等扫描器 | 对照需求与身份上下文判断适用性 | 需求上下文＋失败授权测试 | PR-03、PR-08 |
| 影响 | 调用图、静态索引 | 列出受影响的 API、调用方与状态 | 受影响调用方清单与证据 | PR-02 |

**规范任务**应当先清理低级噪音。Ruff、格式化器和依赖检查本身就能完成确定性检查；模型的工作是把扫描器输出映射回文件和行号，告诉作者"为什么需要修改"，并避免一个常见的失真：**把风格问题伪装成安全阻断**。PR-01 只补充了转账响应字段的文档说明，风险路由把它判为低风险；此时若仍启动全部专业 Agent，得到的只是更高成本和更多无关评论（见 9.3.7）。

**缺陷任务**要从控制流走到不变量。缺陷评审要追踪状态读取、校验、写入和异常路径。以主线案例 PR-04 为例，关键不是"代码少了一把锁"这句表面描述，而是完整的失败模式：两个请求读取同一余额，两个请求都通过校验，随后各自写入，最终余额可能为负，且总余额与转账记录不再符合业务定义。一个合格 Finding 必须把**源码位置、失败模式和修复边界**写在一起——三者的关系见 9.4.4 的 Schema。

**安全任务**验证的是身份、对象和输入的边界。PR-03 删除了服务层对 `source.owner_id == current_user.id` 的检查：客户端提交的钱包 ID 只能用于定位资源，不能作为授权证据。安全 Agent 必须同时看到需求、身份上下文和失败授权测试，才能把"缺少一个条件判断"提升为对象级授权绕过（AUTHZ-001）——只看到 Diff 的模型会把它当成普通缺陷甚至漏掉。PR-08 则把源码注释当作不可信输入来验证（完整展开见 9.11）。

**影响任务**回答"这个改动还影响谁"。模型适合做跨文件阅读与模式归纳：概括 PR 意图，列出受影响的 API 和状态，关联测试失败与源码位置，对照需求寻找边界条件。但必须声明边界：**本地影响分析只有单仓库证据；跨仓库的调用影响索引是生产环境待验证事项**，模型不得用"显然没有其他调用方"代替搜索证据。

## 9.4.2 任务契约六要素与 correctness Agent 示例

"AI 擅长什么"是一句无法验收的宣传语。工程上更有用的写法是**任务契约**（task contract）：把一次评审任务的所有边界写成可检查的条款。契约至少包含六要素：

- **输入**（input）：模型被允许看到的材料；

- **允许使用的工具**（tools）：可调用的确定性能力，其余一律禁止；

- **必须产出的证据**（output evidence）：输出结构的最小义务；

- **不能做的动作**（forbidden）：权限边界，触碰即失败；

- **失败时的升级路径**（escalation）：何时必须把问题交给人或高风险通道；

- **验收断言**（acceptance）：判定一次输出是否合格的机器可检查条件。

```mermaid
<code>flowchart LR
  A["输入<br/>Diff / 调用图 / 不变量 / 测试结果"] --> B["允许的工具<br/>read_file / run_pytest / git_diff"]
  B --> C["必须产出的证据<br/>结构化 Finding / no_finding"]
  C --> D{"命中金额或授权标签?"}
  D -- 否 --> E["验收断言<br/>Schema 合法 / 证据可解析"]
  D -- 是 --> F["升级路径<br/>needs_human = true"]
  E --> G["输出交付"]
  F --> G
  H["不能做的动作<br/>修改工作树 / 冒充已验证 / 自动批准"] -.-> G
</code>
```

**图 9-3 任务契约六要素。** 输入、工具、证据、禁止动作、升级路径、验收断言构成一次评审任务的全部边界；任何要素缺失，输出都无法被机器验收。

以正确性 Agent（correctness Agent）为例，契约可以写成：

```yaml
# 教学模板：任务契约（字段以本书实验项目为准）
agent: correctness
input:
  - diff: standardized_diff        # 标准化 Diff
  - call_graph: affected_functions # 相关函数的调用图
  - invariants: requirement_invariants  # 需求中的不变量
  - test_results: pytest_json      # 测试结果
tools:
  allow: [read_file, run_pytest, git_diff]
  deny: [write_file, approve_pr]
output:
  - findings: 结构化 Finding 列表，或显式 no_finding
  - every_finding_must: [file_location, evidence_ref]
forbidden:
  - 修改工作树
  - 把“测试尚未执行”写成“已验证”
  - 以置信度替代证据
escalation:
  - if invariant_tag in [money, authorization]: needs_human = true
acceptance:
  - schema_valid
  - evidence_resolvable
  - no_finding 仅当无阻断证据
```

任务契约把模型从"自由发挥的审阅者"变成流程中的一个**受限组件**，价值有三。第一，它让评审可替换：同一契约可以由不同模型、规则引擎甚至人工执行，比较的是结果而不是文案风格。第二，它让"越权"可检测：模型声称"确认生产数据库当前没有其他客户端"时，契约可以指出该任务缺少可观察输入，任何确定语气都是越权推断；"批准这笔转账"是责任动作，不能因为模型置信度高就自动执行。第三，它揭示不适合模型的任务——这正是 9.1 讨论的四种不确定性的工程化落点。

## 9.4.3 摘要与影响分析的纪律

模型擅长把多种证据组织成一条人类易读的因果链，但这恰恰是最容易失控的环节。**摘要纪律**有三条：

第一，**摘要只能陈述证据支持的内容**。概括 PR 意图、列出受影响的 API 与状态、关联测试失败与源码位置——这些都以输入材料为上限。第二，**失败状态不能被解释为成功**。工具执行失败、测试未运行、模型超时、证据缺失，都必须如实标注为"未取得证据"，不得在摘要中写成"未发现问题"。第三，**解释与事实分层书写**。"测试通过"是事实，"代码设计正确"是解释，摘要必须让读者一眼分清哪句是哪句（9.1.2 的 PR-02 反例正是混淆两者的代价）。

影响分析（impact analysis）的纪律与之对应：列出受影响的调用方时必须区分"已由调用图与索引证实"与"推测可能受影响"；涉及跨仓库调用时，明确标注为生产环境待验证，而不是让模型用流畅的推理掩盖索引缺失。

## 9.4.4 从 Diff 到结构化 Finding

单 Agent 评审的终点是一份**结构化 Finding**。它把一次评审压缩为机器可读、可仲裁、可评测的最小单位。一个合格 Finding 至少包含四要素：**位置**（文件与行号）、**失败模式与根因**、**可复核证据**、**修复边界**。

以主线案例 PR-04 为例，统一 Finding Schema（unified Finding Schema）的教学模板如下：

```json
{
  "id": "CONCURRENCY-001",
  "pr": "PR-04",
  "category": "correctness",
  "severity": "must_fix",
  "root_cause": "余额检查位于原子边界之外，检查与更新非原子",
  "location": { "file": "app/repository.py", "lines": [42, 55] },
  "failure_mode": "两个并发请求同时通过余额校验并各自写入，余额可能为负，总余额与转账记录不符",
  "evidence": [
    { "type": "test", "ref": "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend" },
    { "type": "test_log", "ref": "book-assets/PR-04-concurrent-double-spend/evidence/pytest-fail.log" }
  ],
  "fix_direction": "将读取、校验、更新置于同一原子边界（锁 / 事务 / CAS）",
  "confidence": 0.92,
  "needs_human": true
}
```

Schema 有两条底线。**第一，每条 Finding 必须有可复核的证据引用**：`evidence` 必须指向真实存在的测试、日志或扫描结果，模型不得只凭阅读 Diff 就断言"必然出错"。**第二，阻断类（must_fix）Finding 必须同时携带文件位置与可复核证据**：二者缺一，该 Finding 不满足验收断言，应被降级为建议或丢弃。

还要明确 `confidence` 与 `needs_human` 的语义：**confidence 只用于排序候选，不能作为批准依据**（9.1.5 的原则在这里落到字段上）；`needs_human` 则由路由规则决定——命中金额或授权标签时契约强制置真，与模型的自信心无关。Finding 与 9.3.5 的 Oracle 逐字段对齐，是 9.9 评测 Precision/Recall 的基础：Oracle 说"根因是 CONCURRENCY-001"，Agent 说"根因是 CONCURRENCY-001"，这才构成一次命中。

## 9.4.5 与工业系统的对照：单 Agent 边界并非教学特例

wallet-review-lab 把评审拆成四类任务并施加契约，工业界系统用同样的思路限制单 Agent——只是包装不同。

**对照一：任务分类在工业界表现为角色分工。** CodeRabbit 的官方架构把评审拆成 Review、Verification、Chat、Pre-Merge Checks、Finishing Touches 五类专业 Agent 并行工作，并把评审过程显式编排为"分析—验证—决策"（Analyze–Verify–Decide）三阶段，验证阶段专门负责收集支撑结论的证据。这与四类任务同构：**不同任务配不同职责、不同工具、不同证据义务**，而不是一个万能提示词扫全量 Diff。

**对照二：契约的输入与工具边界就是 Custom Checks 的受控环境。** CodeRabbit 的自定义检查（Custom Checks）在安全的只读环境中运行，Agent 可用的输入与工具被明确列出：变更文件与代码片段、git 历史、PR 标题与关联 issue、ast-grep 与 ripgrep 等模式搜索、沙盒内的 shell 命令、公开文档查询与内部系统 MCP 工具。这与任务契约的"输入＋允许工具"完全对应。权限边界同样明确：CodeRabbit 定位为发布评论的评审者，**不自行合并或推送代码，团队仍决定合并前需要哪些检查与人工批准**——这与契约中"不能做的动作"一致：评审 Agent 永远不是门禁本身。

**对照三：单 Agent 的结构性局限是走向多 Agent 的理由。** CodeAgent 论文明确指出，传统的单输入输出生成模型难以模拟代码评审固有的协作性——多个评审者各有视角、互为补充；而 CodeRabbit 对"agentic review"的定义是研究代码库（收集仓库上下文、追踪依赖、使用分析工具），而不是把 Diff 塞进提示词。RADAR 同样只把 LLM 评审作为风险漏斗中的一环，其后还有确定性验证把关。**单 Agent 的价值在于受限，局限在于单一视角**：一个 Agent 只能沿一条证据路径推理，无法同时从正确性、测试、安全、影响四个方向逼近同一个 Diff——这正是下一节引入专业化多 Agent 的原因。

## 9.4.6 练习与小结

**9.4 练习**

1. 为你的团队评审流程写一份 correctness Agent 的任务契约（六要素齐全），并指出其中哪些条款机器可检查、哪些仍依赖人工；

2. 取一个真实 PR，把它的风险按规范/缺陷/安全/影响四类归类，说明每类各需要什么确定性证据；

3. 检查你最近收到的 AI 评审意见：哪些是"证据支持的事实"，哪些是"流畅的推测"，哪些是"尚未执行却写成已验证"；

4. 讨论：如果 Finding 没有文件位置或证据引用，它是否还配得上 must_fix 的严重级别？

**9.4 小结**：单 Agent 评审的工程本质不是"让模型读代码"，而是**把评审任务契约化**——四类任务划分职责，六要素契约划定边界，摘要纪律约束表达，统一 Schema 规范产出。工业界系统的角色分工与受控环境印证了同样的原则。但单 Agent 只有一个视角，它的结论再规范也只是"一条证据路径上的解释"。9.5 将回答：多个专业化 Agent 如何分工，又如何共享证据而不共享结论。

**来源说明**：CodeRabbit 官方架构（五类专业 Agent）、Custom Checks 的 Analyze–Verify–Decide 流程与受控工具集、agentic review 定位与人工批准边界；CodeAgent 论文关于单模型局限的论述；RADAR 漏斗中的 LLM 评审与确定性验证。第三方介绍仅用于补充"只评论不合并"的行为边界，主引用为官方文档。
