# 9.4 单 Agent 评审：从任务分类到任务契约

## 9.4.1 评审任务要有可验证的输出

本章的单 Agent 接口是 `ReviewAgent.review(ReviewContext) → list[Finding]`。任务不是“帮我看看代码”，而是结合规则、待审变更和工具证据指出哪个不变量在什么输入下被破坏。ORD-09 的 correctness 任务聚焦退款来源；ORD-06 聚焦计算阶段与门槛，不能只做代码风格检查。

ReviewContext 包含 case_id、patch_path、changed_paths、semantic_labels、project_root、code_revision、requirements 和 evidence_manifest。模型适配器发送未受信任的需求与 Diff，以及控制器核验的证据；这些数据不能修改角色、权限或系统指令。

## 9.4.2 统一 Finding v2

以下是 ORD-09 的录制控制夹具形态，数值用于验证流程，不代表实时模型判断：

```json
{
  "schema_version": 2,
  "finding_id": "REFUND-001",
  "root_cause_id": "ORD-09:REFUND-001",
  "invariant": "order-rules-v1",
  "source": "correctness",
  "category": "correctness",
  "severity": "must_fix",
  "confidence": 0.95,
  "file": "order-infra/src/main/java/com/xinghe/order/infra/OrderApplicationService.java",
  "line_start": 104,
  "claim": "退款重新使用实时券规则",
  "evidence": [
    {
      "type": "test",
      "ref": "book-assets/ORD-09/tool-evidence/raw/buggy.txt"
    }
  ],
  "suggested_fix": "Restore the frozen business contract and rerun the regression",
  "blocking": true,
  "needs_human": true
}
```

准确行号以案例中的实际 Finding 和 Oracle 为准。严重性只使用 `must_fix / concern / nitpick`；证据字段为 `evidence: [{type, ref}]`，不用旧稿中的 evidence_ref。根因、不变量与位置各有独立字段，不能用一个“高风险”值同时表示业务损失、扫描严重性和路由等级。

## 9.4.3 Schema 校验与证据校验是两道门

Pydantic 验证字段、枚举、置信区间和行号；阻断意见必须是 must_fix 且至少带一项证据。但非空 ref 仍可能不存在，因而订单回放额外检查证据 manifest：Case ID、代码版本、run_id 和文件 SHA-256 必须一致，Finding 的工具引用必须属于这次运行。

这能发现错版本、丢文件与篡改输出，不能凭空证明工具覆盖完整。源码定位由 Oracle 的文件和行区间辅助评分；未实现跨版本符号解析，不能声称任意重构后仍可准确定位。

## 9.4.4 单 Agent 的实验边界

`RecordedAgent` 是确定性的夹具读取器，`ResponsesReviewAgent` 是实时 API 适配器。录制 general-review 列表故意为空，用来测试漏报是否被正确计为 FN；专业角色夹具包含预设根因。由此得到的模式差异来自夹具设计，不能写成“多 Agent 比单 Agent 更准确”。

实时适配器记录模型、响应 ID、延迟和原始 usage。API 请求成功不等于 Finding 合法；只有输出解析和 Schema 校验成功才标为 validated。调用失败和模型拒答需要保留原始状态，不能伪造为空 Finding 后自动批准。

## 9.4.5 练习

分别为 ORD-06 和 ORD-09 写一份最小上下文包，指出少给“满减门槛基数”或“快照不可变”规则会带来什么漏检。再修改一个证据文件，观察哈希校验如何拒绝复用旧 Finding。
