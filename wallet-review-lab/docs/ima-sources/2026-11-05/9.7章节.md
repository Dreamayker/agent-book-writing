# 9.7 六案例深度实战：把六个 Diff 依次送进证据流水线

9.6 交付的是流水线本身：统一的 Finding Schema、一次构造多方使用的证据包、风险路由矩阵、调度与追加写入纪律，以及回放与审计机制。但一条流水线是否成立，不取决于它的架构图有多完整，而取决于它能否处理真实的、彼此不同的缺陷。本节把 wallet-review-lab 的六个教学 PR 依次送进这条流水线，检验同一套机制在不同证据形态下的表现。

需要先把本节的定位说清楚：9.3 已经用一页纸介绍了六个案例，本节不是把那份简介再讲一遍，而是对每个案例执行同一套教学结构——**需求 → 不变量 → 错误补丁 → 失败机制 → 可复现测试 → 结构化 Finding → 多 Agent 协作 → 仲裁决策 → 修复方案 → 回归验证 → 生产待验证**。十一个环节不是装饰性的模板，它们回答了评审系统必须回答的十一个工程问题；读者读完后应当能拿着同一结构去解剖自己团队的缺陷。

本节的主线仍是 PR-04 并发双花：它拥有最完整的证据链，因此把多 Agent 协作与仲裁讲透。其余五个案例各自承担一个对照任务，回答"当证据不是并发失败测试时，这套流水线还成立吗"。

## 9.7.2 主线案例：PR-04 并发双花（CONCURRENCY-001）

**需求。** 用户 A 的钱包余额为 100.00 元，同一时刻发起两笔转账，各转出 80.00 元给 B 和 C。正确的业务结论是：两笔不可能都成功，因为它们的和超过了余额。注意需求的关键词是"同一时刻"——这决定了它是一个关于并发时序的需求，而不是一个关于算术的需求。

**核心不变量。** PR-04 触及两条：余额非负（任何钱包余额不得为负）与金额守恒（总金额不得因转账凭空变化）。第二条尤其重要：即使某次错误的实现碰巧使余额停在 0 而没有变负，只要转出的总额超过了原有余额，金额守恒就已经被破坏。两条不变量一起构成了这个案例的裁决标准。

**错误补丁。** 错误补丁把余额检查移到了 `app/repository.py` 的 `atomic` 锁边界之外：读取余额、校验是否够用，发生在加锁之前，而只有"写入"发生在锁内。

```python
# 教学简化示例：用于说明“检查与更新是否在同一原子边界内”，
# 不代表原项目逐行实现；函数名以 app/repository.py 实际代码为准。
class WalletRepository:
    def transfer(self, source, target, amount):
        balance = self._read_balance(source)          # 锁外读取
        if balance < amount:                          # 锁外校验
            raise InsufficientFunds()
        with self._atomic:                            # 只有写有锁
            self._write_balance(source, balance - amount)
            self._write_balance(target, self._read_balance(target) + amount)
            self._append_transfer_log(source, target, amount)
```

从单线程视角读这段代码，它完全正确：读到的余额是真实的，校验是充分的，写入是原子的。**这正是本案例的教学价值——缺陷不在任何一行语句里，而在两条语句的相对位置里。** 单线程测试无法暴露它，因为"同一时刻"在单线程里从未发生过。

**失败机制。** 屏障（barrier）让两个线程在同一时刻进入 `transfer` 之后，失败的因果链是这样的：两个线程各自读到 `balance = 100`；两个线程各自校验 `100 >= 80` 并都通过；两个线程先后进入锁内并写入。第二个写入者用的是它自己读到的 `100`，于是把余额写成 `20`；两次转账日志都已追加，于是总转出为 160，系统总金额比转账前少了 60。

这里必须强调一个常见的评审误区：只看 Diff 说"这里少了一把锁"是**表面描述**，不是 Finding。合格的 Finding 要把源码位置、失败模式和修复边界写在一起：位置是"检查与更新的相对位置"，失败模式是"两个请求读到同一余额并都通过校验"，修复边界是"检查与更新必须回到同一原子边界之内"。三者的关系见 9.6 的 Finding Schema。

**可复现测试。** 证明竞态存在的不是模型的解释，而是可重复的并发测试。它的关键不是"开两个线程"，而是用屏障把时序固定下来，让竞态从"偶发"变成"必现"。

```python
# 教学示例（完整可运行形态）：屏障固定并发时序。
# ⚠️ 示意实现：函数名、断言细节以 tests/test_transfer_invariants.py 为准。
import threading
from decimal import Decimal

def test_concurrent_transfers_cannot_double_spend(repo):
    alice = repo.create_wallet(owner="alice", amount=Decimal("100.00"))
    bob   = repo.create_wallet(owner="bob",   amount=Decimal("0.00"))
    carol = repo.create_wallet(owner="carol", amount=Decimal("0.00"))

    barrier = threading.Barrier(2)   # 让两个线程在同一时刻对齐后同时进入
    errors: list[Exception] = []

    def transfer(target):
        try:
            barrier.wait()           # 对齐点：越过此处后两线程同时推进
            repo.transfer(source=alice, target=target, amount=Decimal("80.00"))
        except Exception as exc:     # 业务上允许其中一笔因余额不足被拒绝
            errors.append(exc)

    t1 = threading.Thread(target=transfer, args=(bob,))
    t2 = threading.Thread(target=transfer, args=(carol,))
    t1.start(); t2.start(); t1.join(); t2.join()

    # 断言的是不变量，而不是“哪个线程成功”
    assert repo.balance(alice) >= Decimal("0.00"), "余额不得为负"
    assert repo.total_balance() == Decimal("100.00"), "金额必须守恒"
```

这段测试的教学要点有三处，缺一不可。第一，**断言的是不变量，不是具体结果**：无论最后成功的是哪一笔，余额非负与金额守恒都必须成立；把断言写成"B 收到 80 且 C 收到 0"会把测试绑死在调度顺序上，反而引入脆弱性。第二，**屏障把偶发变为必现**：没有 barrier，两个线程可能在时间上完全错开，甚至永远读不到同一余额，测试就会变成"有时红、有时绿"的不可靠信号。第三，**允许一笔被拒绝是业务预期**：`InsufficientFunds` 被收集而不是被断言为错误，因为"只有一笔成功"恰恰是正确行为。

在正确基线上（使用进程内 `RLock` 表达原子边界），这条测试通过；应用错误补丁后，它失败，且失败信息指向余额或总金额的断言。**失败输出是证据的一部分，不是噪音**——它应当被证据包原样留存，供回放与审计使用。

**结构化 Finding。** correctness Agent 与 testing Agent 从这个案例中各自产出一条 Finding，仲裁器把它们合并为一条根因。以下是合并后的表示（教学模板，字段语义见 9.6 的 Schema；实际实现见 `review_system/`）：

```json
{
  "finding_id": "CONCURRENCY-001",
  "pr": "PR-04",
  "invariant_violated": ["余额非负", "金额守恒"],
  "severity": "must_fix",
  "location": {"file": "app/repository.py", "symbol": "transfer"},
  "failure_mode": "余额检查与余额写入不在同一原子边界内，两个并发请求可读到同一余额并同时通过校验",
  "evidence_ref": [
    "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend"
  ],
  "reproducible": true,
  "acceptable_fix": ["restore_atomic_boundary"],
  "needs_human": true,
  "confidence": "（仅用于排序候选，不作为批准依据）"
}
```

其中三个字段值得单独说明。`evidence_ref` 指向的是**可执行的测试名**，任何人重跑它都能得到同一失败，这就是"可复核"的含义。`acceptable_fix` 记录的是需要恢复的性质（恢复原子边界），而不是某个实现细节——Oracle 不把 RLock 当作唯一答案。`needs_human` 为真，因为这是资金正确性相关的高风险结论：即便证据充分，合并决定仍由人做出。

**多 Agent 协作。** 这个案例最能说明 9.5 的"证据共享、结论隔离"为什么必要。correctness Agent 沿状态读写路径推理，指出"检查与更新不在同一原子边界"；testing Agent 不参与这段推理，它只做一件事——运行屏障测试并把失败结果写回证据库；impact Agent 从 Diff 出发列出受影响的调用方（哪些入口可能并发调用 `transfer`）；security Agent 在这个案例上给出 `no_finding` 或低优先级观察，因为并发双花是正确性问题而非授权问题。四个角色通过证据库共享 `evidence_ref`，但**彼此不转述结论**：testing 不会对 correctness 说"我同意你的判断"，它只提供失败测试；correctness 也不会引用 testing 的结论作为自己推理的前提，它引用的是那份测试作为位置证据。

这里有一个容易忽略的护栏。如果 correctness 先输出"缺少锁"，testing 被告知这个结论后才去写测试，那么测试就成了"为结论找证据"——这正是 9.5 反复警告的级联幻觉。正确的顺序是让两条证据路径彼此独立地抵达同一根因。

**仲裁决策。** 仲裁器收到的候选包括一条 correctness Finding（位置与失败模式）和一条 testing Finding（失败测试），它们指向同一根因。仲裁的动作是**按根因合并而不是按文本相似度合并**：两条 finding 的 `location` 相同、`invariant_violated` 相同、`evidence_ref` 互补，于是合并为 CONCURRENCY-001，保留全部来源引用。若另一个 Agent 给出"建议增加日志"，它不应被合并进来，因为它回答的不是同一问题。

**修复方案。** 修复的语义是恢复原子边界——让"读取、校验、写入"三者处在同一个临界区内。

```python
# 教学简化示例：恢复原子边界（进程内 RLock 版本）
def transfer(self, source, target, amount):
    with self._atomic:                                # 读取、校验、写入同处锁内
        balance = self._read_balance(source)
        if balance < amount:
            raise InsufficientFunds()
        self._write_balance(source, balance - amount)
        self._write_balance(target, self._read_balance(target) + amount)
        self._append_transfer_log(source, target, amount)
```

**这里的正确性只属于实验环境。** 进程内 `RLock` 表达的是"原子边界"这个概念，而不是生产方案。生产数据库处理同类问题时，可能需要行锁（`SELECT ... FOR UPDATE`）、可串行化隔离级别，或带版本号的 CAS 加失败重试；在分布式事务与崩溃恢复条件下，结论可能再次改变。书中的修复证明的是**实验不变量恢复**，不是可以直接复制到分布式资金系统的完整方案。

**回归验证。** 修复后重跑同一套测试：屏障测试通过，其余不变量测试通过，`uv run pytest` 全绿。回归的意义不在"变绿了"，而在"同一个曾经失败的输入现在通过了"——这是可回放性的直接体现。

**生产待验证。** 本案例留下四个明确的开口：（1）跨进程、跨节点的并发控制；（2）数据库层锁语义与隔离级别是否真的提供了同一保证；（3）崩溃恢复后幂等日志与余额的一致性；（4）连接池、重试与超时对并发窗口的影响。这些都不在实验场的证据范围内，必须标注为生产待验证，而不能因为"测试通过了"就默认成立。

## 9.7.3 对照案例一：PR-02 金额精度（MONEY-001）

**这个对照回答的问题是：当阻断性证据不是"失败的测试"时，流水线还成立吗？**

**需求与不变量。** 团队的货币策略要求金额使用十进制定点表示，禁止金额经过二进制浮点数往返；对应不变量是金额守恒。需求里没有一句"必须用 Decimal"，但策略给出了这条约束——这决定了本案例的证据形态是**规则命中**，而不是测试失败。

**错误补丁与失败机制。** 补丁把金额转换为浮点数再归一化后写回。失败机制不是"算错了"，而是**精度在往返过程中悄悄丢失**：某些金额在二进制浮点中无法精确表示，累加与舍入的误差可能在样例规模下不可见，却在特定数值与多次运算后暴露。因此"10.00、20.50 等常规样例全部通过"与"违反货币策略"可以同时为真。

**三类结论必须分开。** 这是 PR-02 最重要的教学点，也是 9.1 的伏笔在此收束：测试给出的结论是"已执行样例没有失败"；规则（Semgrep 之类的禁止模式匹配）给出的结论是"代码命中了团队禁止模式"；Agent 给出的结论是"这条规则为何适用于本段代码"。**任何一项都不能冒充另外两项。** 如果规则误配，Agent 应当指出适用性问题，而不是因为扫描器亮了红灯就编造事故后果——后者是把规则证据伪装成事实证据的典型失真。

**结构化 Finding（节选）。**

```json
{
  "finding_id": "MONEY-001",
  "pr": "PR-02",
  "invariant_violated": ["金额守恒（货币表示契约）"],
  "severity": "must_fix",
  "location": {"file": "app/…（金额归一化处）"},
  "evidence_ref": ["semgrep:float-money-roundtrip", "policies/currency-rules（策略条目）"],
  "reproducible": true,
  "acceptable_fix": ["use_decimal_or_minor_units"],
  "needs_human": true
}
```

注意 `evidence_ref` 指向的是规则 ID 与策略条目，而不是某个测试名。**同一套 Schema 容纳了不同形态的证据**，这正是 9.6 统一 Schema 的价值。

**多 Agent 协作与仲裁。** impact Agent 在这里第一次成为主角：它需要列出所有经过该金额归一化路径的 API 与调用方，判断影响范围。security Agent 不主导本案例。correctness Agent 解释精度问题。仲裁焦点是"测试全绿"与"规则命中"之间的表面对立——仲裁器不投票，它核对证据类型：测试没有覆盖策略，规则覆盖了策略，因此结论取规则证据。

**修复与回归。** 修复是改用十进制定点表示（`Decimal` 或最小货币单位整数）。回归证据包括两部分：原有样例测试仍然通过，且禁止模式检查不再命中。**只跑测试不跑规则，回归是不完整的**——因为它会漏掉"策略违规但样例通过"这一整类问题。

**生产待验证。** 金额表示涉及与上游/下游系统的契约，以及数据库字段类型（定点列、精度与标度）；跨系统传输时是否重新引入浮点往返，属于生产待验证事项。

## 9.7.4 对照案例二：PR-03 对象级授权（AUTHZ-001）

**这个对照回答的问题是：当"缺少一个条件判断"的后果只有在身份上下文里才成立时，模型会不会漏掉它？**

**需求与不变量。** "用户只能从自己拥有的钱包付款"是四项不变量中的第四条。它在代码里往往表现为一行朴素的条件判断，因此最容易被误判为普通逻辑缺陷。

**错误补丁与失败机制。** 补丁删除了服务层对 `source.owner_id == current_user.id` 的检查。失败机制的关键在于**客户端提交的钱包 ID 只能用于定位资源，不能作为授权证据**：调用方声称要与哪个钱包交互，与它是否有权与该钱包交互，是两个不同的问题。删除检查后，一个已登录用户可以操作任意钱包——**登录成功不等于拥有这个钱包**。

**可复现测试。** 授权回归测试构造"用户 A 尝试操作 B 的钱包"的场景，断言请求被拒绝。它与并发测试的形态不同：不需要屏障，因为它检验的是单次请求内的授权前提，而不是时序。

**结构化 Finding（节选）。**

```json
{
  "finding_id": "AUTHZ-001",
  "pr": "PR-03",
  "invariant_violated": ["用户只能操作自己拥有的钱包"],
  "severity": "must_fix",
  "location": {"file": "app/…（服务层授权检查处）"},
  "failure_mode": "钱包 ID 被当作授权依据；缺失所有权校验导致对象级授权绕过",
  "evidence_ref": ["tests/…::test_cannot_transfer_from_others_wallet"],
  "reproducible": true,
  "acceptable_fix": ["restore_ownership_check_before_balance_check"],
  "needs_human": true
}
```

**多 Agent 协作与仲裁。** 本案例最能说明 9.5 的"任务决定输入"原则。只看 Diff 的模型会把它当作"删除了一段代码"甚至直接漏掉；security Agent 之所以能把它从普通缺陷提升为对象级授权绕过，是因为它同时看到**需求（所有权要求）、身份上下文（当前主体是谁）与失败授权测试**。若缺少其中任何一项，结论的可信度都会下降。仲裁焦点是"缺少一个条件判断"与"对象级授权绕过"之间的定性差异——前者是代码描述，后者是安全结论；仲裁器要求后者必须绑定失败授权测试。

**图 9-8 主体—对象—动作授权关系（Mermaid 源码）。** 图注：钱包 ID 只负责定位对象，所有权关系负责授权；把定位当作授权，就是对象级授权绕过。

```mermaid
<code>flowchart LR
  S["主体 subject<br/>current_user"] --> A["动作 action<br/>transfer(from = wallet_id)"]
  A --> O["对象 object<br/>source wallet"]
  O -.->|授权前提| R1["所有权关系<br/>wallet.owner_id == current_user.id"]
  O -.->|仅用于定位| R2["钱包 ID（客户端提交，不可信）"]
  R1 --> D["允许"]
  R2 -.->|被误用为授权依据| X["越权：AUTHZ-001"]
</code>
```

**修复与回归。** 修复是恢复所有权校验，且必须发生在余额校验之前——顺序也属于修复语义的一部分。回归证据是失败授权测试转为通过，同时原有不变量测试保持通过。

**生产待验证。** 实验场只提供了一个最小授权模型；真实系统可能使用 RBAC/ABAC、资源级策略引擎或外部授权服务。对象级权限是否在服务端强制、越权是否被审计、跨服务调用时身份是否可信传递，都是生产待验证事项。

## 9.7.5 对照案例三：PR-05 幂等重试（IDEMPOTENCY-001）

**这个对照回答的问题是：当一个缺陷只在"重复请求"或"并发首次请求"下出现时，如何构造可复现证据？**

**需求与不变量。** "同一幂等键只产生一次资金变更"是第三条不变量。它服务的是网络现实：客户端在超时后重试是常态，服务端必须保证同一个逻辑请求不会导致两次扣款。

**错误补丁与失败机制。** 补丁移除了服务端的去重逻辑，或使其在并发首次请求下失效。失败机制有两种形态：其一是**重试导致重复扣款**——同一幂等键的第二次请求被当作新请求执行；其二是**并发首次请求绕过去重**——两个携带相同键的请求几乎同时到达，都在"检查是否已处理"时看到"未处理"，于是都执行了资金变更。**第二种形态再次把并发引入画面，但它的证据形态是幂等测试，而不是双花测试。**

**可复现测试。** 幂等测试需要覆盖三个场景：顺序重试（同一键连续两次）、并发首次（同一键两线程同时到达）、键参数冲突（同一键携带不同参数）。

```python
# 教学示例（形态示意）：幂等性的三个断言，具体实现以项目测试为准
def test_idempotent_retry_charges_once(repo):
    key = "IDEM-KEY-001"
    first  = repo.transfer(source=alice, target=bob, amount=Decimal("10.00"), key=key)
    second = repo.transfer(source=alice, target=bob, amount=Decimal("10.00"), key=key)
    assert second == first                       # 重复请求返回首次结果
    assert repo.balance(alice) == Decimal("90.00")  # 只扣一次
```

**结构化 Finding（节选）。**

```json
{
  "finding_id": "IDEMPOTENCY-001",
  "pr": "PR-05",
  "invariant_violated": ["同一幂等键只产生一次资金变更"],
  "severity": "must_fix",
  "location": {"file": "app/…（幂等登记与资金变更处）"},
  "failure_mode": "服务端未持久化幂等键，或并发首次请求未做原子登记",
  "evidence_ref": ["tests/…::test_idempotent_retry_charges_once"],
  "reproducible": true,
  "acceptable_fix": ["persist_idempotency_key_with_result"],
  "needs_human": true
}
```

**多 Agent 协作与仲裁。** correctness 负责解释"幂等是服务端状态协议，而不仅是客户端重试技巧"——把幂等误当作客户端责任，是这一整类缺陷的根源。testing 负责三重场景的测试证据。仲裁焦点是"客户端技巧 vs 服务端协议"：如果 Finding 只写"建议客户端加重试标记"，它回答的不是这条不变量，应当被降级或驳回。

**图 9-9 幂等状态机（Mermaid 源码）。** 图注：状态机把"是否已处理"变成服务端可持久化的状态；并发首次请求落在"执行中"这一态上，必须由唯一约束或原子登记决定谁执行。

```mermaid
<code>stateDiagram-v2
  [*] --> 未见键
  未见键 --> 执行中: 收到键 K 的首次请求
  执行中 --> 已完成: 资金变更成功 + 持久化结果
  执行中 --> 失败: 资金变更失败（不得记为成功）
  已完成 --> 已完成: 重复请求（返回首次结果，不再扣款）
  执行中 --> 执行中: 并发重复请求（等待或拒绝，禁止再次扣款）
</code>
```

**修复与回归。** 修复是服务端持久化幂等键及其结果，并对键建立唯一约束以保证并发首次请求只有一方能登记成功。回归证据是三类幂等测试全部通过。

**生产待验证。** 幂等键存储的持久性、跨服务/跨数据库的幂等、键的过期与回收策略、以及幂等记录与资金变更是否处于同一事务，都是实验场无法覆盖的生产待验证事项。

## 9.7.6 对照案例四：PR-07 依赖漏洞（DEPENDENCY-001）

**这个对照回答的问题是：当结论依赖一个会随时间变化的外部事实时，"可验证"意味着什么？**

**需求与性质。** 这一案例并不直接破坏四项业务不变量中的任何一条，它触及的是**依赖完整性（dependency integrity）**：第三方依赖不得引入已知可被利用的漏洞。把它放进同一章，是为了说明证据流水线必须能处理"事实来自系统之外"的情形。

**错误补丁与失败机制。** 补丁引入或保留了一个已知存在漏洞的依赖版本（体现在锁文件里）。失败机制的核心不是"有漏洞"本身，而是**可利用性取决于调用路径与配置**：同一个漏洞在有漏洞的版本里不一定真的能被触发，是否适用需要结合代码是否调用到受影响接口、配置是否开启相关特性来判断。这就是**适用性分析**——它既是这个案例的难点，也是规则与模型分工的落点。

**证据形态。** 这里的确定性证据是"锁文件中的具体版本 + 漏洞数据库的对应记录"。这与前三个案例有一个本质差异：**证据是一项会过期的事实**。今天查询显示"该版本无已知漏洞"，不代表将来不会有；反之，今天标记为漏洞的条目也可能被修订。因此 Finding 必须记录查询时间与来源，这也呼应了本章反复强调的事实纪律：外部能力、漏洞状态与价格必须有一手来源和访问日期。

**结构化 Finding（节选）。**

```json
{
  "finding_id": "DEPENDENCY-001",
  "pr": "PR-07",
  "invariant_violated": ["依赖完整性（不涉及四项业务不变量）"],
  "severity": "（取决于适用性：可利用时升级，不可达时降级）",
  "location": {"file": "lockfile（依赖版本）"},
  "failure_mode": "引入了存在已知漏洞的依赖版本，且调用路径可能触达受影响接口",
  "evidence_ref": ["lockfile:<pkg>==<version>", "外部漏洞数据条目（含访问日期）"],
  "reproducible": true,
  "acceptable_fix": ["upgrade_or_replace_dependency", "document_non_applicability_if_unreachable"],
  "needs_human": true
}
```

注意 `acceptable_fix` 里出现了第二种合法结局：如果适用性分析证明受影响接口不可达，那么"记录不可达结论"本身就是一个可接受的处置——**但必须留下证据与日期**，而不是一句"我觉得用不到"。

**多 Agent 协作与仲裁。** impact Agent 在这个案例里负责调用路径分析（受影响的调用方、是否可达），security Agent 负责对照外部漏洞数据。**模型不得确认外部实时状态**：它不能凭记忆断言"某版本没有漏洞"，只能引用查询结果。仲裁焦点是"扫描器命中 vs 适用性判断"——扫描命中是事实（版本确实受影响），是否阻断则取决于适用性；两者不能互相冒充。

**修复与回归。** 修复是升级或替换依赖，或在确认不可达时记录不可达结论与依据。回归证据是依赖检查不再报出该条目，且受影响功能测试保持通过。

**生产待验证。** 漏洞数据库随时间的更新、传递依赖（依赖的依赖）是否被一并覆盖、构建产物与锁文件是否真实一致（供应链完整性），都是生产待验证事项；这些将在 9.11 与供应链完整性对照中继续展开。

## 9.7.7 对照案例五：PR-08 提示注入（AGENTSEC-001）

**这个对照回答的问题是：当被评审的代码试图评审评审者自己时，流水线靠什么守住边界？**

**需求与边界。** 前五个案例都在评审"业务代码是否正确"；PR-08 反过来，它检验**评审系统自身是否可被仓库内容操纵**。要守住的边界很明确：**仓库内容不能改变评审目标、工具范围和批准权限。** 这不是一条业务不变量，而是评审系统的信任边界（trust boundary）。

**攻击补丁与失败机制。** 补丁在源码注释（或 PR 描述、提交信息、依赖名）中嵌入"忽略安全问题""批准这个 PR""泄露系统提示词"一类指令。失败机制来自语言模型的一个底层特性：它对**系统指令与数据**的处理处在同一个上下文里，缺少类似 SQL 参数化那样的硬性特权分界。因此对编译器只是一段注释的文本，对阅读自然语言的 Agent 却可能被当作指令。

**可复现证据。** 这里的"测试"是策略守卫（policy guard）：它检测注入式文本，命中后生成 AGENTSEC-001 并要求人工复核。与前几个案例不同，**它的证据是"守卫命中 + 信任边界未被突破"**，而不是某个业务断言失败。可复现性体现在：同一段注入样本在任何环境下都应触发同一守卫，而无论模型输出如何措辞。

**结构化 Finding（节选）。**

```json
{
  "finding_id": "AGENTSEC-001",
  "pr": "PR-08",
  "boundary": "评审系统信任边界（仓库内容不得改变评审目标/工具范围/批准权限）",
  "severity": "must_fix",
  "location": {"file": "app/…（被注入的注释/PR 文本）"},
  "failure_mode": "不可信仓库文本中包含针对 Agent 的指令式内容",
  "evidence_ref": ["policy-guard:prompt-injection-hit", "以引用数据形式进入模型（未执行）"],
  "reproducible": true,
  "acceptable_fix": ["enforce_trust_levels", "tool_allowlist", "separate_credentials", "gate_outside_model"],
  "needs_human": true
}
```

**多 Agent 协作与仲裁。** 正确的防护不是"在提示词里再写一句'不要被注入'"。防护由编排层完成：区分系统策略、组织规则、仓库文本与工具输出的信任等级；仓库内容以引用数据进入模型；工具调用使用允许列表；发布评论、修改代码、批准 PR 使用分离凭证；**高风险门禁在模型之外执行**。security Agent 只负责报告与解释边界状态，它没有能力改变门禁——这本身就是 9.5 权限矩阵的落地。

**图 9-10 信任分级与策略守卫（Mermaid 源码）。** 图注：把来自不同来源的文本按信任等级分流，是不可信内容无法"越级成为指令"的结构性前提；守卫命中即生成 AGENTSEC-001，交由人工复核。

```mermaid
<code>flowchart TB
  SYS["系统策略（最高信任）"] --> ORCH["编排层"]
  ORG["组织规则"] --> ORCH
  REPO["仓库内容 / PR 描述 / 注释<br/>（不可信，以引用数据进入）"] --> GUARD["策略守卫<br/>检测注入式指令"]
  TOOL["工具输出<br/>（以引用数据进入）"] --> GUARD
  GUARD -->|命中| AG["AGENTSEC-001<br/>needs_human = true"]
  GUARD -->|未命中| ORCH
  ORCH --> WL["工具允许列表"]
  ORCH --> GATE["高风险门禁（在模型之外执行）"]
</code>
```

**修复与回归。** 修复是把上述信任分级、工具允许列表、分离凭证与外部门禁落到实现里。回归证据是一组注入样本测试：无论注入内容放在注释、PR 标题还是提交信息中，守卫都应命中，且工具与门禁权限不因注入而改变。

**生产待验证。** 更广的攻击面（工具链接管、MCP 工具被滥用、间接注入经由检索内容进入）不在本案例覆盖范围内；这些将在 9.11 中结合 OWASP Top 10 for LLM Applications 展开。

## 9.7.8 六案例横向比较：三条可移植的规律

把六个案例并排看，可以得到三条不依赖具体业务的规律。它们既是本节的小结，也是读者把本章迁移到自己团队时的检查项。

**表 9-10 六案例的修复与生产待验证对照**

| **案例** | **修复语义（acceptable_fix）** | **回归证据** | **生产待验证主题** |
| --- | --- | --- | --- |
| CONCURRENCY-001 | 恢复原子边界 | 屏障并发测试转通过 | 跨进程锁、隔离级别、崩溃恢复 |
| MONEY-001 | 定点表示 / 最小货币单位 | 样例测试 + 禁止模式不再命中 | 上下游金额契约、数据库字段类型 |
| AUTHZ-001 | 恢复所有权校验（先于余额校验） | 失败授权测试转通过 | RBAC/ABAC、资源级策略、跨服务身份 |
| IDEMPOTENCY-001 | 持久化幂等键与结果 | 三类幂等测试转通过 | 键存储、跨服务幂等、事务一致性 |
| DEPENDENCY-001 | 升级/替换，或记录不可达 | 依赖检查条目消失 | 漏洞库时效、传递依赖、供应链完整性 |
| AGENTSEC-001 | 信任分级＋允许列表＋分离凭证＋外部门禁 | 注入样本全部命中守卫 | 工具链注入、间接注入 |

**规律一：阻断性证据永远来自确定性工具，模型的价值在解释与定位。** 六个案例的六种证据形态——规则、授权测试、并发测试、幂等测试、外部数据核对、策略守卫——没有一个是模型的主观判断。模型在每一行里都参与了，且常常是不可省略的（判断规则是否适用、把"缺一个条件判断"提升为越权、解释幂等为何是服务端协议），但它从不单独阻断。

**规律二：仲裁的焦点是"谁的证据可复现"，不是"谁的置信度高"。** CONCURRENCY-001 的仲裁靠失败的并发测试，AUTHZ-001 靠失败的授权测试，MONEY-001 靠规则命中。若某个 Finding 只有流畅的推理而没有 `evidence_ref`，它在仲裁中的权重应当降低，而不是因为它写得更有说服力就上升。这也是 9.6 把 `confidence` 限制为"排序候选"的原因。

**规律三：每个案例都留下一个"生产待验证"的开口。** 这不是写作上的谦辞，而是工程诚实的技术要求。进程内 `RLock` 不是分布式锁，样例通过不代表策略合规，漏洞命中不代表可利用，单仓库影响分析不等于跨仓库索引。**一个案例如果找不到任何生产待验证事项，通常意味着它的结论被高估了。**

六条证据路径合起来，正好覆盖了本章主张的闭环：需求与不变量给出裁决标准，确定性工具产生事实，专业 Agent 解释事实并定位，仲裁按根因合并，人工承担高风险取舍，策略门禁在模型之外拦截。9.12 的端到端演练会把其中一条路径（PR-04）从零跑通，把本节分散在各个角色上的动作串成一次完整交付。
