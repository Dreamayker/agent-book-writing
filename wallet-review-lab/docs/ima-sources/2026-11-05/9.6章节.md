# 9.6 证据流水线：把评审变成一条可回放的轨迹

9.4～9.5 使用现成证据包准备输入并汇合意见；本节回到上游，解释证据怎样生成、保存和绑定。但过了几天，开发者问“这个 6400 是在哪版代码上跑出来的”，只保存聊天记录就很难回答。证据流水线要处理的，正是把一次会话里的判断保存成别人能够重新核对的过程。

可以把它想成一次实验的记录本：实验对象是什么，条件怎样设置，使用了什么工具，实际看到什么，后来据此得出了什么结论。记录的价值在于让第二位读者沿相同条件检查结论。文件多、日志长，都不能自动实现这一点；材料之间的关系需要明确写出来。

## 9.6.1 冻结的不只是代码

一次可重复的评审需要固定业务规则、待审代码、Diff、工具命令和输入数据。代码 SHA 相同而优惠规则不同，结果仍可能变化；日志相同而来自修复版本，也不能证明待审缺陷。

ORD-09 的正确基线是 `7a61a4f`，错误提交是 `84bdb55`。两个短值只是阅读坐标，实际清单保存完整 SHA。重跑后生成新提交和 run_id，应将它视作新的运行，不能一半使用旧日志、一半使用新清单。

固定样例来自 `fixtures/refund-stacking.json`；错误和修复补丁分别保存。控制器在独立 worktree 重放，保持业务修改与作者当前工作区分离。这里的版本隔离不提供进程或网络隔离，安全边界见 9.11。

### 为什么“我本地跑过了”还不够

同一句命令，在不同条件下可能做不同的事。依赖是否已经下载，容器镜像是否相同，券规则是否更新，目标测试是否真的被选中，都会改变结果。面对业务缺陷，第一步先确认执行已经到达我们关心的行为，再讨论行为是否违背规则。

一条可解释的记录至少连起三项：输入条件、执行动作、原始输出。例如先用规定券配置创建订单，再改变满减，执行指定退款测试，保存断言结果。缺少输入条件，6400 无法与 6600 比较；缺少执行动作，不知道日志是否来自目标测试；只剩自然语言摘要，则无法检查摘要有没有遗漏失败位置。

冻结信息不意味着系统永不升级。我们可以维护新依赖并重跑，但新运行应有自己的记录。旧证据回答旧环境下发生什么，新证据回答新环境下是否仍成立。把两者保存好，才能解释一次依赖升级后为什么测试数量、日志或序列化行为有所变化。

## 9.6.2 证据包怎样绑定一次执行

```text
book-assets/ORD-09/
├── requirement.md、case.yaml、buggy.patch
├── tool-evidence/raw/buggy-source.txt
├── tool-evidence/raw/buggy.txt、fixed.txt
├── tool-evidence/observed.yaml、manifest.json
├── runs/recorded-agents.json
└── oracle.yaml、fixed.patch、human-verdict.yaml
```

这份目录既保存评审输入，也保存评分和验收资产，读取权限不能仅按“同目录”决定。普通模型输入只包含允许的规则、待审 Diff 和证据。Oracle、修复补丁和修复日志不因路径相邻就自动获得输入资格。

以下为冻结运行 manifest 的真实字段摘录。完整文件列出源码和错误日志两个证据文件；这里保留日志一项以便观察绑定关系。

```json
{
  "run_id": "0f43ca1f-1fc5-4c20-ace6-405e77d5879a",
  "case_id": "ORD-09",
  "code_revision": "84bdb55deb5da622aca5363b807f3a6f96dfa97a",
  "files": [{
    "path": "book-assets/ORD-09/tool-evidence/raw/buggy.txt",
    "sha256": "9771447e02308e790d36667d566641d5246e4957e3a13998a4745850ab33bbb9"
  }]
}
```

run_id 标识一次证据集合，code_revision 标识待审代码，sha256 检查文件内容是否与清单一致。门禁会比较案例与代码版本，并要求 run_id 非空；当前没有独立预期 run_id 用于进一步认证这次运行。哈希可以发现内容不一致，不能证明写清单的人被授权，也不能阻止攻击者同时修改文件和清单。当前实现没有签名或不可抵赖证明。

### 从一条引用往回走

假设报告引用 buggy.txt。复核者首先要知道这个相对路径在哪个工程下，再核对该文件是否属于 ORD-09 当前运行，随后检查文件内容有没有变动，最后才阅读其中的断言。这条逆向路径与生成顺序对应：材料先被控制器绑定，角色再引用它，报告保留引用。

manifest 为这条路径提供目录与校验信息。可以把文件哈希理解为依据内容算出的校验值：同一内容应得到同一值，核对不一致就应停止使用。它没有回答“谁有权声明这一运行有效”。如果清单本身来自不可信贡献者，就还需要可信的生成过程和权限安排。

因此，证据治理可以分步建设。先保证案例、版本、路径和内容对得上，再根据组织需求增加签名和受控执行者。把每一步的作用讲清，读者就不会因为看见一个很长的 SHA-256 字符串而误以为整个信任问题都已经解决。

## 9.6.3 退出码怎样还原成失败原因

一个非零退出码可能来自业务断言，也可能是下载失败、编译失败或缺少 Docker。只有目标测试真的运行，并出现与案例相符的失败，才能说构造缺陷被击穿。

**表 9-7 工具执行结果的解释与后续动作**

| 观察 | 可以说明什么 | 后续动作 |
| --- | --- | --- |
| 目标用例 expected 6600、actual 6400 | 该输入下出现业务差额 | 定位调用，检查数据库与修复 |
| 编译错误或 Docker 不可用 | 实验尚未执行到目标行为 | 修复环境，保留失败记录 |
| 超时 | 未在限定时间内完成 | 标未完成，检查环境与执行状态 |
| 测试返回 0 | 已执行断言通过 | 再检查是否覆盖可疑机制 |
| 扫描返回 0 | 扫描器按自身规则未报告阻断 | 核查包解析、数据与控制样本 |

运行器会读取 JUnit XML 确认目标断言失败，ORD-05 则识别重试产生的特定 DomainException。JUnit XML 是测试框架保存的机器可读结果，运行器由此核对具体用例与失败类型。它不把任意构建失败当成“发现退款问题”。测试命令及耗时保存在 observed.yaml，原始日志不经过模型总结后再替代保存。

### 沿执行阶段判断失败

命令结束后，可以按准备、构建、测试、业务断言四个阶段阅读结果。准备阶段无法取得镜像，说明环境尚不具备；构建阶段编译失败，说明目标程序没有运行；测试启动但找不到目标用例，说明选择条件不对；只有目标用例实际比较了退款金额，才进入案例的业务判断。

这条阶段线对自动化尤其重要。错误版本按设计应该触发目标失败，但“预期失败”不能让所有非零退出都变成成功。如果网络中断也被记录成“已发现缺陷”，整个后续 Finding 会建立在没有发生的观察上。运行器读取 JUnit，是为了比退出码再多确认一步。

修复验证也沿同样阶段检查。BUILD SUCCESS 只在构建真正包含预期测试时有意义。若为了让命令成功而跳过目标测试，就改变了实验问题，不能继续与之前的失败作同条件对照。

## 9.6.4 从真实日志到引用校验

ORD-09 的错误日志包含：

```text
OrderIT.refundUsesImmutableSnapshotAfterRuleChange
org.opentest4j.AssertionFailedError: expected: <6600> but was: <6400>
```

这支持“给定规则变化后，退款金额不符”的判断，尚未单独证明是哪一行导致。模型还需结合待审源码解释从 snapshot.pricing() 改为实时 quote 的因果关系。

Finding 引用 `evidence: [{type, ref}]`。进入仲裁前，门禁比较案例和代码版本，检查 run_id 非空、文件存在及哈希一致，再检查非 SOURCE 工具引用是否属于允许集合。SOURCE 引用不走这项工具清单限制，源码定位与解释仍须另行核对；9.4.5 已说明这一边界。路径解析拒绝越出项目根目录。日志内容中的指令仍是不可信文本，不会因通过哈希检查而成为系统命令。

本地可以构造三项失败：把 context 版本改成另一个 SHA，门禁报告版本不一致；修改日志而不更新哈希，门禁报告内容不一致；引用 fixed.txt，门禁报告超出本次清单。练习应在临时复制品中进行，不修改冻结证据后假称仍为原运行。

## 9.6.5 一次真实的工具分歧

执行记录：本项目维护依赖时，OSV Scanner Action v2.5.0 在本地和 GitHub 解析了 Python 清单及 Java SBOM，返回空结果；对相同 Maven 坐标直接查询 OSV API，却收到漏洞公告。差异原因尚未确定，因而“扫描成功”不足以成为依赖健康的结论。

处理顺序是先确认聚合 SBOM 确实包含传递依赖及测试依赖，再直接查询全部外部 Java 包，加入已知受影响的 Commons Compress 1.24.0 作为控制样本。如果控制样本也未被识别，门禁拒绝用这次响应作判断。

随后升级有兼容补丁的依赖。两个 Spring WebMVC 公告要求特定视图功能，当前 JSON 控制器未使用这些路径；适用性记录绑定完整版本、生产源码哈希和 2026-12-05 复查期限。新增视图、修改源码、到期或出现新公告都要求重新判断。

这不是“工具不可信所以交给模型决定”。工具分歧应产生补证据任务，模型可帮助整理条件，但放行必须落到可检查的判断记录。[工程记录](../../../../order-review-lab/docs/dependency-advisories.md) 保存升级版本、控制样本及原始报告，后续维护以实时检查为准。

### 从工具分歧学习“阴性结果”的含义

检测报告没有问题，可能因为确实不存在问题，也可能因为材料没有被正确解析、规则未覆盖或数据更新不完整。本项目发生扫描分歧后，先检查 SBOM 中是否真的含有目标包，就是在确认检测对象。加入已知受影响版本作为控制样本，则检查同一查询路径能否对一个已知问题作出响应。

控制样本的思想很容易迁移。如果一套安全检查对故意加入的标准载荷完全无反应，它的干净报告就不值得照单使用；如果一份测试对已知错误变体也全部通过，需要先检查测试是否具有辨别力。控制样本帮助暴露检测流程的盲区，但通过一个控制样本也不意味着覆盖了所有问题。

公告、适用性和可利用性还要继续区分。公告说明某个组件版本存在已知问题；适用性核对本工程是否具备相关功能和条件；利用验证再检查具体攻击路径。当前资料支持到了哪一步，就把结论写到哪一步。这样处理工具分歧，既能利用工具，也保留继续调查的空间。

## 9.6.6 修复验收如何避免只把一个数字改绿

正确修复恢复原始快照的使用。若只是把 HTTP 返回值改成 6600，数据库可能仍记 6400；若写死一个常量，换商品和数量就会失败。回归应检查返回、持久化和调用来源，并覆盖部分退款、同键重试、父子单共享单位和跨用户请求。

本案例运行器要求 fixed.patch 恢复冻结正确基线，再重跑相同用例。这使教学对照容易解释，但它不是任意生产修复必须与旧源码逐字相同的要求。实际修复可以不同，只要恢复规则并经独立测试确认。

### 用三种检查防止“修了表面”

第一种是结果检查：该输入应退 6600，修复后返回也为 6600。第二种是一致性检查：退款记录、返回结果和原快照互相对应。第三种是机制检查：退款期间没有重新读取实时计价条件。它们分别排除返回错误、存储不一致和仍依赖错误数据源的可能性。

三种检查需要适度配合。只有机制检查，可能正确读取快照却汇总错单位；只有结果检查，可能恰好在当前规则下得到相同数字；把内部调用细节全部锁死，又可能让合理重构难以进行。ORD-09 检查不读取实时计价，是因为时间来源正是本案关键约束；迁移到其他系统时，要选择与业务失败直接相关的机制观察。

从一个成功样例到可接受修复，还需覆盖相邻关系。多数量检查单位选择，重试检查响应协议，拆单检查共享身份，跨用户检查所有权。相关回归的范围来自这些业务关系，避免无边界地要求“把所有测试加一遍”。

## 9.6.7 与标准对照：交换格式、来源和可观测性

SARIF 2.1.0 为静态分析结果提供交换格式，包含规则、级别、消息与定位。[R3] 本章 Finding 为教学协议，未完成 SARIF 映射；稳定去重和跨运行匹配也不能仅靠一个字段自动实现。

SLSA provenance 描述工件的构建来源、输入和产出。[R4] 它启发我们记录评审材料如何生成，但本项目文件哈希清单不具备供应链签名体系的授权证明。借鉴字段结构与实现该标准是不同层次。

OpenTelemetry 的 GenAI 语义约定可用于统一记录模型操作、用量及延迟。[R5] 本项目目前保存 last_usage，尚未导出标准 trace；即使完成 trace，也只能说明过程发生过，不能直接证明意见正确。内容捕获还应有明确选择和敏感信息处理。

## 9.6.8 练习与参考要点

在临时目录复制 ORD-09 的证据文件与 manifest，分别制造错版本、坏哈希和错误引用。完成标志是能指出失败发生在“执行、材料绑定、意见引用”中的哪层，而非只看到一个异常。

参考要点：错版本不能靠重写模型意见解决；坏哈希要核对原始产物；缺少业务失败则必须补实验。原始内容哈希、身份签名、执行权限与语义正确性分别回答不同问题，不应合并成“证据可信”一个结论。

有了证据绑定，评审者才能把“我认为有问题”连接到特定条件下的实际观察。9.7 沿同样的方法阅读不同订单案例，比较金额、状态与安全问题分别需要哪类证据。
