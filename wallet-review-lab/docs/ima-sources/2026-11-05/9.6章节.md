# 9.6 证据流水线：把评审变成一条可回放的轨迹

## 9.6.1 冻结输入与版本

案例的最小输入包含规则版本、正确基线 SHA、错误变更 SHA、Diff、固定业务数据和工具命令。订单样例使用 fixtures/refund-stacking.json；每个 ORD 案例通过 case.yaml 指向具体版本。文件名叫“最新”不能证明版本一致，内容哈希和 Git 提交才能为复核提供稳定坐标。

案例脚本在独立 worktree 应用错误补丁并提交，执行失败用例，再应用 fixed.patch 提交修复，重跑相同命令。主工作区始终保留正确业务，教学漏洞保存在独立分支与补丁中。

## 9.6.2 执行工具并区分失败种类

ORD-09 执行真实 MySQL 用例 refundUsesImmutableSnapshotAfterRuleChange。断言检查返回金额 6600 分、持久化退款和退款期间的实时计价调用次数。错误版本出现实际 6400 分，修复版本恢复 6600 分。

```bash
cd order-review-lab
python3 scripts/replay_cases.py verify --case ORD-09
```

前提是已有 case.yaml 指定的基线与 Git 历史、JDK 17 和 Docker。脚本仅执行仓库控制器定义的命令，不接受模型生成的 shell；运行缺陷时临时跳过格式门禁，以免把格式错误当作业务失败。正确基线仍执行格式检查。

超时、编译失败、缺少 Docker 与业务回归失败分别处理。脚本要求目标 JUnit 用例出现断言失败；ORD-05 则明确识别同键重试产生的“Unit already refunded”业务异常。它们都不能由一个非零退出码替代。

## 9.6.3 证据包与可信边界

```text
book-assets/ORD-09/
├── requirement.md
├── case.yaml
├── oracle.yaml
├── buggy.patch / fixed.patch
├── tool-evidence/raw/buggy.txt
├── tool-evidence/raw/buggy-source.txt
├── tool-evidence/raw/fixed.txt
├── tool-evidence/observed.yaml
├── tool-evidence/manifest.json
├── runs/recorded-agents.json
└── human-verdict.yaml
```

observed.yaml 记录命令、退出码、耗时及基线/变更/修复版本。评审使用的 manifest 只绑定待审版本的日志和源码；修复日志单独作为验收证据保存，不能把固定答案偷偷输入盲评。Oracle 与 fixed.patch 仅供评分和修复验收。

“控制器核验”说明输出来自指定运行，并不把输出中的自然语言变成系统指令。源码注释、测试文本和业务附件仍是不可信数据。哈希校验不等于密码学签名，也不能防止有权同时改写证据和 manifest 的控制器被攻破。

## 9.6.4 结构化解释与引用校验

角色读取需求、Diff 和经过校验的证据后输出 Finding v2。Schema 校验字段和阻断约束；证据门禁校验 Case ID、代码版本、run_id、文件存在与 SHA-256，拒绝引用其他运行的工具结果。路径解析拒绝越出项目根目录。

模型可以解释“为什么退款快照被绕过”，不能把 confidence 当作测试结果。一次输出即使语义正确，引用了错误版本的日志，也应退回重新取证。

## 9.6.5 路由与规则仲裁

路径规则强制识别核心计价、数据库、快照和 API；混合文档变更不能抵消强制人工要求。当前角色顺序执行；multi_arbitrated 随后按根因去重，汇总证据，并调用规则函数。

高风险或 needs_human 返回 escalate；普通阻断 Finding 返回 request_changes；非阻断意见返回 comment；其余返回 approve。这里的 approve 是评审报告值，不会直接操作 GitHub 合并。工具权限动作应单独设计，不能把 approve_once 等权限用语混入 PR 裁决枚举。

## 9.6.6 修复与复核

修复应恢复快照不变量，不能只让一个固定金额断言变绿。回归要覆盖规则变化、部分数量、父子单重复退款、同键重试与授权。错误/修复补丁的内容必须回到同一正确业务基线，再解释差异，否则一次环境变化也可能被误判为修复效果。

以下工业对照保留既有来源与格式。它们解释目标机制；SARIF 交换、SLSA 签名、OTel 和确定性模拟测试尚未完整接入本地订单工程，不是本项目实测结果。历史钱包举例只用于机制比较，订单实战以 ORD 证据包为准。

## 9.6.7 与工业界对照：provenance、CI 产物与审计

"把产物来源变成可验证元数据"并非评审领域独有。软件供应链安全领域已经为此建立了一整套标准，证据流水线可以从中借到语言和结构。

**对照一：SLSA 的 provenance。** SLSA（Supply-chain Levels for Software Artifacts）把 provenance 定义为"关于软件工件的可验证信息，描述它在何处、何时、如何被生产"，用途是让消费者验证工件确实按预期方式构建、并在需要时重建它。其声明结构记录构建模板（buildType）、外部输入参数（externalParameters）、解析后的依赖（resolvedDependencies）、构建平台（builder.id）与产出工件（subject）。证据包是同一思想在评审域的实现：SLSA 回答"这个二进制怎么来的"，证据包回答"这条评审结论怎么来的"——两者的字段一一对应：buildType 对应流水线定义，externalParameters 对应 PR 输入，resolvedDependencies 对应 Diff 与依赖，builder.id 对应编排器与工具版本。

**对照二：in-toto 的布局与链接元数据。** in-toto 是保障软件供应链完整性的框架，其核心机制是：项目所有者签署一份**布局**（layout），列出供应链的步骤序列与每个步骤被授权的执行者（functionary）；执行者完成步骤时生成**链接元数据**（link metadata），记录所用命令与相关文件，从而建立一条可对照布局验证的连续证据链。布局之于供应链，正如路由规则之于评审流水线；链接元数据之于供应链步骤，正如轨迹记录之于评审步骤。in-toto 论文将其概括为"收集关于链本身的密码学可验证信息"——这与证据包的哈希链是同一种信任模型：**不信任叙述，只信任带来源、可验证的记录。**

**对照三：CI/CD 产物与证据包的差别。** 主流 CI 系统都会留存构建产物与日志，这属于工程常识，但产物与"结论"是分离的：CI 记录"构建成功/失败"，不绑定"为什么得出这个评审结论、依据是什么"。证据包的一等公民是**结论与证据的绑定关系**——每条 Finding 必须携带可解析的 evidence_ref。差异源于目标不同：供应链 provenance 防的是攻击者篡改产物；证据包防的是评审自身的失真：漏报、误报、越权、级联幻觉（9.5.3）。两者共同的底线是：凡是影响决策的记录，都必须能够回到源头。

事实边界声明：本节对 SLSA 与 in-toto 的描述基于其官方文档与论文摘要；证据包的设计借鉴了二者的结构，但并未实现其签名体系，教学项目中的哈希链是简化示范，不构成对供应链安全标准的实现或认证。

## 9.6.8 与工业标准的补充对照：结果交换、排序信号与可回放性

9.6.7 回答了「出处怎么证明」：SLSA Provenance 与 in-toto 把构建过程变成可签名的陈述。但证据流水线还有另外三个问题没有对照到：**结果以什么格式交换、信号以什么原则排序、运行以什么方式回放**。本小节把 9.6 的核心构件逐一映射到工业界已有的机制。本节所引外部资料访问日期统一为 2026-10-20。

**第一，统一 Finding Schema 的外部先行者：SARIF。** Static Analysis Results Interchange Format（SARIF，静态分析结果交换格式）是 OASIS 的标准化 JSON 格式，用于交换静态分析工具的输出，当前版本为 2.1.0，顶层是 `runs`，每条 `result` 携带 `ruleId`、`level`（如 `error`、`warning`）、`message` 与定位信息。两个细节与本章直接同构。其一，SARIF 的 `partialFingerprints` 属性用于跨运行匹配"逻辑上相同的两个结果"，GitHub 代码扫描正是用它防止同一问题产生重复警报，且要求 `ruleId` 与文件路径在各次分析间保持一致才能计算稳定指纹——这就是 9.6.1 根因去重的工业实现：去重键必须稳定，否则一次编辑就产生一串新警报。其二，SARIF 的 `suppressions` 允许在报告文件里携带分诊决定（kind、status 与自由文本 justification），但标准本身不规定**决定者、日期与过期时间**，仍需一份附加记录来承载这些审计信息。这恰好印证了本章 schema 的设计：统一格式解决交换，但"谁批准的、为什么、何时失效"必须由证据包自带的 provenance 字段回答，格式解决不了审计问题。

**第二，风险路由的外部镜像：CVSS、EPSS 与 CISA KEV 的分工。** 工业界在漏洞优先级问题上已经形成明确的分工共识。CVSS 描述技术严重性；FIRST 维护的 EPSS（Exploit Prediction Scoring System，利用预测评分系统）是一个数据驱动的机器学习模型，每天为每个 CVE 输出未来 30 天内被实际利用的概率（0–1）与百分位，数据免费开放，其定位是"估计利用可能性"而非替代 CVSS；CISA 的 KEV（Known Exploited Vulnerabilities，已知被利用漏洞目录）则记录已有野外利用证据的漏洞，是证据驱动、非此即彼的判断。多篇工程指南给出的使用原则是：KEV 列出的漏洞无论 EPSS 分数如何都应优先处理，EPSS 用于给其余漏洞排序，而组织自身的暴露面、可达性与业务影响必须由组织自己评估；FIRST 还明确警告"分数洗白"（score laundering）——把 EPSS 与序数 CVSS 相乘得不到可解释的风险分数。

这与 `risk-rules.yaml` 的"只升不降"是同一原则的两种表述：**外部信号可以抬升优先级，但不能被内部加权稀释，更不能直接充当批准依据**。EPSS/KEV 与本章 `confidence` 的处境完全一致——它们都是排序信号，不是决策信号；多个信号应当分别存储、分别回答问题，而不是合并成一个自制分数。差别在于：EPSS/KEV 排序的是"漏洞目录中的条目"，本章路由排序的是"Agent 产出的 Finding"，但两者的治理结构相同：排序交给统计，批准留给规则与人工。

**第三，证据包的可观测性先行者：OpenTelemetry GenAI 语义约定。** OpenTelemetry 的 GenAI SIG（2024 年 4 月启动）定义了 `gen_ai.*` 命名空间下的标准 span 类型与属性：`gen_ai.operation.name`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens` 等，使同一份 trace 无需翻译即可被 Langfuse、Phoenix、Datadog 等不同后端接收。与本章最贴近的一条规则是**内容捕获的默认边界**：规范规定插桩默认不应当捕获输入输出内容，捕获需要显式选择开启。这正是 9.5「证据共享＋结论隔离」与 9.6 证据包「只存证据引用、不存全文」在工业界的同构表述：trace 记录"调用了什么模型、花了多少 token、属于哪个会话"，但不默认复制被调用的内容本身。

边界必须写明：**trace 回答"发生了什么"，不回答"结论是否正确"。** 一条 span 记录了某次模型调用及其 token 用量，并不等于这次调用的输出经得起复核——可观测性保证的是"过程可查"，不是"结论可证"。这与 OpenTelemetry 官方对自身文档"内容可能过期、使用前应交叉验证"的提醒是同一态度的体现，也再次指向本章反复保留的那条边界：录制回放只证明过程可回放，不证明模型能力可复现。

**第四，编排器回放的外部进阶版：确定性模拟测试。** 本章编排器用 `make replay-pr04` 把录制数据回放成确定性的编排证据；工业界把同一思想推进到整个系统层面。FoundationDB 的模拟器在单线程离散事件模拟器中控制全部非确定性来源（调度器、时钟、随机数、网络、磁盘、进程死亡），随机故障调度由一个种子驱动，同一种子可逐字节重放；Antithesis 把整个系统放进一个确定性 hypervisor，在运行中收集所有事件存入数据库，检查系统级与代码级属性是否被违反，发现缺陷后可以精确重放整个运行。其中一条工程经验对本章的"回归测试"边界极其重要：**种子就是复现**——一个失败的种子反复重放都失败，修复后重放同一种子应当通过；但代码改动之后，同一种子可能走上不同的路径，因此"一个通过的种子并不证明修复"。

对照之下，本章编排器的录制回放是轻量级的确定性模拟：只固定编排层输入（屏障时序与录制数据），不模拟模型内部，也不穷举交错；工业 DST 以控制全部非确定性为代价，换取"能找到你没想到的交错"。两者不是替代关系——DST 是 9.10 与 9.12 里值得标注的生产待验证扩展方向，而本章的取舍始终是：**为每个已设计场景提供可回放的证据，比追求覆盖未知交错更优先**。

**对照之后的三条判断。** 第一，工业界已经用标准回答了"结果怎么交换"（SARIF）与"信号怎么排序"（CVSS/EPSS/KEV），但两者都停在输入一侧：SARIF 不承诺证据充分性，EPSS/KEV 不承诺批准正确性；本章把同一原则推进到决策一侧——任何分数都只排序，不批准。第二，可观测性与可回放是两个层次：trace 记录"发生了什么"，确定性重放证明"同一种子下会再发生一次"；两者都不能证明"模型不会再犯同样的错"。第三，本小节的读法不是工具清单，而是印证：本章的构件不是发明新概念，而是把工业界已验证的机制收敛到"可验证、可回放、可审计、可问责"这一个目标上；SARIF、EPSS/KEV、OTel 语义约定与 DST，都可以作为本书生产化章节（9.10、9.12）的迁移目标。

> **事实边界声明**：本节外部资料访问日期为 2026-10-20。SARIF 的字段语义以 OASIS 规范文档为准，GitHub 对 `partialFingerprints` 的用法以其官方文档为准；EPSS 的描述以 FIRST 官方页面为准，KEV 相关表述来自多篇工程指南转述；OpenTelemetry 语义约定来自其官方仓库与 SIG 文档；FoundationDB 与 Antithesis 的机制描述来自工程文献与产品文档，Antithesis 为商业产品，其营销性数字（如"发现 75+ 严重缺陷"等）未采用。本节所有外部机制仅用于对照，不用于推导 wallet-review-lab 的实验结论。
