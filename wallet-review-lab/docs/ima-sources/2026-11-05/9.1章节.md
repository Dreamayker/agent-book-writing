# 9.1 评审的困境与证据闭环

## 9.1.1 生成速度之外，还有正确性的证明

代码能编译、测试能通过，不意味着业务规则完整。优惠叠加涉及计算顺序、资格、门槛、互斥、舍入和退款状态；漏掉其中任何一项，代码在局部看起来都可能合理。评审的第一步是写出可被反驳的业务判断，而不是让另一个模型给出一段赞同意见。

本章使用整数分表示金额。活动价合计 40000 分，满减券抵扣 5000 分，新人券抵扣 2000 分，最终实付 33000 分。分摊后的 A/B/C 实付分别为 9900、16500、6600 分。这个例子为代码、测试、评审意见和人工裁决提供共同参照。

## 9.1.2 先定义不变量

| 业务不变量 | 可观察证据 |
| --- | --- |
| 活动价 = 实际券抵扣 + 实付 | PricingResult 与分摊守恒断言 |
| 每张券的分摊总和等于实际抵扣 | DiscountAllocator 测试及快照明细 |
| 退款读取下单快照 | 实时规则变更后的 6600 分退款与零计价调用 |
| 每个购买单位最多退一次 | order_units 状态与并发退款测试 |
| 同键同请求返回原结果 | 幂等响应、退款笔数及累计退款 |
| 只有订单所有者可操作 | 用户 B 访问用户 A 订单的 HTTP 403 |
| 拆单不改变原单位实付 | 子单合计、原单位映射与共享退款账本 |

不变量让评审具有明确的失败条件。“这里可能有问题”需要进一步收敛为“在输入 X 下，实际值 Y 违反了期望 Z”。Oracle 记录人工确认的根因与可接受修复；测试提供执行证据，两者承担不同职责。

## 9.1.3 为什么正常退款测试会漏检

当下单和退款之间规则没有变化，错误实现重新计价也可能得到同样的结果。ORD-09 因此明确加入时间维度：先按满减 5000 分下单，再将实时满减改为 6000 分，然后退 C。

正确算法读取快照：8000 − 1000 − 400 = 6600。错误算法读取实时规则：8000 − 1200 − 400 = 6400。失败测试同时检查返回金额、数据库记录和计价接口调用次数，避免只修正 HTTP 返回值而留下错误账本。

“退款时重算”并不总是少退。若用原实付减去剩余商品重新计价，本例可能退 8000 分。每个错误变体必须固定算法，不能用一个模糊事故描述替代证据。

## 9.1.4 工具、模型、策略和人的分工

编译器回答代码能否构建；JUnit/MySQL 回答已执行输入下的行为；静态扫描给出危险模式；模型解释需求与跨文件状态的联系；策略决定何时阻断或升级；人处理业务取舍与最终责任。

模型不因给出高置信度就获得合并权限。规则仲裁也不因叫作“仲裁器”就成为另一个模型。本项目的角色按顺序运行，`arbitrate()` 是确定性 Python 函数；并行角色与模型仲裁是可扩展方向，当前不能写成已实现能力。

## 9.1.5 一条完整的证据链

```text
规则版本 order-rules-v1 → 正确基线 → 独立错误补丁
→ 失败测试与实际数据库行为 → 结构化 Finding
→ 证据引用校验 → 规则仲裁 → 人工复核
→ 修复补丁 → 同一测试通过 → 相关回归
```

每次运行都记录代码版本、命令、退出码及文件哈希。基础设施不可用、构建失败与业务断言失败必须分开；缺少 Docker 的测试失败不能当作发现并发退款缺陷。

## 9.1.6 练习与小结

![订单快照退款与证据流程](../../../../order-review-lab/docs/figures/refund-evidence.svg)

先读 ORD-09 的需求、Diff 和失败日志，不打开 Oracle，写出一条包含位置、证据及修复方向的 Finding。再判断：只把新人券金额写死为 2000 分是否恢复了快照不变量？只断言退款不超过原实付是否足以发现少退？

评审闭环要求每一个结论都能回到输入、规则与执行结果。后面的多角色、去重和成本控制，都围绕这条链构建。
