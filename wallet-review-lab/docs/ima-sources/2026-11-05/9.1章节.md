# 9.1 评审的困境与证据闭环

## 9.1.1 当瓶颈从"写代码"转向"证明代码"

代码评审（Code Review）长期是现代软件工程保障质量与知识流转的关键环节。过去十年，它的成本结构是稳定的：人写代码，人审代码，速度大致匹配。大语言模型驱动的 AI 编程助手（如 GitHub Copilot、Cursor 等）大规模普及后，这个平衡被打破——开发者生成代码的速度呈指数级增长，而人类评审者的阅读与判断速度没有同步提升。供需失衡的直接后果是：评审队列积压、发布周期拉长、人类评审容量成为软件发布周期的核心瓶颈。

自动化代码评审（Automated Code Review, ACR）正是在这个背景下经历范式转移：从静态代码扫描工具（Static Analysis Tools），到单体生成式语言模型，再到基于多 Agent 协同的架构。单体大模型做评审有两个结构性缺陷。其一是上下文窗口限制：复杂的工业级代码库无法整体载入，模型只能看到被截断的局部。其二是注意力衰减（attention decay）：在长上下文中，模型会逐渐遗忘早期出现的关键约束，产生与业务上下文脱节的"幻觉"（hallucination）评论。大量无关痛痒或虚假的警告淹没真实缺陷，工程团队称之为"通知疲劳"（Notification Fatigue）——评审系统输出得越多，开发者越倾向于忽略全部输出。

多 Agent 架构的回应是角色专业化分工：把抽象语法树（AST）分析、逻辑推理、安全渗透、多步验证等不同能力分配给不同角色，将复杂审查任务拆解为可控的智能工作流。但这里必须澄清一个容易混淆的前提：**多 Agent 本身并不解决"评论质量"问题。** 如果每个 Agent 都只是用自然语言发表意见，系统只是把"一条幻觉"放大成"多条幻觉"。

本章的核心命题因此是：

> **AI 代码评审的工程价值不在于生成更多评论，而在于构建一条可验证、可回放、可审计、可问责的证据闭环。**

确定性工具产生事实，模型连接与解释事实，策略引擎执行不可绕过的规则，人类承担高风险取舍与最终责任。本章以 wallet-review-lab 数字钱包服务为主线实验场，并在各节对照工业界真实系统（Meta RADAR、CodeRabbit、CodeAgent）与评测基准（SWR-Bench、ReviewBench、CodeScope）讨论生产落地。wallet-review-lab 不连接真实资金，却保留了足以让评审变得严肃的四条业务不变量（见 9.3）。

## 9.1.2 测试通过不等于代码正确：PR-02 反例

"测试全绿，可以合并"是许多团队默认的验收直觉。本章的第一个反例正来自这个直觉。

PR-02 将金额转换为浮点数再归一化。常规示例中的 `10.00`、`20.50` 可能全部通过，但团队的货币策略要求金额使用十进制定点表示，禁止经过二进制浮点数往返。Semgrep 可以标出这一禁止模式，Agent 则负责解释它与账务风险的关系。

这里存在三种不同性质的结论，如表 9-1 所示：

**表 9-1 三种结论的性质边界**

| **结论** | **由谁产生** | **证明的范围** | **不能冒充什么** |
| --- | --- | --- | --- |
| 测试证明 | 确定性测试 | 已执行样例没有失败 | 设计正确性 |
| 规则证明 | 静态分析/扫描器 | 代码命中了团队禁止模式 | 事故后果 |
| Agent 解释 | 大模型 | 规则为何适用、风险如何传导 | 测试或规则本身 |

任何一项都不能冒充另外两项。若规则误配，Agent 应指出适用性问题，而不是因为扫描器亮红灯就编造事故后果。这个案例的完整评审在 9.7 展开，现在只需要记住一条原则：**测试通过只能证明"已执行样例未失败"，不能证明"设计正确"。** 后者需要不变量、规则与人工确认共同支撑。

## 9.1.3 确定性工具、模型解释与策略引擎的分工

AI 适合处理跨文件阅读、模式归纳和解释性工作：概括 PR 意图，列出受影响的 API 与状态，关联测试失败与源码位置，对照需求寻找边界条件，并把已确认的问题写成可执行的评审意见。它尤其适合把多种证据组织成一条人类易读的因果链。

AI 不适合单独证明并发、账务或安全属性，也不应确认外部实时状态、自主改变门禁或批准资金和权限变更。两个贯穿全章的例证：

- **PR-04（并发双花）**：Agent 可以指出"余额检查与更新不在同一原子边界"，却不能凭置信度替代并发测试。真正证明竞态存在的，是可重复的并发测试与清晰的不变量；

- **PR-03（对象级授权）**：Agent 可以解释"登录成功不等于拥有这个钱包"，但授权回归测试才是阻断证据。

由此得到本章最基本的四层分工：

1. **确定性工具**（测试、静态分析、扫描器、锁文件解析）产生事实；

2. **Agent** 解释并连接事实；

3. **策略引擎**（风险路由、门禁）执行不可绕过的规则；

4. **人类**承担高风险取舍与最终责任。

所谓"AI 适合做什么"，因此不是模型能力的抽象排名，而是任务是否具有可观察输入、可复现结果与明确的升级边界。

## 9.1.4 四种不确定性必须分开处理

工程上最危险的错误，是把所有"不确定"混为一谈，再用模型的自信语气统一覆盖。至少四种不确定性需要分开处理：

1. **来自代码本身的不确定性**：并发、异常回滚、事务隔离通常需要运行测试或查看数据库语义，单凭 Diff 只能提出假设；

2. **来自外部事实的不确定性**：依赖是否存在漏洞、某个 API 当前是否支持某参数，需要锁文件与官方文档等一手来源，不能靠模型记忆；

3. **来自模型自身的不确定性**：幻觉与置信度漂移，只能通过证据约束与评测暴露；

4. **来自责任归属的不确定性**：批准变更、确认实时状态属于责任动作，不能因为模型置信度高就自动执行。

四种不确定性对应四种不同的取证手段，混用其中任何一种，都会把推断误写成事实。

## 9.1.5 为什么自然语言、置信度与投票不能代替证据

三句"听起来合理"的说法，在本章都会被否定：

- **"Agent 之间用自然语言传递意见就够了。"** 不够。自然语言没有结构、无法校验，也区分不了"事实"与"推测"。若上游 Agent 产生幻觉，下游 Agent 会把这句话当作事实继续传播，形成错误级联。多 Agent 之间必须使用结构化 Finding 与工具证据作为通信协议（见 9.5、9.6）；

- **"置信度高就能阻断。"** 不能。置信度只能用于排序，不能替代证据。Finding Schema 中的 `confidence` 字段的作用是排序候选，而不是批准依据；

- **"多数 Agent 投票就能定论。"** 不能。若一个 Agent 持有可重现的并发失败，而另外三个 Agent 只是"未发现问题"，多数票不能抵消失败测试——"未发现"不是反证。

## 9.1.6 本章阅读地图

承接 9.1.5"三个流行答案为什么不够"的论证，本章的路线可以概括为一条从困境到系统的链路：

本章主线是一条可复用的证据闭环，对应图 9-1：

**需求与不变量 → 确定性工具 → 独立证据 → 专业 Agent 解释 → 根因仲裁 → 人工责任 → 策略门禁 → 可复现评测 → 持续改进。**

```mermaid
<code>flowchart LR
  A["需求与不变量"] --> B["确定性工具<br/>测试 / 静态分析 / 扫描器 / 锁文件"]
  B --> C["独立证据<br/>结构化 Finding"]
  C --> D["专业 Agent 解释<br/>correctness / test / security / impact"]
  D --> E["根因仲裁<br/>去重 / 冲突处理"]
  E --> F["人工责任<br/>Tech Lead 终审 / 裁决记录"]
  F --> G["策略门禁<br/>不可绕过"]
  G --> H["可复现评测<br/>Oracle / Precision / Recall"]
  H --> I["持续改进<br/>影子模式 → 有限门禁"]
  I --> A
</code>
```

**图 9-1 证据闭环逻辑链。** 图中每个环节都必须在下一环节开始前留下可复核产物：工具留下测试日志与扫描结果，Agent 留下带证据引用的结构化 Finding，仲裁留下合并记录，人工留下裁决记录。任何环节缺失，闭环即断裂，系统退化为"把自然语言搬进 CI"。

- **9.2** 先看工业界三个系统（RADAR、CodeRabbit、CodeAgent）如何应对同样的困境，取其架构经验而非营销数字；

- **9.3** 建立实验场 wallet-review-lab：数字钱包、四项不变量、Oracle 与可回放基线，让后续每一节都有可执行的载体；

- **9.4–9.6** 从单 Agent 评审契约，到专业化多 Agent 分工，再到证据流水线（统一 Schema、证据包、风险路由、录制回放）——这是本章的机制内核；

- **9.7** 用六个案例深度实战，把机制放到真实缺陷上检验；**9.8–9.10** 解决治理、评测与成本问题；**9.11** 补上安全防御维度；**9.12** 以一次端到端演练收束全章。

全局导航——案例体系表、PR-06 编号约定、三档阅读路径——已在章首导语给出，本节不再重复；四角色命名以 9.5 为准，Finding 字段定义以 9.6 为准。读完全章后，建议回到导语对照案例表检查一遍：每个案例你都能说出它违反哪条不变量、最终由谁仲裁、如何被回放验证。

**本节小结**：评审的困境不是"模型评论不够多"，而是"评论无法被验证"。本章所有机制——不变量、Oracle、任务契约、Schema、证据包、仲裁、门禁、评测——都是为同一个目标服务：把模型的每一次判断都变成可复核的工程事实。

**9.1 练习**

1. 回顾你团队最近一次"测试全绿但线上出错"的变更，指出被测试遗漏的业务不变量；

2. 把一次真实评审意见拆成"事实 / 解释 / 决策"三列，检查哪一列缺少证据支撑；

3. 讨论：如果评审 Agent 只输出自然语言评论，你的 CI 门禁能否判断它是否应该阻断合并？
