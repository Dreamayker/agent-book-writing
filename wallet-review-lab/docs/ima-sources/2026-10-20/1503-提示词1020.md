# 提示词1020

# 任务：基于原始技术稿，创作一部具有出版质量的 AI 代码评审与多 Agent 工程实践图书

## 一、任务目标

请以我提供的《第9章 AI代码评审与多Agent协同》为核心素材，创作一版系统、完整、深入、可实操的图书内容。

不要仅仅润色或扩写原文，也不要把原文拆成更多小标题。你的任务是将现有稿件作为核心技术素材，重新组织为一套循序渐进的知识体系，让读者从理解基本原理，逐步掌握架构设计、工程实现、测试评估、安全治理和实际部署。

**全书核心观点：AI Agent 的工程价值不在于生成更多评论，而在于构建可验证、可回放、可审计、可问责的证据闭环。**

## 二、目标读者与写作定位

目标读者包括有一定编程基础的开发者、技术负责人、AI 工程师，以及希望将大模型和多 Agent 引入研发流程的团队。

写作要求：

- 兼顾原理深度与实践可操作性，不写成泛泛的 AI 科普文章，也不写成缺乏解释的工具手册。

- 采用优秀技术图书的风格：逻辑严密、解释充分、案例贯穿、层层递进。

- 对复杂概念先解释问题背景，再讲原理、方案、权衡与实现。

- 每个重要结论尽量通过代码、测试、时序图、架构图、数据结构或具体案例支撑。

- 避免营销文案、空洞口号、重复论述和过度碎片化的小标题。

- 面向中文读者，技术术语保留必要的英文原文，首次出现时解释清楚。

## 三、内容组织原则

先完整分析原稿，再提出全书目录。不要机械地沿用原稿的第9章结构，应根据知识依赖关系重新设计章节。

建议围绕以下主线组织内容：

1. **问题与基本原理**：AI 代码评审的价值、局限，以及为什么测试通过不等于代码正确。

2. **建立可验证的实验环境**：以 wallet-review-lab 数字钱包服务为贯穿案例，定义业务不变量、正确基线、错误补丁、Oracle 和测试体系。

3. **单 Agent 评审架构**：需求解析、Diff 分析、工具调用、Finding 生成和风险分类。

4. **专业化多 Agent 协同**：general-review、correctness、test、security、impact、arbitrator 等角色的职责、输入、输出及权限边界。

5. **证据流水线与编排系统**：证据包、结构化 Schema、任务路由、并行调度、超时、重试、缓存和失败降级。

6. **典型缺陷的深度实战**：金额精度、对象级授权、并发双花、幂等重试、依赖漏洞和提示注入。

7. **仲裁与人工治理**：根因去重、证据冲突、严重性判定、人工裁决、审计记录和不可绕过的门禁。

8. **系统评测与成本优化**：Oracle 设计、Precision、Recall、误报、漏报、重复率、延迟、Token 成本和人工成本。

9. **从实验到生产**：影子模式、有限门禁、监控、权限隔离、回滚条件、持续评估与迭代。

10. **端到端项目实践**：从搭建实验环境到完成一次可复现的多 Agent 评审，形成完整工程交付物。

以上只是建议。你应根据原稿实际内容确定最终目录；如需合并或拆分章节，应说明结构调整的理由。

## 四、必须保留并深化的核心素材

不得遗漏原稿中的关键技术结论和重要案例，尤其包括：

- 数字钱包的四项核心不变量：金额守恒、余额非负、幂等键只产生一次资金变更、用户只能从自己拥有的钱包付款。

- PR-01 零缺陷样本，以及 PR-02 金额浮点精度问题。

- PR-03 对象级授权绕过。

- PR-04 并发双花及通过屏障固定并发时序的确定性测试。

- PR-05 幂等重试、并发首次请求和键参数冲突。

- PR-07 依赖漏洞识别与适用性分析。

- PR-08 提示注入与 Agent 信任边界。

- 统一 Finding Schema、证据包、风险路由、多 Agent 仲裁和人工裁决。

- Oracle、Precision、Recall、误报率、漏报率、根因去重和零缺陷评测。

- Token 成本、上下文缓存、风险预算、真实模型实验与生产上线策略。

对每个核心案例，尽量采用统一的教学结构：

**业务需求 → 核心不变量 → 错误补丁 → 失败机制 → 可复现测试 → 结构化 Finding → 多 Agent 协作 → 仲裁决策 → 修复方案 → 回归验证 → 尚未解决的生产问题。**

不要为了追求篇幅而重复同一案例；应在首次出现时完整讲解，在后续章节中引用并扩展新的知识点。

## 五、技术深度与代码要求

对于关键技术机制，必须深入解释，而不是停留在概念层面。

重点包括：

- 为什么自然语言评论不能充当 Agent 之间唯一的通信协议。

- 为什么置信度和多数投票不能代替可复核证据。

- 为什么查询、校验、状态更新和结果记录必须满足相应的原子性要求。

- 为什么进程内 RLock 不能直接证明分布式生产系统的正确性。

- 为什么认证与对象授权是两个不同的安全问题。

- 为什么幂等性是服务端状态协议，而不仅是客户端重试技巧。

- 为什么工具执行失败、测试未运行、模型超时和证据缺失不能被解释为成功。

- 为什么提示注入必须通过权限隔离、工具白名单、信任分级和外部策略门禁共同防护。

- 为什么评测必须以根因 Finding 为单位，并同时包含缺陷样本和零缺陷样本。

需要代码时，优先使用原稿已有的 Python、pytest、Ruff、mypy、Schema、YAML 和项目命令。对关键实现给出必要的上下文、核心代码、运行方法、预期结果和失败解释。

所有代码示例必须明确标记为以下之一：

- 完整可运行实现；

- 为解释原理而简化的示例；

- 伪代码或待补充实现。

如果无法确认某段代码与原项目一致，不要声称可以直接运行。优先沿用原稿提供的项目结构和命令，不要擅自编造不存在的文件、函数、测试结果或实验数据。

## 六、事实、证据与外部研究规范

原稿中已经明确指出：录制 Agent 输出用于验证编排、Schema、去重和评分，不代表真实模型能力。必须保留这一边界。

严格区分：

- **已验证事实**：由本次真实执行的测试、扫描器、代码或人工审查支持。

- **合理推断**：基于代码结构、架构或已知机制提出的解释。

- **尚未验证**：当前实验或证据不足以确认的结论。

- **生产环境待验证事项**：例如跨进程事务、分布式锁、数据库崩溃恢复和跨仓库调用影响。

不得伪造模型实验、性能数据、漏洞状态、成本数字、参考文献或外部产品能力。

如需补充外部资料，应优先使用官方文档、标准、漏洞公告和原始研究，并提供可追溯链接、发布日期或访问日期。外部资料应服务于原稿的主题，而不是将图书扩展成无关的工具百科。

明确区分原稿提供的事实、外部资料和作者推论。

## 八、最终交付要求

请分阶段完成，避免一次性输出导致内容缩水。

**阶段一：全书设计**

1. 分析原稿的知识体系、已有优势、缺失内容和重复部分。

2. 提出书名、副标题、目标读者、核心价值和全书定位。

3. 给出完整目录，细化到三级标题。

4. 说明各章目标、核心论点、案例、代码、图表和前后章节关系。

5. 建立原稿内容映射表，确保关键案例、技术结论和实验边界都有明确归属。

**阶段二：正文创作**

1. 按最终目录逐章创作，使用完整的出版级正文，而不是提纲式说明。

2. 每章均有清晰的开篇问题、系统论证、案例讲解、必要的图表或代码、实践练习和章末总结。

6. 输出审校报告、未解决问题清单和最终目录。
