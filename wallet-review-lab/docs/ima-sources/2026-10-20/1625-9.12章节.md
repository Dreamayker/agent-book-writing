# 9.12 端到端演练：让一个 PR 走完证据闭环

## 9.12.2 准备与路由：PR-04 为什么值得全量矩阵

**需求。** 用户 A 的钱包余额为 100.00 元，同一时刻并发发起两笔各 60.00 元的转账。正确行为：两笔中恰好一笔成功，余额变为 40.00，另一笔因余额不足失败；错误行为：两笔都成功，余额变为 -20.00。

**不变量。** 本案例同时检验两条不变量：不变量 2（余额非负——最常被并发错误击穿的底线）与不变量 1（金额守恒）[9.3.2]。

**路由。** triage 先跑规则优先：`policies/risk-rules.yaml` 中"资金路径 + 并发变更"规则命中，直接判高风险，不降级（9.5.3 只升不降原则）；随后进入角色路由——`correctness` 与 `testing` 主导，`security` 与 `impact` 并行扫描；难度路由确认属于高难度（并发缺陷），全程 `route_reason` 写入审计与成本台账（9.10.5）。低风险路径的对照样本是 PR-01（仅文档说明的零缺陷 PR，只走路由 + 摘要，不启动全量矩阵）——不是每个 PR 都值得全量矩阵，这正是 9.10 成本纪律的起点。

## 9.12.3 主演练：PR-04 并发双花的完整评审

**错误补丁与失败机制。** 错误补丁把转账实现为"先读余额、再扣减"的非原子序列（`balance -= amount` 在两条并发路径上交错执行），产生**读-改-写丢失更新**：两笔转账都读到 100.00，各自扣减 60.00 后写回，最终余额 40.00 而非 -20.00——检查与更新失去原子边界，不变量 2 被静默破坏。

**可复现测试。** `tests/test_transfer_invariants.py` 中的屏障并发测试用同步屏障对齐两个线程的执行点，使交错是确定性的：

```python
# tests/test_transfer_invariants.py（教学示例，完整可运行形态；细节以项目实际文件为准）
def test_concurrent_transfer_barrier():
    # 屏障对齐：两个线程同时执行"读余额-扣减-写回"
    t1 = Thread(target=transfer, args=(alice, bob, 60))
    t2 = Thread(target=transfer, args=(alice, carol, 60))
    barrier = threading.Barrier(3)  # 主线程 + 两个转账线程
    # ... 注入屏障到扣减前，断言任意时刻 balance >= 0
    assert alice.balance >= 0            # 不变量 2：余额非负
```

**四个角色并行评审**（结论互不引用，只引用证据，9.5）。`correctness` 读到"表面描述"——补丁逻辑看起来顺序正确；`testing` 执行屏障测试得到失败输出——"失败模式"；两角色意见冲突时，仲裁焦点正是「表面描述 vs 失败模式」，而裁决依据是测试证据而非模型表述。`impact` 评估资金路径影响面；`security` 并行扫描该 Diff（在 PR-08 变体中，security 才会命中策略守卫；本例无注入信号）。

**证据包。** 一次构造、多方使用（9.6）：pytest 失败输出、并发时序证据（9.7 的 PR-04 时序图）、`provenance`（测试命令、代码版本、时间戳）构成证据包；Finding 只引用 `evidence_ref`，不引用其他 Agent 的结论。

**结构化 Finding**（教学模板，字段沿用 9.7 已确认项，`root_cause` 系教学 Oracle 设定）：

```json
{
  "finding_id": "CONCURRENCY-001",
  "root_cause": "atomicity_violation",
  "invariant_violated": "balance_non_negative",
  "severity": "high",
  "needs_human": true,
  "confidence": 0.9,
  "acceptable_fix": "restore_atomic_boundary",
  "evidence_ref": ["evt-barrier-test-042", "evt-timing-seq-042"]
}
```

**仲裁与人工裁决。** 仲裁层做静态聚合比对（9.8.2）：`correctness` 与 `testing` 的冲突被根因级去重（`dedup_key` = 根因类别 + 文件 + 不变量，9.9）归一为同一个 CONCURRENCY-001，不产生重复 Finding；冲突不消除时升级人工。`needs_human: true` 使本 Finding 进入人工裁决出口（9.8），裁决记录（教学模板）要求仲裁人具名：

```json
{
  "verdict_id": "VERDICT-PR04-001",
  "finding_ids": ["CONCURRENCY-001"],
  "route": "human_verdict_high_risk",
  "route_reason": "funds_path_and_concurrency_rule_hit",
  "verdict": "approve_once",
  "reason": "修复方案 restore_atomic_boundary 已确认；允许本次修复合并，后续同类变更重新评审",
  "reviewer": "tech-lead-zhang",
  "evidence_refs": ["evt-barrier-test-042"],
  "created_at": "2026-10-20T20:40:00+08:00"
}
```

裁决动作沿用 9.8 的动作定义（本例用 `approve_once`，仅对本次修复生效；注入可疑对应 `deny` 并升级复核，超时默认 `refuse`，见 9.8.4 与 9.11.7；动作全集以 9.8 已交付正文为准）。

**修复与回归。** 应用 `fixed.patch`：把扣减改回原子边界（进程内锁/原子更新原语），屏障并发测试恢复通过；不变量断言重新全部成立。

**评测与门禁。** 用 9.9 的双层 Oracle 给本次评审打分：程序化 Oracle 判定"并发测试失败 → 结果错误"（结果级），根因 Oracle 判定"根因是否被识别为原子性缺失"（理由级）；`evaluation/metrics.py` 对 CONCURRENCY-001 计入命中。零缺陷门禁（仅覆盖关键根因，漏报高危即 FAIL）在本例通过——因为余额非负是门禁覆盖的关键根因，且未被漏报。

**生产待验证。** 以上一切在录制回放与教学沙箱内完成。并发语义在真实生产负载下的行为、真实模型对该类缺陷的根因 Recall，均未验证（见 9.12.6 协议）。

## 9.12.6 回放与真实模型实验协议

**回放验证什么。** `make replay-pr04` 用 `recorded-agents.json`（控制夹具）重放录制输出，验证的是编排层一致性：相同输入能否通过 Schema 校验、路由、去重与评分，结果是否可重现。它**不回答**"模型能否发现这个缺陷"——回放不代表真实模型能力，此边界贯穿全书（9.3、9.7、9.11 均已显式标注）。

**真实模型实验协议**（兑现 9.3/9.7 的预告）。API Key 就绪后执行：

1. **选择两个模型家族**（如 Sonnet 与 Haiku 系、或闭源与开源各一），每个案例运行 3～5 次；

2. 每次运行保存**原始输出**，并记录：模型精确版本、提示词哈希、上下文构造版本、Token 用量、延迟、当日价格；

3. 用 `evaluation/metrics.py` 按 9.9 口径评分（双层 Oracle、根因级去重、Precision/Recall）；

4. 实验只回答三个问题：**专业分工是否提高根因 Recall？仲裁是否降低重复与错误阻断？新增成本是否落在风险预算内？**

结果以 9.9 的基准纪律呈现：分数绑定基准版本与评分器哈希；通过率不等于正确率；安全指标（9.11 的对抗子集）独立计分。**本协议的结论属"尚未验证"，须在生产影子模式中复核后才可升级为"已验证"。**

## 9.12.7 生产上线与全书收束

**上线策略**：影子模式（旁路打分、不阻断）→ 有限门禁（仅关键根因 + 人工裁决出口）→ 生产门禁（不可绕过，配合 9.9 零缺陷门禁与 9.10 预算熔断）。每一步的晋升条件都必须是评测数字而非模型厂商的宣传。

**生产待验证清单**（截至本书交付，全部为"尚未验证"）：真实模型对六类根因的 Recall/Precision 与成本方差（9.10 已述行业观测存在数倍方差）；PR-08 防御对新型注入的鲁棒性（9.11）；并发语义在真实负载下的行为；门禁误报率与开发流程摩擦；CaMeL 类防御在真实流水线上的开销-收益。

**全书收束**。把模型放进一条可验证、可回放、可问责的证据流水线，全部机制最终落为三句话：

> **机器解决分歧，人对解决负责，证据记住一切**（9.8）；**评审的价值不在更多评论，而在可验证、可回放、可审计、可问责的证据闭环**（9.7、9.1）；**模型是证据流水线中的一个不可信组件，不是权威**（9.11）。

**练习**：① 按 9.12.1 的阅读路线独立走完 PR-03，先写 Finding 再对 Oracle，记录你在"缺一个条件判断 vs 越权"上的判断过程；② 用 9.10 的记账结构复算 PR-08 一次评审的成本（注意策略守卫命中后的人工复核阶段没有模型成本，但这笔工时该记在哪个账上）；③ 为你的团队把 9.12.6 的实验协议改写成一份一周内可执行的实验计划，并提前声明哪些结论只能算"尚未验证"。
