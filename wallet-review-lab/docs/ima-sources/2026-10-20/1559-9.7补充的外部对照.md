## 9.7.8 与工业系统和学术研究的对照

前七个小节用同一套结构走完了六个案例，结论是：同一套流水线能容纳六种不同的证据形态。但这个结论目前只在 wallet-review-lab 内部成立。本小节把六类缺陷逐一映射到工业界与学术界已有的处理机制，回答一个更严格的问题：**教学案例里的每一种「阻断性证据」，在真实世界里对应什么方法；这些方法与本章的取舍是同构的，还是相互矛盾的。** 本节所引外部资料访问日期统一为 2026-10-20。

**对照一：金额精度与货币策略（PR-02 / MONEY-001）。** 在规则层面，SEI CERT 的 Java 编码标准中有一条 NUM04-J「需要精确计算时不要使用浮点数」，其依据正是 float / double 的有限尾数无法精确表示 0.1 这类十进制有限小数；值得注意的是，该条目页面已标注为可能被类似指南取代（标注 Deprecated，版本 1.0 日期为 2014-06-28）。在工具层面，Sonar 的 S1244「浮点数不应用于相等比较」自 2024 年 3 月起被提升进 .NET 的 Sonar Way 默认质量配置，并在 2023 年扩展到 Python / Numpy 的计算规则集；社区讨论则显示这类规则的边界（与 0 比较是否应豁免、`>=` 等比较运算是否覆盖）仍需人工裁量。在工程层面，通行做法是把金额一律落到定点类型（Java 用 BigDecimal，数据库用 DECIMAL，传输用字符串），用字符串而非 double 构造 BigDecimal，除法显式指定精度与舍入模式，比较用专用方法，并保证精度与舍入模式全链路一致。

差异在于证据形态：本案例的阻断性证据是 `policies/risk-rules.yaml` 里禁止模式命中，外部则是语言无关的通用规则集；两者共享同一个前提——**金额语义必须先被写进契约**，否则工具无从判断哪个 float 代表钱。这也正是 9.7.3 仲裁焦点「测试通过 vs 策略违规」在工业界的对应问题：规则只拦住模式，是否真的破坏「金额守恒」，仍要由不变量断言回答。

**对照二：对象级授权（PR-03 / AUTHZ-001）。** OWASP API Security Top 10（2023 版）把 Broken Object Level Authorization（BOLA，对象级授权失效，在 Web 语境下也常称 IDOR）列为第一项，其定义就是 API 未核实请求者是否有权访问该具体对象；该缺陷对应 CWE-639 与 CWE-862 两类。CWE-862 官方页面对检测能力给出了相当诚实的说明：自动化静态分析难以检测自定义授权方案，且当某项功能本就对任意用户开放时，检测「缺少授权」会产生误报；动态分析可以找出不需要授权的接口，但「这是否违反业务逻辑」仍需人工判断；同时页面也肯定了自动化静态分析对常见授权惯用法与配置文件的检测价值。行业报告亦把对象级授权受损列为 API 安全的突出问题之一。

学术界围绕「缺一个条件判断」这个看起来简单的缺陷，给出的答案都指向同一处困难。RoleCast（2011）的核心论点就是：Web 应用不存在跨应用统一的检查模式，分析器必须先从这个应用自己的代码里**推断**出角色相关的检查集合。AUTHCHECK 用程序状态分析检测访问控制缺陷。LLM4BOLA 则把这一步交给大模型：先推断特定业务场景下的对象级敏感操作与自定义授权策略，再检测从请求入口到敏感操作路径上的对象级权限缺失，论文报告其精度优于基于规则的方法。这一点与本章的分工形成有意思的对照：**工业研究让模型参与「策略推断」，而本章仍要求 security Agent 的 Finding 必须携带失败授权测试作为阻断证据。** 动态侧最贴近本案例的做法，是把每一个成功的已认证请求以另一个用户重放，标记「仍然成功且返回相同响应指纹」的调用——这就是 BOLA 的确定性判定形式，它与 PR-03 的失败授权测试同构：判定依据是「另一个主体是否拿到了同一结果」，而非「模型觉得这段代码可疑」。最后需要记下一个厂商视角的判断：授权类缺陷缺少像注入那样可写下来的 source→sink「形状」，因此是静态分析最难覆盖的一类。

**对照三：并发双花（PR-04 / CONCURRENCY-001）。** Jepsen 的 Bank 工作负载与本案例的目标几乎一致：并发执行转账的同时周期性读取总余额，检查「系统总金额恒定」这一不变量，在快照隔离下任意一次读都应看到同一总额，违反即说明出现了异常（如 G-SIb / missed effects）。这类测试已被数据库厂商日常化，YugabyteDB 把 Bank 列为每个主要版本的常规 Jepsen 测试场景；而在 Dgraph 的 Jepsen 分析中，bank 测试曾观察到账户余额的永久性变化（读偏斜导致的数据损坏）。银行业自身的测评模型也单独设计转账场景，通过比对最终余额与隔离级别支持情况评价一致性能力。另一条路线是 TLA+：把「余额非负 / 总额恒定」写成不变式，用 TLC 穷举交错，在设计阶段找出测试与代码评审都漏掉的并发缺陷；据一篇工程记述，有团队在为某注册表重写垃圾回收器时用 TLA+ 模型检验发现了测试与评审未察觉的缺陷。

三种方法的取舍不同，这是本小节最值得记录的对照：Jepsen 用随机化并发与故障注入换取覆盖面，但违例是概率性的、需要事后从历史中定位；TLA+ 不执行真实代码，用穷举状态空间换取完备性，但证明的是模型而非实现；本案例用屏障固定并发时序，牺牲覆盖面换取「一次失败即一次可复现的证据」。这解释了本章为什么把确定性测试放在门禁位置——门禁要的不是「跑很多次可能发现」，而是「跑一次必然复现」。代价也必须写明：教学案例只覆盖被设计出来的那一种交错，Jepsen 与 TLA+ 式的更广覆盖对它是生产待验证项。

**对照四：幂等重试（PR-05 / IDEMPOTENCY-001）。** Stripe 的幂等键语义是这类机制最完整的公开描述：幂等键由客户端生成，服务端保存该键首次请求的状态码与响应体（无论成功或失败），后续同键请求返回同一结果，包括 500 错误；键保留至少 24 小时后可能被移除，移除之后重用可能执行一次新操作；建议使用 V4 UUID 等有足够熵的随机串，键长上限 255 字符，避免用邮箱等敏感数据作为键；当结果不确定时，应把重试限制在首次请求后的 24 小时内并使用相同键与参数，超过窗口后不得用旧键或新键重试，而应检索对象、检查原始请求并用 Webhook 事件对账。服务端实现序列则给出了与 PR-05「键参数冲突」直接对应的语义：以唯一键插入 `in_progress` 行、由主键承担加锁；插入冲突表示该键已见过——仍在处理中返回 409（理想情况下带 Retry-After），指纹不一致返回 422，并且**绝不在旧键下运行新载荷**；已完成且指纹一致时直接返回存储的状态与响应，不执行任何操作。同一篇文章还提醒键必须按已认证账户作用域隔离，否则一个租户可能与其他租户的键碰撞或探测。

标准化现状同样值得一提：IETF HTTPAPI 工作组的 Idempotency-Key 头字段草案，据该文转述最新修订为 -07（2025-10-15），在草案跟踪页上状态为 Expired，其文本声明 2026-04-18 到期，因此应把它视为进行中的工作而不是标准。与教学案例的差异由此清晰：Stripe 的语义来自产品文档与实现，保留窗口是产品选择；而 PR-05 证明的是「服务端状态协议一旦被破坏，可以被确定性复现」，不是「照抄某家语义即正确」。两者共享的判断仍是同一句：**幂等性属于服务端状态协议，不是客户端重试技巧。**

**对照五：依赖漏洞与适用性（PR-07 / DEPENDENCY-001）。** 工业界对同一问题的答案是可达性分析（reachability analysis）：版本匹配只说明脆弱代码「存在」，可达性进一步问「你的应用是否会调用到那个脆弱函数」，工具据调用图给每条 finding 打上可达 / 不可达标签用于优先级排序，且厂商文档明确说明它「不是安全证明」。Snyk 的做法是静态程序分析结合若干 AI 技术判定应用是否调用了与漏洞相关的代码元素（函数、类、模块），并把可达性作为风险评分的一部分，能力按语言与集成分批开放；OSV-Scanner 的 Go call analysis 把问题收窄为「静态分析能否找到从项目到 advisory 所命名脆弱函数的路径」，并明确受 advisory 缺少符号信息、工具链要求与分析限制的约束。噪声口径方面，多篇工具作者与供应商的文章主张「扫描器标记的 CVE 中 60–80% 在应用代码中不可达」；这类数字出自供应商及其客户的测量，属于其自身口径，不能当中立统计使用——它们只说明一件事：版本匹配与可利用性不是同一个判断。

对照结论与本案例的取舍一致：DEPENDENCY-001 只做「锁文件加漏洞数据核对，并逐条列出可利用条件」；外部工具把可达性自动化了一层，但把「可达」当成「可利用」仍然越过了证据边界。9.7.6 的仲裁焦点「扫描命中 vs 适用性」在工业界是同一个问题：工具输出的是输入，不是结论。

**对照六：审查系统的信任边界（PR-08 / AGENTSEC-001）。** OWASP Top 10 for LLM Applications 中，LLM01 Prompt Injection（提示注入）在 2023 与 2025 两版均列首位，并明确覆盖直接注入与间接注入——后者指攻击者把指令埋进模型随后会读取的数据源（检索结果、网页、工具输出）；2025 版对清单做了重组并新增了若干类目。研究脉络上，Greshake 等于 2023 年提出间接提示注入，在当时已部署的系统（Bing Chat、代码补全引擎）上演示了数据外泄、蠕虫化与持久错误信息等危害；AgentDojo 把该威胁模型变成可复用基准，包含 97 个跨邮件、银行、Slack、行程预订的多工具任务与 629 个安全测试用例，专门评估工具型智能体而非聊天机器人；CaMeL 的路线是在模型之外建一层：从可信查询中提取控制流与数据流，用能力机制阻止私密数据经未授权的数据流外泄，论文报告在 AgentDojo 上解决了 77% 的任务且可证明不发生策略违规（另有摘要口径为 67%），同时承认效用下降。

与本章主题更贴近的是几项把「来源与权威分离」当作核心机制的工作（以下信息均取自知识库中相应论文的摘要）：PIPES 针对工具响应缺少来源与语义先验的问题，提出基于来源层级与语义先验的筛查，报告在六项基准上把平均自适应攻击成功率从 84.7% 降至 2.3%，良性效用保持在 92.5%；NetInjectBench 在网络运维工具型智能体场景中报告朴素执行的不安全动作率为 82.50%，多种防御可降至 10.00%–25.63%，静态白名单虽能把该比例降至 5.00% 却会完全阻断合法变更，因此主张「执行时授权边界结合元数据感知的策略门」；分布式后门研究形式化了可观测性边界，证明当攻击载荷被拆分到多个智能体的输出、在局部监控视图中各自良性且与良性流量不可区分时，任何局部检测器都无法有效检测，而查看组装后对象的网关可以阻断全部测试攻击；记忆来源洗白研究指出外部低信任观察被整合进长期记忆后权威会被放大，需要不可篡改的来源元数据与风险感知的执行门控；框架鸿沟研究显示显式注入会被拒绝，但把同一载荷改写为「合法字段」式表述可使外泄率达到 100%，而目标允许列表与能力隔离能把该风险归零。

差异在于观察对象：AGENTSEC-001 要守的是**评审系统自身的信任边界**——注入指令出现在被评审的 PR 文本或代码里，而评审 Agent 同时是读者与执行者。上述工作的共同结论（控制流与数据流分离、能力或目的允许列表、外部策略门禁、局部监控不足）与本章 9.4.3、9.5、9.11 的主张一致；但每条数字都是各自环境下的测量，不能外推成「装了守卫就安全」。分布式后门的结论尤其直接：**多 Agent 的局部证据之和并不等于全局结论**——这正是 9.6 要求证据包在组装层再做一次策略校验的原因。

**对照之后的三条判断。** 第一，机制同构，性能不可迁移：六类缺陷在工业界与学术界都有对应方法，但没有一种外部方法能替代「把不变量写成可执行断言」这一步；外部数字只用于说明机制，不构成对本章教学实验的结论支持。第二，世界的共识与本节的取舍一致：确定性证据负责阻断，模型负责解释与定位（对照二中 LLM4BOLA 这类「让模型推断策略」的工作是少数例外，值得作为 9.11 的讨论素材）。第三，六类缺陷的可验证性呈梯度：金额与依赖有可写下来的模式，授权需要推断业务语义，并发与幂等只能在执行路径上被发现，而注入面对的是会主动适应防御的攻击者——这个梯度解释了为什么本章的六案例必须配六种证据形态，而不能只保留一种。
