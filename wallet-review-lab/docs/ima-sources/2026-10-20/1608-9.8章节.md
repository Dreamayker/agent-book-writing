# 9.8 仲裁与人工治理：把"意见"变成"裁决"

风险路由把 Finding 分向自动处理、复核或人工裁决三个出口之后，流水线还剩最后一个决策关节：**当多个 Agent 的意见不一致时，信谁？当机器裁决不了时，人如何裁决，且不会变成橡皮图章？** 本节回答这两个问题。核心立场与全章一致：仲裁不是给意见投票，而是**把意见冲突变成一份可回放、可审计、可问责的裁决记录**；人工治理不是把按钮交给人类，而是**设计一个人类真正在看、且看得到证据的界面**。

## 9.8.1 意见不是证据：仲裁层的定位

回顾 9.5 的角色划分：correctness、security、testing、impact 四个 Agent 各自独立工作，只共享证据、不共享结论。这种隔离保证了证据质量，却也制造了一个必然结果——**四个 Agent 可能给出相互冲突的结论**。correctness 判定某补丁正确，security 同时判定它引入了对象级授权绕过；这不一定是故障，恰恰是隔离设计的预期输出。

因此需要一层专门处理冲突的组件：仲裁器（arbitrator）。它的定位必须说清楚：

1. **仲裁的输入是意见，不是证据**。每个 Agent 输出的是带 `confidence` 的 Finding，而 9.6 已确立纪律：`confidence` 只用于排序，不用于批准。仲裁器无权把某个 Finding 的 `confidence` 更高当作"它赢了"的理由。

2. **仲裁的输出是裁决（verdict），不是真相**。仲裁器不声称自己发现了正确答案，只声称"在这些证据、这些规则下，分歧以这种方式被解决"。裁决本身要入证据包，接受日后复核。

3. **仲裁必须可回放**。与全章的取证纪律一致：同一条录制数据、同一个仲裁协议，必须得到同一份裁决记录。任何引入随机性的仲裁协议（例如随机抽样多数票）都与这个目标冲突，除非随机种子被记录。

一句话：**多数票不等于正确，仲裁器保证的是"分歧以可复现的方式被消解"，而不是"分歧被正确地消解"。** 后者是 9.9 评测要回答的问题。

## 9.8.2 仲裁协议：从多数票到稳定性检测

仲裁协议（arbitration protocol）决定"多份意见如何合并"。这里有三层，工业界的做法从简到繁：

**第一层：静态聚合。** 多数投票（majority voting）是最朴素的基线。学术转述数据给出一个参考量级：在 JudgeBench 上，raw GPT-4o-mini 判断精度约 61.7%，最佳单智能体 meta-judge 约 69.3%，多智能体多数投票配置约 77.3%。但同一个来源也提醒：聚合策略与任务相关——加权平均在部分推理任务上更好，多数投票适合通用任务，panel discussion（小组讨论）在数学任务上更好，且两智能体小组有时胜过三智能体小组（群思效应 groupthink 更小）。这说明**没有普适的聚合公式，协议必须作为配置项暴露、且每次裁决都记录所用协议**。

一个值得借鉴的细化是**按子声明加权**：与其让 Agent 给整个 Finding 一个顶层置信度，不如要求它按子声明（sub-claim）拆分置信度，再合成加权票——"95% 置信且证据扎实的主张，不该与 51% 置信的犹豫主张同权"。

**第二层：动态辩论与稳定性检测。** 辩论（debate）让 Agent 轮流质询对方后再投票。工业学术界的进展集中在**何时停止**：自适应稳定性检测用随时间变化的模型跟踪各轮判断分布，当连续轮次的分布足够接近（例如 Kolmogorov–Smirnov 准则）时提前终止辩论，在多数投票之上获得 1–5 点的精度增益，同时省下固定轮次的开销。对本章的意义有二：其一，**轮次是成本，不是美德**——三回合往往是最优平衡点；其二，停止条件必须是确定性规则，而不是"感觉谈得差不多了"。

**第三层：对共识本身的怀疑。** 更深的教训来自"confabulation consensus"（虚构共识）：多个 Agent 共享相关偏差，可能在同一个错误理由上"达成一致"，多数投票对此无能为力。相应的研究方向是对分歧点本身做审计、并用反共识偏好优化（Anti-Consensus Preference Optimization）在多数票失败的样本上训练裁决器，在多个多智能体设定上比多数票高出至多约 5 个百分点的绝对精度[web_403 转述 Yang et al.，arXiv 2602.09341]。本章不采用训练裁决器的路线（不可回放），但采纳其诊断：**共识本身需要被检查，尤其是当所有 Agent 共享同一模型骨干时**——有观察指出 LLM 法官会"一贯偏袒与自己共享同一模型骨干的一方"。因此仲裁配置至少有两种安全选择：全员同质角色（消除偏袒差异）或完全异构模型（让偏差互相抵消），前者更便宜，后者更稳健，取舍留给 9.10 成本讨论。

对 wallet-review-lab 而言，仲裁协议采用**确定性多数票 + 可选一轮复核**的教学简化配置（见 9.8.7），并把协议名写入仲裁记录——升级为稳定性检测或异构模型是生产待验证方向，不是默认配置。

## 9.8.3 仲裁的输入纪律与记录

仲裁器最容易犯的错误是"看结论不看证据"。三条纪律必须写进实现：

1. **只传证据引用，不传结论全文**。延续 9.5 的证据共享＋结论隔离：仲裁器拿到的是各 Agent 的 `evidence_ref` 列表与各自结论，而不是彼此的完整论证。这防止"谁嗓门大谁有理"——Agent 之间无法互相说服，只能各自对着同一份证据表态。

2. **每次仲裁都记录"谁、在什么输入上、按什么协议、投了什么"**。仲裁记录（arbitration record）字段：`protocol`（多数/加权/辩论轮数）、`rounds`、`votes`（含每个角色的结论与置信度）、`stability_metric`（若启用）、`verdict`、`evidence_refs`、`timestamp`、`schema_version`。这份记录本身作为一条新证据追加进证据包，参与哈希链——**裁决过程不是流水线的旁观者，而是证据的一部分**。

3. **仲裁器本身无自由意志**。它是纯函数：同输入必同输出。任何模型组件都不得进入仲裁器核心；如果某个裁决维度需要模型判断（例如"两条证据是否指向同一根因"），该判断必须由独立 Agent 作为普通角色完成，再进入确定性仲裁。

## 9.8.4 人工裁决：只裁决机器裁决不了的

仲裁器的输出有三种去向：意见一致且风险低 → 自动执行；意见一致但风险高 → 进入人工裁决（`needs_human=true`，由 9.6 的 `risk-rules.yaml` 只升不降地决定）；意见冲突 → 先仲裁，仲裁后仍冲突或触及高风险档 → 人工裁决。**人的位置不在流水线起点，而在路由明确标记"机器解决不了"的终点**。

人工裁决的界面设计，比裁决本身更重要。工业实践给出的基线：

- **裁决动作不要只有二元**。"yes exactly this / no never" 的两按钮界面会产生批准；有效选项至少包括：`approve`（批准）、`approve_narrower`（批准但收窄参数）、`approve_once`（仅此一次）、`deny`（拒绝并隔离）。这四个动作对应 9.5 权限矩阵的粒度，也对应 `acceptable_fix` 的"修复可接受性"语义。

- **超时默认拒绝，绝不静默执行**。裁决请求必须在策略中定义超时窗；超时未决的默认行为是 refuse（拒绝），这是工业界反复强调的 fail-closed 原则。

- **审批绑定短暂凭证**。批准不是解锁常驻权限，而是铸造一把"只够完成该动作、且立即过期"的窄作用域凭证。这与 9.5 权限矩阵的"只追加、最小权限"一致：批准的对象是动作，不是会话。

- **给裁决人看证据包，而不是看全文流**。裁决页展示：Finding 摘要、分歧双方立场、证据引用（可展开查看冻结原文）、可选修复建议、路由理由。页面必须能回答"为什么把这件事送到我面前"——这是 9.6 证据包的第一个真正用户。

## 9.8.5 防橡皮图章：人在回路不是控制

本节最需要直面的工业教训：**"有人在回路里"不构成控制**。自动化偏差（automation bias）是人类因素研究中最有据可查的现象之一：人对自动化系统的建议过度信任，表现为错误的作为（不加审查地接受）与不作为（放弃监控）两类。当系统 99% 的情况下正确时，审批人的警惕性会自然衰减——"正确率高"恰恰是注意力流失的原因，而非保障。

三个被反复记录的失败机制，本章直接采用为设计约束：

1. **解释反而加深顺从**。有转述指出，一项 2024 年的哈佛商学院研究给 228 名评估者展示带清晰解释的 AI 推荐后，评估者与 AI 结论一致的比例比对照组高 19 个百分点；AI 再提供叙事性理由，顺从度再升 5 个百分点。**结论：给审批人看"更漂亮的解释"不能防止橡皮图章，甚至可能加重它。** 有效的是让对方看到证据与反证，而不是看到更流畅的论证。

2. **队列规模是预算，不是结果**。审批请求到达的速度超过人类阅读速度时，监督就退化为盖章。缓解设计有四条被反复验证的路径：刻意保持小队列（策略层多过滤）、展示推理依据而不只是请求、度量审批人行为、轮换与按所有权路由。

3. **必须度量审批人本身**。拒绝率、决策中位时长、"5 秒内批准"占比、升级量——**一个从未拒绝过任何东西的审批人是一个信号，不是一个明星**；这些指标应进入月度治理评审。wallet-review-lab 在生产前至少应采集这些基线指标——该项标注为**生产待验证**，教学环境无法验证真实人类的审批行为。

值得一提的巧合是：欧盟《人工智能法案》第 14 条在措辞上直接吸收了自动化偏差概念，要求高风险系统让监督者"意识到自动依赖或过度依赖系统输出的可能倾向（automation bias）"。也就是说，"防橡皮图章"不是本章的发明，而是立法文本中的设计要求。

## 9.8.6 问责链：谁批准、谁负责

人工裁决的最后一步是把"机器决策"变成"人的决定"。问责链（accountability chain）的四条铁律：

1. **命名的人，而不是角色名**。监督职责必须落到具名自然人（named approver），并有备份与轮值表。角色名"安全负责人"无法在审计时回答"当时是谁"。

2. **按路径所有权路由，而不是按通用队列**。工业界在代码审查上的对应物是 CODEOWNERS：仓库用 `CODEOWNERS` 文件把目录映射到具名的人或团队，配合分支保护强制"触碰该路径的改动必须经其所有者批准"。经验排序是：先覆盖认证代码、CI 与基础设施定义、以及 CODEOWNERS 文件本身——"短的、被强制执行的列表，胜过长的、没人读的列表"。对 AI 生成代码，这条实践同样适用：AI 写的代码需要由触碰路径的所有者按与人类代码相同的规则审查。本章的映射：`policies/risk-rules.yaml` 决定"要不要人"，路径所有权决定"哪个具体的人"。

3. **覆盖权限本身受限**。GitHub 允许把"驳回审查"（dismiss reviews）限制到特定的人或团队；"最近一次推送者不能是唯一批准者"也作为可配置规则存在。本章的对应：人工裁决记录一旦入证据包即只追加，修改或撤销必须产生新记录并写明理由，原始记录永不删除。

4. **拒绝与超时与批准同等重要**。工业实践明确要求"把拒绝和超时记录得像批准一样仔细——没有发生的动作往往是最有价值的证据"。证据包哈希链因此不只记录"发生了什么"，也记录"什么被阻止了"。

## 9.8.7 演示：PR-04 的仲裁与人工裁决

沿用统一教学结构，把仲裁与人工治理落到主线案例 PR-04（并发双花，CONCURRENCY-001，`app/repository.py`）。

**需求**：`transfer(from, to, amount)` 必须满足四项不变量（金额守恒、余额非负、幂等键只产生一次资金变更、用户只能操作自己的钱包）。

**不变量**：并发场景下校验重点是金额守恒与余额非负。

**错误补丁**：在 9.4 的场景中，错误修复方案在 `from == to` 或并发交错下破坏守恒。

**失败机制**：检查后提交（check-then-act）的竞态——两个并发转移都读到了旧余额。

**可复现测试**：`tests/test_transfer_invariants.py` 中固定并发时序的回归测试；`make replay-pr04` 回放录制数据。

**Finding**：correctness 与 security 各自独立产出 Finding——correctness 判定错误补丁"逻辑正确"，security 判定其"违反金额守恒不变量"，两个结论冲突。

**多 Agent 协作**：双方只共享 `evidence_ref`（回放片段与测试输出），不共享结论。

**仲裁**。以下是教学简化示例——确定性多数票 + 强制复核，完整可运行版本见配套代码仓库（本节代码均为教学简化示例，未声称可直接运行）：

```python
# review_system/arbitration.py（教学简化示例）
from dataclasses import dataclass, field

@dataclass
class Arbitrator:
    protocol: str = "deterministic_majority"

    def arbitrate(self, findings, role_count):
        """确定性多数票：同输入必同输出，随机种子被禁止使用。"""
        votes = {"CONFLICT": 0, "SAFE": 0, "VIOLATION": 0}
        for f in findings:                      # f: Finding, 含 role/verdict/confidence
            votes[f.verdict] += 1
        verdict = max(votes, key=votes.get)
        return {
            "protocol": self.protocol,
            "rounds": 1,
            "votes": votes,                     # 记录每角色的表决
            "verdict": verdict,
            "needs_human": verdict == "CONFLICT" or self._tie(votes),
            "evidence_refs": [f.evidence_ref for f in findings],
            "schema_version": "1.0",
        }
```

**仲裁结果与路由**。若裁决为 `CONFLICT`（双方各执一词）且风险规则命中高风险档（资金路径），`needs_human=true`，进入人工裁决。裁决记录 schema（教学简化示例，字段风格与 9.6 Finding Schema 一致）：

```json
{
  "schema_version": "1.0",
  "arbitration_ref": "hash://arbitration/pr04-2026-10-20-01",
  "approver": "named-person-id（具名自然人，非角色名）",
  "decision": "approve_narrower",
  "rationale": "接受 restore_atomic_boundary 修复；拒绝并行执行路径",
  "acceptable_fix": "restore_atomic_boundary",
  "evidence_refs": ["hash://ev/replay-pr04-01", "hash://ev/test-transfer-001"],
  "decision_ms": 184000,
  "timeout_policy": "refuse",
  "timestamp": "2026-10-20T20:31:00+08:00"
}
```

**修复与回归**：人工裁决确认 `acceptable_fix` 为 9.4 确立的 `restore_atomic_boundary`（原子边界恢复）；随后应用修复、运行 `uv run pytest tests/test_transfer_invariants.py` 与 `uv run ruff check .`，再用 `make replay-pr04` 回放同一录制数据，确认裁决、修复与回归全部落在同一份证据链上。**生产待验证**：真实审批人行为（拒绝率、决策时长）与仲裁协议升级（稳定性检测、异构模型）均未在生产数据上验证，本节演示只证明教学场景下流水线可复现。

**三条判断。** 第一，工业界与学术界对"机器裁决"的共识是：**聚合协议必须可配置、可记录、可怀疑**——多数票不是终点，稳定性检测、加权与反共识审计都在同一个方向上前进；本章的确定性选择是教学约束，不是工业结论。第二，"人在回路"在立法与工程两个方向上都已被降级为"需要被设计的控制"：EU AI 法案把自动化偏差写进第 14 条，工程实践则要求度量审批人本身——这印证了本章的立场：**人工治理的成败不在"有没有人"，而在"人有没有在看、看没看到证据"**。第三，所有权机制（CODEOWNERS）证明"具名+路径"是问责链的成熟工业形态，本章的 `named approver` 与路径路由与之同构；区别在于本章把同一机制延伸到 AI Agent 产出的裁决记录，并让记录参与证据包哈希链。
