# 9.6 证据流水线：把评审变成一条可回放的轨迹

9.4 给出了组件（任务契约、Finding Schema），9.5 给出了组织（角色、隔离、编排配置）。但一次评审的真实产物不是"几条评论"，而是一条**轨迹**：变更进入、路由决策、角色执行、证据汇聚、证据包冻结。本节把这条轨迹显式化为**证据流水线**（evidence pipeline）——证据闭环从一句口号变成可验证、可回放、可审计、可问责的物理装置。

## 9.6.1 从静态结构到动态轨迹

把 9.4 与 9.5 的成果串起来看：契约规定了"组件被允许做什么"，角色集规定了"谁负责哪条证据路径"，隔离规定了"结论如何互不污染"。但三者都是静态结构，没有回答一个工程问题：**一次评审从输入到结论，中间发生了什么，以及如何证明"发生了什么"就是记录里写的那样。**

证据流水线回答这个问题。它把一次评审的全部输入、步骤、工具调用、中间产物与最终结论按时间顺序记录为一条可校验的轨迹。每一条轨迹的终点是一个**证据包**（evidence package）：冻结的、不可篡改的评审档案。流水线的价值与 9.1 确立的评审困境一一对应：

- **可验证**：每条结论都能沿证据引用回到原始材料，现场复核；

- **可回放**：同一输入在同一流水线版本下可以重演，确定性步骤结果应当一致；

- **可审计**：每一步记录"谁、在什么输入上、用什么工具、产出什么"；

- **可问责**：每条结论可归因到具体角色与具体证据，而不是"模型说"。

## 9.6.2 统一 Finding Schema 与验收断言

Finding 是流水线的日志单元，Schema 是日志的格式。9.4.4 已经定义了四要素（位置、失败模式与根因、可复核证据、修复边界），流水线要求在此基础上加两样东西：

**版本化**。`schema_version` 字段记录 Schema 版本，使旧证据包在新版本下仍可解析；Schema 演进不能靠改字段含义完成，只能发布新版本。

**机器可检查的验收断言**（acceptance）。一条 Finding 只有通过全部断言才允许进入证据包：

- Schema 合法（字段齐全、类型正确、`severity` 取值合法）；

- `evidence` 中的每条引用可解析——指向真实存在的测试、日志或文件；

- 阻断级（must_fix）Finding 必须同时携带文件位置与证据引用，二者缺一即不满足断言，降级为建议或丢弃。

教学模板（沿用 9.4.4 的 CONCURRENCY-001，扩充流水线所需字段）：

```json
{
  "schema_version": "1.0",
  "id": "CONCURRENCY-001",
  "pr": "PR-04",
  "category": "correctness",
  "severity": "must_fix",
  "root_cause": "余额检查位于原子边界之外，检查与更新非原子",
  "invariant_violated": "余额非负；金额守恒",
  "location": { "file": "app/repository.py", "lines": [42, 55] },
  "failure_mode": "两个并发请求同时通过余额校验并各自写入，余额可能为负，总余额与转账记录不符",
  "evidence": [
    { "type": "test", "ref": "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend" },
    { "type": "test_log", "ref": "book-assets/PR-04-concurrent-double-spend/evidence/pytest-fail.log" }
  ],
  "fix_direction": "将读取、校验、更新置于同一原子边界（锁 / 事务 / CAS）",
  "needs_human": true,
  "provenance": {
    "pipeline_version": "v0.4.0",
    "agent": "correctness",
    "inputs_hash": "sha256:<输入材料摘要>"
  }
}
```

`invariant_violated` 与 `root_cause` 字段与 9.3.5 的 oracle.yaml 逐字段对齐——这是 9.9 评测 Precision/Recall 的前提：Oracle 说根因是"原子边界外检查"，Finding 也说同一个根因，才构成一次命中。`provenance` 块记录流水线版本与输入摘要，是回放与审计的钥匙。

## 9.6.3 证据包：不可变的最小交付单元

证据包把一次评审的全部可审计信息装进一个不可变单元：

**表 9-9 证据包的组成**

| **组成** | **内容** | **用途** |
| --- | --- | --- |
| 变更元数据 | PR 号、Diff 摘要（hash）、提交信息 | 精确定位被评审的输入 |
| 输入材料 | 标准化 Diff、不变量定义、需求片段 | 复现评审的前提条件 |
| 执行证据 | 测试输出、失败日志、扫描结果 | 支撑每条 Finding 的证据引用 |
| Finding 列表 | 结构化 Finding（含 evidence_ref） | 仲裁（9.8）与评测（9.9）的输入 |
| 路由记录 | 路由决策、启动的角色、采用的配置 | 审计"为什么走这条路" |
| 版本元数据 | 流水线版本、工具版本、模型版本 | 回放与复现 |

教学项目中，证据包落在 `book-assets/<PR>-<场景>/evidence/` 目录：`pytest-fail.log`、测试矩阵、`findings.json` 等，与 `make replay-pr04` 命令（9.6.5）配套。

不可变性有两层保证。第一层是**只追加**（append-only）：证据包一旦冻结，任何角色不得改写已写入的 Finding，后续只允许追加标注（如仲裁结论"驳回"）。第二层是**哈希链**：每条记录携带前一条记录的摘要，证据包整体可校验——任何一条被篡改，链条断裂，仲裁与评测即拒绝采信。不可变是回放的前提：如果输入可以被事后修改，"同一输入重演"就失去意义；不可变也是仲裁的前提：9.8 的裁决者必须确信自己看到的证据就是评审当时产生的证据。

## 9.6.4 风险路由：决定走哪条路

流水线入口的第一道决策是**风险路由**（risk routing）：根据变更的元数据与静态信号，决定这次评审走哪条路径。路由规则写在 `policies/risk-rules.yaml`，本身是版本化的代码，而不是提示词：

```yaml
# 教学模板：风险路由规则（字段以本书实验项目为准）
route:
  - id: RULE-001
    when:
      path_match: ["app/repository.py", "app/transfer*"]
      keyword_hit: ["balance", "amount", "owner_id"]
    then:
      config: hybrid
      agents: [correctness, security, testing, impact]
      needs_human: true

  - id: RULE-002
    when:
      path_match: ["docs/", "*.md"]
      no_behavior_change: true
    then:
      config: lint_only
      agents: []
      needs_human: false

  - id: RULE-003
    when:
      dependency_changed: true
    then:
      agents: [security, impact]
      needs_human: true
```

路由的三个要点。第一，**信号要静态可判**：命中不变量核心文件（如 `app/repository.py`）或金额、授权关键字，意味着结论可能触发 9.4.2 契约中的 `needs_human` 升级路径——路由在流水线层面提前执行同一规则。第二，**路由决策本身入证据包**：任何一次评审都能回答"为什么启动这些角色"，而非事后补解释。第三，**路由是成本的第一道闸门**：PR-01 这类文档改动走 `lint_only` 路径，不启动任何专业 Agent——多 Agent 的成本（9.10 展开）只在风险需要时才值得支付。

## 9.6.5 调度与可回放执行

路由决定路径，**编排器**（orchestrator）执行路径：按路由决策启动角色（9.5.5 的串行/并行/混合配置）、按权限矩阵注入最小输入（9.5.4）、收集执行证据、执行 9.6.2 的验收断言、组装并冻结证据包。每一步的"组件、输入引用、输出、工具版本"都写入轨迹记录。

可回放性由两个要素保证：

1. **版本锁定**：证据包记录流水线版本、工具版本与模型版本。`make replay-pr04` 重放时，使用同一版本的确定性组件对同一输入摘要重新执行。

2. **区分可回放与不可回放**。测试、lint、依赖扫描是确定性步骤，同一输入重跑结果应当逐字节一致；模型生成 Finding 不是确定性步骤——采样随机性意味着模型不会、也不被承诺逐字复现同样的文字。因此证据包对模型步骤的记录方式是：**记录该次运行产出了什么、引用了哪些证据，回放时验证证据引用可解析、Schema 合法、确定性步骤一致**，而不去验证"模型再次说出同样的话"。

这里必须守住一条事实边界，它在本章反复出现：**录制回放不代表真实模型能力**。`make replay-pr04` 回放的是流水线与证据，不是模型推理；一条 Finding 的"可复现"指的是它的证据链可以在不重新询问模型的情况下被验证，而不是模型在相同输入下必然再次发现它。前者是工程事实，后者是能力声明——把两者混为一谈，正是 9.1.2 批评的"测试通过等于代码正确"式偷换。

## 9.6.6 端到端示例：PR-04 走一遍流水线

把以上机制串起来，看主线案例 PR-04 如何走完流水线（此处只演示骨架，完整教学结构在 9.7 展开）：

```mermaid
<code>flowchart LR
  IN["PR-04 Diff"] --> R["风险路由<br/>policies/risk-rules.yaml"]
  R -- "hybrid + needs_human" --> A1["correctness Agent"]
  R --> A2["security Agent"]
  R --> A3["testing Agent"]
  R --> A4["impact Agent"]
  ES["共享证据库<br/>不变量 / 基线测试 / Oracle"] -.-> A1
  ES -.-> A2
  A1 --> F1["CONCURRENCY-001"]
  A2 --> F2["无 AUTHZ 命中"]
  A3 --> F3["测试矩阵证据"]
  A4 --> F4["影响面说明"]
  F1 & F2 & F3 & F4 --> ACC["验收断言<br/>evidence_ref 可解析"]
  ACC --> EP["证据包 evidence package<br/>hash 冻结"]
</code>
```

**图 9-6 PR-04 的证据流水线轨迹。** 路由命中 `app/repository.py` 与金额关键字，走混合配置并强制人工；四个角色从共享证据库取证据、产出独立结论；编排器验收后冻结证据包。

**表 9-10 PR-04 流水线步骤记录**

| **步骤** | **组件** | **输入** | **产出** | **证据** |
| --- | --- | --- | --- | --- |
| 1 入口登记 | 编排器 | PR-04 Diff | 输入摘要 | diff hash 记录 |
| 2 风险路由 | risk-rules.yaml | 路径＋关键字 | hybrid、全角色、needs_human | 路由记录 |
| 3 缺陷评审 | correctness Agent | Diff＋调用图＋不变量＋基线测试 | CONCURRENCY-001 | `pytest-fail.log` |
| 4 测试证据 | testing Agent | 测试矩阵 | 并发覆盖缺口说明 | 测试清单 |
| 5 安全与影响 | security / impact | 授权测试 / 调用图 | 无 AUTHZ 命中；影响限于 transfer 模块 | 授权回归结果 |
| 6 验收冻结 | 编排器 | 全部 Finding | 证据包（hash） | 验收断言结果 |

注意第 5 步：security 的"无命中"与 impact 的"影响面说明"也是证据包的一部分。**"没发现问题"和"发现问题"一样需要证据**——没有授权回归结果支撑的"无 AUTHZ 命中"只是一句断言，这正是 9.4.3 摘要纪律在流水线层面的体现。冻结后的证据包进入 9.8 的仲裁：人工裁决者看到的是四个独立结论与共享证据，而不是一组互相印证的评论。

## 9.6.7 与工业界对照：provenance、CI 产物与审计

"把产物来源变成可验证元数据"并非评审领域独有。软件供应链安全领域已经为此建立了一整套标准，证据流水线可以从中借到语言和结构。

**对照一：SLSA 的 provenance。** SLSA（Supply-chain Levels for Software Artifacts）把 provenance 定义为"关于软件工件的可验证信息，描述它在何处、何时、如何被生产"，用途是让消费者验证工件确实按预期方式构建、并在需要时重建它。其声明结构记录构建模板（buildType）、外部输入参数（externalParameters）、解析后的依赖（resolvedDependencies）、构建平台（builder.id）与产出工件（subject）。证据包是同一思想在评审域的实现：SLSA 回答"这个二进制怎么来的"，证据包回答"这条评审结论怎么来的"——两者的字段一一对应：buildType 对应流水线定义，externalParameters 对应 PR 输入，resolvedDependencies 对应 Diff 与依赖，builder.id 对应编排器与工具版本。

**对照二：in-toto 的布局与链接元数据。** in-toto 是保障软件供应链完整性的框架，其核心机制是：项目所有者签署一份**布局**（layout），列出供应链的步骤序列与每个步骤被授权的执行者（functionary）；执行者完成步骤时生成**链接元数据**（link metadata），记录所用命令与相关文件，从而建立一条可对照布局验证的连续证据链。布局之于供应链，正如路由规则之于评审流水线；链接元数据之于供应链步骤，正如轨迹记录之于评审步骤。in-toto 论文将其概括为"收集关于链本身的密码学可验证信息"——这与证据包的哈希链是同一种信任模型：**不信任叙述，只信任带来源、可验证的记录。**

**对照三：CI/CD 产物与证据包的差别。** 主流 CI 系统都会留存构建产物与日志，这属于工程常识，但产物与"结论"是分离的：CI 记录"构建成功/失败"，不绑定"为什么得出这个评审结论、依据是什么"。证据包的一等公民是**结论与证据的绑定关系**——每条 Finding 必须携带可解析的 evidence_ref。差异源于目标不同：供应链 provenance 防的是攻击者篡改产物；证据包防的是评审自身的失真：漏报、误报、越权、级联幻觉（9.5.3）。两者共同的底线是：凡是影响决策的记录，都必须能够回到源头。

事实边界声明：本节对 SLSA 与 in-toto 的描述基于其官方文档与论文摘要；证据包的设计借鉴了二者的结构，但并未实现其签名体系，教学项目中的哈希链是简化示范，不构成对供应链安全标准的实现或认证。

## 9.6.8 练习与小结

**9.6 练习**

1. 为 CONCURRENCY-001 补全 `schema_version` 与 `provenance` 字段，说明每个字段支撑哪一条审计需求（可验证/可回放/可审计/可问责）；

2. 设计一条新的 risk-rules.yaml 规则（信号→配置），并解释为什么路由决策必须写入证据包而不能只存在于编排器日志；

3. 解释"回放流水线不等于回放模型"：确定性步骤与模型步骤在回放时分别验证什么，证据包如何记录两者的差异；

4. 讨论：若证据包哈希校验失败（内容被篡改），流水线应如何反应——拒绝仲裁、强制重审还是告警放行？为什么？

**9.6 小结**：证据流水线把评审从"输出评论"改造成"冻结轨迹"。Schema 规范化结论（9.6.2），证据包冻结轨迹（9.6.3），风险路由决定路径（9.6.4），编排器执行路径并保证可回放（9.6.5），PR-04 演示了全过程（9.6.6），供应链领域的 provenance 标准提供了同构的工业语言（9.6.7）。至此，本章的"管线"已经完整：组件（9.4）、组织（9.5）、轨迹（9.6）。但流水线跑出来的证据包还要经过一个环节才能变成决策——冲突如何仲裁、人工如何治理，这是 9.8 的内容；在此之前，9.7 先用六个真实案例把这条流水线压一遍。
