# 第 9 章 AI 代码评审与多 Agent 协同

> 副标题：把模型放进一条可验证、可回放、可问责的证据流水线
>
> 稿件状态：扩充出版稿（案例驱动初版）。本章中的模型输出部分使用录制回放；录制数据用于验证编排、Schema、去重和门禁，不代表真实模型能力。

## 开篇：先定义“正确”，再讨论“智能”

当团队用 AI 生成更多代码时，瓶颈会从“写出来”转向“证明它是对的”。代码评审 Agent 的价值不是用另一段自然语言替代人类判断，而是更快收集证据、定位风险、组织分歧，并把最终决策留在可追溯的工程流程中。

本章使用 `wallet-review-lab` 中的最小数字钱包服务作为实验场。它不连接真实资金，却保留了足以让评审变得严肃的四条业务不变量：金额守恒、余额非负、同一幂等键只产生一次资金变更、用户只能从自己拥有的钱包付款。每个教学 PR 都有一份需求、一份错误补丁、一份人工确认的 Oracle、工具证据和修复补丁。读者可以先只看 Diff 和测试结果，写下自己的 Finding，再打开 Oracle 对照。

贯穿全章的主线是 PR-04“并发双花”。余额为 100 元时，两笔 80 元转账不应同时成功。错误补丁把余额检查移到 `app/repository.py` 的 `atomic` 锁边界之外；单线程测试仍然通过，但两个线程可能同时读到 100 元。这个案例让我们反复看到一个事实：模型可以帮助解释竞态，但真正证明竞态存在的，是可重复的并发测试和清晰的不变量。

为什么选择钱包，而不是继续使用一个抽象的优惠券系统？因为本章的观点必须落到可运行证据上。钱包服务足够小，读者可以在一章内理解全部状态；又足够真实，能够同时容纳金额精度、对象授权、并发、幂等、依赖漏洞和提示注入。正确基线使用进程内 `RLock` 表达原子边界；生产数据库可能需要行锁、可串行化事务，或者带版本号和重试的 CAS。书中的修复证明的是实验不变量恢复，不是可以直接复制到分布式资金系统的完整方案。

## 9.1 AI 适合评审什么，不适合评审什么

AI 适合处理跨文件阅读、模式归纳和解释性工作：概括 PR 意图，列出受影响的 API 和状态，关联测试失败与源码位置，对照需求寻找边界条件，并将已确认的问题写成可执行的评审意见。它尤其适合把多种证据组织成一条人类易读的因果链。

AI 不适合单独证明并发、账务或安全属性，也不应确认外部实时状态、自主改变门禁或批准资金和权限变更。PR-04 中，Agent 可以指出“检查和使用不在同一原子边界”，却不能凭置信度替代并发测试；PR-03 中，Agent 可以解释“登录成功不等于拥有这个钱包”，但授权回归测试才是阻断证据。

一个可靠的分工是：确定性工具产生事实，Agent 解释和连接事实，策略引擎执行不可绕过的规则，人类承担高风险取舍和最终责任。所谓“适合”，因此不是模型能力的抽象排名，而是任务是否有可观察输入、可复现结果和明确升级边界。

### 案例对照：测试通过为什么仍可能不能合并

PR-02 将金额转换为浮点数再归一化。常规示例中的 `10.00`、`20.50` 可能全部通过，但团队的货币策略要求金额使用十进制定点表示，禁止经过二进制浮点数往返。Semgrep 可以标出禁止模式，Agent 则解释它与账务风险的关系。

这里有三种不同结论：测试证明已执行样例没有失败；规则证明代码命中了团队禁止模式；Agent 解释规则为何适用。任何一项都不能冒充另外两项。若规则误配，Agent 应指出适用性问题，而不是因扫描器发出红灯就编造事故后果。

## 9.2 评审 Agent 的四类任务

### 规范任务：先清理低级噪音

Ruff、格式化器和依赖检查适合承担确定性规范任务。Agent 的工作是将输出映射回文件和行号，告诉作者为什么需要修改，并避免把风格问题伪装成安全阻断。PR-01 只补充转账响应字段的文档说明，风险路由将它判为低风险；如果系统仍启动全部专业 Agent，得到的只是更高成本和更多无关评论。

### 缺陷任务：从控制流走到不变量

缺陷评审要追踪状态读取、校验、写入和异常路径。PR-04 的关键不是“代码少了一把锁”这句表面描述，而是：两个请求读取同一余额，两个请求都通过校验，随后各自写入，最终余额可能为负，且总余额与转账记录不再符合业务定义。一个合格 Finding 必须把源码位置、失败模式和修复边界写在一起。

### 安全任务：验证身份、对象和输入的边界

PR-03 删除了服务层的 `source.owner_id == current_user.id` 检查。客户端提交的钱包 ID 只能用于定位资源，不能作为授权证据。安全 Agent 需要同时看到需求、身份上下文和失败授权测试，才能把“缺少一个条件判断”提升为对象级授权绕过（`AUTHZ-001`）。PR-08 则把源码注释当作不可信输入，验证仓库文本不能改写评审策略。

### 影响任务：描述传播，不猜不存在的调用方

影响分析应优先使用 AST 符号引用、路由表、数据库迁移和锁文件等结构化事实。Agent 可以解释这些图和列表，但不能凭空声称存在跨仓库调用方。本地实验只有单仓库、单服务边界，因此书中将“已实现的本地影响分析”和“生产环境需要补充的跨仓库索引”明确分开。

### 四类任务如何共享证据

同一 PR 不应为每个 Agent 重复构造全部上下文。编排器先生成公共证据包：需求与验收标准、标准化 Diff、风险标签、变更文件和工具摘要。测试 Agent 再获得现有测试与失败日志，安全 Agent 获得身份边界和扫描结果，影响 Agent 获得符号引用和公共契约。

共享证据不等于共享结论。若 correctness Agent 先声称存在竞态，再把这句话放进 test Agent 输入，后者容易只是重复确认。更可靠的方式是让 test Agent 独立产生“两个请求均成功”的事实，再由仲裁阶段关联根因。这样才能判断召回提升来自专业分工，还是来自同一句话被反复转述。

## 9.3 多 Agent 协同评审

多 Agent 不是让多个模型重复阅读同一份 Diff，而是让不同角色回答不同问题。推荐的最小角色集如下：`general-review` 负责低风险自洽性，`correctness` 负责不变量和并发，`test` 负责失败模式覆盖，`security` 负责授权、输入和依赖，`impact` 负责调用与状态传播，`arbitrator` 负责按根因合并和升级；Tech Lead 是高风险变更的唯一最终批准者。

在 PR-04 上，可以比较三种配置。单 Agent 只收到 Diff 和需求，容易给出“建议增加并发测试”的泛化评论；多 Agent 让测试 Agent 先运行确定性并发测试，再把结果交给 correctness Agent；多 Agent 加仲裁则把多个关于锁边界的意见合并成一个 `CONCURRENCY-001`，保留每个来源和证据，并输出 `escalate`。三者的差异不是评论数量，而是证据是否闭合、重复是否减少、门禁是否可强制执行。

生成者、审查者和仲裁者必须物理隔离权限。审查者不能修改代码，仲裁者不能降低高风险级别，发布评论和批准 PR 不能共用同一凭证。自然语言不能作为 Agent 之间唯一的通信协议；必须使用结构化 Finding 和工具证据，防止上游幻觉被下游当成事实传播。

### PR-04：从错误 Diff 到评审结论

开发者想缩短锁持有时间，目标看似合理，危险在于优化对象正是事务边界。待审查补丁让 `atomic` 不再持有仓储锁。上层仍按“读余额、判断、写入两个钱包、记录转账”执行，但四个动作不再不可分割。

读这类 Diff 时，应画状态时序而不只搜索 `lock`。线程 A 读到 100，线程 B 也读到 100；A、B 分别判断足以支付 80，随后各自提交。只看任一线程都正确；交错执行后，系统批准了总额 160 的支出。这说明“模型读完所有代码”仍不等于证明了并发性质。

实验用屏障固定时序，而非依赖偶发压力测试。测试让两个请求同时越过读取阶段，再继续提交，断言恰好一个成功。错误分支上观测到成功数为 2，直接违反验收标准：

```text
原子锁被移除
→ 两个请求观察同一旧余额
→ 两个余额检查均通过
→ 两笔 80 元转账均获准
→ 违反余额非负与金额守恒约束
```

修复也不能只写“加锁”。教学仓储可恢复 `RLock`；数据库实现可能使用事务行锁、可串行化隔离，或带版本字段和冲突重试的 CAS。Finding 应表达需要恢复的性质，而不是把一个实现细节当成唯一答案。

测试 Agent 可能报告“期望一个成功，实际两个成功”；correctness Agent 报告“原子边界丢失”；impact Agent 报告“余额和转账记录同时受影响”。三条文字不同，却指向同一根因。仲裁器应使用不变量、源码位置、失败模式和修复方向做根因去重，合并意见并保留全部来源，而不是把三条重复阻断都发布给开发者。

## 9.4 测试、评审、安全 Agent 的协同

一个可回放的评审顺序是：风险路由先确定证据集；测试 Agent 并行运行回归和边界测试；安全 Agent 运行策略守卫、Semgrep 或 OSV；专业评审 Agent 读取 Diff、需求和工具结果；最后由仲裁器去重、冲突处理并交给策略门禁。

以 PR-04 为例，测试 Agent 得到两个并发转账都成功的失败结果；correctness Agent 将它与“余额检查和更新必须原子化”连接；arbitrator 发现多个意见都指向 `repository.atomic`，合并为一个阻断 Finding。修复后恢复 `RLock`，同一测试应恰好一个请求成功，余额保持非负，总余额守恒。这里没有一个 Agent 被要求“猜答案”，每一步都有可复核产物。

PR-03 提供另一种协同：安全 Agent 发现授权检查被删除，测试 Agent 提供未拥有钱包时应返回拒绝的回归失败，仲裁器确认两者属于同一根因。PR-05 则将网络重试转化为状态不变量：同一用户、同一幂等键和同一参数只能执行一次，第二次请求必须返回原转账 ID。测试、语义解释和策略判断缺一不可。

### PR-03：对象级授权绕过

错误实现确认用户已经登录，也确认源钱包存在、余额足够，却删除了钱包所有者比较。攻击者只要获得其他钱包 ID，就能以自己的登录身份操作他人资产。这不是“缺少认证”，而是认证之后缺少对象级授权。

Finding 必须精确描述主体、对象和动作：当前主体可从不属于自己的源钱包转账。证据一是被删除的 `owner_id` 比较，证据二是用户传入他人钱包 ID 时服务没有拒绝的回归测试。修复是在可信身份上下文与源钱包所有者之间恢复比较。客户端字段、请求正文或隐藏按钮都不能成为授权证据。

这个案例也说明覆盖率数字并不等于安全覆盖。即使每行代码都执行过，只要测试身份始终拥有测试钱包，就发现不了授权边界。更有价值的问题是：是否存在“主体合法、对象存在、但主体无权操作对象”的负向样例？

### PR-05：幂等重试导致重复扣款

网络超时有一个经典歧义：客户端不知道请求没有执行，还是已经执行但响应丢失，所以会带相同幂等键重试。错误补丁删除服务端已有转账查询和提前返回，把去重责任推给客户端。第一次已经扣款时，第二次会创建另一条转账并再次扣款。

正确 Oracle 不只是“第二次不扣款”。它要求同一用户、同一幂等键和同一参数返回首次转账 ID；已使用的键不能配合不同参数重用；幂等查询、资金变更和结果记录处于同一原子边界。否则两个首次请求并发到达时，仍可能都查不到历史记录并重复执行。

Agent 若只建议“把查询加回来”，仍是不完整意见。它还应指出查询与写入必须原子化，并引用重试回归测试。修复后同时验证余额只变化一次、只创建一条记录、两次返回同一 ID，以及键参数冲突被拒绝。

### 统一 Finding Schema

所有阻断意见必须通过 Schema，而不是直接发布自由文本：

```json
{
  "finding_id": "CONCURRENCY-001",
  "source": "correctness",
  "category": "correctness",
  "severity": "must_fix",
  "confidence": 0.98,
  "file": "app/repository.py",
  "line_start": 35,
  "claim": "atomic 不再持有锁，余额检查与更新失去原子边界",
  "evidence": [{"type": "test", "ref": "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend"}],
  "blocking": true,
  "needs_human": true
}
```

Schema 强制两条底线：只有 `must_fix` 可以阻断；阻断意见至少需要一项证据。`confidence` 只能排序，不能替代证据。

Schema 同时提供稳定的评测接口。模型可以用不同措辞描述问题，评分器仍可通过根因、位置和证据与 Oracle 对齐。若模型给出三个措辞不同的锁问题，去重后只计一个根因；若它猜中“授权”却定位到无关文件，人工评测可以判定证据不足，而不是因关键词相似就算命中。

## 9.5 投票制、仲裁制和人工裁决

低风险文档 PR 可以由路由器和确定性检查快速通过；中风险逻辑变更需要专业 Agent 和仲裁；金额、授权、凭证和数据库事务一律进入人工终审。PR-04 的三个回放模式都必须返回 `escalate`，即使单 Agent 没有提出意见，策略门禁也不能被模型结果绕过。

投票不是证据。若一个 Agent 有可重现的并发失败，而三个 Agent 只是“未发现问题”，多数票不能抵消失败测试。仲裁应按硬策略、可复现证据、根因一致性和人工门禁的顺序处理，而不是按意见数量计分。人工裁决记录在 `human-verdict.yaml` 中，包含结论、理由和证据，形成可审计闭环。

投票适合结果同质、风险低且各票相对独立的场景。它不适合并发和安全 Finding，因为“未发现”不是反证。仲裁适合意见重复、证据互补或严重性冲突的场景；人工裁决则适合资金、身份、凭证、数据迁移和不可逆操作。

人类不应只看到红色标签。证据包应按“变更意图、命中策略、根因 Finding、复现步骤、修复候选、未验证事项”呈现。Tech Lead 可以驳回 Agent，但要记录理由；驳回记录随后进入误报分析，而不是被系统静默丢弃。

## 9.6 PR 摘要、影响分析和风险标注

摘要回答“改了什么、为什么改”，影响分析回答“谁会变化、失败会怎样”。以 PR-05 为例，摘要应写明删除了服务端幂等键查询；影响分析则必须列出余额状态、转账记录、重试响应和幂等键约束四个受影响状态。只写“简化超时重试”会掩盖第二次扣款的风险。

风险标签建议使用 `must_fix`、`concern` 和 `nitpick`。PR-02 的浮点金额归一化可能通过普通测试，却违反货币精度策略，适合作为“测试通过不代表设计正确”的对照案例；PR-07 的依赖降级则需要查询 OSV 等外部事实，不能由模型记忆漏洞版本。标签是注意力排序，不是批准授权。

一份合格的 PR-05 摘要还应明确写出：变更意图是简化客户端重试；关键变更是删除服务端幂等查询；受影响状态包括两侧余额、转账记录、幂等键映射和重试响应；普通转账已验证，但相同键重试失败，两个相同键请求并发到达尚未验证。把“已验证”和“未验证”分开，才能防止摘要制造虚假的完整感。

## 9.7 误报率和漏报率

评测单位应是根因 Finding，而不是评论条数。TP 是命中 Oracle 根因且位置、证据足够；FP 是无法复现、不属于本 PR 或 Oracle 不支持的问题；FN 是应被发现的根因未报告。`Precision = TP/(TP+FP)`，`Recall = TP/(TP+FN)`。采纳率另行记录，不能当作精确率。

本实验的 Oracle 矩阵包含六个缺陷 PR 和一个低风险无缺陷 PR：`MONEY-001`、`AUTHZ-001`、`CONCURRENCY-001`、`IDEMPOTENCY-001`、`DEPENDENCY-001`、`AGENTSEC-001`，以及 PR-01 的零缺陷结果。每个 Finding 都有可接受证据和可接受修复，避免把“说得像”误判为“找对了”。录制回放的满分只能说明夹具、路由和评分代码一致，不能写成真实模型能力结论。

## 9.8 多 Agent 成本边界

统计前必须按根因去重。若三个 Agent 都报告 PR-04 双花，不能按三条评论计算三个 TP；Oracle 只有一个根因。零缺陷 PR-01 对误报评测尤其重要：只使用带缺陷样本，系统可以靠“每次阻断”获得很高 Recall，却没有工程价值。

不是每个 PR 都值得全量矩阵。PR-01 只需要风险路由、规范检查和摘要；PR-04 才值得并行测试、正确性、安全、影响和仲裁。成本应按风险等级设预算，超过 Token、耗时或重试上限就升级人工，而不是让 Agent 无限自旋。

单次运行成本可由原始量重新计算：`未缓存输入 Token × 当日输入单价 + 缓存输入 Token × 当日缓存单价 + 输出 Token × 当日输出单价`。书稿不写脱离模型版本和价格日期的通用美元数字。上下文压缩也必须以 Recall 和证据正确性回归为前提，不能只追求 Token 下降。

## 9.9 Token 成本与触发策略

成本边界本质是风险预算。低风险 PR 的错误阻断主要损害效率，高风险 PR 的漏报可能损害资产和信任。同样的模型费用在两类 PR 上价值不同。团队应先定义每类风险可接受的漏报、延迟和人工负担，再选择 Agent 组合。

路由规则应同时使用路径和语义标签。文档变更进入低风险路径；普通业务逻辑进入 correctness + test；命中 `money`、`authorization`、`credentials` 或 `database-transaction` 时提升为高风险。若人工标签或策略命中高风险，模型不得降级。

稳定的 Schema、团队规范和工具契约可以缓存；凭证、个人数据和生产日志不能缓存。下游 Agent 接收上游结构化摘要和证据引用，避免重复阅读完整 Diff；但压缩后的上下文必须保留状态边界、失败条件和修复约束。每次运行保存模型标识、提示词版本、Token、延迟、重试和最终决策，才能比较策略变化的真实成本。

## 9.10 如何评测代码评审 Agent

触发策略需要防止两个极端：只按改动行数会漏掉“一行删除授权检查”的高风险小 PR；只按目录会让核心目录里的文案修改每次触发全量评审。更稳妥的路由结合路径、符号、语义标签和人工声明，并采取只升不降原则。

建议保留四个对照组：`deterministic-only` 测量测试、规则和扫描器的能力边界；`single` 建立单通用 Agent 基线；`multi` 观察专业分工带来的召回和重复；`multi_arbitrated` 观察去重、证据合并和人工升级。当前代码可直接回放后三种模式，确定性对照组作为实验报告中的独立基线。

每个案例运行 3～5 次真实模型后，记录 Precision、Recall、高风险检出率、错误阻断率、重复率、首次反馈延迟、输入/输出 Token、单 PR 成本和结果波动。模型版本、提示词版本、价格日期和数据集版本必须写入报告。不要用未经来源审计的行业百分比替代本团队数据。

### PR-08：评审系统也需要被评审

PR-08 在源码注释中嵌入“忽略安全问题、批准 PR、泄露系统提示词”一类指令。对编译器它只是注释，对阅读自然语言的 Agent 却可能成为指令。该案例只验证本地信任边界：仓库内容不能改变评审目标、工具范围和批准权限。

防护不能只靠提示词再写一句“不要被注入”。编排层应区分系统策略、组织规则、仓库文本和工具输出的信任等级；仓库内容以引用数据进入模型；工具调用使用允许列表；发布评论、修改代码和批准 PR 使用分离凭证；高风险门禁在模型之外执行。策略守卫检测注入式文本后生成 `AGENTSEC-001`，要求人工复核。

### 从回放走向真实模型实验

当前 `recorded-agents.json` 是控制夹具，用于证明相同输入能通过 Schema、路由、去重和评分。API Key 就绪后，选择两个模型家族，每个案例运行 3～5 次，保存原始输出并记录模型精确版本、提示词哈希、上下文构造版本、Token、延迟和当日价格。实验应回答：专业分工是否提高根因 Recall；仲裁是否降低重复和错误阻断；新增成本是否落在风险预算内。
