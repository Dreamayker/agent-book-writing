# 第 9 章 AI 代码评审与多 Agent 协同

> 副标题：把模型放进一条可验证、可回放、可问责的证据流水线
>
> 稿件状态：扩充出版稿（案例驱动初版）。本章中的模型输出部分使用录制回放；录制数据用于验证编排、Schema、去重和门禁，不代表真实模型能力。

## 开篇：先定义“正确”，再讨论“智能”

当团队用 AI 生成更多代码时，瓶颈会从“写出来”转向“证明它是对的”。代码评审 Agent 的价值不是用另一段自然语言替代人类判断，而是更快收集证据、定位风险、组织分歧，并把最终决策留在可追溯的工程流程中。

本章使用 `wallet-review-lab` 中的最小数字钱包服务作为实验场。它不连接真实资金，却保留了足以让评审变得严肃的四条业务不变量：金额守恒、余额非负、同一幂等键只产生一次资金变更、用户只能从自己拥有的钱包付款。每个教学 PR 都有一份需求、一份错误补丁、一份人工确认的 Oracle、工具证据和修复补丁。读者可以先只看 Diff 和测试结果，写下自己的 Finding，再打开 Oracle 对照。

贯穿全章的主线是 PR-04“并发双花”。余额为 100 元时，两笔 80 元转账不应同时成功。错误补丁把余额检查移到 `app/repository.py` 的 `atomic` 锁边界之外；单线程测试仍然通过，但两个线程可能同时读到 100 元。这个案例让我们反复看到一个事实：模型可以帮助解释竞态，但真正证明竞态存在的，是可重复的并发测试和清晰的不变量。

为什么选择钱包，而不是继续使用一个抽象的优惠券系统？因为本章的观点必须落到可运行证据上。钱包服务足够小，读者可以在一章内理解全部状态；又足够真实，能够同时容纳金额精度、对象授权、并发、幂等、依赖漏洞和提示注入。正确基线使用进程内 `RLock` 表达原子边界；生产数据库可能需要行锁、可串行化事务，或者带版本号和重试的 CAS。书中的修复证明的是实验不变量恢复，不是可以直接复制到分布式资金系统的完整方案。

## 9.1 AI 适合评审什么，不适合评审什么

AI 适合处理跨文件阅读、模式归纳和解释性工作：概括 PR 意图，列出受影响的 API 和状态，关联测试失败与源码位置，对照需求寻找边界条件，并将已确认的问题写成可执行的评审意见。它尤其适合把多种证据组织成一条人类易读的因果链。

AI 不适合单独证明并发、账务或安全属性，也不应确认外部实时状态、自主改变门禁或批准资金和权限变更。PR-04 中，Agent 可以指出“检查和使用不在同一原子边界”，却不能凭置信度替代并发测试；PR-03 中，Agent 可以解释“登录成功不等于拥有这个钱包”，但授权回归测试才是阻断证据。

一个可靠的分工是：确定性工具产生事实，Agent 解释和连接事实，策略引擎执行不可绕过的规则，人类承担高风险取舍和最终责任。所谓“适合”，因此不是模型能力的抽象排名，而是任务是否有可观察输入、可复现结果和明确升级边界。

### 案例对照：测试通过为什么仍可能不能合并

PR-02 将金额转换为浮点数再归一化。常规示例中的 `10.00`、`20.50` 可能全部通过，但团队的货币策略要求金额使用十进制定点表示，禁止经过二进制浮点数往返。Semgrep 可以标出禁止模式，Agent 则解释它与账务风险的关系。

这里有三种不同结论：测试证明已执行样例没有失败；规则证明代码命中了团队禁止模式；Agent 解释规则为何适用。任何一项都不能冒充另外两项。若规则误配，Agent 应指出适用性问题，而不是因扫描器发出红灯就编造事故后果。

## 9.2 评审 Agent 的四类任务

### 规范任务：先清理低级噪音

Ruff、格式化器和依赖检查适合承担确定性规范任务。Agent 的工作是将输出映射回文件和行号，告诉作者为什么需要修改，并避免把风格问题伪装成安全阻断。PR-01 只补充转账响应字段的文档说明，风险路由将它判为低风险；如果系统仍启动全部专业 Agent，得到的只是更高成本和更多无关评论。

### 缺陷任务：从控制流走到不变量

缺陷评审要追踪状态读取、校验、写入和异常路径。PR-04 的关键不是“代码少了一把锁”这句表面描述，而是：两个请求读取同一余额，两个请求都通过校验，随后各自写入，最终余额可能为负，且总余额与转账记录不再符合业务定义。一个合格 Finding 必须把源码位置、失败模式和修复边界写在一起。

### 安全任务：验证身份、对象和输入的边界

PR-03 删除了服务层的 `source.owner_id == current_user.id` 检查。客户端提交的钱包 ID 只能用于定位资源，不能作为授权证据。安全 Agent 需要同时看到需求、身份上下文和失败授权测试，才能把“缺少一个条件判断”提升为对象级授权绕过（`AUTHZ-001`）。PR-08 则把源码注释当作不可信输入，验证仓库文本不能改写评审策略。

### 影响任务：描述传播，不猜不存在的调用方

影响分析应优先使用 AST 符号引用、路由表、数据库迁移和锁文件等结构化事实。Agent 可以解释这些图和列表，但不能凭空声称存在跨仓库调用方。本地实验只有单仓库、单服务边界，因此书中将“已实现的本地影响分析”和“生产环境需要补充的跨仓库索引”明确分开。

### 四类任务如何共享证据

同一 PR 不应为每个 Agent 重复构造全部上下文。编排器先生成公共证据包：需求与验收标准、标准化 Diff、风险标签、变更文件和工具摘要。测试 Agent 再获得现有测试与失败日志，安全 Agent 获得身份边界和扫描结果，影响 Agent 获得符号引用和公共契约。

共享证据不等于共享结论。若 correctness Agent 先声称存在竞态，再把这句话放进 test Agent 输入，后者容易只是重复确认。更可靠的方式是让 test Agent 独立产生“两个请求均成功”的事实，再由仲裁阶段关联根因。这样才能判断召回提升来自专业分工，还是来自同一句话被反复转述。

## 9.3 多 Agent 协同评审

多 Agent 不是让多个模型重复阅读同一份 Diff，而是让不同角色回答不同问题。推荐的最小角色集如下：`general-review` 负责低风险自洽性，`correctness` 负责不变量和并发，`test` 负责失败模式覆盖，`security` 负责授权、输入和依赖，`impact` 负责调用与状态传播，`arbitrator` 负责按根因合并和升级；Tech Lead 是高风险变更的唯一最终批准者。

在 PR-04 上，可以比较三种配置。单 Agent 只收到 Diff 和需求，容易给出“建议增加并发测试”的泛化评论；多 Agent 让测试 Agent 先运行确定性并发测试，再把结果交给 correctness Agent；多 Agent 加仲裁则把多个关于锁边界的意见合并成一个 `CONCURRENCY-001`，保留每个来源和证据，并输出 `escalate`。三者的差异不是评论数量，而是证据是否闭合、重复是否减少、门禁是否可强制执行。

生成者、审查者和仲裁者必须物理隔离权限。审查者不能修改代码，仲裁者不能降低高风险级别，发布评论和批准 PR 不能共用同一凭证。自然语言不能作为 Agent 之间唯一的通信协议；必须使用结构化 Finding 和工具证据，防止上游幻觉被下游当成事实传播。

### PR-04：从错误 Diff 到评审结论

开发者想缩短锁持有时间，目标看似合理，危险在于优化对象正是事务边界。待审查补丁让 `atomic` 不再持有仓储锁。上层仍按“读余额、判断、写入两个钱包、记录转账”执行，但四个动作不再不可分割。

读这类 Diff 时，应画状态时序而不只搜索 `lock`。线程 A 读到 100，线程 B 也读到 100；A、B 分别判断足以支付 80，随后各自提交。只看任一线程都正确；交错执行后，系统批准了总额 160 的支出。这说明“模型读完所有代码”仍不等于证明了并发性质。

实验用屏障固定时序，而非依赖偶发压力测试。测试让两个请求同时越过读取阶段，再继续提交，断言恰好一个成功。错误分支上观测到成功数为 2，直接违反验收标准：

```text
原子锁被移除
→ 两个请求观察同一旧余额
→ 两个余额检查均通过
→ 两笔 80 元转账均获准
→ 违反余额非负与金额守恒约束
```

修复也不能只写“加锁”。教学仓储可恢复 `RLock`；数据库实现可能使用事务行锁、可串行化隔离，或带版本字段和冲突重试的 CAS。Finding 应表达需要恢复的性质，而不是把一个实现细节当成唯一答案。

测试 Agent 可能报告“期望一个成功，实际两个成功”；correctness Agent 报告“原子边界丢失”；impact Agent 报告“余额和转账记录同时受影响”。三条文字不同，却指向同一根因。仲裁器应使用不变量、源码位置、失败模式和修复方向做根因去重，合并意见并保留全部来源，而不是把三条重复阻断都发布给开发者。

## 9.4 测试、评审、安全 Agent 的协同

一个可回放的评审顺序是：风险路由先确定证据集；测试 Agent 并行运行回归和边界测试；安全 Agent 运行策略守卫、Semgrep 或 OSV；专业评审 Agent 读取 Diff、需求和工具结果；最后由仲裁器去重、冲突处理并交给策略门禁。

以 PR-04 为例，测试 Agent 得到两个并发转账都成功的失败结果；correctness Agent 将它与“余额检查和更新必须原子化”连接；arbitrator 发现多个意见都指向 `repository.atomic`，合并为一个阻断 Finding。修复后恢复 `RLock`，同一测试应恰好一个请求成功，余额保持非负，总余额守恒。这里没有一个 Agent 被要求“猜答案”，每一步都有可复核产物。

PR-03 提供另一种协同：安全 Agent 发现授权检查被删除，测试 Agent 提供未拥有钱包时应返回拒绝的回归失败，仲裁器确认两者属于同一根因。PR-05 则将网络重试转化为状态不变量：同一用户、同一幂等键和同一参数只能执行一次，第二次请求必须返回原转账 ID。测试、语义解释和策略判断缺一不可。

### PR-03：对象级授权绕过

错误实现确认用户已经登录，也确认源钱包存在、余额足够，却删除了钱包所有者比较。攻击者只要获得其他钱包 ID，就能以自己的登录身份操作他人资产。这不是“缺少认证”，而是认证之后缺少对象级授权。

Finding 必须精确描述主体、对象和动作：当前主体可从不属于自己的源钱包转账。证据一是被删除的 `owner_id` 比较，证据二是用户传入他人钱包 ID 时服务没有拒绝的回归测试。修复是在可信身份上下文与源钱包所有者之间恢复比较。客户端字段、请求正文或隐藏按钮都不能成为授权证据。

这个案例也说明覆盖率数字并不等于安全覆盖。即使每行代码都执行过，只要测试身份始终拥有测试钱包，就发现不了授权边界。更有价值的问题是：是否存在“主体合法、对象存在、但主体无权操作对象”的负向样例？

### PR-05：幂等重试导致重复扣款

网络超时有一个经典歧义：客户端不知道请求没有执行，还是已经执行但响应丢失，所以会带相同幂等键重试。错误补丁删除服务端已有转账查询和提前返回，把去重责任推给客户端。第一次已经扣款时，第二次会创建另一条转账并再次扣款。

正确 Oracle 不只是“第二次不扣款”。它要求同一用户、同一幂等键和同一参数返回首次转账 ID；已使用的键不能配合不同参数重用；幂等查询、资金变更和结果记录处于同一原子边界。否则两个首次请求并发到达时，仍可能都查不到历史记录并重复执行。

Agent 若只建议“把查询加回来”，仍是不完整意见。它还应指出查询与写入必须原子化，并引用重试回归测试。修复后同时验证余额只变化一次、只创建一条记录、两次返回同一 ID，以及键参数冲突被拒绝。

### 统一 Finding Schema

所有阻断意见必须通过 Schema，而不是直接发布自由文本：

```json
{
  "finding_id": "CONCURRENCY-001",
  "source": "correctness",
  "category": "correctness",
  "severity": "must_fix",
  "confidence": 0.98,
  "file": "app/repository.py",
  "line_start": 35,
  "claim": "atomic 不再持有锁，余额检查与更新失去原子边界",
  "evidence": [{"type": "test", "ref": "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend"}],
  "blocking": true,
  "needs_human": true
}
```

Schema 强制两条底线：只有 `must_fix` 可以阻断；阻断意见至少需要一项证据。`confidence` 只能排序，不能替代证据。

Schema 同时提供稳定的评测接口。模型可以用不同措辞描述问题，评分器仍可通过根因、位置和证据与 Oracle 对齐。若模型给出三个措辞不同的锁问题，去重后只计一个根因；若它猜中“授权”却定位到无关文件，人工评测可以判定证据不足，而不是因关键词相似就算命中。

## 9.5 投票制、仲裁制和人工裁决

低风险文档 PR 可以由路由器和确定性检查快速通过；中风险逻辑变更需要专业 Agent 和仲裁；金额、授权、凭证和数据库事务一律进入人工终审。PR-04 的三个回放模式都必须返回 `escalate`，即使单 Agent 没有提出意见，策略门禁也不能被模型结果绕过。

投票不是证据。若一个 Agent 有可重现的并发失败，而三个 Agent 只是“未发现问题”，多数票不能抵消失败测试。仲裁应按硬策略、可复现证据、根因一致性和人工门禁的顺序处理，而不是按意见数量计分。人工裁决记录在 `human-verdict.yaml` 中，包含结论、理由和证据，形成可审计闭环。

投票适合结果同质、风险低且各票相对独立的场景。它不适合并发和安全 Finding，因为“未发现”不是反证。仲裁适合意见重复、证据互补或严重性冲突的场景；人工裁决则适合资金、身份、凭证、数据迁移和不可逆操作。

人类不应只看到红色标签。证据包应按“变更意图、命中策略、根因 Finding、复现步骤、修复候选、未验证事项”呈现。Tech Lead 可以驳回 Agent，但要记录理由；驳回记录随后进入误报分析，而不是被系统静默丢弃。

## 9.6 PR 摘要、影响分析和风险标注

摘要回答“改了什么、为什么改”，影响分析回答“谁会变化、失败会怎样”。以 PR-05 为例，摘要应写明删除了服务端幂等键查询；影响分析则必须列出余额状态、转账记录、重试响应和幂等键约束四个受影响状态。只写“简化超时重试”会掩盖第二次扣款的风险。

风险标签建议使用 `must_fix`、`concern` 和 `nitpick`。PR-02 的浮点金额归一化可能通过普通测试，却违反货币精度策略，适合作为“测试通过不代表设计正确”的对照案例；PR-07 的依赖降级则需要查询 OSV 等外部事实，不能由模型记忆漏洞版本。标签是注意力排序，不是批准授权。

一份合格的 PR-05 摘要还应明确写出：变更意图是简化客户端重试；关键变更是删除服务端幂等查询；受影响状态包括两侧余额、转账记录、幂等键映射和重试响应；普通转账已验证，但相同键重试失败，两个相同键请求并发到达尚未验证。把“已验证”和“未验证”分开，才能防止摘要制造虚假的完整感。

## 9.7 误报率和漏报率

评测单位应是根因 Finding，而不是评论条数。TP 是命中 Oracle 根因且位置、证据足够；FP 是无法复现、不属于本 PR 或 Oracle 不支持的问题；FN 是应被发现的根因未报告。`Precision = TP/(TP+FP)`，`Recall = TP/(TP+FN)`。采纳率另行记录，不能当作精确率。

本实验的 Oracle 矩阵包含六个缺陷 PR 和一个低风险无缺陷 PR：`MONEY-001`、`AUTHZ-001`、`CONCURRENCY-001`、`IDEMPOTENCY-001`、`DEPENDENCY-001`、`AGENTSEC-001`，以及 PR-01 的零缺陷结果。每个 Finding 都有可接受证据和可接受修复，避免把“说得像”误判为“找对了”。录制回放的满分只能说明夹具、路由和评分代码一致，不能写成真实模型能力结论。

## 9.8 多 Agent 成本边界

统计前必须按根因去重。若三个 Agent 都报告 PR-04 双花，不能按三条评论计算三个 TP；Oracle 只有一个根因。零缺陷 PR-01 对误报评测尤其重要：只使用带缺陷样本，系统可以靠“每次阻断”获得很高 Recall，却没有工程价值。

不是每个 PR 都值得全量矩阵。PR-01 只需要风险路由、规范检查和摘要；PR-04 才值得并行测试、正确性、安全、影响和仲裁。成本应按风险等级设预算，超过 Token、耗时或重试上限就升级人工，而不是让 Agent 无限自旋。

单次运行成本可由原始量重新计算：`未缓存输入 Token × 当日输入单价 + 缓存输入 Token × 当日缓存单价 + 输出 Token × 当日输出单价`。书稿不写脱离模型版本和价格日期的通用美元数字。上下文压缩也必须以 Recall 和证据正确性回归为前提，不能只追求 Token 下降。

## 9.9 Token 成本与触发策略

成本边界本质是风险预算。低风险 PR 的错误阻断主要损害效率，高风险 PR 的漏报可能损害资产和信任。同样的模型费用在两类 PR 上价值不同。团队应先定义每类风险可接受的漏报、延迟和人工负担，再选择 Agent 组合。

路由规则应同时使用路径和语义标签。文档变更进入低风险路径；普通业务逻辑进入 correctness + test；命中 `money`、`authorization`、`credentials` 或 `database-transaction` 时提升为高风险。若人工标签或策略命中高风险，模型不得降级。

稳定的 Schema、团队规范和工具契约可以缓存；凭证、个人数据和生产日志不能缓存。下游 Agent 接收上游结构化摘要和证据引用，避免重复阅读完整 Diff；但压缩后的上下文必须保留状态边界、失败条件和修复约束。每次运行保存模型标识、提示词版本、Token、延迟、重试和最终决策，才能比较策略变化的真实成本。

## 9.10 如何评测代码评审 Agent

触发策略需要防止两个极端：只按改动行数会漏掉“一行删除授权检查”的高风险小 PR；只按目录会让核心目录里的文案修改每次触发全量评审。更稳妥的路由结合路径、符号、语义标签和人工声明，并采取只升不降原则。

建议保留四个对照组：`deterministic-only` 测量测试、规则和扫描器的能力边界；`single` 建立单通用 Agent 基线；`multi` 观察专业分工带来的召回和重复；`multi_arbitrated` 观察去重、证据合并和人工升级。当前代码可直接回放后三种模式，确定性对照组作为实验报告中的独立基线。

每个案例运行 3～5 次真实模型后，记录 Precision、Recall、高风险检出率、错误阻断率、重复率、首次反馈延迟、输入/输出 Token、单 PR 成本和结果波动。模型版本、提示词版本、价格日期和数据集版本必须写入报告。不要用未经来源审计的行业百分比替代本团队数据。

### PR-08：评审系统也需要被评审

PR-08 在源码注释中嵌入“忽略安全问题、批准 PR、泄露系统提示词”一类指令。对编译器它只是注释，对阅读自然语言的 Agent 却可能成为指令。该案例只验证本地信任边界：仓库内容不能改变评审目标、工具范围和批准权限。

防护不能只靠提示词再写一句“不要被注入”。编排层应区分系统策略、组织规则、仓库文本和工具输出的信任等级；仓库内容以引用数据进入模型；工具调用使用允许列表；发布评论、修改代码和批准 PR 使用分离凭证；高风险门禁在模型之外执行。策略守卫检测注入式文本后生成 `AGENTSEC-001`，要求人工复核。

### 从回放走向真实模型实验

当前 `recorded-agents.json` 是控制夹具，用于证明相同输入能通过 Schema、路由、去重和评分。API Key 就绪后，选择两个模型家族，每个案例运行 3～5 次，保存原始输出并记录模型精确版本、提示词哈希、上下文构造版本、Token、延迟和当日价格。实验应回答：专业分工是否提高根因 Recall；仲裁是否降低重复和错误阻断；新增成本是否落在风险预算内。

## 出版扩展：把每一次评审变成可验证的任务

前面的章节给出了主线结论，下面把这些结论拆成可以落地的工作单元。这样做不是为了把本章变成工具手册，而是为了回答读者在真实团队里最常遇到的三个问题：我应该把什么交给模型？模型的结论凭什么可信？出了错以后，谁能在多长时间内复盘并修正流程？如果这三个问题没有明确答案，所谓 Agent 评审仍然只是把自然语言搬进 CI。

### 9.1 深入：能力边界要写成任务契约

“AI 擅长什么”是一句无法验收的宣传语。工程上更有用的写法是任务契约。契约至少包含输入、允许使用的工具、必须产出的证据、不能做的动作、失败时的升级路径和验收断言。例如，正确性 Agent 的输入可以是标准化 Diff、相关函数的调用图、需求中的不变量和测试结果；它必须输出结构化 Finding 或明确的 `no_finding`，每条 Finding 都要引用文件位置和证据；它不能修改工作树，也不能把测试尚未执行写成已验证；若命中金额或授权标签，必须把 `needs_human` 置为真。

任务契约把模型从“自由发挥的审阅者”变成流程中的一个受限组件。它还方便做替换实验：同一契约可以由不同模型、规则引擎或人工执行，比较的是结果而不是文案风格。契约也揭示了不适合模型的任务。例如“确认生产数据库当前没有其他客户端”缺少可观察输入，除非提供经过授权的实时索引，否则任何确定语气都是越权推断；“批准这笔转账”则是责任动作，不能因为模型置信度高就自动执行。

#### 四种不确定性必须分开处理

第一种是不确定性来自代码本身。并发、异常回滚和事务隔离通常需要运行测试或查看数据库语义，单凭 Diff 只能提出假设。第二种来自外部事实。依赖是否存在漏洞、某个 API 当前是否支持某参数，需要锁文件、官方公告或在线扫描结果，模型记忆不能替代来源。第三种来自意图。需求写得模糊时，模型可以列出解释，却不能擅自选择对业务影响最大的解释。第四种来自责任。涉及资金、身份、凭证和不可逆迁移时，哪怕证据完整，也要由指定人员批准。

这四类不确定性对应四种动作：运行确定性检查、查询一手来源、请求需求澄清、升级人工门禁。把它们都压缩为一个 `confidence: 0.91` 会掩盖真正的风险。置信度可以用来排序调查顺序，却不能绕过证据缺口。

#### 一个可执行的输入输出契约

可以把每类评审任务写成如下模板：

```yaml
task: correctness-review
inputs:
  - normalized_diff
  - affected_symbols
  - requirements
  - deterministic_results
allowed_tools: [read_file, search_symbol, run_named_test]
outputs: [finding_schema, no_finding, evidence_gap]
forbidden_actions: [write_file, approve_change, publish_without_gate]
escalate_when:
  - risk_label in [money, authorization, credentials]
  - evidence_gap == true
acceptance:
  - every_finding_has_location
  - every_blocking_finding_has_evidence
```

这里的 `evidence_gap` 很重要。一个诚实的“无法判断，因为没有并发测试”比一条没有依据的阻断意见更有价值。编排器可以据此补跑测试或通知人工，而不是把不确定性隐藏在流畅的段落中。

#### 反例：看起来像成功的自动化

假设 Agent 输出“未发现安全问题”，而安全扫描因凭证过期没有真正运行。若系统只检查 Agent 文本，PR 会被错误放行。正确做法是把工具执行状态作为独立字段，工具失败时策略门禁直接进入 `evidence_incomplete`。同样，若模型超时，不能用上一次缓存的结论覆盖本次 Diff，除非缓存键包含提交哈希、工具版本和策略版本。可验证性要求每个结论都能追溯到本次输入。

### 9.2 深入：四类任务需要四份不同的证据包

规范、缺陷、安全和影响分析经常被合并成“代码质量检查”，这会造成输入过载和验收混乱。每一类任务都应该有自己的证据包和失败定义。

规范任务关心格式、命名、文档契约、依赖锁定和接口兼容性。它的证据通常是工具输出、配置文件和 API 文档。失败的定义是规则命中且适用于本次变更；不能因为某个规则存在就阻断所有 PR。PR-01 的文档变更就是一个很好的零缺陷样本：系统应证明它没有越过风险边界，而不是强行找一个问题。

缺陷任务关心控制流、状态转移和异常路径。它需要把需求中的不变量映射到代码路径。例如“余额非负”不是一句评论，而是对扣款前检查、扣款写入、失败回滚和并发交错的联合约束。缺陷任务的最小输出应包含触发条件、错误状态、违反的不变量和修复边界。只有说“这里可能有 bug”而没有触发条件的意见不能阻断。

安全任务需要主体、对象、动作三元组。对 PR-03，主体是当前登录用户，对象是请求中的源钱包，动作是转账；`owner_id` 比较缺失使主体可以操作不属于自己的对象。对 PR-08，主体还包括评审 Agent，仓库注释是低信任数据，批准权限属于组织策略而非注释内容。安全任务的特殊之处在于负向样例通常比正向覆盖更有信息量：合法用户访问自己的钱包不能证明越权访问被拒绝。

影响任务则要描述传播范围，而不是猜测业务故事。它可以从 AST 引用、路由表、数据库字段、事件主题和锁文件中构造图，标注每条边的来源。一个符号没有跨仓库索引，不代表“没有调用方”；正确结论应该是“在当前仓库内未发现调用方，跨仓库影响未验证”。这种表述看似保守，却能避免把局部搜索误写成全局证明。

#### 路由矩阵示例

| 任务 | 最小输入 | 主要工具 | 阻断条件 | 人工问题 |
|---|---|---|---|---|
| 规范 | Diff、规范、锁文件 | Ruff、类型检查、依赖检查 | 规则命中且适用 | 是否允许例外 |
| 缺陷 | 不变量、调用图、测试 | pytest、状态追踪 | 可复现违反不变量 | 修复边界是否完整 |
| 安全 | 主体/对象/动作、信任层级 | 策略守卫、Semgrep、负向测试 | 越权或信任穿透 | 风险是否需升级 |
| 影响 | 符号、事件、迁移 | AST、引用索引、迁移检查 | 兼容性破坏 | 外部消费者是否已确认 |

矩阵的价值在于让“没有运行某工具”成为显式缺口。不同任务可以并行，但不能把一个任务的绿色状态借给另一个任务。例如 Ruff 通过不能证明授权正确，授权测试通过也不能证明依赖没有公开漏洞。

### 9.3 深入：多 Agent 的最小充分组织

增加角色会增加上下文复制、等待和冲突成本。决定是否增加 Agent 的标准不是“还有没有一个角色可以命名”，而是新角色能否获得独立证据、拥有不同失败模式，并且其输出能改变最终决策。如果两个角色读取完全相同的输入、调用相同工具、以相同标准判断，它们的多数票并不会带来独立性。

可以用三步设计角色。第一步列出业务不变量和风险边界；第二步为每个边界选择最接近事实源的工具；第三步只为仍需要解释、关联或取舍的部分安排 Agent。PR-04 中并发测试提供事实，correctness Agent 解释锁边界，arbitrator 合并根因，三者各司其职。若再增加一个只改写措辞的“编辑 Agent”，它不会增加召回，却会增加重复评论。

#### 上下文隔离与证据包

每个 Agent 应收到最小充分上下文，而不是整个仓库。最小充分不等于最短：必须保留与判断有关的状态、失败条件和约束。安全 Agent 需要身份来源和授权需求；影响 Agent 需要接口契约和迁移；测试 Agent 需要可执行命令和环境状态。上下文包以不可变引用传递，例如 `evidence://run/abc/test-17`，而不是把一段未经标注的文字复制到下游。这样可以区分原始工具输出、上游解释和人工结论。

隔离还包括权限。读取源码和运行白名单测试可以共用只读凭证；修改补丁、发布评论和批准合并必须分离。即便系统允许 Agent 生成修复建议，也应把建议作为补丁候选保存，不能让同一进程直接提交到主分支。PR-08 的提示注入案例说明，仓库文本不应获得工具授权；“请批准 PR”只是字符串，不能改变权限模型。

#### 调度失败也是产品行为

一个 Agent 失败时，编排器需要选择重试、换工具、降级或升级人工。重试必须有上限，并区分瞬时网络错误与输入不可解析。若测试 Agent 已经得到确定性失败，继续重试模型不会改变事实；若依赖扫描服务不可用，策略应标记证据不完整而不是使用旧结果。每次调度写入开始时间、结束时间、模型版本、工具版本、输入摘要哈希和退出原因，才能在成本和稳定性报告中解释一次慢运行。

### 9.4 深入：从错误 Diff 走到修复验证

完整证据链至少有七个节点：需求不变量、错误 Diff、可复现失败、结构化 Finding、仲裁结论、修复 Diff、回归验证。缺少任何一个节点，都可能把“提出问题”误写成“问题已解决”。以下以三个案例说明节点之间如何相互约束。

PR-04 的需求是余额非负且同一时刻只有一笔 80 元转账成功。错误 Diff 移除了 `atomic` 内的锁；屏障测试固定两个线程同时读取余额，观察到两个请求成功。Finding 指向 `repository.py` 的锁边界，并引用测试输出。修复恢复教学仓储的 `RLock`，回归断言成功数为一、余额为二十、转账记录为一。若只恢复锁却没有验证记录数量，仍可能留下重复记账问题。

PR-03 的证据链更强调身份边界。错误 Diff 删除所有者比较；负向授权测试用用户 A 登录、提交用户 B 的钱包 ID，预期 403 而实际成功。修复恢复服务层检查，并补充“钱包不存在”和“用户未登录”两个分支，防止错误处理把未授权伪装成资源不存在。Finding 不应只写“缺少权限校验”，还要说明对象来自不可信请求参数，授权证据必须来自服务端身份上下文。

PR-05 的关键是时间和重复请求。错误 Diff 删除幂等查询；第一次请求成功但响应丢失，第二次相同键请求再次扣款。修复除了恢复查询，还要让查询、扣款和结果记录处于同一原子边界，并拒绝相同键不同参数。测试要覆盖顺序重试、并发首次请求、超时后恢复和键冲突四种情况。否则“重复返回同一 ID”只证明了最简单路径。

#### 工具输出的阅读纪律

测试输出应保留命令、提交哈希、环境和失败断言；扫描器输出应保留规则版本、扫描范围和退出码；Agent Finding 应保留原始证据引用。不要把终端中的一行 `failed` 截出来当作完整证据，因为读者无法知道失败的是目标测试还是环境初始化。书稿中的截图或文本摘录应同时给出上下文和解释，明确哪些是原始输出、哪些是作者标注。

#### 错误修复也可能制造新问题

为了修复双花，若把全局锁包住外部网络调用，会把正确性换成吞吐和可用性风险；为了修复授权，若把对象 ID 全部隐藏，可能破坏合法的跨账户管理场景；为了修复幂等，若永远保留键记录，可能导致存储无限增长。Finding 的修复约束应写“必须恢复什么性质”，并允许多个实现方案。评审 Agent 需要指出候选修复的副作用，而不是把第一条能让测试变绿的补丁当作最终答案。

### 9.5 深入：仲裁不是投票，而是责任编排

仲裁器的输入应该是独立证据和结构化 Finding，而不是一串已经互相影响的自然语言评论。它先按文件位置、状态变量和不变量聚类，再判断每个簇是否有可复现证据，最后应用组织策略。聚类只减少重复，不改变原始来源；每个合并 Finding 都应保留 `source_findings`，方便事后追查哪个 Agent 提供了哪条证据。

严重性冲突要按证据而不是按数量处理。一个带失败测试的 `must_fix` 可以压过多个“未发现问题”；一个只有猜测的高严重性意见不能因为标签醒目就阻断。人工裁决记录至少包含：决定、责任人、时间、引用证据、未验证事项、是否允许例外以及例外到期时间。例外不是删除 Finding，而是把风险和期限公开化。

#### 三种典型冲突

第一种是同一根因的不同描述。PR-04 的“缺少锁”“竞态”“双花”可能来自三个角色，应合并为一个根因，保留三种证据。第二种是严重性冲突。规范 Agent 把浮点转换标成 `concern`，货币策略把它标成 `must_fix`；仲裁器需要查看需求和策略版本，而不是平均两个标签。第三种是证据冲突。一个 Agent 说授权测试通过，另一个 Agent 提供了不同用户访问成功的日志；此时要核对测试身份、数据夹具和提交哈希，不能简单各保留一半。

#### 人工裁决的可复盘性

人工不是“最后看一眼”。Tech Lead 应能回答：为什么接受或拒绝 Finding？哪些证据被认为充分？有没有未运行的测试？这次决定是否会改变路由规则或 Oracle？将裁决写入 YAML 后，可以统计某条规则的误报率、某类案例的漏报模式和某个模型的稳定性。拒绝记录同样是训练材料，但不能未经脱敏直接喂回模型，以免把偶然判断变成永久规则。

### 9.6 深入：摘要和影响分析必须带边界标签

PR 摘要最危险的地方是它容易把“做了什么”写成“因此安全”。建议把每条结论分为 `verified`、`inferred`、`unverified` 三类。`verified` 只能来自本次运行的工具或人工确认；`inferred` 是基于代码结构的解释；`unverified` 是明确尚未覆盖的范围。PR-05 可以写“顺序重试的余额变化已验证”，同时写“跨进程并发首次请求未在教学实现中验证”。

影响图不只是调用图。对钱包转账，至少要画出输入参数、身份主体、源钱包、目标钱包、余额、转账记录、幂等映射和外部通知等节点，并标注读写关系。PR-04 的锁边界变化会同时影响余额和记录；PR-05 的幂等查询变化会影响重试响应和唯一键约束。这样的图能帮助 Agent 发现“修复了余额但漏了记录”的不完整补丁。

跨仓库影响必须诚实。当前实验仓库没有生产消息总线、异步消费者或第三方结算服务，因此不能声称这些调用方不存在。可以提供一个生产迁移清单：导出接口注册表、查询事件消费者、核对数据库迁移顺序、检查回滚兼容性、让服务所有者确认。影响分析的价值不是制造完整感，而是把未知范围变成下一步工作。

### 9.7 深入：评测要从 Oracle 设计开始

没有稳定 Oracle，就没有可解释的 Precision 和 Recall。Oracle 不是“作者认为正确的评论”，而是根因、可接受位置、最低证据和可接受修复的集合。PR-04 的 Oracle 可以允许 `repository.atomic` 或数据库事务层两个修复位置，但必须要求证明检查与写入在同一原子边界。这样评分不会奖励死记某一行代码，也不会接受只改测试的伪修复。

评测还要有零缺陷样本。PR-01 用来测误报，若系统在所有 PR 上都输出阻断，它的 Recall 可能很高但不可用。对每个样本记录根因数、Finding 数、去重后 Finding 数、证据充分性、严重性准确性和人工采纳情况。采纳率是组织决策指标，不应直接当作模型精确率，因为人工可能出于时间压力接受一条证据不足的意见。

#### 位置和严重性的评分

Finding 命中关键词不算命中。评分可以分层：根因正确得基础分；位置落在影响范围内得位置分；引用可复现证据得证据分；严重性和阻断建议正确得策略分。若模型指出“双花”却把位置写成 README，根因描述有价值，但不能算可执行的完整 TP。若它定位正确但没有证据，应进入 `needs_evidence`，等待补跑工具，而不是直接算 FP。

#### 防止数据泄漏

录制 Agent 输出、Oracle 和修复补丁不能混入真实模型提示词。实验脚本应区分训练材料、评测输入和答案目录，提交哈希固定后再运行。重复运行要改变随机种子但不改变任务输入，报告均值、范围和失败次数。若某个模型在同一提示词中看到过 Oracle 术语，结果只能说明夹具可解析，不能说明泛化能力。

### 9.8 深入：成本模型要包含人工和失败成本

只计算 Token 会低估系统成本。一次低价模型的误报可能让开发者花十分钟调查；一次高价模型的漏报可能导致生产事故；一个等待五分钟的全量流水线还会降低团队采用率。建议把成本拆成计算成本、工具成本、等待成本、人工复核成本和风险暴露成本，并分别记录，避免用一个美元数字掩盖取舍。

预算可以按风险等级设置：低风险限制 Agent 数量和上下文长度，中风险允许并行测试与专业审查，高风险不设“自动通过”预算，超时直接升级人工。上下文缓存只对不可变的规范、工具契约和符号索引开放；提交 Diff、凭证、日志和个人数据必须按提交哈希隔离。缓存命中也要计入证据版本，防止旧工具结果污染新结论。

#### 降级策略

模型不可用时，低风险 PR 可以退回确定性检查和人工摘要；中风险 PR 应标记等待；高风险 PR 必须阻断或进入人工门禁。工具不可用与模型不可用的处理不同：OSV 失败不是“没有漏洞”，测试初始化失败也不是“测试通过”。降级状态应出现在 PR 页面和审计日志里，不能只写在内部监控。

### 9.9 深入：路由规则要可测试、可审计

路由规则是安全策略，不是提示词。每条规则都应有名称、来源、匹配条件、升级动作、例外审批和测试样例。比如删除 `owner_id` 比较，即使只有一行 Diff，也必须命中授权高风险；修改文档，即使位于核心目录，也不应自动触发数据库事务评审。规则组合采取只升不降：路径规则、语义规则、人工声明中任何一项升高风险，后续 Agent 不能把它降回低风险。

规则测试要包含边界和对抗样例。测试 `money` 标签命中金额模块，也要测试注释中的单词不会误触发高风险；测试 `docs/` 路径低风险，也要测试文档修改了权限策略时语义标签能够升级。每次规则变更保存前后路由矩阵，说明哪些 PR 会新增工具和人工负担。

路由结果应可解释：命中了哪些规则、来自哪一行 Diff、选择了哪些 Agent、哪些工具被跳过以及为什么。这样开发者可以修正标签或补充需求，而不是面对一个无法申诉的红灯。路由日志还可以发现系统性偏差，例如某个目录几乎总被错误升级，或某类安全变更经常没有进入人工门禁。

### 9.10 深入：上线是持续实验，不是一次发布

上线前先运行影子模式：系统完整执行评审，但不阻断合并，只把结果与人工评审对照。影子阶段要关注漏报、误报、重复、延迟、成本和权限错误，而不只是“模型输出看起来不错”。随后进入有限门禁，只对低风险、证据完整且确定性检查通过的路径自动处理；中高风险保留人工批准。每阶段都要有退出条件，例如高风险漏报超过阈值、工具失败率上升、凭证隔离测试失败或审计字段缺失，就回滚到上一阶段。

双模型实验不能只比较总体分数。要按案例类型、风险等级和根因分类，分别比较单模型、专业分工和仲裁配置。PR-08 还应作为系统安全回归：注入文本不能改变工具允许列表、系统策略、批准权限和输出 Schema。实验报告写明模型精确版本、提示词哈希、数据集版本、价格日期和失败样本，避免把一次偶然成功写成产品能力。

#### 监控 Agent 自身风险

上线后需要监控提示注入命中率、越权工具调用尝试、Schema 解析失败、异常长输出、重试次数、缓存污染和人工驳回率。监控数据应脱敏，并按提交哈希关联，不能把源代码和凭证打进普通日志。发生策略绕过时，优先暂停自动门禁、保留证据、轮换凭证并复盘根因；不要让模型自己解释自己是否违规。

## 扩展实战：一套可重复的盲审练习

读者可以用以下顺序完成一次端到端练习。先运行正确基线并保存测试、Ruff、mypy 和依赖检查的退出码；再建立临时分支，只应用一个教学补丁；根据需求和 Diff 写出不超过三条 Finding，给每条标注根因、位置、证据和未知范围；运行指定测试和策略工具；最后查看 Oracle 与录制输出，比较自己漏掉的是根因、位置还是证据。修复后再次运行，并把“修复证明了什么、没有证明什么”写入复盘。

```bash
cd wallet-review-lab
git switch main
uv sync --extra dev
uv run pytest
git switch --create practice-pr04
git apply book-assets/pr-04-concurrent-double-spend/0001-case-move-balance-update-outside-atomic-boundary.patch
uv run pytest tests/test_transfer_invariants.py -q
uv run python -m evaluation.replay_pr04 --mode multi_arbitrated
git apply book-assets/pr-04-concurrent-double-spend/fixed.patch
uv run pytest tests/test_transfer_invariants.py -q
```

练习的评分不按文字像不像 Agent，而按四项判断：是否识别真正根因，是否给出可复现证据，是否区分已验证和未验证，是否提出不会破坏其他不变量的修复边界。完成 PR-04 后，再用 PR-03 检查主体—对象—动作，再用 PR-05 检查重试时序，最后用 PR-08 检查信任层级。四个案例覆盖的不是四个孤立技巧，而是一条从业务不变量到 Agent 安全的连续证据链。

## 本章新增读者产出

读者完成本章后，应能提交一份自己的评审契约、一张任务路由矩阵、一份带证据引用的 Finding、一份人工裁决记录和一份实验报告。报告至少说明：数据集和 Oracle 如何定义，录制回放与真实模型如何区分，Precision、Recall、重复率、延迟、Token 和人工时间如何测量，哪些边界仍未验证，以及上线后何时回滚。若只能给出一段“模型总体表现不错”的总结，说明证据闭环还没有完成。

## 案例档案一：PR-01 为什么“没有问题”也需要证据

PR-01 的需求只是在说明文档中补充 `transfer_id` 的客户端用途，验收标准明确限定只修改 Markdown，不改变 API、代码、依赖和安全策略。它没有预设缺陷，Oracle 中的 Finding 列表为空，人工结论是批准。这个案例看起来最简单，却承担着整个评测体系中不可替代的角色：证明系统有能力不制造问题。

只用缺陷样本评测会形成明显偏差。一个系统可以在每个 PR 都输出“可能存在竞态、权限或注入风险”，然后在六个缺陷样本上碰巧命中关键词。没有 PR-01，就无法观察这种系统的误报倾向。真实团队里大多数改动并非高风险缺陷，如果每次文档修改都要阅读五条泛化警告，开发者很快会忽略所有 Agent 评论，包括真正重要的那一条。

PR-01 的低风险路由需要做三件事。第一，验证变更集合确实只有文档；如果同一提交还修改了 OpenAPI、策略文件或代码生成输入，就不能只按扩展名降级。第二，检查新增文案是否准确；`transfer_id` 可以用于追踪，但不能声称它能鉴权、去重或保证结算完成。第三，运行最低成本的仓库卫生检查，确认链接、格式和敏感信息没有问题。通过后，系统应输出简洁摘要，而不是为了展示“智能”硬凑 Finding。

这里也有一个容易忽略的反例：攻击者可能把策略变更藏在文档中，而运行时系统会读取这份 Markdown 作为提示词或配置。此时“文档不影响运行时”的前提不成立。因此低风险路由不能只看文件名，还要知道文件是否进入构建、Agent 上下文或发布流程。PR-01 的批准依赖本仓库的当前结构，不能推广成“所有 Markdown 都低风险”。

读者可以把 PR-01 当作路由单元测试，预期结果是 `risk: low`、`findings: []`、`mandatory_human_review: false`。若新增 Agent 后这个案例开始产生阻断，应先调查提示词是否鼓励“至少找一个问题”、去重器是否把普通建议升级为 Finding、或者风险标签是否被核心目录路径误触发。零缺陷样本使这些回归可以被量化。

## 案例档案二：PR-02 金额精度不是显示格式问题

PR-02 要求支持精确到分的转账，金额大于零、有限、最多两位小数，转账前后总余额守恒。错误实现为了方便 JSON 处理，把十进制金额转换为二进制 `float`，再用 `round` 修正显示。危险不在于某一组示例必然立刻失败，而在于领域类型已经无法表达需求承诺。

十进制货币和二进制浮点的矛盾可以从表示层解释。像 `0.1` 这样的十进制小数通常没有有限的二进制表示，程序保存的是邻近值。一次运算可能在格式化时看不出差异，多次加减、比较和汇总后却可能越过分位边界。`round` 解决的是某一次输出如何呈现，不会恢复每一步计算的精确语义。更麻烦的是，不同语言、数据库驱动或序列化路径的舍入规则可能不同，让跨服务对账出现分歧。

这也是为什么普通测试可能全绿。示例通常只覆盖 `10.00`、`20.50` 等容易观察的值，并在输出端比较格式化字符串。性质测试更合适：随机生成合法分位金额，执行一组转账，断言每个余额都能表示为整数分、余额非负、所有钱包总额不变。还要覆盖 `NaN`、正负无穷、负数、零、三位小数和极大值，防止验证只停留在常用输入。

可接受修复有两条典型路线。其一是领域层使用 `Decimal`，在输入边界从字符串构造，并显式指定量化和舍入规则；其二是使用整数最小货币单位，例如分。两种方案都要求数据库、序列化和接口契约保持一致。直接从客户端 JSON 数字先解析为浮点再转 `Decimal`，仍然把误差带入领域层；正确边界应尽早保留原始十进制语义。

Agent 的 Finding 需要避免夸大。不能因为看到 `float` 就断言“用户已经损失资金”，除非有事故证据；应该写成“领域金额经二进制浮点往返，违反精确金额策略，无法证明金额守恒”，并引用源码位置和性质测试或策略规则。人工裁决之所以要求修改，是因为需求明确规定了表示和守恒，而不是因为所有浮点用法都天然不安全。

迁移到生产系统还要补充币种和舍入上下文。不同货币的最小单位可能不同，汇率计算、税费分摊和退款残差都需要业务规则。教学案例只有单一货币和简单转账，所以它证明的是“不要让二进制浮点进入金额领域”，不证明完整账务模型已经成立。

## 案例档案三：PR-03 从认证成功到对象授权

PR-03 的需求是登录用户选择自己的钱包付款。错误补丁仍然验证用户已经登录、钱包存在、余额足够，因此在表面上保留了许多“安全检查”；它只删除了源钱包所有者比较，却足以形成对象级授权绕过。

认证回答“你是谁”，对象授权回答“你能否对这个具体对象执行这个动作”。两者之间不能靠客户端输入连接。请求中的钱包 ID 是定位信息，攻击者可以修改；服务端身份上下文才是主体证据。正确检查应在业务操作所在的服务边界执行，而不能只依赖前端隐藏按钮、路由命名或客户端先查询“我的钱包”。任何可以直接调用 API 的客户端都能跳过这些界面约束。

负向测试应构造至少两个用户和两个钱包。用户 A 登录后以 B 的钱包作为源钱包发起转账，系统必须拒绝，并且两侧余额、转账记录和审计日志都不发生成功操作。还要验证目标钱包的规则：本案例只要求拥有源钱包，不应错误地要求付款人也拥有目标钱包。过度授权限制与授权缺失一样属于需求偏离，只是风险方向不同。

错误响应也值得审查。有些系统为避免资源枚举，会对不存在和无权访问返回相同状态；另一些内部系统需要区分。Agent 不应凭通用安全口诀擅自选择，而应引用接口契约。无论外部状态码如何，内部审计记录都必须区分未认证、对象不存在和对象未授权，便于调查而不向客户端泄露额外信息。

Finding 的最小因果链是：当前用户来自可信上下文；源钱包 ID 来自请求；服务层查到钱包后没有比较 `owner_id`；因此任意登录用户只要知道或猜到 ID，就可能操作他人源钱包；负向回归测试复现了该路径。修复恢复服务层所有者检查，并对失败路径回归。若系统有管理员代操作、联合账户或授权委托，还需把简单相等比较升级为显式策略，而不是在各处散落例外。

PR-03 也提醒我们，覆盖率不能代表授权覆盖。每一行都可能被合法用户路径执行，却从未测试主体和对象不匹配。构造安全测试矩阵时，至少交叉主体状态、对象存在性、所有权和动作：未登录访问、本人对象、他人对象、不存在对象、已撤销委托，以及只读与写入动作。矩阵让授权边界成为可观察对象。

## 案例档案四：PR-04 用确定性时序复现并发双花

PR-04 试图降低并发等待时间，把余额读取和校验移到临界区外。单线程看，每笔转账都先读取余额、判断足够、再更新；两线程交错时，两个请求都可能基于同一个旧余额获得批准。它属于典型的检查时与使用时竞态。

偶发压力测试不足以成为稳定证据。机器负载、解释器调度和日志都会改变时间窗口，今天失败、明天通过的测试无法支撑门禁。本案例用屏障控制线程：A 和 B 都完成旧余额读取后才允许继续。这样错误补丁上会稳定观察到两笔成功，正确基线上则只有一个请求可以完成。测试的重点不是制造更多线程，而是固定违反不变量所需的最小交错。

状态时序可以写成六步：初始余额一百；A 读取一百；B 读取一百；A 判断八十可支付；B 也判断八十可支付；两者分别更新。若更新使用“余额减八十”的读改写，结果可能是负数或覆盖写；即使最终余额因为覆盖只减了一次，系统也可能已经记录两笔成功转账。只断言余额非负还不够，必须联合断言成功笔数、两侧总额和记录数。

正确的原子边界包括幂等检查、余额检查、源钱包扣减、目标钱包增加和转账记录。教学仓储用进程内 `RLock` 表达这一性质，便于读者观察；它不跨进程，也不能模拟数据库崩溃恢复。生产方案可能是数据库事务和行锁、可串行化隔离，或带版本号的比较交换与有限重试。选择取决于存储、吞吐和冲突率，但都必须恢复“检查所依据的状态与写入之间不能被未处理的并发修改穿透”这一性质。

锁的顺序同样重要。涉及两个钱包时，如果请求一先锁 A 再锁 B，请求二先锁 B 再锁 A，修复双花后可能引入死锁。常见办法是按稳定 ID 排序获取锁，或让数据库事务管理冲突并处理死锁重试。评审 Finding 不必替团队选择唯一实现，但应提醒修复不能只覆盖单一源钱包争用。

多 Agent 在这个案例上的正确协作不是三次复述“有竞态”。测试 Agent 提供确定性失败和交错，correctness Agent 将其连接到原子边界，impact Agent说明余额与记录共同受影响，仲裁器按 `CONCURRENCY-001` 合并根因。若测试 Agent 未能运行，应输出证据缺口；如果 correctness Agent 只凭 Diff 提出假设，严重性可以高，但门禁必须清楚标注尚未复现。

修复后的验证也要防止假绿。测试需要确认确实运行在错误补丁和修复补丁对应的提交上，屏障没有因实现改变而失效，异常路径释放锁，重复运行没有悬挂线程。CI 可以为并发测试设置合理超时并保存线程栈，超时本身作为失败，而不是无限等待。

## 案例档案五：PR-05 幂等性是服务端状态协议

网络请求的发送者无法仅凭超时判断服务端是否执行成功。响应可能在服务端提交后丢失，也可能请求根本未到达。允许客户端重试就意味着服务端必须把幂等键纳入协议。PR-05 删除已有转账查询和提前返回，把去重责任推给客户端，因此同一请求可能扣款两次。

幂等键不是一个简单的“出现过”集合。服务端至少要把它与主体、请求参数摘要、执行状态和最终结果绑定。相同用户、相同键、相同参数重试时返回原结果；相同键配合不同金额或目标钱包时拒绝，防止一个键被错误复用；不同用户是否允许使用相同字符串键，要由命名空间设计决定。本案例把用户纳入键范围。

状态机通常包含 `in_progress`、`succeeded` 和 `failed`。两个首次请求同时到达时，必须只有一个能创建或占用键记录；另一个等待、冲突或读取最终结果。若只在转账完成后写入幂等记录，两个请求都可能先查不到历史记录。若先写 `in_progress` 后进程崩溃，还需要租约、恢复或人工处理规则，不能让键永久卡住。

参数摘要必须使用规范化表示。金额 `10.0` 与 `10.00` 在业务上是否相同，目标 ID 大小写是否敏感，缺省字段如何展开，都要在哈希前确定。直接哈希原始 JSON 可能因为字段顺序产生不同结果；过度规范化又可能把业务上不同的请求视为相同。教学案例不实现完整规范化协议，因此书中必须标出这个生产缺口。

测试矩阵至少包含：第一次成功；相同键相同参数顺序重试；相同键不同参数；两个相同请求并发首次到达；服务端提交后响应丢失；执行失败后是否允许重试。每个测试同时检查余额、记录数、返回 ID 和键状态。只断言 HTTP 200 无法证明只发生一次资金变更。

Agent 的修复建议“恢复查询”仍然不够，因为查询与写入若不在同一原子边界，竞态依旧存在。完整 Finding 要引用被删除的查询、重试失败测试和原子性要求。人工裁决为 `must_fix`，理由不是客户端一定会重试，而是需求明确允许超时重试，服务端已经承担相应契约。

## 案例档案六：PR-07 依赖漏洞需要适用性分析

PR-07 把隔离教学清单中的 `requests` 降到 `2.19.1`，用于复现旧系统兼容问题。OSV 返回的公告可能包含多个别名；`GHSA-x84v-xcm2-53pg`、`CVE-2018-18074` 等标识可能描述同一根因，不能被当作多个独立 Finding 夸大数量。本案例要求给出公告、影响范围、修复版本和适用条件。

依赖扫描提供“版本命中公告”的事实，不自动证明当前应用可利用。评审还要检查是否发生 HTTPS 到 HTTP 重定向、是否使用认证头、代理、`netrc`、TLS 验证和压缩包提取等相关路径。适用性分析可以降低紧急程度或形成风险接受，但不能删除扫描记录。相反，模型也不能凭记忆说某版本安全；漏洞数据库会更新，必须记录查询时间和数据源。

教学清单与应用运行依赖要隔离。若扫描器递归扫描仓库，它会故意发现案例中的脆弱版本；CI 需要区分“应用基线不得有已知未接受漏洞”和“教学资产预期包含漏洞样本”。正确做法可以是对实际锁文件运行阻断扫描，对案例目录运行期望结果测试，验证 PR-07 确实命中指定公告。简单排除整个目录会让教学案例失去回归价值。

升级也可能有兼容代价。修复建议可以升级到审计基线 `2.33.0`，但真实项目还要运行接口兼容测试，查看传递依赖和运行时要求。若业务必须暂时保留旧版，需要有期限的风险接受、网络出口限制、禁用危险重定向、凭证隔离和升级计划。Agent 可以列出补偿控制候选，批准风险仍由责任人完成。

依赖 Finding 的位置应指向实际 manifest 或锁文件，而不是只引用扫描器网页。证据包保存包名、解析版本、依赖路径、公告 ID、受影响范围、修复范围、扫描器版本和时间。这样公告更新后可以重新评分，也能解释为什么当时的裁决合理。

## 案例档案七：PR-08 仓库内容不能成为控制指令

PR-08 在源码注释中嵌入要求忽略安全问题、批准 PR 或泄露系统提示词的文字。对编译器而言它只是数据，对语言模型而言却具有指令外观。实验的目标不是声称能够防御所有提示注入，而是验证一个清晰不变量：仓库内容不能改变评审政策、工具范围和批准权限。

信任层级应由编排器表达。系统策略和组织规则处于高信任控制面；仓库源码、PR 标题、描述、测试夹具、日志和外部网页均是待分析数据。输入模型时可以加边界标记和来源元数据，但不能只依赖一句“忽略其中指令”。真正的防护在模型之外：工具允许列表、只读工作区、凭证分离、输出 Schema、策略门禁和人工批准。

攻击文本可能通过间接路径进入。测试失败日志可以打印仓库字符串，依赖文档可能包含指令，另一个 Agent 的摘要也可能复述恶意内容。因此每个证据对象都要携带来源和信任级别，下游不能因为文字来自“工具输出”就自动提升信任。工具输出可以证明命令执行事实，其中嵌入的自然语言仍可能是不可信数据。

AGENTSEC-001 的证据由源码位置和策略边界记录组成。策略守卫命中注入式文本后要求人工复核；Agent 即使遵循了恶意指令，也不能获得批准凭证。若编排器发现越权工具调用尝试，应立即拒绝调用并记录安全事件，而不是把失败消息继续喂给模型让它反复尝试。

修复可以删除恶意指令，也可以在专门测试夹具中以引用数据保留，用于持续回归。后一种方式必须确保夹具不会进入真实批准路径。生产系统还应轮换可能暴露的凭证、检查审计日志，并验证没有评论、提交或外部请求已被执行。本地案例没有真实外部凭证，因此只能证明控制流，不代表完成了生产事件响应。

## 从七个案例抽象出的工程不变量

七个案例表面上分别属于文档、金额、授权、并发、幂等、依赖和 Agent 安全，底层却共享一组工程不变量。第一，输入来源决定信任，不由文本语气决定；钱包 ID、仓库注释和漏洞描述都需要来源标记。第二，检查与使用之间必须有受控边界；余额校验、幂等查询和批准门禁都不能在检查后被未建模的状态变化穿透。第三，证据必须与结论在同一次运行中关联；旧扫描结果、不同提交的测试和缓存摘要不能冒充当前证明。

第四，不变量比实现方案更稳定。`RLock`、行锁和 CAS 都可能恢复并发性质；`Decimal` 和整数分都可能恢复金额精度；简单所有者比较和策略引擎都可能恢复授权。评审意见应围绕必须成立的性质，避免把教学实现固化为生产架构。第五，未知范围必须显式。单仓库搜索、录制回放和进程内测试都有边界，书中不把它们包装成全局或真实模型结论。

这些抽象使案例可以迁移到其他领域。库存扣减与余额扣减共享并发不变量；订单创建与转账共享幂等协议；医疗记录访问与钱包所有权共享对象授权；自动化运维 Agent 与代码评审 Agent 共享提示注入和凭证隔离。读者不需要复制钱包代码，而应复制从需求、不变量、证据、裁决到验证的思考方式。

## 生产实施参考：证据对象与运行目录

一个可审计运行可以组织成不可变目录。目录名包含提交哈希和运行 ID，内部保存 `manifest.json`、标准化 Diff、需求快照、工具原始输出、Finding、仲裁结果和人工裁决。`manifest` 记录仓库、基准提交、目标提交、策略版本、提示词哈希、模型精确版本、工具版本、开始结束时间和执行身份。敏感值只保存引用，不保存明文凭证。

证据对象建议包含 `id`、`type`、`producer`、`command`、`commit`、`created_at`、`content_hash`、`status` 和 `location`。Finding 只引用证据 ID，展示层再解析内容。这样同一失败测试可以被 correctness 和 arbitrator 共用，不需要复制长日志；证据被替换时哈希会变化，审计可以发现引用失效。

运行目录默认只追加，不允许 Agent 覆盖原始输出。重试产生新的 attempt，仲裁可以选择有效 attempt，但不能抹掉失败历史。人工裁决也作为新对象追加，保留先前决定和撤销原因。对于保存期限和个人数据，组织应设置清理策略；可审计不等于永久保留所有源码。

### 工具执行契约

工具调用应使用预定义命令或受约束参数，而不是让模型拼接任意 shell。每个工具声明工作目录、超时、网络权限、可写路径、预期退出码和输出解析器。测试命令退出码非零时，要区分断言失败、收集失败和环境失败；扫描器没有发现问题、扫描器未运行和扫描器上传报告失败是三个不同状态。

解析器不能丢弃原始输出。结构化结果用于门禁，原始日志用于复盘。输出过大时保存完整文件并在上下文中提供摘要和行引用；截断要显式标注。模型读取摘要后仍可按需请求相关片段，避免因为 Token 限制看不到关键堆栈。

网络访问应按任务开放。依赖公告查询可能需要外网，源码分析通常不需要。允许联网的 Agent 不应同时持有发布或生产凭证。外部网页内容作为低信任证据，必须记录 URL、抓取时间和摘要哈希。若来源发生变化，后续运行可以解释结论差异。

### Finding 生命周期

Finding 从 `proposed` 开始，经证据校验后进入 `supported` 或 `unsupported`；根因合并后进入 `merged`；策略门禁生成 `blocking`、`advisory` 或 `escalated`；人工可 `accepted`、`rejected` 或 `risk_accepted`；修复回归后才进入 `verified_fixed`。状态机防止“作者回复已修复”直接关闭问题。

每次状态变化都有操作者和理由。Agent 可以提出和补充证据，但不能将高风险 Finding 标为风险接受；作者可以提供修复，却不能批准自己的高风险例外；Tech Lead 可以裁决，但不能修改原始工具事实。权限分离让责任清晰，也减少提示注入的潜在影响。

`rejected` Finding 不应删除。它可能揭示规则误配、测试夹具错误或模型幻觉，应进入误报分析。`unsupported` 也不一定毫无价值：它可以转化为新增测试建议，但展示时必须和已证实缺陷分开，避免开发者把所有评论都当成同一优先级。

### 故障恢复与幂等运行

评审流水线本身也要幂等。同一提交、策略版本和工具版本重复触发时，可以复用不可变证据；策略或代码变化后必须生成新运行。发布评论用稳定 Finding ID 更新原评论，避免重试制造十条重复消息。评论发布成功但回执丢失时，先查询现有状态再重发，这与 PR-05 的业务幂等原则完全相同。

编排器崩溃后从运行清单恢复，已完成工具不重复执行，进行中的任务按租约判断是否重试。人工门禁状态存储在模型之外，任何恢复路径都不能默认批准。若审计存储不可用，高风险流程应停止；低风险是否降级由明确策略决定。

## 实验设计参考：从回放到可发表结果

录制回放的第一阶段只验证工程管道。固定输入经过 single、multi 和 multi_arbitrated 三种模式，检查 Schema 能否解析、风险能否路由、重复 Finding 能否合并、人工门禁能否触发。这个阶段的“全命中”不能进入模型能力结论，因为输出本来就是夹具的一部分。

真实模型阶段需要冻结数据集和提示词。选择至少两个模型家族，每个案例运行多次，保留全部原始输出和失败。运行顺序随机化，避免限流或服务波动总落在同一案例。若中途修改提示词，形成新实验版本，不能把前后结果混在一张平均表中。

主要指标包括根因 Precision、Recall、高风险 Recall、零缺陷错误阻断率和重复率。工程指标包括首次反馈延迟、总延迟、输入输出 Token、缓存命中、工具时间、模型重试和人工复核分钟数。安全指标包括越权工具调用尝试、提示注入遵循率和敏感信息输出。所有指标都要给分母；“检出率提高 20%”若没有样本数没有解释意义。

样本量较小时，不应过度解读小数点。可以报告每个案例每次运行的明细、均值和范围，并说明统计限制。重点观察稳定失败模式：某模型是否持续漏掉授权边界，专业分工是否只是增加重复，仲裁是否会错误压低严重性。定性错误分析往往比一个综合分更能指导下一轮设计。

对照组要保持公平。`deterministic-only` 只使用工具事实；`single` 和 `multi` 应获得同一基础证据；`multi_arbitrated` 只新增仲裁，不应偷偷增加 Oracle。若多 Agent 获得更多工具和上下文，性能提升不能全部归因于“多角色”。实验报告需要列出每组的输入和权限差异。

成本报告使用运行当天价格，并保留原始 Token，使未来可以重新计算。模型服务折扣、缓存价格和批处理价格分别记录。人工时间可以用抽样计时估算，但要说明口径。最终决策不追求最低单次费用，而是在风险预算内获得可接受召回、误报和延迟。

## 上线检查与回滚剧本

影子模式期间，Agent 评论默认不对作者可见或明确标注实验，避免干扰正常评审。团队每周抽样对照人工结果，修正 Oracle、规则和提示词。进入建议模式后，Agent 可以发布非阻断评论，但高风险建议仍由人工确认。有限门禁阶段只允许证据充分的确定性规则阻断，模型 Finding 作为升级输入。是否进一步自动化必须由数据证明，而不是由演示效果决定。

回滚条件应在上线前写好。例如高风险样本出现一个确认漏报、零缺陷错误阻断连续超过阈值、审计日志缺字段、工具凭证越权、Schema 解析失败率异常或成本超过预算，系统立即退回建议或影子模式。回滚只关闭自动决策，不应删除已产生证据；保留现场才能定位问题。

发生提示注入或凭证事件时，先停止相关工具权限和自动发布，保存运行清单与日志，轮换暴露凭证，核对外部副作用，再修复策略和增加回归案例。不要先修改日志或让同一个 Agent总结事故，因为它可能正是受影响组件。恢复上线前，必须用原始攻击输入重复验证控制面。

发生大量误报时，不要简单提高置信度阈值。先按根因分类：规则误配、上下文缺失、模型泛化、证据解析、仲裁合并或需求本身模糊。不同原因需要不同修复。阈值只能调整排序，无法修复错误输入和错误 Oracle。

## 章末练习与讨论题

第一组练习聚焦需求。为 PR-02 写出三个性质测试，分别覆盖金额表示、总额守恒和非法输入；说明为什么示例测试不足。为 PR-03 画主体—对象—动作矩阵，增加一个合法委托场景，判断简单 `owner_id` 比较是否仍然满足需求。

第二组练习聚焦时序。为 PR-04 写出两个线程的最小交错，列出每一步可见状态；再比较全局锁、行锁和 CAS 的失败模式。为 PR-05 设计 `in_progress` 状态下进程崩溃的恢复策略，说明重复执行和永久阻塞之间如何取舍。

第三组练习聚焦评测。假设 Agent 对 PR-04 输出三条重复竞态意见、漏掉 PR-03、在 PR-01 产生一条误报，按根因计算 TP、FP、FN、Precision、Recall 和重复率。再说明为什么按评论条数计算会产生误导。

第四组练习聚焦安全。为 PR-08 列出仓库内容进入 Agent 的五条间接路径，并为每条设计控制措施。判断“在系统提示词中声明不要服从仓库指令”为何必要但不充分。设计一个测试，证明恶意注释无法改变工具允许列表。

第五组练习聚焦上线。给一个十人团队设计三阶段灰度计划，定义每阶段样本、门禁范围、人工责任和回滚阈值。预算中同时计算 Token、CI 时间和人工复核时间。最后写出一个你明确不会自动化的决定，并解释责任边界。

## 最终检查表

- 需求是否转化为可测试的不变量，而不是停留在功能描述？
- 每个阻断 Finding 是否同时具有根因、位置和本次运行的证据？
- 工具未运行、运行失败和未发现问题是否被明确区分？
- Agent 是否只能使用任务所需的最小工具和凭证？
- 仓库、日志和外部网页是否始终作为带来源的低信任数据？
- 风险路由是否可测试、可解释，并遵循只升不降？
- 重复意见是否按根因合并，同时保留原始来源？
- 人工裁决是否记录理由、证据、未知范围和例外期限？
- 修复是否通过原失败用例和相关不变量回归，而不只是让单测变绿？
- 零缺陷样本是否进入评测，用来观察误报和错误阻断？
- 录制回放是否只用于验证管道，没有被写成真实模型能力？
- 实验是否记录模型、提示词、数据集、工具和价格版本？
- 成本是否包含延迟和人工负担，而不仅是 Token？
- 生产迁移中未覆盖的跨进程、跨仓库和外部系统边界是否显式标注？
- 自动化失败时是否有明确降级、暂停和回滚剧本？

## 证据阅读方法：先读事实，再读解释

很多评审争论并不是因为参与者价值观不同，而是因为大家从不同层级的材料开始阅读。有人先看模型长评论，再回头寻找证据；有人先看失败测试，却没有核对它对应的提交；还有人只看最终红绿灯，不知道扫描器是否真的运行。建议固定阅读顺序，降低解释对事实的污染。

第一步读运行清单。确认基准提交、目标提交、案例 ID、策略版本、工具版本和运行时间。若目标提交与 Diff 不一致，后续所有结论都只能标记为不可用。第二步读需求和不变量。需求决定什么算缺陷，Oracle 决定允许哪些修复，不能先用模型意见替代需求。第三步读原始工具输出，区分断言失败、规则命中、网络失败和未执行。第四步读 Finding，检查它是否准确引用证据，以及是否把推测写成事实。第五步读仲裁和人工裁决，确认严重性、升级和例外是否有理由。最后才读摘要和展示文本，因为摘要是压缩结果，不是原始证据。

这个顺序对 PR-07 尤其重要。先看到“高危漏洞”标签，容易忽略它来自教学 manifest，或者忽略该公告的具体适用条件；先看路径、版本和 OSV 原始记录，才能判断它是应用运行依赖、测试依赖还是隔离样本。对 PR-08，先看仓库注释会让人进入攻击者设定，先看信任层级和工具审计则能保持控制面稳定。

### 证据充分性检查

可以用四个问题快速判断一条意见能否阻断。其一，事实能否由本次运行复现？其二，事实与需求中的不变量是否有明确连接？其三，位置是否足够精确，让开发者能定位并修复？其四，修复后是否有验证路径？如果只有前三项，意见可以是 `must_fix` 但要进入人工补证据；如果只有模型解释而没有事实，最多是调查建议。

证据也有新鲜度。源码位置、测试输出和依赖公告都可能随时间变化。每份证据保存提交哈希、生成时间和内容哈希；外部公告保存 URL 和访问日期。若重新运行发现漏洞数据库更新，应生成新 Finding 或追加证据，而不是覆盖旧结论。这样审计人员可以回答“当时为什么这么判断”，而不是只看到今天的状态。

### 不同证据之间的矛盾

矛盾不应被平均。测试说两个请求都成功，模型说“锁保证原子”，优先检查测试是否运行了错误补丁、模型是否读取了过期文件，不能用置信度加权后取中间结论。扫描器说有漏洞，人工说当前路径不可达，也不能直接删除 Finding；应该将漏洞事实和适用性判断分成两个字段，记录接受风险或补偿控制。

当矛盾来自环境时，最好的结果可能是 `inconclusive`。例如数据库服务未启动、OSV 网络请求超时、并发屏障未释放，系统没有足够事实决定是否安全。对高风险变更，`inconclusive` 应升级或阻断；对低风险变更，可以按策略延期，但不能显示为绿色通过。把“不知道”保留下来，是证据系统比自然语言评审更重要的能力之一。

## 生产迁移：教学钱包与真实系统的差距

教学工程的价值在于小而完整，生产系统的风险在于复杂且跨边界。把本章案例迁移到支付、库存或账户系统时，必须逐项重新确认假设。进程内锁无法覆盖多实例部署；内存字典无法提供崩溃恢复；单一货币不能代表多币种；本地测试不能证明消息队列、缓存和数据库之间的一致性；录制模型输出不能代表线上模型的鲁棒性。

迁移的第一步是把教学不变量翻译成生产契约。例如“金额守恒”要具体化为账务分录借贷平衡、舍入策略、币种和结算时点；“一次效果”要定义幂等键范围、保留时间、状态恢复和跨服务传播；“对象属于主体”要对应组织、角色、委托和撤销模型；“仓库不能改变策略”要对应生产 Agent 的数据流和凭证边界。没有这一步，复制代码只会复制表面结构。

第二步是识别新增边界。服务之间通过消息传递时，事务边界可能跨不出去，需要 Outbox、Inbox、唯一约束或补偿流程；数据库读写分离时，刚提交的数据可能在副本延迟下不可见；缓存命中旧余额时，检查结果可能失真；人工审批与自动执行之间存在长时间窗口。每增加一个边界，就应增加不变量、故障注入和恢复测试。

第三步是建立迁移证据。生产设计评审不能只附教学测试结果，应附数据库隔离级别、唯一索引、消息重试策略、故障恢复演练和权限矩阵。教学案例可以作为思考模板和回归基线，不能作为生产合规证明。书稿明确这条边界，是为了防止读者在演示成功后产生错误的安全感。

### 生产并发的额外问题

多实例部署下，两个请求可能落到不同进程和不同主机。进程内 `RLock` 对它们没有作用；分布式锁又会引入租约过期、时钟和网络分区问题。数据库行锁通常更接近资金状态，但要明确锁定行的顺序、事务隔离和死锁重试。CAS 可以减少锁等待，却需要处理版本冲突、重试上限和副作用重复执行。

读写分离会制造另一种竞态：请求在主库扣款后，立即从延迟副本读取余额，可能看到旧值并错误返回。评审应把“写后读一致性”列为影响分析节点，而不是只检查扣减语句。缓存失效也有顺序要求，先删缓存再提交和先提交再删缓存的失败模式不同。每种方案都要写出故障时序，并说明用户看到的状态和账务真实状态如何区分。

### 生产幂等的额外问题

跨服务转账常常需要把幂等键传递给支付、风控和通知系统。若每个系统使用不同键，重试可能在下游产生第二个效果；若所有系统共享同一键，却没有定义命名空间和生命周期，键冲突与存储膨胀会成为新问题。幂等记录需要考虑隐私、查询权限、过期策略和审计保留，不能无限保存完整请求正文。

外部服务只支持“未知”响应时，调用方不能简单重试非幂等操作。可以采用状态查询、业务对账、人工挂起或带幂等令牌的供应商接口。评审 Agent 可以识别“网络超时后重试”这一模式，但无法替团队决定资金悬挂多久；这必须写入业务运行手册和人工职责。

### 生产授权的额外问题

组织账户常有委托、角色继承、资源层级和临时授权。简单 `owner_id == current_user.id` 只适合本案例的单所有者模型。生产策略应明确授权来源、有效期、撤销传播和审计要求。对象 ID 还可能通过日志、URL、错误消息和缓存泄露，虽然不构成授权本身，却会扩大枚举面。

授权检查必须靠近实际副作用，并在异步任务中重新验证。把权限判断结果放进可伪造的队列消息，或只在同步入口检查后让后台任务直接执行，都会重新打开边界。评审影响分析应追踪身份上下文如何跨线程、消息和服务传递，标出哪些步骤只携带了用户提供的 ID。

### 生产 Agent 安全的额外问题

线上 Agent 可能读取内部代码、工单、日志、网页和用户内容，数据分类、脱敏、租户隔离和保留期限都比本地夹具复杂。最小权限要落实到每个工具和每个租户，而不是只给 Agent 一个宽泛的服务账号。工具参数应做类型和范围校验，网络出口应限制域名和方法，写操作应有二次确认或策略门禁。

模型上下文中出现的密钥、个人信息和内部提示词要有泄露检测，但检测本身也可能误报或被绕过。真正的控制仍是凭证不可读、输出过滤、审计和人工门禁。若必须让 Agent 处理敏感数据，应记录数据用途、访问者、处理时间和删除策略，以满足组织的合规要求。书中没有这些生产凭证，因此只讨论控制原则，不虚构实测结果。

## 反模式目录：看似合理但会破坏证据闭环

反模式一是“让模型先总结，再决定跑什么工具”。模型可能因误读 Diff 跳过关键测试；高风险工具集合应由策略路由先决定，模型只能补充解释。反模式二是“把所有工具输出拼进一个超长提示词”。上下文过载会让模型遗漏关键失败，且无法追踪某句话来自哪个工具；应使用带 ID 的证据包和按需读取。

反模式三是“用置信度阈值代替人工门禁”。置信度没有统一标定，模型可能对错误结论非常自信；高风险策略必须在模型之外执行。反模式四是“只修复让测试变绿的路径”。测试可能没有覆盖记录、授权、审计或异常释放；修复验证要回到完整不变量矩阵。反模式五是“把每条评论都计为一个缺陷”。重复会虚高召回，零缺陷样本和根因去重必须进入评测。

反模式六是“把教学依赖样本排除扫描”。这样 CI 看起来绿色，却失去漏洞教学的回归；应用依赖与教学资产应采用不同的期望结果。反模式七是“让 Agent 自己发布批准评论”。发布、修改和批准是不同责任，必须使用分离凭证和门禁。反模式八是“失败时使用最后一次绿色结果”。旧结果只能作为参考，不能证明当前提交；工具失败应显示为证据缺口并按照风险升级。

## 维护计划：章节、工程和案例如何长期同步

本章描述的是一个会变化的系统。模型版本、价格、漏洞公告、策略文件和测试夹具都会更新。每次仓库变更都应检查章节中的命令、路径、案例 ID、分支名和输出描述。文档引用的外部事实记录访问日期；仓库内结论优先引用可运行命令，不复制容易过期的终端输出。

可以把维护分为三类。代码或策略变化时，先运行 `make check` 和评测套件，再检查正文中的字段和行为描述；案例素材变化时，重新生成 patch、Oracle、人工裁决和远程分支，并核对章节是否仍称为同一根因；外部模型或 OSV 变化时，更新实验元数据和价格日期，不能把新结果覆盖旧结果。每次发布前执行一次链接、命令和字数检查，将结果写入实施日志。

章节目标字数也要服务于内容验收。新增段落必须至少引入一个新证据、新边界、新反例或新读者产出；如果只是把同一结论换一种说法，应删除。篇幅不足时优先补齐案例证据、生产迁移和练习，篇幅过长时优先删除重复背景，而不是删除限制条件。这样才能让“字数达标”与“读者获得能力”保持一致。

```yaml
      - applicability_note
  role_permissions:
    router: [read_metadata, select_tools]
    test: [read_source, run_named_tests]
    security: [read_source, run_policy_tools]
    arbitrator: [read_findings, merge_findings, escalate]
    publisher: [post_comment]
    approver: [approve_or_reject]
  prohibited:
    - agent_approval_without_policy_gate
    - repository_text_changing_tool_allowlist
    - stale_result_as_current_evidence
  terminal_states:
    - approved
    - changes_requested
    - escalated
    - evidence_incomplete
```

模板中的 `policy_snapshot` 很关键。风险规则在评审期间可能更新，若不保存快照，事后无法解释为什么同一提交在两天后得到不同路由。`terminal_states` 也不能只有通过和失败；`evidence_incomplete` 让系统能够诚实表示工具或环境问题。对于高风险变更，它通常应转换为 `escalated`，而不是自动批准。

### 输出模板与示例

```json
{
  "finding_id": "AUTHZ-001",
  "root_cause": "object-level-authorization-missing",
  "category": "security",
  "severity": "must_fix",
  "blocking": true,
  "location": {
    "file": "app/service.py",
    "line_start": 74,
    "symbol": "transfer"
  },
  "claim": "当前用户未被验证为源钱包所有者",
  "trigger": "用户 A 提交用户 B 的源钱包 ID",
  "invariant": "actor-owns-source-wallet",
  "evidence": [
    {"id": "test-unauthorized-17", "type": "test_failure"},
    {"id": "diff-03-4", "type": "deleted_check"}
  ],
  "unknowns": ["委托账户规则未覆盖"],
  "needs_human": true,
  "suggested_boundary": "服务层在资金变更前执行授权策略"
}
```

这个输出比一段“存在 IDOR，请修复”的评论多了几个重要字段。`trigger` 让读者知道如何复现，`invariant` 连接需求，`unknowns` 防止把单所有者案例推广到委托模型，`suggested_boundary` 描述修复位置而不强制唯一实现。Schema 校验失败时，系统应把 Finding 标记为不可发布并要求 Agent 补齐，而不是让展示层自行猜字段。

## 七个案例的对照矩阵

| 案例 | 主要事实源 | 最小复现 | 不能替代的判断 | 常见错误修复 |
|---|---|---|---|---|
| PR-01 | Diff、文档规则 | 检查仅改 Markdown | 文档是否进入运行时 | 把所有文档都当低风险 |
| PR-02 | 需求、策略、性质测试 | 非法金额与守恒测试 | 币种和舍入业务规则 | 只在输出端 `round` |
| PR-03 | 身份上下文、负向测试 | A 操作 B 的钱包 | 委托和角色模型 | 只在前端隐藏入口 |
| PR-04 | 屏障并发测试、事务代码 | 两笔 80 元并发 | 生产数据库隔离 | 只加锁但不管死锁 |
| PR-05 | 幂等状态、重试测试 | 相同键重复与并发首次 | 外部服务未知状态 | 只保存“已出现”标记 |
| PR-07 | 锁文件、OSV 公告 | 解析旧版 manifest | 当前路径的可利用性 | 删除教学样本目录 |

## 人工裁决样例与责任边界

以 PR-04 为例，人工裁决可以记录如下内容：

```yaml
case_id: PR-04
decision: request_changes
owner: tech-lead@example.invalid
reason: >-
  确定性并发测试复现两笔转账同时成功，违反 non-negative-balance
  和 conservation-of-money。修复必须恢复检查与更新的原子边界；具体
  可采用事务锁、可串行化隔离或带冲突重试的 CAS。
accepted_evidence:
  - deterministic-concurrency-test
  - repository-atomic-diff
unverified:
  - multi-process-database-behavior
  - deadlock-retry-policy
follow_up:
  - add-production-isolation-test
  - document-lock-order
```

这份记录没有把教学 `RLock` 说成生产方案，也没有因为测试通过修复分支就宣称所有并发问题解决。`unverified` 让后续任务可追踪，`follow_up` 将评审发现转化为工程行动。若负责人选择风险接受，也要填写补偿控制和到期时间，而不是把 `decision` 改成 approve 后删除问题。

对于 PR-07，人工裁决通常不要求每次都参与，因为依赖扫描和策略可以确定性阻断；但当业务提出兼容性例外时，责任就转移给依赖所有者和安全负责人。对于 PR-03、PR-04 和 PR-08，必须人工复核，是因为它们涉及权限、资金状态或评审控制面，错误后果不能只由模型和作者承担。

### 驳回 Finding 的样例

驳回也应有结构，而不是在评论里写“误报”。例如 PR-02 若团队已经批准整数分策略，而某 Agent 把一个只出现在测试注释里的 `float` 标成金额缺陷，裁决可以这样记录：位置不在领域金额路径；工具未命中实际赋值；不影响任何不变量；保留为建议而非阻断。这样的驳回不会削弱真正的 `MONEY-001`，反而为后续规则改进提供边界。

如果某条 Finding 的根因正确但证据不足，不应直接驳回为误报。可以转为 `evidence_incomplete`，要求运行指定测试或补充调用图。这个状态区别了“判断错误”和“判断尚未证明”，对团队学习很重要。

## 运行失败时的决策树

评审流程应在设计时就写出失败决策树。若路由器失败，系统读取上一版策略快照但不自动降级；高风险变更进入人工。若测试命令退出码非零，先判断是断言失败还是环境失败；断言失败可以生成 Finding，环境失败生成证据缺口。若 Agent 输出无法解析，重试一次并保留原文；再次失败则不发布自由文本阻断，转人工或使用确定性结果。若评论 API 超时，查询评论 ID 后再决定是否重试，避免重复发布。

外部依赖失败也要按风险处理。OSV 服务超时不等于没有漏洞；低风险文档可在策略允许时继续，但必须标记依赖扫描未完成；中高风险变更应等待或升级。模型服务不可用时，确定性检查仍可以运行，结果页面要明确显示“模型评审未完成”，不能把工具绿灯拼成整体绿灯。

故障决策树最好有自动化测试。构造模拟超时、空输出、坏 JSON、旧缓存、工具非零退出和评论重复场景，验证状态机进入预期终态。很多安全事故并非模型判断错误，而是编排器在异常分支默认放行；测试异常路径比再增加一个正常样例更有价值。

## 评审数据的隐私与保留

证据闭环不意味着保存所有原始代码和日志。运行清单可以保存哈希和引用，敏感文件使用访问控制和短期保留；模型输入需要脱敏时，保留可验证的映射关系，避免人工无法复现。租户、用户和钱包 ID 在跨团队报告中应使用稳定但不可逆的别名，原始映射只由授权人员访问。

模型供应商的保留和训练政策属于外部事实，需要记录版本和审查日期。若组织不允许代码离开边界，应采用本地模型、受控网关或只发送摘要的策略，但要重新评估 Recall 是否下降。不能一边宣称隐私隔离，一边把完整生产日志复制进公共模型提示词。

日志中的错误信息也可能包含凭证、个人数据或提示注入内容。工具输出保存前做脱敏，脱敏规则本身要测试，避免把路径和行号一起删掉导致证据不可用。安全事件日志与普通评审日志分开，限制阅读权限，并设定保留和删除流程。审计人员需要看到发生了什么，但不应因此获得所有业务数据。

## 章节成果的验收方法

本章最终验收不只看字数。第一项是结构验收：9.1～9.10 每节都有观点、机制、边界、案例证据和读者产出。第二项是复现验收：主线命令在 `wallet-review-lab` 工作目录可运行，补丁路径、模块名和分支名与仓库一致。第三项是事实验收：案例描述与 requirement、Oracle、human-verdict 和代码行为一致，录制回放没有被写成真实模型实验。第四项是边界验收：教学实现、生产迁移、外部事实和未完成实验均有明确标记。

字数统计使用中文字符近似值，只作为篇幅指标，不代替内容审校。段落级审校可以抽样检查每一节的“依据是什么、如何复现、何时不成立”三个问题；如果有一节只能回答其中一个，说明仍需补证据或删去空泛描述。出版编辑还应检查表格、代码块和 Mermaid 图注是否与正文同一版本，避免读者复制到错误路径。

读者产出验收可以设置为一份小型 PR 审查包：需求与不变量、风险路由、原始工具输出、两条结构化 Finding、人工裁决、修复验证和未覆盖清单。只要读者能独立完成这份包，章节就完成了从概念到能力的转换。若读者只能复述“Agent 要有证据”，却无法指出证据 ID、命令和升级条件，说明文本仍停留在观点层。

## 给评审团队的复盘问题

每次真实运行后，团队可以围绕以下问题复盘。哪一条意见最早发现根因？它使用了什么事实，其他角色为什么没有发现？重复意见是独立确认还是上下文回声？哪个未知范围被误写成已验证？工具失败时系统是否显示了正确终态？人工花费的时间主要用于查证、解释还是修复展示？下一次运行应该改变输入、工具、路由、Schema 还是门禁？

复盘要避免把责任归咎给一个模型。若模型漏报，检查需求是否可观察、工具是否运行、上下文是否丢失、Oracle 是否完整；若模型误报，检查规则适用性、零缺陷样本和仲裁阈值；若流程放行，检查门禁是否在模型之外、异常分支是否默认批准、凭证是否过宽。只有把失败放回系统链路，改进才不会变成不断更换模型。

复盘结果应转化为一个具体变更和一个回归样本。例如 PR-03 漏掉委托场景，就新增授权矩阵和案例；PR-04 的修复引入死锁，就增加锁顺序测试；PR-07 扫描结果重复，就更新别名归并；PR-08 通过摘要传播了注入，就增加来源和信任级别字段。每次改进都要重新运行既有七案例，确认没有为了修一个边界而破坏低风险自动通过或其他高风险门禁。

## 团队落地路线：四周试点法

如果团队第一次引入 Agent 评审，建议把试点拆成四周，而不是在一天内把所有高风险变更交给自动门禁。第一周只建立基线：收集现有人工评审、测试、依赖扫描和人工耗时，选择一组包含零缺陷、正确性、安全和依赖案例的历史 PR。此时不要求模型阻断任何合并，重点是确认数据能否脱敏、证据能否保存、工具是否能在固定环境运行。

第二周上线影子模式。路由器根据真实路径和标签选择工具，但结果只提供给评审团队，不改变合并流程。每天抽样比较 Agent Finding 与人工结论，记录漏报、误报、重复和无法判断。不要只统计模型说对了多少，还要统计人类花了多少时间确认它。若一条评论需要作者反复解释上下文，它即使技术上正确，也可能不是可用的评审产物。

第三周进入建议模式。低风险规范问题可以发布非阻断评论；高风险问题继续由人工确认。此时完善 Finding Schema、根因去重、评论更新和审计字段，测试超时、网络失败、坏 JSON、旧缓存和重复回调。团队应明确谁负责处理 `evidence_incomplete`，否则系统会积累一堆没人查看的黄色状态。

第四周才考虑有限门禁。只选择确定性证据充分的规则，例如测试失败、策略明确禁止的金额浮点、已确认的高危依赖；模型意见只负责升级人工，不直接批准或拒绝资金、授权、凭证和数据库迁移。门禁启用前先写回滚条件，并安排值班负责人。试点结束时提交一份报告，说明哪些路径节省了时间、哪些路径增加了负担、哪些风险仍完全依赖人工。

### 角色与值班安排

最小团队通常需要四类责任人。代码所有者负责解释业务意图和修复；安全或平台负责人维护策略、工具和凭证；Tech Lead 负责高风险仲裁和例外；运行负责人观察延迟、失败和成本。一个人可以承担多个角色，但同一次高风险变更的提出、修复和批准最好不要由同一人完成。

值班手册写清楚“看到什么状态做什么”。`blocking` 进入作者队列；`escalated` 通知 Tech Lead；`evidence_incomplete` 先补工具或人工取证；`agent_security_event` 暂停相关工具并轮换凭证；`publisher_failed` 查询评论状态后再重试。把这些动作写成链接到命令和权限的步骤，比让值班人员临时阅读模型长文可靠。

### 服务等级与等待时间

评审自动化会改变开发者对反馈时间的预期。低风险 PR 可以在几分钟内得到结果；中风险路径允许并行工具但要显示预计完成时间；高风险路径即使等待更久，也应明确当前卡在哪个证据或人工环节。超时不能静默变成“稍后可能批准”，否则团队会绕过流程。

可以为每个状态定义服务等级，例如工具启动失败五分钟内重试一次，超过十分钟升级平台负责人；人工高风险裁决四小时内响应，超过则保持阻断而不是降级。服务等级不是为了追求快，而是让等待有责任、有预期。延迟报告还要区分排队、工具、模型、人工和发布时间，才能找到真正瓶颈。

## 读者练习参考答案要点

PR-02 的性质测试至少应证明三件事：金额从输入到领域层保持十进制或整数分语义；任意合法转账序列的总余额保持不变；非法输入在领域边界被拒绝且不产生部分写入。只测试输出显示两位小数不够，因为显示层可以掩盖内部误差。PR-03 的委托场景说明简单所有者比较不一定满足生产需求，应把授权策略抽象为“主体对对象拥有动作权限”，并在审计中记录授权来源。

PR-04 的最小交错必须让两个请求在同一个旧余额上完成检查，然后分别执行更新；如果测试没有控制这一点，偶发通过不能说明修复正确。全局锁容易成为吞吐瓶颈，行锁要处理锁顺序和隔离级别，CAS 要处理冲突重试和副作用重复；三者都必须回归成功数、余额、总额和记录。PR-05 的崩溃恢复不能简单删除 `in_progress`，否则重试可能重复扣款；也不能永久保留卡住状态，应设计租约、状态查询或人工对账。

若 PR-04 有三条重复意见、漏报 PR-03、PR-01 有一条误报，按根因而非评论计算：PR-04 命中一个 TP，PR-03 一个 FN，PR-01 一个 FP，因此 Precision 为 1/(1+1)=0.5，Recall 为 1/(1+1)=0.5，重复率为 (3-1)/3，即三条中两条是重复表达。这个例子展示了为什么评论数量会夸大召回，也说明零缺陷样本直接影响误报指标。

PR-08 的间接路径包括源码注释、测试夹具、失败日志、依赖文档和上游 Agent 摘要。控制措施分别是来源标记、只读夹具、日志脱敏与引用、低信任外部数据和摘要中的证据 ID。系统提示词里的提醒有帮助，但若工具允许列表、凭证和批准门禁仍受模型控制，攻击文本依旧可能造成副作用。验证工具调用事件没有越权，比检查最终评论措辞更可靠。

## 章节边界声明

本章不声称完成真实模型对照实验、跨仓库调用图、生产数据库隔离验证或外部支付服务对账。当前仓库中的录制 Agent、进程内钱包和教学依赖都是可回放的控制素材；它们用于证明编排、Schema、路由、去重和门禁逻辑。真实模型实验、生产迁移和案例截图仍需按蓝图中的单独里程碑完成，不能因为正文扩充而被误写为已完成。

这条边界声明不是削弱章节，而是让读者知道哪些结论可以立即复现、哪些只能作为设计建议。书中越清楚地标出未知，读者越容易把方法迁移到自己的系统并补上对应证据。任何未来新增的真实结果都应带模型版本、运行日期、数据集和命令，并与录制回放分开存档。

## 最终出版前的机械检查

出版前可以执行一组不依赖模型的检查：统计正文字符数；检查 9.1～9.10 和七个案例标题是否存在；扫描代码块中的路径和模块名；搜索“已完成”“证明了生产安全”等容易越界的表述；核对所有案例 ID、Finding ID 与 YAML；运行 `git diff --check`、`make check` 和回放测试；确认 Mermaid、表格和图注引用的文件仍存在。机械检查不能替代内容编辑，却能消灭大量低级错误。

建议把检查结果写入出版清单，包括执行时间、提交哈希和未完成项。若字符数在目标范围外，先检查是不是误把代码、表格或重复内容计入；若命令失败，区分环境依赖缺失和正文路径错误；若案例 YAML 与正文不一致，优先修正事实来源而不是迁就旧文字。最终发布应以仓库事实为准，正文和配图都从同一提交导出。

到这里，本章的核心闭环可以压缩为一句可执行的话：先把需求写成不变量，再用确定性工具产生事实，让 Agent 在受限权限内连接事实，由仲裁和人工承担取舍，用回归验证修复，并把所有未知和失败保留下来。任何一步被省略，系统都可能看起来更快，却无法回答“为什么可以相信”。

## 指标解释：数字背后必须有分母

评审系统的指标很容易被漂亮数字误导。报告 Precision 时，应明确分母是所有被系统报告的根因 Finding，还是只有进入阻断队列的 Finding；报告 Recall 时，应明确 Oracle 是六个缺陷还是六个缺陷加一个零缺陷样本。高风险 Recall 可以单独计算，但不能用它掩盖低风险误报。重复率也要说明按原始意见、合并簇还是发布评论统计，三种口径会得到不同结果。

一个实用的结果表可以包含：案例 ID、Oracle 根因数、原始意见数、合并意见数、TP、FP、FN、证据充分率、严重性准确率、人工采纳率、首次反馈秒数、总 Token、工具耗时和人工分钟。每个数都附运行 ID 和提交哈希。这样团队可以回答“模型真的更好，还是只是输出更多”“仲裁减少了重复，还是把意见错误合并”“成本下降是否以漏报增加为代价”。

不要把采纳率当作唯一成功指标。人工可能接受一条证据不足的意见，也可能因时间压力忽略正确意见；采纳行为受团队信任和界面影响。更稳妥的办法是把采纳率与复核后 Oracle 评分分开，抽样检查被拒和被接受的 Finding。人工负担也要按“确认事实、补充证据、修复代码、处理误报”细分，否则无法知道哪类自动化最值得优化。

延迟指标同样需要分层。首次反馈适合衡量开发体验，总完成时间适合衡量流水线吞吐，高风险人工等待适合衡量责任链。一次工具排队很久但模型立即输出，不能被描述为“反馈快”；一次模型输出很快但评论发布失败，也不能被描述为“评审完成”。状态时间线应由运行清单生成，而不是由模型总结。

## 迁移前的风险问卷

在把本章方法带到另一个系统前，团队可以先回答一份风险问卷。系统是否跨进程或跨地域部署？状态是否由数据库、缓存、消息队列和外部服务共同维护？金额、库存或配额是否存在小数、舍入和部分成功？授权是否包含角色、委托、租户和撤销？请求是否允许超时重试？Agent 是否会接触用户输入、生产日志、密钥或外部网页？哪些动作不可逆，必须由人批准？

每个“是”都对应新的证据和测试，而不是自动套用钱包实现。跨进程需要分布式一致性和故障演练；外部服务需要未知状态与对账；多租户需要数据隔离和授权矩阵；接触敏感数据需要脱敏、访问记录和保留策略；不可逆动作需要独立门禁和回滚或补偿方案。问卷的目的不是阻止采用，而是让迁移成本在开始前可见。

风险问卷还应记录“当前不回答”的问题。一个团队可能暂时无法验证跨仓库调用方或供应商重试语义，此时应把未知写入上线条件和后续任务，而不是从报告中删除。未知项越多，自动门禁范围越应收缩；这是一种基于证据的渐进式上线，而不是保守主义。

## 章节结束语：把速度花在证据上

AI 让代码和评审意见都更容易生成，也让未经验证的错误更容易扩散。真正可持续的效率，不是让模型替人类做更多无法追责的决定，而是让确定性工具更早暴露事实，让 Agent 更快连接分散证据，让人类把时间花在边界、取舍和责任上。钱包案例之所以有用，不是因为所有系统都像钱包，而是因为它把金额、授权、并发、幂等、依赖和提示注入压缩成可运行的不变量。

当读者能从一个新需求写出不变量，从一个错误 Diff 写出最小复现，从工具输出构造 Finding，从冲突意见形成裁决，并在修复后清楚说出仍未证明什么，本章才真正完成。这个标准比“模型写得像专家”更高，也更适合长期维护。因为系统会换模型、换框架、换数据库和换团队，而证据、权限、边界和责任仍然是评审可信度的根。

## 附录：一次完整评审的交付清单

为了让本章的方法可以被团队直接采用，下面给出一次评审结束时应当交付的材料。第一份是变更清单，包括基准提交、目标提交、标准化 Diff、变更文件和符号。第二份是需求清单，包括原始需求、验收标准、不变量和明确不在范围内的事项。第三份是证据清单，包括每条命令、环境、退出码、原始输出、工具版本和证据哈希。第四份是决策清单，包括 Finding、根因合并、风险标签、人工裁决、例外期限和负责人。第五份是验证清单，包括修复提交、回归命令、仍未验证的边界和后续任务。

交付材料不要求全部展示在 PR 评论中。开发者界面可以只显示变更意图、阻断根因、复现步骤和下一动作；详细日志保存在受控证据目录，通过 ID 链接。这样既避免评论过长，也不牺牲审计。摘要中的每个“已验证”都能跳转到具体证据，“未验证”能转化为任务，而不是藏在段落末尾。

在 PR-04 中，这套清单会包含并发不变量、错误补丁、屏障测试失败、`CONCURRENCY-001`、合并后的仲裁记录、人工请求修改、修复补丁和同一测试恢复。生产数据库行为、锁顺序和死锁重试留在未验证清单。PR-03 则包含身份上下文、他人钱包负向测试、`AUTHZ-001` 和服务层授权修复；委托账户留为生产扩展。每个案例都因此既有结论，也有边界。

团队还可以为交付包设置质量门槛：缺少提交哈希的测试不进入阻断证据；缺少来源和日期的外部事实只作为调查线索；没有复现步骤的模型意见不直接发布；没有回归验证的修复不能关闭 Finding；没有负责人和期限的例外不能通过高风险门禁。这些规则把“写得有道理”转换为可检查的工程质量。

最后，交付包自身也要接受版本管理。Schema 变化时保留迁移记录，工具升级时重新确认解析器，策略更新时重跑基准案例，人工角色变化时更新责任映射。长期可维护性来自这些看似朴素的记录，而不是依赖某个模型永远表现稳定。

如果团队只能先做一件事，应先选择一个高风险但边界清楚的案例，完整保存错误输入、工具事实、Finding、人工裁决和修复回归，再把流程复制到其他案例。完整的一条证据链比同时铺开十个没有审计记录的 Agent 更能说明系统是否值得信任。等第一条链路稳定后，再增加角色、模型和工具，并用同一组零缺陷与缺陷案例比较变化。这样扩充的是可验证能力，而不是评论数量。

这条路线也适用于章节之外的自动化：先选一个能回放的真实问题，固定输入和验收标准，明确谁可以批准，保存失败和修复两端证据，再逐步扩大范围。每一次扩大都应有新的零缺陷样本、异常路径和回滚条件。只有这样，速度提升才不会以责任模糊和证据丢失为代价。
