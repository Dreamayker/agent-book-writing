# 9.4 测试、评审、安全 Agent 的协同

[返回第 9 章目录](README.md)

一个可回放的评审顺序是：风险路由先确定证据集；测试 Agent 并行运行回归和边界测试；安全 Agent 运行策略守卫、Semgrep 或 OSV；专业评审 Agent 读取 Diff、需求和工具结果；最后由仲裁器去重、冲突处理并交给策略门禁。

以 PR-04 为例，测试 Agent 得到两个并发转账都成功的失败结果；correctness Agent 将它与“余额检查和更新必须原子化”连接；arbitrator 发现多个意见都指向 `repository.atomic`，合并为一个阻断 Finding。修复后恢复 `RLock`，同一测试应恰好一个请求成功，余额保持非负，总余额守恒。这里没有一个 Agent 被要求“猜答案”，每一步都有可复核产物。

PR-03 提供另一种协同：安全 Agent 发现授权检查被删除，测试 Agent 提供未拥有钱包时应返回拒绝的回归失败，仲裁器确认两者属于同一根因。PR-05 则将网络重试转化为状态不变量：同一用户、同一幂等键和同一参数只能执行一次，第二次请求必须返回原转账 ID。测试、语义解释和策略判断缺一不可。

## 统一 Finding Schema

所有阻断意见必须通过 Schema，而不是直接发布自由文本：

```json
{
  "finding_id": "CONCURRENCY-001",
  "source": "correctness",
  "category": "correctness",
  "severity": "must_fix",
  "confidence": 0.98,
  "file": "app/repository.py",
  "line_start": 35,
  "claim": "atomic 不再持有锁，余额检查与更新失去原子边界",
  "evidence": [{"type": "test", "ref": "tests/test_transfer_invariants.py::test_concurrent_transfers_cannot_double_spend"}],
  "blocking": true,
  "needs_human": true
}
```

Schema 强制两条底线：只有 `must_fix` 可以阻断；阻断意见至少需要一项证据。`confidence` 只能排序，不能替代证据。

Schema 同时提供稳定的评测接口。模型可以用不同措辞描述问题，评分器仍可通过根因、位置和证据与 Oracle 对齐。若模型给出三个措辞不同的锁问题，去重后只计一个根因；若它猜中“授权”却定位到无关文件，人工评测可以判定证据不足，而不是因关键词相似就算命中。

## 深入：从错误 Diff 走到修复验证

完整证据链至少有七个节点：需求不变量、错误 Diff、可复现失败、结构化 Finding、仲裁结论、修复 Diff、回归验证。缺少任何一个节点，都可能把“提出问题”误写成“问题已解决”。以下以三个案例说明节点之间如何相互约束。

PR-04 的需求是余额非负且同一时刻只有一笔 80 元转账成功。错误 Diff 移除了 `atomic` 内的锁；屏障测试固定两个线程同时读取余额，观察到两个请求成功。Finding 指向 `repository.py` 的锁边界，并引用测试输出。修复恢复教学仓储的 `RLock`，回归断言成功数为一、余额为二十、转账记录为一。若只恢复锁却没有验证记录数量，仍可能留下重复记账问题。

PR-03 的证据链更强调身份边界。错误 Diff 删除所有者比较；负向授权测试用用户 A 登录、提交用户 B 的钱包 ID，预期 403 而实际成功。修复恢复服务层检查，并补充“钱包不存在”和“用户未登录”两个分支，防止错误处理把未授权伪装成资源不存在。Finding 不应只写“缺少权限校验”，还要说明对象来自不可信请求参数，授权证据必须来自服务端身份上下文。

PR-05 的关键是时间和重复请求。错误 Diff 删除幂等查询；第一次请求成功但响应丢失，第二次相同键请求再次扣款。修复除了恢复查询，还要让查询、扣款和结果记录处于同一原子边界，并拒绝相同键不同参数。测试要覆盖顺序重试、并发首次请求、超时后恢复和键冲突四种情况。否则“重复返回同一 ID”只证明了最简单路径。

### 工具输出的阅读纪律

测试输出应保留命令、提交哈希、环境和失败断言；扫描器输出应保留规则版本、扫描范围和退出码；Agent Finding 应保留原始证据引用。不要把终端中的一行 `failed` 截出来当作完整证据，因为读者无法知道失败的是目标测试还是环境初始化。书稿中的截图或文本摘录应同时给出上下文和解释，明确哪些是原始输出、哪些是作者标注。

### 错误修复也可能制造新问题

为了修复双花，若把全局锁包住外部网络调用，会把正确性换成吞吐和可用性风险；为了修复授权，若把对象 ID 全部隐藏，可能破坏合法的跨账户管理场景；为了修复幂等，若永远保留键记录，可能导致存储无限增长。Finding 的修复约束应写“必须恢复什么性质”，并允许多个实现方案。评审 Agent 需要指出候选修复的副作用，而不是把第一条能让测试变绿的补丁当作最终答案。

## 生产实施参考：证据对象与运行目录

一个可审计运行可以组织成不可变目录。目录名包含提交哈希和运行 ID，内部保存 `manifest.json`、标准化 Diff、需求快照、工具原始输出、Finding、仲裁结果和人工裁决。`manifest` 记录仓库、基准提交、目标提交、策略版本、提示词哈希、模型精确版本、工具版本、开始结束时间和执行身份。敏感值只保存引用，不保存明文凭证。

证据对象建议包含 `id`、`type`、`producer`、`command`、`commit`、`created_at`、`content_hash`、`status` 和 `location`。Finding 只引用证据 ID，展示层再解析内容。这样同一失败测试可以被 correctness 和 arbitrator 共用，不需要复制长日志；证据被替换时哈希会变化，审计可以发现引用失效。

运行目录默认只追加，不允许 Agent 覆盖原始输出。重试产生新的 attempt，仲裁可以选择有效 attempt，但不能抹掉失败历史。人工裁决也作为新对象追加，保留先前决定和撤销原因。对于保存期限和个人数据，组织应设置清理策略；可审计不等于永久保留所有源码。

### 工具执行契约

工具调用应使用预定义命令或受约束参数，而不是让模型拼接任意 shell。每个工具声明工作目录、超时、网络权限、可写路径、预期退出码和输出解析器。测试命令退出码非零时，要区分断言失败、收集失败和环境失败；扫描器没有发现问题、扫描器未运行和扫描器上传报告失败是三个不同状态。

解析器不能丢弃原始输出。结构化结果用于门禁，原始日志用于复盘。输出过大时保存完整文件并在上下文中提供摘要和行引用；截断要显式标注。模型读取摘要后仍可按需请求相关片段，避免因为 Token 限制看不到关键堆栈。

网络访问应按任务开放。依赖公告查询可能需要外网，源码分析通常不需要。允许联网的 Agent 不应同时持有发布或生产凭证。外部网页内容作为低信任证据，必须记录 URL、抓取时间和摘要哈希。若来源发生变化，后续运行可以解释结论差异。

### Finding 生命周期

Finding 从 `proposed` 开始，经证据校验后进入 `supported` 或 `unsupported`；根因合并后进入 `merged`；策略门禁生成 `blocking`、`advisory` 或 `escalated`；人工可 `accepted`、`rejected` 或 `risk_accepted`；修复回归后才进入 `verified_fixed`。状态机防止“作者回复已修复”直接关闭问题。

每次状态变化都有操作者和理由。Agent 可以提出和补充证据，但不能将高风险 Finding 标为风险接受；作者可以提供修复，却不能批准自己的高风险例外；Tech Lead 可以裁决，但不能修改原始工具事实。权限分离让责任清晰，也减少提示注入的潜在影响。

`rejected` Finding 不应删除。它可能揭示规则误配、测试夹具错误或模型幻觉，应进入误报分析。`unsupported` 也不一定毫无价值：它可以转化为新增测试建议，但展示时必须和已证实缺陷分开，避免开发者把所有评论都当成同一优先级。

### 故障恢复与幂等运行

评审流水线本身也要幂等。同一提交、策略版本和工具版本重复触发时，可以复用不可变证据；策略或代码变化后必须生成新运行。发布评论用稳定 Finding ID 更新原评论，避免重试制造十条重复消息。评论发布成功但回执丢失时，先查询现有状态再重发，这与 PR-05 的业务幂等原则完全相同。

编排器崩溃后从运行清单恢复，已完成工具不重复执行，进行中的任务按租约判断是否重试。人工门禁状态存储在模型之外，任何恢复路径都不能默认批准。若审计存储不可用，高风险流程应停止；低风险是否降级由明确策略决定。

## 证据阅读方法：先读事实，再读解释

很多评审争论并不是因为参与者价值观不同，而是因为大家从不同层级的材料开始阅读。有人先看模型长评论，再回头寻找证据；有人先看失败测试，却没有核对它对应的提交；还有人只看最终红绿灯，不知道扫描器是否真的运行。建议固定阅读顺序，降低解释对事实的污染。

第一步读运行清单。确认基准提交、目标提交、案例 ID、策略版本、工具版本和运行时间。若目标提交与 Diff 不一致，后续所有结论都只能标记为不可用。第二步读需求和不变量。需求决定什么算缺陷，Oracle 决定允许哪些修复，不能先用模型意见替代需求。第三步读原始工具输出，区分断言失败、规则命中、网络失败和未执行。第四步读 Finding，检查它是否准确引用证据，以及是否把推测写成事实。第五步读仲裁和人工裁决，确认严重性、升级和例外是否有理由。最后才读摘要和展示文本，因为摘要是压缩结果，不是原始证据。

这个顺序对 PR-07 尤其重要。先看到“高危漏洞”标签，容易忽略它来自教学 manifest，或者忽略该公告的具体适用条件；先看路径、版本和 OSV 原始记录，才能判断它是应用运行依赖、测试依赖还是隔离样本。对 PR-08，先看仓库注释会让人进入攻击者设定，先看信任层级和工具审计则能保持控制面稳定。

### 证据充分性检查

可以用四个问题快速判断一条意见能否阻断。其一，事实能否由本次运行复现？其二，事实与需求中的不变量是否有明确连接？其三，位置是否足够精确，让开发者能定位并修复？其四，修复后是否有验证路径？如果只有前三项，意见可以是 `must_fix` 但要进入人工补证据；如果只有模型解释而没有事实，最多是调查建议。

证据也有新鲜度。源码位置、测试输出和依赖公告都可能随时间变化。每份证据保存提交哈希、生成时间和内容哈希；外部公告保存 URL 和访问日期。若重新运行发现漏洞数据库更新，应生成新 Finding 或追加证据，而不是覆盖旧结论。这样审计人员可以回答“当时为什么这么判断”，而不是只看到今天的状态。

### 不同证据之间的矛盾

矛盾不应被平均。测试说两个请求都成功，模型说“锁保证原子”，优先检查测试是否运行了错误补丁、模型是否读取了过期文件，不能用置信度加权后取中间结论。扫描器说有漏洞，人工说当前路径不可达，也不能直接删除 Finding；应该将漏洞事实和适用性判断分成两个字段，记录接受风险或补偿控制。

当矛盾来自环境时，最好的结果可能是 `inconclusive`。例如数据库服务未启动、OSV 网络请求超时、并发屏障未释放，系统没有足够事实决定是否安全。对高风险变更，`inconclusive` 应升级或阻断；对低风险变更，可以按策略延期，但不能显示为绿色通过。把“不知道”保留下来，是证据系统比自然语言评审更重要的能力之一。

## 附录：一次完整评审的交付清单

为了让本章的方法可以被团队直接采用，下面给出一次评审结束时应当交付的材料。第一份是变更清单，包括基准提交、目标提交、标准化 Diff、变更文件和符号。第二份是需求清单，包括原始需求、验收标准、不变量和明确不在范围内的事项。第三份是证据清单，包括每条命令、环境、退出码、原始输出、工具版本和证据哈希。第四份是决策清单，包括 Finding、根因合并、风险标签、人工裁决、例外期限和负责人。第五份是验证清单，包括修复提交、回归命令、仍未验证的边界和后续任务。

交付材料不要求全部展示在 PR 评论中。开发者界面可以只显示变更意图、阻断根因、复现步骤和下一动作；详细日志保存在受控证据目录，通过 ID 链接。这样既避免评论过长，也不牺牲审计。摘要中的每个“已验证”都能跳转到具体证据，“未验证”能转化为任务，而不是藏在段落末尾。

在 PR-04 中，这套清单会包含并发不变量、错误补丁、屏障测试失败、`CONCURRENCY-001`、合并后的仲裁记录、人工请求修改、修复补丁和同一测试恢复。生产数据库行为、锁顺序和死锁重试留在未验证清单。PR-03 则包含身份上下文、他人钱包负向测试、`AUTHZ-001` 和服务层授权修复；委托账户留为生产扩展。每个案例都因此既有结论，也有边界。

团队还可以为交付包设置质量门槛：缺少提交哈希的测试不进入阻断证据；缺少来源和日期的外部事实只作为调查线索；没有复现步骤的模型意见不直接发布；没有回归验证的修复不能关闭 Finding；没有负责人和期限的例外不能通过高风险门禁。这些规则把“写得有道理”转换为可检查的工程质量。

最后，交付包自身也要接受版本管理。Schema 变化时保留迁移记录，工具升级时重新确认解析器，策略更新时重跑基准案例，人工角色变化时更新责任映射。长期可维护性来自这些看似朴素的记录，而不是依赖某个模型永远表现稳定。

如果团队只能先做一件事，应先选择一个高风险但边界清楚的案例，完整保存错误输入、工具事实、Finding、人工裁决和修复回归，再把流程复制到其他案例。完整的一条证据链比同时铺开十个没有审计记录的 Agent 更能说明系统是否值得信任。等第一条链路稳定后，再增加角色、模型和工具，并用同一组零缺陷与缺陷案例比较变化。这样扩充的是可验证能力，而不是评论数量。

这条路线也适用于章节之外的自动化：先选一个能回放的真实问题，固定输入和验收标准，明确谁可以批准，保存失败和修复两端证据，再逐步扩大范围。每一次扩大都应有新的零缺陷样本、异常路径和回滚条件。只有这样，速度提升才不会以责任模糊和证据丢失为代价。

在最终交稿时，作者、技术审校和出版编辑还应分别签署三种结论：作者确认观点和案例完整，技术审校确认代码、命令与边界准确，出版编辑确认结构、图表、术语和引用一致。三种确认不能互相替代。技术正确但引用混乱会阻碍读者复现，文字流畅但命令错误会损害整章可信度，案例齐全但边界夸大则会把教学结果误传为生产保证。把这三类验收并列，才能让长篇幅真正转化为出版质量，而不是单纯达到字数指标。

本章后续若加入真实模型实验，应以新增实验报告的方式扩展，而不是改写录制回放的历史结论。旧结果保留运行 ID和版本，新结果附原始输出、失败样本与成本口径；若两者结论不同，正文解释差异而不是选择更好看的数字。可追溯的修订历史本身就是本章倡导的证据原则。
