# 9.10 如何评测代码评审 Agent

[返回第 9 章目录](README.md)

触发策略需要防止两个极端：只按改动行数会漏掉“一行删除授权检查”的高风险小 PR；只按目录会让核心目录里的文案修改每次触发全量评审。更稳妥的路由结合路径、符号、语义标签和人工声明，并采取只升不降原则。

建议保留四个对照组：`deterministic-only` 测量测试、规则和扫描器的能力边界；`single` 建立单通用 Agent 基线；`multi` 观察专业分工带来的召回和重复；`multi_arbitrated` 观察去重、证据合并和人工升级。当前代码可直接回放后三种模式，确定性对照组作为实验报告中的独立基线。

每个案例运行 3～5 次真实模型后，记录 Precision、Recall、高风险检出率、错误阻断率、重复率、首次反馈延迟、输入/输出 Token、单 PR 成本和结果波动。模型版本、提示词版本、价格日期和数据集版本必须写入报告。不要用未经来源审计的行业百分比替代本团队数据。

## 从回放走向真实模型实验

当前 `recorded-agents.json` 是控制夹具，用于证明相同输入能通过 Schema、路由、去重和评分。API Key 就绪后，选择两个模型家族，每个案例运行 3～5 次，保存原始输出并记录模型精确版本、提示词哈希、上下文构造版本、Token、延迟和当日价格。实验应回答：专业分工是否提高根因 Recall；仲裁是否降低重复和错误阻断；新增成本是否落在风险预算内。

## 深入：上线是持续实验，不是一次发布

上线前先运行影子模式：系统完整执行评审，但不阻断合并，只把结果与人工评审对照。影子阶段要关注漏报、误报、重复、延迟、成本和权限错误，而不只是“模型输出看起来不错”。随后进入有限门禁，只对低风险、证据完整且确定性检查通过的路径自动处理；中高风险保留人工批准。每阶段都要有退出条件，例如高风险漏报超过阈值、工具失败率上升、凭证隔离测试失败或审计字段缺失，就回滚到上一阶段。

双模型实验不能只比较总体分数。要按案例类型、风险等级和根因分类，分别比较单模型、专业分工和仲裁配置。PR-08 还应作为系统安全回归：注入文本不能改变工具允许列表、系统策略、批准权限和输出 Schema。实验报告写明模型精确版本、提示词哈希、数据集版本、价格日期和失败样本，避免把一次偶然成功写成产品能力。

### 监控 Agent 自身风险

上线后需要监控提示注入命中率、越权工具调用尝试、Schema 解析失败、异常长输出、重试次数、缓存污染和人工驳回率。监控数据应脱敏，并按提交哈希关联，不能把源代码和凭证打进普通日志。发生策略绕过时，优先暂停自动门禁、保留证据、轮换凭证并复盘根因；不要让模型自己解释自己是否违规。

## 实验设计参考：从回放到可发表结果

录制回放的第一阶段只验证工程管道。固定输入经过 single、multi 和 multi_arbitrated 三种模式，检查 Schema 能否解析、风险能否路由、重复 Finding 能否合并、人工门禁能否触发。这个阶段的“全命中”不能进入模型能力结论，因为输出本来就是夹具的一部分。

真实模型阶段需要冻结数据集和提示词。选择至少两个模型家族，每个案例运行多次，保留全部原始输出和失败。运行顺序随机化，避免限流或服务波动总落在同一案例。若中途修改提示词，形成新实验版本，不能把前后结果混在一张平均表中。

主要指标包括根因 Precision、Recall、高风险 Recall、零缺陷错误阻断率和重复率。工程指标包括首次反馈延迟、总延迟、输入输出 Token、缓存命中、工具时间、模型重试和人工复核分钟数。安全指标包括越权工具调用尝试、提示注入遵循率和敏感信息输出。所有指标都要给分母；“检出率提高 20%”若没有样本数没有解释意义。

样本量较小时，不应过度解读小数点。可以报告每个案例每次运行的明细、均值和范围，并说明统计限制。重点观察稳定失败模式：某模型是否持续漏掉授权边界，专业分工是否只是增加重复，仲裁是否会错误压低严重性。定性错误分析往往比一个综合分更能指导下一轮设计。

对照组要保持公平。`deterministic-only` 只使用工具事实；`single` 和 `multi` 应获得同一基础证据；`multi_arbitrated` 只新增仲裁，不应偷偷增加 Oracle。若多 Agent 获得更多工具和上下文，性能提升不能全部归因于“多角色”。实验报告需要列出每组的输入和权限差异。

成本报告使用运行当天价格，并保留原始 Token，使未来可以重新计算。模型服务折扣、缓存价格和批处理价格分别记录。人工时间可以用抽样计时估算，但要说明口径。最终决策不追求最低单次费用，而是在风险预算内获得可接受召回、误报和延迟。

## 上线检查与回滚剧本

影子模式期间，Agent 评论默认不对作者可见或明确标注实验，避免干扰正常评审。团队每周抽样对照人工结果，修正 Oracle、规则和提示词。进入建议模式后，Agent 可以发布非阻断评论，但高风险建议仍由人工确认。有限门禁阶段只允许证据充分的确定性规则阻断，模型 Finding 作为升级输入。是否进一步自动化必须由数据证明，而不是由演示效果决定。

回滚条件应在上线前写好。例如高风险样本出现一个确认漏报、零缺陷错误阻断连续超过阈值、审计日志缺字段、工具凭证越权、Schema 解析失败率异常或成本超过预算，系统立即退回建议或影子模式。回滚只关闭自动决策，不应删除已产生证据；保留现场才能定位问题。

发生提示注入或凭证事件时，先停止相关工具权限和自动发布，保存运行清单与日志，轮换暴露凭证，核对外部副作用，再修复策略和增加回归案例。不要先修改日志或让同一个 Agent总结事故，因为它可能正是受影响组件。恢复上线前，必须用原始攻击输入重复验证控制面。

发生大量误报时，不要简单提高置信度阈值。先按根因分类：规则误配、上下文缺失、模型泛化、证据解析、仲裁合并或需求本身模糊。不同原因需要不同修复。阈值只能调整排序，无法修复错误输入和错误 Oracle。

## 运行失败时的决策树

评审流程应在设计时就写出失败决策树。若路由器失败，系统读取上一版策略快照但不自动降级；高风险变更进入人工。若测试命令退出码非零，先判断是断言失败还是环境失败；断言失败可以生成 Finding，环境失败生成证据缺口。若 Agent 输出无法解析，重试一次并保留原文；再次失败则不发布自由文本阻断，转人工或使用确定性结果。若评论 API 超时，查询评论 ID 后再决定是否重试，避免重复发布。

外部依赖失败也要按风险处理。OSV 服务超时不等于没有漏洞；低风险文档可在策略允许时继续，但必须标记依赖扫描未完成；中高风险变更应等待或升级。模型服务不可用时，确定性检查仍可以运行，结果页面要明确显示“模型评审未完成”，不能把工具绿灯拼成整体绿灯。

故障决策树最好有自动化测试。构造模拟超时、空输出、坏 JSON、旧缓存、工具非零退出和评论重复场景，验证状态机进入预期终态。很多安全事故并非模型判断错误，而是编排器在异常分支默认放行；测试异常路径比再增加一个正常样例更有价值。

## 给评审团队的复盘问题

每次真实运行后，团队可以围绕以下问题复盘。哪一条意见最早发现根因？它使用了什么事实，其他角色为什么没有发现？重复意见是独立确认还是上下文回声？哪个未知范围被误写成已验证？工具失败时系统是否显示了正确终态？人工花费的时间主要用于查证、解释还是修复展示？下一次运行应该改变输入、工具、路由、Schema 还是门禁？

复盘要避免把责任归咎给一个模型。若模型漏报，检查需求是否可观察、工具是否运行、上下文是否丢失、Oracle 是否完整；若模型误报，检查规则适用性、零缺陷样本和仲裁阈值；若流程放行，检查门禁是否在模型之外、异常分支是否默认批准、凭证是否过宽。只有把失败放回系统链路，改进才不会变成不断更换模型。

复盘结果应转化为一个具体变更和一个回归样本。例如 PR-03 漏掉委托场景，就新增授权矩阵和案例；PR-04 的修复引入死锁，就增加锁顺序测试；PR-07 扫描结果重复，就更新别名归并；PR-08 通过摘要传播了注入，就增加来源和信任级别字段。每次改进都要重新运行既有七案例，确认没有为了修一个边界而破坏低风险自动通过或其他高风险门禁。

## 团队落地路线：四周试点法

如果团队第一次引入 Agent 评审，建议把试点拆成四周，而不是在一天内把所有高风险变更交给自动门禁。第一周只建立基线：收集现有人工评审、测试、依赖扫描和人工耗时，选择一组包含零缺陷、正确性、安全和依赖案例的历史 PR。此时不要求模型阻断任何合并，重点是确认数据能否脱敏、证据能否保存、工具是否能在固定环境运行。

第二周上线影子模式。路由器根据真实路径和标签选择工具，但结果只提供给评审团队，不改变合并流程。每天抽样比较 Agent Finding 与人工结论，记录漏报、误报、重复和无法判断。不要只统计模型说对了多少，还要统计人类花了多少时间确认它。若一条评论需要作者反复解释上下文，它即使技术上正确，也可能不是可用的评审产物。

第三周进入建议模式。低风险规范问题可以发布非阻断评论；高风险问题继续由人工确认。此时完善 Finding Schema、根因去重、评论更新和审计字段，测试超时、网络失败、坏 JSON、旧缓存和重复回调。团队应明确谁负责处理 `evidence_incomplete`，否则系统会积累一堆没人查看的黄色状态。

第四周才考虑有限门禁。只选择确定性证据充分的规则，例如测试失败、策略明确禁止的金额浮点、已确认的高危依赖；模型意见只负责升级人工，不直接批准或拒绝资金、授权、凭证和数据库迁移。门禁启用前先写回滚条件，并安排值班负责人。试点结束时提交一份报告，说明哪些路径节省了时间、哪些路径增加了负担、哪些风险仍完全依赖人工。

### 角色与值班安排

最小团队通常需要四类责任人。代码所有者负责解释业务意图和修复；安全或平台负责人维护策略、工具和凭证；Tech Lead 负责高风险仲裁和例外；运行负责人观察延迟、失败和成本。一个人可以承担多个角色，但同一次高风险变更的提出、修复和批准最好不要由同一人完成。

值班手册写清楚“看到什么状态做什么”。`blocking` 进入作者队列；`escalated` 通知 Tech Lead；`evidence_incomplete` 先补工具或人工取证；`agent_security_event` 暂停相关工具并轮换凭证；`publisher_failed` 查询评论状态后再重试。把这些动作写成链接到命令和权限的步骤，比让值班人员临时阅读模型长文可靠。

### 服务等级与等待时间

评审自动化会改变开发者对反馈时间的预期。低风险 PR 可以在几分钟内得到结果；中风险路径允许并行工具但要显示预计完成时间；高风险路径即使等待更久，也应明确当前卡在哪个证据或人工环节。超时不能静默变成“稍后可能批准”，否则团队会绕过流程。

可以为每个状态定义服务等级，例如工具启动失败五分钟内重试一次，超过十分钟升级平台负责人；人工高风险裁决四小时内响应，超过则保持阻断而不是降级。服务等级不是为了追求快，而是让等待有责任、有预期。延迟报告还要区分排队、工具、模型、人工和发布时间，才能找到真正瓶颈。
