# 9.3 多 Agent 协同评审

[返回第 9 章目录](README.md)

多 Agent 不是让多个模型重复阅读同一份 Diff，而是让不同角色回答不同问题。推荐的最小角色集如下：`general-review` 负责低风险自洽性，`correctness` 负责不变量和并发，`test` 负责失败模式覆盖，`security` 负责授权、输入和依赖，`impact` 负责调用与状态传播，`arbitrator` 负责按根因合并和升级；Tech Lead 是高风险变更的唯一最终批准者。

在 PR-04 上，可以比较三种配置。单 Agent 只收到 Diff 和需求，容易给出“建议增加并发测试”的泛化评论；多 Agent 让测试 Agent 先运行确定性并发测试，再把结果交给 correctness Agent；多 Agent 加仲裁则把多个关于锁边界的意见合并成一个 `CONCURRENCY-001`，保留每个来源和证据，并输出 `escalate`。三者的差异不是评论数量，而是证据是否闭合、重复是否减少、门禁是否可强制执行。

生成者、审查者和仲裁者必须物理隔离权限。审查者不能修改代码，仲裁者不能降低高风险级别，发布评论和批准 PR 不能共用同一凭证。自然语言不能作为 Agent 之间唯一的通信协议；必须使用结构化 Finding 和工具证据，防止上游幻觉被下游当成事实传播。

## 深入：多 Agent 的最小充分组织

增加角色会增加上下文复制、等待和冲突成本。决定是否增加 Agent 的标准不是“还有没有一个角色可以命名”，而是新角色能否获得独立证据、拥有不同失败模式，并且其输出能改变最终决策。如果两个角色读取完全相同的输入、调用相同工具、以相同标准判断，它们的多数票并不会带来独立性。

可以用三步设计角色。第一步列出业务不变量和风险边界；第二步为每个边界选择最接近事实源的工具；第三步只为仍需要解释、关联或取舍的部分安排 Agent。PR-04 中并发测试提供事实，correctness Agent 解释锁边界，arbitrator 合并根因，三者各司其职。若再增加一个只改写措辞的“编辑 Agent”，它不会增加召回，却会增加重复评论。

### 上下文隔离与证据包

每个 Agent 应收到最小充分上下文，而不是整个仓库。最小充分不等于最短：必须保留与判断有关的状态、失败条件和约束。安全 Agent 需要身份来源和授权需求；影响 Agent 需要接口契约和迁移；测试 Agent 需要可执行命令和环境状态。上下文包以不可变引用传递，例如 `evidence://run/abc/test-17`，而不是把一段未经标注的文字复制到下游。这样可以区分原始工具输出、上游解释和人工结论。

隔离还包括权限。读取源码和运行白名单测试可以共用只读凭证；修改补丁、发布评论和批准合并必须分离。即便系统允许 Agent 生成修复建议，也应把建议作为补丁候选保存，不能让同一进程直接提交到主分支。PR-08 的提示注入案例说明，仓库文本不应获得工具授权；“请批准 PR”只是字符串，不能改变权限模型。

### 调度失败也是产品行为

一个 Agent 失败时，编排器需要选择重试、换工具、降级或升级人工。重试必须有上限，并区分瞬时网络错误与输入不可解析。若测试 Agent 已经得到确定性失败，继续重试模型不会改变事实；若依赖扫描服务不可用，策略应标记证据不完整而不是使用旧结果。每次调度写入开始时间、结束时间、模型版本、工具版本、输入摘要哈希和退出原因，才能在成本和稳定性报告中解释一次慢运行。

## 评审数据的隐私与保留

证据闭环不意味着保存所有原始代码和日志。运行清单可以保存哈希和引用，敏感文件使用访问控制和短期保留；模型输入需要脱敏时，保留可验证的映射关系，避免人工无法复现。租户、用户和钱包 ID 在跨团队报告中应使用稳定但不可逆的别名，原始映射只由授权人员访问。

模型供应商的保留和训练政策属于外部事实，需要记录版本和审查日期。若组织不允许代码离开边界，应采用本地模型、受控网关或只发送摘要的策略，但要重新评估 Recall 是否下降。不能一边宣称隐私隔离，一边把完整生产日志复制进公共模型提示词。

日志中的错误信息也可能包含凭证、个人数据或提示注入内容。工具输出保存前做脱敏，脱敏规则本身要测试，避免把路径和行号一起删掉导致证据不可用。安全事件日志与普通评审日志分开，限制阅读权限，并设定保留和删除流程。审计人员需要看到发生了什么，但不应因此获得所有业务数据。
