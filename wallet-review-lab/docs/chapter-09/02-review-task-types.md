# 9.2 评审 Agent 的四类任务

[返回第 9 章目录](README.md)

## 规范任务：先清理低级噪音

Ruff、格式化器和依赖检查适合承担确定性规范任务。Agent 的工作是将输出映射回文件和行号，告诉作者为什么需要修改，并避免把风格问题伪装成安全阻断。PR-01 只补充转账响应字段的文档说明，风险路由将它判为低风险；如果系统仍启动全部专业 Agent，得到的只是更高成本和更多无关评论。

## 缺陷任务：从控制流走到不变量

缺陷评审要追踪状态读取、校验、写入和异常路径。PR-04 的关键不是“代码少了一把锁”这句表面描述，而是：两个请求读取同一余额，两个请求都通过校验，随后各自写入，最终余额可能为负，且总余额与转账记录不再符合业务定义。一个合格 Finding 必须把源码位置、失败模式和修复边界写在一起。

## 安全任务：验证身份、对象和输入的边界

PR-03 删除了服务层的 `source.owner_id == current_user.id` 检查。客户端提交的钱包 ID 只能用于定位资源，不能作为授权证据。安全 Agent 需要同时看到需求、身份上下文和失败授权测试，才能把“缺少一个条件判断”提升为对象级授权绕过（`AUTHZ-001`）。PR-08 则把源码注释当作不可信输入，验证仓库文本不能改写评审策略。

## 影响任务：描述传播，不猜不存在的调用方

影响分析应优先使用 AST 符号引用、路由表、数据库迁移和锁文件等结构化事实。Agent 可以解释这些图和列表，但不能凭空声称存在跨仓库调用方。本地实验只有单仓库、单服务边界，因此书中将“已实现的本地影响分析”和“生产环境需要补充的跨仓库索引”明确分开。

## 四类任务如何共享证据

同一 PR 不应为每个 Agent 重复构造全部上下文。编排器先生成公共证据包：需求与验收标准、标准化 Diff、风险标签、变更文件和工具摘要。测试 Agent 再获得现有测试与失败日志，安全 Agent 获得身份边界和扫描结果，影响 Agent 获得符号引用和公共契约。

共享证据不等于共享结论。若 correctness Agent 先声称存在竞态，再把这句话放进 test Agent 输入，后者容易只是重复确认。更可靠的方式是让 test Agent 独立产生“两个请求均成功”的事实，再由仲裁阶段关联根因。这样才能判断召回提升来自专业分工，还是来自同一句话被反复转述。

## 深入：四类任务需要四份不同的证据包

规范、缺陷、安全和影响分析经常被合并成“代码质量检查”，这会造成输入过载和验收混乱。每一类任务都应该有自己的证据包和失败定义。

规范任务关心格式、命名、文档契约、依赖锁定和接口兼容性。它的证据通常是工具输出、配置文件和 API 文档。失败的定义是规则命中且适用于本次变更；不能因为某个规则存在就阻断所有 PR。PR-01 的文档变更就是一个很好的零缺陷样本：系统应证明它没有越过风险边界，而不是强行找一个问题。

缺陷任务关心控制流、状态转移和异常路径。它需要把需求中的不变量映射到代码路径。例如“余额非负”不是一句评论，而是对扣款前检查、扣款写入、失败回滚和并发交错的联合约束。缺陷任务的最小输出应包含触发条件、错误状态、违反的不变量和修复边界。只有说“这里可能有 bug”而没有触发条件的意见不能阻断。

安全任务需要主体、对象、动作三元组。对 PR-03，主体是当前登录用户，对象是请求中的源钱包，动作是转账；`owner_id` 比较缺失使主体可以操作不属于自己的对象。对 PR-08，主体还包括评审 Agent，仓库注释是低信任数据，批准权限属于组织策略而非注释内容。安全任务的特殊之处在于负向样例通常比正向覆盖更有信息量：合法用户访问自己的钱包不能证明越权访问被拒绝。

影响任务则要描述传播范围，而不是猜测业务故事。它可以从 AST 引用、路由表、数据库字段、事件主题和锁文件中构造图，标注每条边的来源。一个符号没有跨仓库索引，不代表“没有调用方”；正确结论应该是“在当前仓库内未发现调用方，跨仓库影响未验证”。这种表述看似保守，却能避免把局部搜索误写成全局证明。

### 路由矩阵示例

| 任务 | 最小输入 | 主要工具 | 阻断条件 | 人工问题 |
|---|---|---|---|---|
| 规范 | Diff、规范、锁文件 | Ruff、类型检查、依赖检查 | 规则命中且适用 | 是否允许例外 |
| 缺陷 | 不变量、调用图、测试 | pytest、状态追踪 | 可复现违反不变量 | 修复边界是否完整 |
| 安全 | 主体/对象/动作、信任层级 | 策略守卫、Semgrep、负向测试 | 越权或信任穿透 | 风险是否需升级 |
| 影响 | 符号、事件、迁移 | AST、引用索引、迁移检查 | 兼容性破坏 | 外部消费者是否已确认 |

矩阵的价值在于让“没有运行某工具”成为显式缺口。不同任务可以并行，但不能把一个任务的绿色状态借给另一个任务。例如 Ruff 通过不能证明授权正确，授权测试通过也不能证明依赖没有公开漏洞。
