# 第 9 章概述：AI 代码评审与多 Agent 协同

[返回第 9 章目录](README.md)

> 副标题：把模型放进一条可验证、可回放、可问责的证据流水线
>
> 稿件状态：扩充出版稿（案例驱动初版）。本章中的模型输出部分使用录制回放；录制数据用于验证编排、Schema、去重和门禁，不代表真实模型能力。

## 开篇：先定义“正确”，再讨论“智能”

当团队用 AI 生成更多代码时，瓶颈会从“写出来”转向“证明它是对的”。代码评审 Agent 的价值不是用另一段自然语言替代人类判断，而是更快收集证据、定位风险、组织分歧，并把最终决策留在可追溯的工程流程中。

本章使用 `wallet-review-lab` 中的最小数字钱包服务作为实验场。它不连接真实资金，却保留了足以让评审变得严肃的四条业务不变量：金额守恒、余额非负、同一幂等键只产生一次资金变更、用户只能从自己拥有的钱包付款。每个教学 PR 都有一份需求、一份错误补丁、一份人工确认的 Oracle、工具证据和修复补丁。读者可以先只看 Diff 和测试结果，写下自己的 Finding，再打开 Oracle 对照。

贯穿全章的主线是 PR-04“并发双花”。余额为 100 元时，两笔 80 元转账不应同时成功。错误补丁把余额检查移到 `app/repository.py` 的 `atomic` 锁边界之外；单线程测试仍然通过，但两个线程可能同时读到 100 元。这个案例让我们反复看到一个事实：模型可以帮助解释竞态，但真正证明竞态存在的，是可重复的并发测试和清晰的不变量。

为什么选择钱包，而不是继续使用一个抽象的优惠券系统？因为本章的观点必须落到可运行证据上。钱包服务足够小，读者可以在一章内理解全部状态；又足够真实，能够同时容纳金额精度、对象授权、并发、幂等、依赖漏洞和提示注入。正确基线使用进程内 `RLock` 表达原子边界；生产数据库可能需要行锁、可串行化事务，或者带版本号和重试的 CAS。书中的修复证明的是实验不变量恢复，不是可以直接复制到分布式资金系统的完整方案。

## 出版扩展：把每一次评审变成可验证的任务

前面的章节给出了主线结论，下面把这些结论拆成可以落地的工作单元。这样做不是为了把本章变成工具手册，而是为了回答读者在真实团队里最常遇到的三个问题：我应该把什么交给模型？模型的结论凭什么可信？出了错以后，谁能在多长时间内复盘并修正流程？如果这三个问题没有明确答案，所谓 Agent 评审仍然只是把自然语言搬进 CI。

## 章末检查表

- 是否从明确需求和不变量出发？
- 阻断 Finding 是否有文件位置和可复核证据？
- 风险路由和人工门禁是否在模型之外执行？
- 多 Agent 是否拥有不同任务、输入和权限？
- 重复意见是否按根因合并并保留来源？
- 是否区分录制回放与真实模型实验？
- 是否区分 Precision、Recall、采纳率和成本？
- 外部产品能力、漏洞状态和价格是否有一手来源与访问日期？

## 最终检查表

- 需求是否转化为可测试的不变量，而不是停留在功能描述？
- 每个阻断 Finding 是否同时具有根因、位置和本次运行的证据？
- 工具未运行、运行失败和未发现问题是否被明确区分？
- Agent 是否只能使用任务所需的最小工具和凭证？
- 仓库、日志和外部网页是否始终作为带来源的低信任数据？
- 风险路由是否可测试、可解释，并遵循只升不降？
- 重复意见是否按根因合并，同时保留原始来源？
- 人工裁决是否记录理由、证据、未知范围和例外期限？
- 修复是否通过原失败用例和相关不变量回归，而不只是让单测变绿？
- 零缺陷样本是否进入评测，用来观察误报和错误阻断？
- 录制回放是否只用于验证管道，没有被写成真实模型能力？
- 实验是否记录模型、提示词、数据集、工具和价格版本？
- 成本是否包含延迟和人工负担，而不仅是 Token？
- 生产迁移中未覆盖的跨进程、跨仓库和外部系统边界是否显式标注？
- 自动化失败时是否有明确降级、暂停和回滚剧本？

## 反模式目录：看似合理但会破坏证据闭环

反模式一是“让模型先总结，再决定跑什么工具”。模型可能因误读 Diff 跳过关键测试；高风险工具集合应由策略路由先决定，模型只能补充解释。反模式二是“把所有工具输出拼进一个超长提示词”。上下文过载会让模型遗漏关键失败，且无法追踪某句话来自哪个工具；应使用带 ID 的证据包和按需读取。

反模式三是“用置信度阈值代替人工门禁”。置信度没有统一标定，模型可能对错误结论非常自信；高风险策略必须在模型之外执行。反模式四是“只修复让测试变绿的路径”。测试可能没有覆盖记录、授权、审计或异常释放；修复验证要回到完整不变量矩阵。反模式五是“把每条评论都计为一个缺陷”。重复会虚高召回，零缺陷样本和根因去重必须进入评测。

反模式六是“把教学依赖样本排除扫描”。这样 CI 看起来绿色，却失去漏洞教学的回归；应用依赖与教学资产应采用不同的期望结果。反模式七是“让 Agent 自己发布批准评论”。发布、修改和批准是不同责任，必须使用分离凭证和门禁。反模式八是“失败时使用最后一次绿色结果”。旧结果只能作为参考，不能证明当前提交；工具失败应显示为证据缺口并按照风险升级。

## 维护计划：章节、工程和案例如何长期同步

本章描述的是一个会变化的系统。模型版本、价格、漏洞公告、策略文件和测试夹具都会更新。每次仓库变更都应检查章节中的命令、路径、案例 ID、分支名和输出描述。文档引用的外部事实记录访问日期；仓库内结论优先引用可运行命令，不复制容易过期的终端输出。

可以把维护分为三类。代码或策略变化时，先运行 `make check` 和评测套件，再检查正文中的字段和行为描述；案例素材变化时，重新生成 patch、Oracle、人工裁决和远程分支，并核对章节是否仍称为同一根因；外部模型或 OSV 变化时，更新实验元数据和价格日期，不能把新结果覆盖旧结果。每次发布前执行一次链接、命令和字数检查，将结果写入实施日志。

章节目标字数也要服务于内容验收。新增段落必须至少引入一个新证据、新边界、新反例或新读者产出；如果只是把同一结论换一种说法，应删除。篇幅不足时优先补齐案例证据、生产迁移和练习，篇幅过长时优先删除重复背景，而不是删除限制条件。这样才能让“字数达标”与“读者获得能力”保持一致。

## 章节成果的验收方法

本章最终验收不只看字数。第一项是结构验收：9.1～9.10 每节都有观点、机制、边界、案例证据和读者产出。第二项是复现验收：主线命令在 `wallet-review-lab` 工作目录可运行，补丁路径、模块名和分支名与仓库一致。第三项是事实验收：案例描述与 requirement、Oracle、human-verdict 和代码行为一致，录制回放没有被写成真实模型实验。第四项是边界验收：教学实现、生产迁移、外部事实和未完成实验均有明确标记。

字数统计使用中文字符近似值，只作为篇幅指标，不代替内容审校。段落级审校可以抽样检查每一节的“依据是什么、如何复现、何时不成立”三个问题；如果有一节只能回答其中一个，说明仍需补证据或删去空泛描述。出版编辑还应检查表格、代码块和 Mermaid 图注是否与正文同一版本，避免读者复制到错误路径。

读者产出验收可以设置为一份小型 PR 审查包：需求与不变量、风险路由、原始工具输出、两条结构化 Finding、人工裁决、修复验证和未覆盖清单。只要读者能独立完成这份包，章节就完成了从概念到能力的转换。若读者只能复述“Agent 要有证据”，却无法指出证据 ID、命令和升级条件，说明文本仍停留在观点层。

## 章节边界声明

本章不声称完成真实模型对照实验、跨仓库调用图、生产数据库隔离验证或外部支付服务对账。当前仓库中的录制 Agent、进程内钱包和教学依赖都是可回放的控制素材；它们用于证明编排、Schema、路由、去重和门禁逻辑。真实模型实验、生产迁移和案例截图仍需按蓝图中的单独里程碑完成，不能因为正文扩充而被误写为已完成。

这条边界声明不是削弱章节，而是让读者知道哪些结论可以立即复现、哪些只能作为设计建议。书中越清楚地标出未知，读者越容易把方法迁移到自己的系统并补上对应证据。任何未来新增的真实结果都应带模型版本、运行日期、数据集和命令，并与录制回放分开存档。

## 最终出版前的机械检查

出版前可以执行一组不依赖模型的检查：统计正文字符数；检查 9.1～9.10 和七个案例标题是否存在；扫描代码块中的路径和模块名；搜索“已完成”“证明了生产安全”等容易越界的表述；核对所有案例 ID、Finding ID 与 YAML；运行 `git diff --check`、`make check` 和回放测试；确认 Mermaid、表格和图注引用的文件仍存在。机械检查不能替代内容编辑，却能消灭大量低级错误。

建议把检查结果写入出版清单，包括执行时间、提交哈希和未完成项。若字符数在目标范围外，先检查是不是误把代码、表格或重复内容计入；若命令失败，区分环境依赖缺失和正文路径错误；若案例 YAML 与正文不一致，优先修正事实来源而不是迁就旧文字。最终发布应以仓库事实为准，正文和配图都从同一提交导出。

到这里，本章的核心闭环可以压缩为一句可执行的话：先把需求写成不变量，再用确定性工具产生事实，让 Agent 在受限权限内连接事实，由仲裁和人工承担取舍，用回归验证修复，并把所有未知和失败保留下来。任何一步被省略，系统都可能看起来更快，却无法回答“为什么可以相信”。

## 迁移前的风险问卷

在把本章方法带到另一个系统前，团队可以先回答一份风险问卷。系统是否跨进程或跨地域部署？状态是否由数据库、缓存、消息队列和外部服务共同维护？金额、库存或配额是否存在小数、舍入和部分成功？授权是否包含角色、委托、租户和撤销？请求是否允许超时重试？Agent 是否会接触用户输入、生产日志、密钥或外部网页？哪些动作不可逆，必须由人批准？

每个“是”都对应新的证据和测试，而不是自动套用钱包实现。跨进程需要分布式一致性和故障演练；外部服务需要未知状态与对账；多租户需要数据隔离和授权矩阵；接触敏感数据需要脱敏、访问记录和保留策略；不可逆动作需要独立门禁和回滚或补偿方案。问卷的目的不是阻止采用，而是让迁移成本在开始前可见。

风险问卷还应记录“当前不回答”的问题。一个团队可能暂时无法验证跨仓库调用方或供应商重试语义，此时应把未知写入上线条件和后续任务，而不是从报告中删除。未知项越多，自动门禁范围越应收缩；这是一种基于证据的渐进式上线，而不是保守主义。

## 章节结束语：把速度花在证据上

AI 让代码和评审意见都更容易生成，也让未经验证的错误更容易扩散。真正可持续的效率，不是让模型替人类做更多无法追责的决定，而是让确定性工具更早暴露事实，让 Agent 更快连接分散证据，让人类把时间花在边界、取舍和责任上。钱包案例之所以有用，不是因为所有系统都像钱包，而是因为它把金额、授权、并发、幂等、依赖和提示注入压缩成可运行的不变量。

当读者能从一个新需求写出不变量，从一个错误 Diff 写出最小复现，从工具输出构造 Finding，从冲突意见形成裁决，并在修复后清楚说出仍未证明什么，本章才真正完成。这个标准比“模型写得像专家”更高，也更适合长期维护。因为系统会换模型、换框架、换数据库和换团队，而证据、权限、边界和责任仍然是评审可信度的根。
